# The X-ray data chain on the grid

One paste in the grid's shell fetches the open X-ray datasets of docs/research/xray-datasets-missing.md and the data platform's own unfetched sources onto the data root, turns each X-ray copy into a bank in the builders' format, ingests every bank into a content-hashed shard, and rebuilds the read-only catalog with its split check (docs/research/data-catalog.md). Nothing here runs on the login node: the two submit scripts call sbatch, df and awk and nothing else, and every byte moves inside a Slurm job on the reqp partition with --qos=requeue, each stage chained with afterany so a failed source strands nothing behind it. Written 2026-10-21 for issue #38; no job has run on the grid yet, so every size below is what the lists state; the one run so far is the container's, under Measured at the end.

4. Tokens, each in a file only you can read, never on a command line: the Kaggle token as a line `KAGGLE_API_TOKEN=...` in `~/.fluorocap/credentials.env` (mode 600; the RSNA 2022 fetch used the same file) for kaggle_scoliosis_yolov5 and rsna_rspect_pe; PhysioNet's sign-in as `machine physionet.org login <you> password <...>` in `~/.netrc` (mode 600) for the opt-in list; a Hugging Face token as `HF_TOKEN=...` in `~/.hf/token.env` (mode 600) for CADS and CT-RATE; the RSNA RATIC presigned link, good until 2026-10-28 02:38 UTC, as the one line of `~/.rsna/ratic_link` (mode 600). `chmod 600` each; the jobs refuse a file anyone else can read.

The "to confirm" fields: grid/fetch-xray.json lists per entry what to read on its page (the licence, a record number, a download link), and grid/banks/<id>.json stops stage 2 for that source until each field spelled "to confirm" is filled in. ## The paste

```
cd ~/SchwingNet && git pull && df -h /rs/rs_grp_oschome && bash grid/run-platform-fetch.sh && bash grid/run-xray-chain.sh
```

That submits the data platform's chain (25 jobs, one per source, each afterany on the one before) and the X-ray chain (three jobs: fetch, bank and ingest, catalog), prints every job id with its dependency and an ETA, and writes them to grid/LAST_RUN.txt. The two chains are independent and run side by side. `squeue -u $USER` watches them; the X-ray stages each write one report, grid/logs/01-fetch-STAGE-REPORT.md, 02-bank-ingest-STAGE-REPORT.md and 03-catalog-STAGE-REPORT.md, and each platform job logs to grid/logs/dp_fetch_<id>_<job>.out with a README.yaml written at its landing. Add `--only <id,id>` to either script for a part, `--credentialed` to the X-ray chain for the PhysioNet opt-in list, `--gated` to the platform chain for the granted gated sources (CADS CT-TRI, RSNA RATIC, RSPECT), and `SBATCH=echo` in front of either for a dry run that submits nothing.

The lines never in a chain, each one job you run or skip:

```
# MIMIC-CXR-JPG, about 570 GB, credentialed: alone, after df shows the room
cd ~/SchwingNet && bash grid/run-xray-chain.sh --credentialed --only mimic_cxr_jpg
# VinDr-CXR (about 180 GB) and VinDr-PCXR (about 30 GB), credentialed, DICOM (banked in the train environment)
cd ~/SchwingNet && bash grid/run-xray-chain.sh --credentialed --only vindr_cxr,vindr_pcxr
# CT-RATE, 21.3 TB, gated: not before your TB number; the token in ~/.hf/token.env
cd ~/SchwingNet/grid && ID=hf_ct_rate ROUTE=hf-token ARGS='--repo ibrahimhamamci/CT-RATE --repo-type dataset --include .' LICENCE='CC BY-NC-SA 4.0' ACCESS=gated TOKEN_FILE=~/.hf/token.env sbatch -D "$PWD" --job-name=dp_fetch_hf_ct_rate --export=ALL platform-fetch.sbatch
# NLST full, 24,713 subjects, 2.3 TB, refused as it stands by the stopping rule
cd ~/SchwingNet/grid && ID=idc_nlst ROUTE=idc ARGS=nlst LICENCE='CC BY 4.0' ACCESS=open sbatch -D "$PWD" --job-name=dp_fetch_idc_nlst --export=ALL platform-fetch.sbatch
```

## What the X-ray chain does

Stage 1, grid/01-fetch.sbatch (4 days of wall time, requeued on preemption): `tools/fetch_sources.py --run` reads grid/fetch-xray.json and runs one helper per entry, the data platform's own reacquire.py (zenodo-get, which verifies the record's md5 per file; hf-get, which verifies the LFS sha256; http-get, which resumes a .part), Mendeley's public API listed and then http-get per file with the sha256 the API gives, figshare's public API listed (api.figshare.com/v2/articles/<id>) and then http-get per file with the md5 and the size the API gives, after which each zip that came is opened in place for the bank stage (Aariz and KUB-StoneX, one zip each), the Kaggle CLI with the token from the file, or wget -r -N -c -np with the login from ~/.netrc for PhysioNet. Every entry lands at /rs/rs_grp_oschome/go2432/data/<id>/raw, the folder its registry entry names; the helper's state is <id>/fetch-state and the record <id>/FETCH.json: what ran, the exit codes, the byte count and the sha256 of every file, computed after the download. A failed entry is reported and the next runs; the stage exits 1 at the end when any failed, and stage 2 still runs on what came.

Stage 2, grid/02-bank-ingest.sbatch: for each recipe grid/banks/<id>.json whose raw folder holds anything, `tools/bank.py --run` writes the bank under <id>/bank (images/train/<stem>.png, meta/<stem>.json with the case, the device, the view and the boxes), then `tools/ingest.py run --bank <bank> --source <id> --kind train --split train --date <today> --code-commit <sha> --person-prefix <prefix>` cuts the shard under <id>/shards/<date>-<12 hex>/. PNG is copied byte for byte, so the shard's name is the raw bytes' content; JPEG, TIFF and BMP convert through Pillow in the train environment; the same bank twice is "already there". The ingest refuses a frozen test person in a train shard and the same bytes under two persons, as docs/research/data-catalog.md says.

Stage 3, grid/03-catalog.sbatch: `tools/catalog.py build --store /rs/rs_grp_oschome/go2432/data/_catalog --manifest <every MANIFEST.json under <data root>/*/shards/*/>` and `split-check` on the new version; a build whose bytes equal the latest is reported as not new. A failed split check exits 1 and no training step reads that version.

Each source's registry entry, data/registry/<id>.json, was written with the chain: the identity level, modality, device class and regions as the sweep read them, every one marked in its notes where the page has not been read, and the person-key rule pointing at the recipe. VertXNet's persons carry the prefix nhanes2, so a NHANES II person is one person across its sources.

## What the platform chain does

grid/run-platform-fetch.sh submits one grid/platform-fetch.sbatch per source of spinesurg-ct-nnunet's data_platform/sources.json at bf1432f that is not on the grid, in this order: STOIC2021 (s3, 240 GB), the two IDC spine collections (spine_mets_ct_seg, spinal_multiple_myeloma_seg), MedPelvis3D, LumVBCanSeg, LUMOS (the version record 18173664, CT zips and the 1,620 radiographs; grid/banks/lumos.json banks the radiographs from this landing, so the record is on disk once), the three TotalSegmentator task sets (fetched into raw with the overlap question written into their README.yaml, out of every split until the authors answer), the TMTV benchmark, the CT Colonography verify run, the cm_spine Google Drive file (gdown into a dated scratch folder under its raw, then file(1) on what came), the ScienceDB probe (curl -I only: whether a login is asked), the VerSe note, the seven other IDC tier-2 collections, UniToChest, VSDFullBody, AbdomenAtlas 2.0 Mini and LIDC-IDRI last. The IDC route writes the collection's manifest from idc-index itself (grid/idc_manifest.py, every CT series of the collection) and hands it to acquisition_fetch.py idc, which verifies each series by its instance count; the zenodo, hf and s3 routes are acquisition_fetch.py's, md5, LFS sha256 and object count, never size alone. Every landing is /rs/rs_grp_oschome/go2432/data/<source id>/raw with a README.yaml as data_platform/LAYOUT.md says, written once and never overwritten.

With `--gated`: CADS (parts CT-TRI first, VISCERAL as a second run with `--include VISCERAL*`), RSNA RATIC through its presigned link read from the file into a curl config, and RSPECT through Kaggle. CT-RATE and NLST full are printed, never submitted.

The 10 VerSe'20 series never downloaded (verse020, 112, 139, 141, 151, 202, 235, 251, 257, 290) need the VerSeFusion clone on the grid, whose slurm/download_raw.sh is the osf_verse route: the chain prints that note and `python3 -I ~/spinesurg-ct-nnunet/data_platform/reacquire/reacquire.py --grid verse19_20` gives the line once the clone is there.

## Re-running one source

- Fetch again: `bash grid/run-xray-chain.sh --only <id>` (the helpers resume their .part files and skip verified units) or `bash grid/run-platform-fetch.sh --only <id>`.
- Bank and ingest again after a recipe was filled in: `cd ~/SchwingNet/grid && ONLY=<id> PYDRV=$HOME/SchwingNet/.pixi/envs/default/bin/python sbatch -D "$PWD" --export=ALL 02-bank-ingest.sbatch`, then `sbatch -D "$PWD" --export=ALL 03-catalog.sbatch`. A bank already written is kept where its bytes are the same; a raw file that changed under a stem is refused by name, since a changed raw copy is your call.
- The dry run of any of it: `SBATCH=echo bash grid/run-xray-chain.sh` in the grid's shell (bash only); `python3 tools/fetch_sources.py --only <id>` and `python3 tools/bank.py --recipe grid/banks/<id>.json` (a plan, nothing written) on your laptop or inside an interactive job (`srun -p reqp --qos=requeue --pty bash`), since the login node kills python by name.
- Off the grid, on a laptop or in a container, the three stage scripts run with bash on a data root of your own: `cd <checkout>/grid && SCHWINGNET=<checkout> PYDRV=<checkout>/.pixi/envs/train-cpu/bin/python DATA_ROOT=<a folder outside every checkout> OUTSIDE_SLURM=1 FETCH_ARGS='--only <id>' bash 01-fetch.sbatch`, then `... DATA_ROOT=<the same> bash 02-bank-ingest.sbatch` and `... bash 03-catalog.sbatch`. DATA_ROOT lands every source under `<root>/<id>/` as the grid's volume does, with the catalog at `<root>/_catalog` and the stages' temp under `<root>/_tmp`; OUTSIDE_SLURM=1 lifts the fetch tool's and the helper's refusal of a shell with no job (the login node stays refused); BANKS=<folder> runs stage 2 on another folder of recipes, a filled-in copy of a shipped one for a test; REACQUIRE names the helper where ~/spinesurg-ct-nnunet is not there, and without it the tool takes the repository's copy data/reproduce/reacquire/reacquire.py, the same file. tests/schwingnet/test_chain_stages.py runs stages 2 and 3 this way.

## What the chain does not do

- DICOM only in the train environment: pydicom, numpy, Pillow and pylibjpeg's decoders are in the train-cpu lock (#44), so stage 2 banks LUMOS's radiographs, VinDr-SpineXR, VinDr-CXR and VinDr-PCXR only when run by train-cpu's python, which the submit script prefers; a default-environment run refuses them by name. A frame is the modality LUT, MONOCHROME1 inverted, then the 0.5 to 99.5 percentile window to 8 bits; a multi-frame file, a flat frame or a pixel array that does not decode stops that source with the file and its transfer syntax named. A plan (`tools/bank.py --recipe R` without --run) reads every header and prints the person count, the most frames of one person and the transfer syntaxes, so a set's first job can be a plan.
- No gated set without its agreement and no credential of yours in any file of this repository: the credentialed and gated lines run only when you name them and their token file is in place.
- Nothing deleted, ever: a fetch resumes, a bank keeps what matches, a shard that exists is "already there", and a catalog version is never rewritten.
- No training step: the split check is the last thing the chain runs.
- No guessing: a recipe field spelled "to confirm" stops that source, an entry whose link is not in the list is skipped with one line, and the Kaggle scoliosis set is banked only after its sha256 list in FETCH.json is compared with the AASCE copy on the grid (the two paths are in its entry); a match means no new person and the source is left out; NIH ChestX-ray14's twelve URLs are the Box page's batch_download_zips.py as three independent copies give it (the list here before had a wrong second URL), and NIH publishes no checksum, so the entry checks every length and every SHA-1 piece against the Academic Torrents release of the same files before it unpacks anything; a torrent that cannot be read fails the entry, since a check that did not run is no check.
- Nothing measured on the grid: every size is what a page or a card states, and the ETA is one hour per 20 GB, a guess until the first log says otherwise; what the container measured is below.
## Measured (2026-10-21, issue #40: the chain run off the grid in a cloud container)

The three stage scripts ran with bash in a Claude cloud container (4 cores, Python 3.11 from the train-cpu environment, pixi 0.81.0), each with `SCHWINGNET=<checkout> DATA_ROOT=<a root outside the checkout> OUTSIDE_SLURM=1 BANKS=<a folder of filled-in recipes>` in front, from the grid/ folder, which is what sbatch does with -D (Re-running one source, above); nothing of the grid itself ran, and every number here is this container's, not a node's.

- Stage 1 fetched nothing: the container's proxy answers `Tunnel connection failed: 403 Forbidden` to api.figshare.com, ndownloader.figshare.com, figshare.com, zenodo.org, data.mendeley.com, huggingface.co and openi.nlm.nih.gov alike (curl and urllib, 2026-10-21 09:44 UTC), so the run on `--only aariz,kub_stonex` wrote two FETCH.json records naming the API's address and that line, exited 1 after 0.8 s, and the next stage still ran, as the chain means it to (a run on verse_2d_projections met the same answer from zenodo.org through the helper's zenodo-get). The two figshare records were read through another route: Aariz.zip is 2,098,209,792 bytes with md5 e0bd645bca6759abdae4f199d841bda6 and KUB-StoneX.zip 20,765,554,562 bytes with md5 277ec7981732dbed5ecf49a371ff8676, both CC BY 4.0, and those are in grid/fetch-xray.json for the job to verify against. No open set of the list is under 1 GB, so none would have been fetched whole here even with the hosts reachable.
- Stages 2 and 3 ran on two synthetic raw copies laid out as two shipped recipes expect, since no real bytes could come: nih_chestxray14 (120 PNG films of 512 x 512 in two archive folders, 40 persons by the file name, 371,591 bytes in all, since the pattern compresses well, and a zip of two more films beside them) and fraiwan_spine_xray (45 JPEG films of 640 x 800 noise under original/<class>/, 14,205,051 bytes, one file one person, converted through Pillow), 14,578,046 bytes in 168 files. Stage 2: 2.6 s wall for both banks and both shards (165 frames converted or copied, hashed, copied again into the shard and verified; the banks 415,811 and 23,118,280 bytes, the shards the same again plus their manifests); stage 3: 0.8 s for version 1 (2 shards, 165 frames, 192,512 bytes of SQLite) and the split check, disjoint, with 36 persons in the first part and 4 in the validation part of the NIH set and 39 and 6 in Fraiwan under the salt of data/splits/rule.json.
- What broke and was fixed on the way, each with a test: the fetch tool had no way to land under another root nor to run outside a Slurm job (`--data-root`, `--outside-slurm`, passed to the helper too; the sbatch scripts take DATA_ROOT, OUTSIDE_SLURM, REACQUIRE and BANKS); the helper's path on the grid does not exist off it (the repository's copy data/reproduce/reacquire/reacquire.py is the fallback); the stages set TMPDIR to the grid's folder, which off the grid is no directory and breaks every tempfile (a `_tmp` under the data root serves there); a zip that came stayed a zip, which the bank stage cannot read (`"unpack": true` opens it in place, once); and a raw copy that grew after a first ingest (the zip's two films unpacked after the 120) cut a second shard beside the first, which the catalog then counted with it: 287 frames for 167 files. Stage 2 now ingests with `--supersedes latest` and stage 3 builds with `--drop-superseded`, so the second run (2.5 s and 0.7 s) cut a successor of 122 frames and 42 persons that names the first shard, and version 2 holds 167 frames from 2 shards with the first NIH shard among its removed_shards.
- A third run of stages 2 and 3 on the same bytes wrote nothing: both shards "already there" (the successor's manifest came out byte for byte, its supersession kept), the catalog's bytes equal to the latest version and reported as not new.
- Not measured: anything on the grid (the reqp partition, the requeue, the 5 TB floor, df, sbatch's dependency chain, a compute node's rate from figshare or Zenodo, hf-get under the acq environment, the Kaggle and PhysioNet routes, the wall time of a real set), Pillow's rate on real films, and the two new recipes themselves, which stop at their "to confirm" fields until the unpacked folders have been looked at.

## Measured (2026-10-21, issue #44: the DICOM path off the grid)

In a Claude cloud container (4 cores, the train-cpu environment of this lock, pydicom 3.0.2), tools/bank.py banked 400 synthetic 512 x 512 12-bit DICOM frames of 150 persons, keyed by the header's PatientID, in 8.9 s with one worker and 2.4 s with four (the two banks the same bytes, a test holds it), and tools/ingest.py cut their shard in 1.3 s: 202 MB of DICOM became 104 MB of PNG, since noise is PNG's worst case. A real film is about twenty times the pixels, so at the stage's eight cores the guess is about 15 films a second: VinDr-SpineXR's 10,466 in about twelve minutes, LUMOS's 1,620 in two, VinDr-CXR's 18,000 in about twenty. Not measured: a real file's transfer syntax (the plan prints them), a node's rate, and the zip reads of LUMOS on Ceph.
