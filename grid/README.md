# The grid runs: the gate words

Nobody types a command on the grid. Every grid run of this repository goes through grid/gate.sh, which the Beethoven grid gate calls with one fixed word, `schwingnet <word>`, after bringing the checkout at ~/SchwingNet to main (a clone when there is none, else a fast-forward): the owner's rule of 2026-10-21 19:37 UTC, issue #53. The gate fetches the open X-ray datasets of docs/research/xray-datasets-missing.md and the data platform's own unfetched sources onto the data root, turns each X-ray copy into a bank in the builders' format, ingests every bank into a content-hashed shard, rebuilds the read-only catalog with its split check (docs/research/data-catalog.md), and trains and scores version 1 on it. On the login node gate.sh runs bash, git, hpcworker, squeue, sacct, scancel, flock and coreutils and nothing else (warrior kills python by name); every byte moves inside a Slurm job.

### How a job reaches Slurm (issue #77)

Every job, the gate's own, the run-*.sh scripts' and flow.py's slurm mode, is queued through hpcworker's `job submit` (framework 25 and later, interface 2), which the grid gate hands gate.sh as HPCWORKER: the owner's order of 2026-10-21, so that the lab's one tested Slurm knowledge places every job and nothing here guesses it. A submission names a class and nothing about where it runs: batch for every CPU job here (the site profile's reqp with the requeue QoS, requeued on preemption with its log appended to), gpu for the version 1 run, the latency GPU job and the sweeps (gmsap, gvohp or galhp with the gpu QoS and one GPU; the latency jobs narrow it to gmsap, the H200 nodes), and cpu for flow.py's local steps on the grid were they ever submitted. So no .sbatch header carries a partition, QoS, gres, requeue or output line; each keeps only its wall time, CPUs and memory, which job submit honours. grid/hpcw.sh is the one helper every script sources: it refuses an hpcworker older than framework 27, which lacks the options and the job environment these calls need, asks each shape but an array's with `--check` (sbatch --test-only) before queueing it (whether --test-only takes --array is not measured on the grid), so a job Slurm would refuse is never queued and its reason comes back whole, turns sbatch's dependency text into job submit's `--after ID:ok|any`, refusing anything else so no job is queued without its wait, and hands a job its settings through the environment, which job submit passes on, never through --export's comma grammar. Each job's output goes to hpcworker's log folder for the project, one line per job in its ledger; the stage reports stay under grid/logs/. Which of the gate's jobs are live is still read from squeue, since `job status` reads every job as ended when neither squeue nor sacct answers, and a gate that took that for nothing live would queue a second graph beside the first. Exit codes: 0 done, 64 a word refused, 75 busy, 2 a file or the checkout missing, 1 a submission failed.

### Why the jobs run in a container

The grid's nodes run CentOS 7 (glibc 2.17) and pixi.lock is solved for glibc 2.34, so the pixi environments cannot run on the nodes as they are. 00-setup.sbatch builds an Apptainer sandbox from docker://node:22-bookworm (glibc 2.36; the module apptainer/1.2.2, unprivileged on a compute node) on the lab volume, links .pixi to the lab volume, installs the four environments inside it with pixi 0.81.0 (its sha256 checked) and imports each once; only then does it write .pixi/SETUP.sha256, which the gate reads to know they are ready. grid/box.sh runs one command inside the sandbox with the lab volume and /dev/shm bound, and --nv on a node Slurm gave a GPU; grid/bin/pixi and grid/bin/train-cpu-python are the shims the stages call, so every stage's PYDRV is the train-cpu python inside the container.

## What to check first

1. The room on the lab volume. Every fetch is held to the owner's size rule of 2026-10-23 (grid/size-rule.sh, issue #160): before it downloads a byte, its exact size, read from its source by grid/fetch_size.py (the Hugging Face tree, the Zenodo record, the S3 listing, idc-index's series sizes, a zip's central directory by range requests, a link's Content-Range), must fit in the room the CephFS quota of /rs/rs_grp_oschome leaves (ceph.quota.max_bytes less ceph.dir.rbytes, read with no walk by getfattr, or by the acq environment's Python on a node with no getfattr, each value up to its first NUL and only as a count of at most 18 digits, since bash's arithmetic wraps a longer number without a word; never df, which on CephFS reports the whole Ceph pool, and nothing at all where neither reader runs or a value is no count) after what the admitted fetches, unpackings and bank words' jobs still queued or running have yet to write (a bank word's admission counts from the moment it queues the job), or its job ends with exit 4 having landed nothing. There is no floor and no margin, so the quota can be filled to the byte, and the rule stops no set part-way (acquisition_fetch.sh runs with FLOOR_TB=0); a job Slurm requeues keeps its admission and goes on. What the rule does not count can still fill the volume under a running set: the X-ray chain's banks and shards, the jobs' TMPDIR on the volume, the group's other users, the moments before CephFS adds new bytes to ceph.dir.rbytes, and a limit on the number of files, which the readout shows where the quota sets one. A fetch the gate sent before the rule (#161) runs the script Slurm copied when it was queued, with the 5 TB floor and the size its line states: let it finish, or cancel it and send it again under the rule. ## What the X-ray chain does

Stage 1, grid/01-fetch.sbatch (4 days of wall time, requeued on preemption): `tools/fetch_sources.py --run` reads grid/fetch-xray.json and runs one helper per entry, the data platform's own reacquire.py (zenodo-get, which verifies the record's md5 per file; hf-get, which verifies the LFS sha256; http-get, which resumes a .part), Mendeley's public API listed and then http-get per file with the sha256 the API gives, figshare's public API listed (api.figshare.com/v2/articles/<id>) and then http-get per file with the md5 and the size the API gives, after which each zip that came is opened in place for the bank stage (Aariz and KUB-StoneX, one zip each), the Kaggle CLI with the token from the file, or wget -r -N -c -np with the login from ~/.netrc for PhysioNet. Every entry lands at /rs/rs_grp_oschome/go2432/data/<id>/raw, the folder its registry entry names; the helper's state is <id>/fetch-state and the record <id>/FETCH.json: what ran, the exit codes, the byte count and the sha256 of every file, computed after the download. A failed entry is reported and the next runs; the stage exits 1 at the end when any failed, and stage 2 still runs on what came.

Stage 2, grid/02-bank-ingest.sbatch: for each recipe grid/banks/<id>.json whose raw folder holds anything, `tools/bank.py --run` writes the bank under <id>/bank (images/train/<stem>.png, meta/<stem>.json with the case, the device, the view and the boxes), then `tools/ingest.py run --bank <bank> --source <id> --kind train --split train --date <today> --code-commit <sha> --person-prefix <prefix>` cuts the shard under <id>/shards/<date>-<12 hex>/. PNG is copied byte for byte, so the shard's name is the raw bytes' content; JPEG, TIFF and BMP convert through Pillow in the train environment; the same bank twice is "already there". The ingest refuses a frozen test person in a train shard and the same bytes under two persons, as docs/research/data-catalog.md says.

Stage 3, grid/03-catalog.sbatch: `tools/catalog.py build --store /rs/rs_grp_oschome/go2432/data/_catalog --manifest <every MANIFEST.json under <data root>/*/shards/*/>` and `split-check --version <the version it built>`, and once the check passes the marker <store>/checked/<file> (the commit and the sha256 of data/splits/test-persons.json and rule.json) that the version 1 run's chooser reads; a build whose bytes equal the latest is reported as not new. One build at a time: the job holds <store>/BUILD.lock (flock) from listing the manifests to the split check, since start's, a fetch's and v1's catalog jobs can start together, and a build that listed the manifests before another job's shards landed must not land after the build that holds them. A failed split check exits 1 and no training step reads that version.

Each source's registry entry, data/registry/<id>.json, was written with the chain: the identity level, modality, device class and regions as the sweep read them, every one marked in its notes where the page has not been read, and the person-key rule pointing at the recipe. VertXNet's persons carry the prefix nhanes2, so a NHANES II person is one person across its sources.

## The leak checks (issue #9)

CHK-6 (near-duplicates across the split: a perceptual hash first, then NCC64 >= 0.97 on a 64 x 64 reduction) and CHK-7 (frames that share their bytes or their 0.5-99.5 percentile 8-bit pixels under persons or sources nobody declared to be one), as spine-program's LEAKAGE.md defines them, over every shard on the volume. The rules are src/schwingnet/leaks.py under the gate; tools/leaks.py reads and writes; unknown is not clean, so a frame that cannot be read, decoded or matched to its manifest's sha256, a shard listed with no fingerprint, an unreadable fingerprint file or a candidate search past its budget fails the run. Declarations live in data/splits/aliases.json (persons and sources, each group with why), empty today; the two halves are read as two separate class maps, so a person key that happens to read like a source joins no source.

```
cd ~/SchwingNet && git pull && HPCW_DRY=1 bash grid/run-leaks.sh    # dry run: the shard count and the two submissions
cd ~/SchwingNet && bash grid/run-leaks.sh                            # every shard under the data root
cd ~/SchwingNet && NEW=<source>/<date>-<hash> bash grid/run-leaks.sh # one new shard against every other
```

grid/run-leaks.sh lists every `<data root>/*/shards/*/` holding a MANIFEST.json, following symbolic links, so a source kept on another volume is listed and not silently left out of a run that checks only its list, into `<data root>/_leaks/runs/<stamp>-<random>/shards.txt`, submits grid/04-leaks.sbatch as an array of one task per shard (16 at a time unless CONCURRENCY says otherwise; reqp, requeue), and grid/05-leaks-join.sbatch afterany on the array, prints both job ids and appends them to grid/LAST_RUN.txt. Each task writes `<data root>/_leaks/fingerprints/<source>__<shard>.jsonl` and keeps a file already there for the same manifest with no failed frame, so a second run redoes nothing; it writes the frames a chunk of 1,024 at a time, each atomically, under `<file>.parts/`, so a task the partition requeues takes up the chunks it finished and decodes only the rest, and the chunks are removed once the whole file is written with no failed frame (with one, they stay, so the next run retries only the chunks that failed). The perceptual hash is integer arithmetic throughout (a fixed-point DCT, every cosine at least 0.0005 from a rounding boundary, the median compared in integers), so a node's floating point cannot flip a bit; fingerprint files are version 2, and a version-1 file is taken again by the fingerprint and refused by the join. The join writes LEAKS.json (every failing row, the counts, the inputs, the verdict) and LEAKS.md beside the shard list, and logs/05-leaks-STAGE-REPORT.md; it exits 1 on FAIL. afterany and not afterok: a task that failed must be counted by the join, not leave it pending for ever. Its part of each person is the frozen split's (data/splits/), taken at the join, so a fingerprint stays valid when the test list grows. A superseded shard is fingerprinted and then dropped by the join, as the catalog drops it. It is not wired into grid/run-xray-chain.sh: the array is sized by the shards on the volume, which exist only once stage 2 has run, so it is submitted after stage 3 has finished, by the line above.

Measured in a Claude cloud container (4 cores, the train-cpu environment, 2026-10-21; nothing on a node):

- Fingerprint, one core, per frame: 5 ms at 256 x 192 8-bit, 41 ms at 1024 x 1024 8-bit, 182 ms at 2048 x 2048 8- or 16-bit, 329 ms at 2500 x 3000 16-bit (noisy PNGs, the slow case for zlib): 0.8, 6.8, 30 and 55 core-minutes per 10,000 frames. A 1,979-frame synthetic shard took 6.2 s on one worker and 2.5 s on four. A fingerprint file is about 5.8 KB a frame (the 64 x 64 reduction in base64 is most of it).
- What a copy keeps: a frame resized to 1/2 or 0.7, brightened by 30, its contrast at 0.8, gamma 0.8 or saved as JPEG at quality 75 stayed within hash distance 4 (a hash sets 32 bits, so distances are even) and at NCC64 0.975 or more, so all of them are caught; a 5 % crop went to distance 2 to 22 and NCC64 0.61 to 0.84 and is not, as LEAKAGE.md's definition leaves it.
- The hash: the integer hash gave the same 64 bits as the earlier floating-point one on 300 test patterns, so what was measured below for version 1 holds for version 2.
- The join: the candidate distance is 6 (four bands of 16 bits probed one bit around, which by the pigeonhole principle misses no pair within 7). On the 1,979 synthetic frames, which share one layout, 1.4 % of random pairs fall within 6: 26,430 candidates, 26,319 across the split and scored, PASS, in 5.3 s on one core and 2.3 s on four; NCC64 costs about 0.17 ms a pair a core and the search 0.2 to 0.3 ms a frame (62 s for 200,000 random hashes); memory about 16 KB a frame in the first version. The join now holds each frame's 64 x 64 reduction as 4 KB in one shared buffer instead of its base64 text, reads each file line by line, and scores and judges the pairs a chunk at a time instead of holding every score: on 100,000 frames with no candidate pair its peak went from 835 MB to 659 MB (about 5 KB a frame over a base of some 150 MB), and on 30,000 frames with 1,485,000 pairs across the split, four processes, from 941 MB to 539 MB, the same rows either way. The search stops past 20,000,000 pairs (--max-pairs) and fails the run, rather than run for days on a corpus whose hashes crowd together.
- End to end off the grid (`OUTSIDE_SLURM=1 DATA_ROOT=<root> bash grid/run-leaks.sh`): two shards cut by tools/ingest.py from synthetic banks, 297 and 101 frames, the second holding a byte copy and a 3/4-size, brightened copy of two frames of the first under new persons: 3.2 s for both tasks and the join, FAIL with exactly those two rows (CHK-7, one store key under two persons; CHK-6, distance 0, NCC64 0.993) and no other.

The estimate per array task, from those rates: 8 cores, 16 GB, a day of wall time (the defaults in 04-leaks.sbatch). NIH ChestX-ray14's 112,120 frames at 1024 x 1024 are about 76 core-minutes, some 10 to 15 minutes on 8 cores with the reads; a MIMIC-sized shard (377,000 frames near 2500 x 3000) about 2,100 core-minutes, some 4.5 hours on 8 cores; the spine sets of a few thousand frames, minutes. The join: 8 cores, 32 GB, 12 hours: 1.5 million frames at about 5 KB each is some 8 GB, and the full pair budget of 20,000,000 candidates about 3 GB more at the measured 160 bytes a pair, so 32 GB leaves room for the workers; its time is the candidate count times 0.17 ms over the cores, which only the first real run measures, since chest films may crowd as the synthetic frames do. Not measured: a node's rate, CephFS's read rate, the candidate rate of real films, and a requeue on the grid itself (the take-up of finished chunks is tested off it, in tests/schwingnet/test_leaks.py).
