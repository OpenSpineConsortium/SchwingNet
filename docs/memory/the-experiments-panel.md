- A request is an issue labelled experiment whose body opens with the marker `<!-- schwingnet-experiment -->` and carries `recipe:`, `epochs:`, `seed:`, `hours:` and one `block: KEY=VALUE` line per block that differs from version 1, or the Experiment issue form's `### key` sections, which tools/experiments_panel.py writes from the same lists and its check holds current; the panel refuses a choice in the trainer's own words and holds the epochs to 1 to EPOCHS_MOST (200). .github/workflows/experiment.yml (tools/experiment_run.py, main's code, on an issue opened or labelled experiment and on Run workflow, which Run as me dispatches) answers it once with the normalised request, the exact command, the gate word `schwingnet-experiment-<issue>` and the owner's exact click, labels it owner-act and records the admitted lines as `<issue>.request` on the branch experiments; a request from someone without write access gets the refusal only, and an unknown value the known list. grid/gate.sh's word `experiment <issue>` fetches that file by git, checks each line's shape on the login node, needs version 1's inputs and submits one GPU job, grid/experiment-driver.sbatch, which checks the values again inside the container (`experiments_panel.py check --request`) before tools/flow.py runs; the Run workflow page sends the word only where symphony-template's scripts/grid-accounts.sh and hpcworker's tools/grid_gate.sh both admit it (symphony-template #459, hpcworker #45) and the gate's clone has taken hpcworker's change with the job word `update`, and `bash ~/SchwingNet/grid/gate.sh experiment <issue>` works from the grid's shell meanwhile.
