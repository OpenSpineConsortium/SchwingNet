The trainer's building blocks: each part of training is chosen by name with --block KEY=VALUE, naming none gives version 1's training to the bit, and tools/block_sweep.py lists the parts, plans a sweep and tables every run.

- The owner's ask of 2026-10-24: build the training improvements "as building block type pieces to make it interchangeable how i do something in case a better way arises" (#202), and then "something i can build on to continually optimize both which samples i use, which architectures, which denoising, augmentation, ect as plug and play pieces" (#207); the loop is docs/research/experiment-framework.md.
- The parts and their names are src/schwingnet/blocks.py (normalise, augment, optimiser with weight_decay and backbone_lr_scale, schedule with warmup_epochs, sampler, loss_weights, select, samples with sources and per_person, architecture, denoise), with the pure arithmetic under the gate's contracts; the torch side is tools/train_blocks.py, one function per name in a table per part (ARCHITECTURES with HEADS, DENOISERS, NORMALISERS, AUGMENTERS, OPTIMISERS, SAMPLERS), and tests/test_train_blocks.py fails when a table and its tuple disagree.
- A new way of doing a part is one name added to its tuple in blocks.py and one function in its table in train_blocks.py, plus the entry the part keys by name where it has one (HEADS for an architecture, AUGMENT_ORDER for an augment change, a branch in _keeps for a samples choice); a new part is a field with version 1's default and an entry in CHOICES or SETTINGS; tools/train.py calls only the tables. `python3 tools/block_sweep.py parts` prints every part, its names and version 1's choice from the code.
- tools/train.py takes --block KEY=VALUE, repeated; tools/flow.py takes the same and refuses a wrong one before any step. checkpoint.json and MODEL.md record the blocks, the parent and the training crops seen of those offered, and the evaluator, the latency tool and the chain evaluation build the model with train.model_for(checkpoint facts), so a checkpoint from before the blocks loads as version 1's model and a run's architecture and filters follow it everywhere.
- samples cuts the train part only, never validation, so every run of a comparison scores the same crops; cap-per-person keeps the first N crops of each person in the catalog's order, fixed and arbitrary; a setting that would act on nothing, or a source the train part does not hold, is refused; the record keeps the block's cut apart from a dry run's --max-frames cap.
- denoise (gaussian, median) and normalise=imagenet are forward pre-hooks on the model, in that order, not layers, so the weights' names do not change and the ONNX export carries the filter and the scaling (parity tested for every architecture); mobilenet-v3-small and efficientnet-b0 carry torchvision's dropout (and stochastic depth), which draw from the device's global generator, so their runs reproduce on the same kind of device, a resnet's on any; MONAI's densenet121, se-resnet50 and se-resnext50 (#211: monai in the train feature's lock, imported only when one of them is built) carry no dropout and reproduce on any, densenet121 reading torchvision's densenet121 ImageNet file in either spelling, the SE two a file in MONAI's names or none.
- A run from a parent checkpoint (--init) must share the parent's architecture, denoise and normalise and its crop size; the trainer refuses the rest in words.
- tools/block_sweep.py plan prints the tools/flow.py command of every combination of the varied blocks, the runs, jobs and GPU-hours, and submits nothing, `--weights [ARCHITECTURE=]FILE` once per architecture named; compare and ledger (every run under a folder, found by itself) rank finished runs by their validation part and witness frames with the latency headline (evaluate/latency.json, a timing and no score) beside, never reading evaluate/results.json.
- prior=level-map with prior_weight (#228) is the 3D prior: a frame's projected level map (the segmented CT's voxels mapped onto the X-ray by the render's geometry or a registered pose, a PNG of level codes beside the frame in the shard, named in the bank's meta as level_map and level_map_from, decoded and checked by the ingest, in the catalog's item row as level_map and level_map_from) is learnt by a training-only head on the backbone's last feature map (FEATURES per architecture in tools/train_blocks.py, PriorHead), its loss added at prior_weight; the box jitter moves the map with the crop; best.pt and every reader are unchanged, prior_head.pt sits beside it, and a run whose train part has no map is refused; no map exists yet, the renders of #59 bring them on the owner's word (docs/research/experiment-framework.md, section 6).
- Which blocks a run uses is the owner's word with the run; no block changes a run that names none.
