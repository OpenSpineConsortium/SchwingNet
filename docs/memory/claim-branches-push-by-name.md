A claim branch is made with --no-track, a clone made for one branch is told to fetch every branch, and every push names its branch, a forced one its tip too, because git's settings decide where a push goes and the push guard reads only the command.

Made with `git switch -c claude/N origin/<default>`, a claim branch tracks the default branch. Where git's push.default is upstream, or its old name tracking, git sends a push of such a branch to that upstream whatever the command names: `git push -u origin claude/N`, `git push origin claude/N` and a push naming no branch all wrote the default branch, in git's own words `claude/7 -> main`, and never made claude/N, and after a rebase the lease push forced the default branch. The push guard passed every one, since it reads the command and not git's settings. Under push.default matching, a push that names no branch sends every branch that has a namesake on origin: the checkpoint's commit pushed that way also wrote a local main that was ahead of origin's, and a lease pushed that way rewound main to a stale local main. Under nothing, such a push sends nothing at all. Under git's own default, simple, and under current, the old steps were safe.

A clone made for one branch (`git clone --single-branch`, or `--depth 1`), as a cloud session's is, fetches no other: `git fetch origin board` leaves origin/board as the session hook fetched it, the claim push records no upstream, a released branch is never fetched, and a lease that names no tip is refused as stale, there being no origin/claude/N to hold it against. `git config --add remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'` mends all of it. A refspec for the one branch claude/N instead makes every fetch fail while that branch does not exist, before the claim and again once a release renames it.

A lease that names no tip holds against whatever the last fetch read, so after the rebase's own `git fetch origin` it forces over anything pushed since: in a scratch run, a claim released and taken anew by another worker was overwritten by the rebase of the worker that held it first. `git push --force-with-lease=claude/N:<tip> origin claude/N`, the tip noted before the fetch, was refused there, and needs no origin/claude/N at all.

So the claim skill makes the branch with `--no-track`, has a clone made for one branch fetch every branch, names the branch in every push (`git push -u origin claude/N`, `git push origin claude/N`, the checkpoint skill's push included) and the tip in the lease, and the worker prompts and the board rule say the same. Measured with git 2.43 in scratch repositories with bare remotes on 2026-10-13: those commands landed on claude/N, with main untouched, under push.default upstream, tracking, simple, current, matching and nothing, in a whole clone and in one made for one branch, and the lease refused a push made since; tests/test_claim_skill.py runs them as the skills write them. A branch made from the checked-out default branch with `git switch -c NAME` takes it as its upstream too when branch.autoSetupMerge is always or inherit, so the start pages make their branches with `--no-track` as well; `git push -u origin HEAD` landed on the branch's own name under every setting.

A repository made from the template before this keeps its old steps, since its protocol.yml brings in tools/ alone: it takes these by a pull request of its own to .claude/skills/claim, .claude/skills/checkpoint, .claude/rules/board.md and its worker prompts, and a claim branch made with the old step 2 is mended with `git branch --unset-upstream claude/N`, then `git push -u origin claude/N`. A guard that asks git where a push goes would be symphony-protocol's change, not this repository's. Found by a review of symphony-protocol 0.4.1 and the reviews of its follow-up.
