The repository is the shared plane for every Claude account and every session: what lives where.

A claude.ai Project belongs to one account, and its memory is private to that account. This project therefore keeps everything that more than one account or session needs in this repository, which every account's Project links and every session clones:

- CLAUDE.md and .claude/rules/: the instructions, read by Claude Code at the start of every session, local or cloud. CLAUDE.md imports docs/project.md, docs/agents/PROTOCOL.md and docs/memory/MEMORY.md with `@` lines, so the goal, the protocol and the memory index load into every session without being asked for.
- docs/project.md: the goal, the scope, the repositories, the model and effort, the owners.
- docs/memory/: the shared memory, one fact per file, with the index in MEMORY.md.
- The board: the file STATE.md on the branch `board`, rewritten by .github/workflows/board.yml from the open issues, the `claude/<issue>` branches, the claim files and the pull requests, and never edited by hand. Read it with `git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`, which the session hook does at the start of every session; docs/agents/STATE.md on the default branch only describes its layout.
- docs/agents/PROTOCOL.md: how an issue is claimed (the first push of the branch `claude/<issue>`), worked in the open and finished.
- docs/agents/claims/: one file per claimed issue while it is claimed; the pull request that finishes the issue deletes it.
- docs/agents/OWNERSHIP.md: which worker owns which area.
- docs/agents/WORKERS.md: the one way of working, from one person alone to several people, routines and workers in GitHub Actions: every one of them is a worker under a name of its own, labelled worker:<name> (a person's sessions under the person's GitHub login), and the coordinator keeps them apart, as code in the board's own run (releasing idle claims, telling overlapping work) and as Claude in .github/workflows/coordinator.yml (planning an issue labelled epic into tasks for registered workers, settling blocked tasks, integrating), with tools/team.py doing the clerical steps.
- .github/symphony/workers/: the registry, one JSON file per routine or worker in Actions, added by the "Add a worker" issue form (.github/workflows/add-worker.yml opens the pull request) or by hand; .github/workflows/workers.yml runs those whose file says "runs": "actions".
- docs/agents/routines/worker.md: the worker prompt, the same for every routine and every worker in Actions but for the name, which takes the next issue that is the worker's to take from the board and carries it to a pull request. A routine keeps only the page's short prompt, which reads the full one, the page's last block, from the default branch on every run, so a merged change to it needs nothing pasted again; the coordinator's page works the same way.
- docs/agents/routines/coordinator.md: the coordinator prompt, which splits requests into issues and tidies the memory; the coordinator workflow runs it weekly on the repository's Claude token, and a repository with no such token, as in crowd mode, runs it as a routine on one account.
- docs/research/: what sessions find out, one file or folder per topic that opens by naming its source, indexed in its README; it accumulates across checkpoints, which point to it and never carry it (.claude/rules/research.md).
- docs/history/: the longer records; today its README and the research behind the split into five repositories.
- .claude/skills/: the three procedures, claim, remember and checkpoint, and two the owner asks for, drive-organize and lens-review.
- .claude/settings.json, .claude/hooks/ and .claude/commands/: the session hook that prints the board, the push guard that refuses a push the board rules forbid (tools/guard_push.py), the edit check that runs the document checks the moment an instruction or memory file changes (tools/check_edit.py), the shared permission allowlist, and /board, which reprints the whole board mid-session.
- docs/start/: the way in for a new user, which README.md points to first: what the five repositories are, a page of copyable steps per way of using them (solo, many cloud sessions at once, a team, volunteers, an existing repository, the benchmark, a change to the protocol), the accounts and tokens table, the prompts to paste and every settings page as a link. A session that is asked how to set something up points there.
- docs/setup/: github.md, what a person with the repository's settings does once, with ruleset-main.json, the default branch's rules as a file to import; claude-project.md, how each account makes its thin Project with blank fields; claude-action.md, how one account's subscription token turns on @claude in issues and pull requests and the other Claude workflows in Actions; and tiers.md, what each GitHub and Claude plan unlocks here.
- scripts/check.sh and tools/: the checks CI runs as "check", the claim-protocol check CI adds on a claude/ pull request, the board's renderer, the registry's check and the "Add a worker" form's words (workers.py, add_worker.py), the hooks' push guard and edit check, the template's one-time initialiser and the marker-section helper the checkpoint skill uses.
- tools/sdlc_protocol: the claim protocol's code, vendored from OpenSpineConsortium/symphony-protocol, which tools/board.py, check_protocol.py, team.py, workers.py and guard_push.py hand their arguments to. tools/VENDORED records the release, the commit and the sha256 of every copied file, scripts/check.sh fails when the copy differs from it, and tests/test_vendored.py also holds the copy to the library's files at that commit, in the clone SDLC_PROTOCOL names, which CI makes, or else one beside this repository, so an edit that rewrote VENDORED to match fails as well. A change to the rules is made in that repository, never edited in place: its sync pull request brings it to OpenSpineConsortium/symphony-template, and a repository made from the template vendors it by hand (protocol-changes-come-from-symphony-protocol.md).

The claude.ai Project is thin on purpose: it links the repository, its instructions, description and memory stay blank (the pointer text only for chats outside code sessions), nothing is copied into it, and nothing scripts it; a thread of a Project and a cloud session opened on the repository load the same files. Nothing in this repository holds a credential or a token, and no API key is used anywhere; when @claude, the workers in Actions or the coordinator workflow run, they run on one account's subscription token, CLAUDE_CODE_OAUTH_TOKEN, held in the repository's Actions secrets, never in a file (docs/setup/claude-action.md).
