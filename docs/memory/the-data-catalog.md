The frame catalog is a SQLite file beside the holding index, built from append-only content-hashed shard manifests and the registry under data/registry/, with the person-keyed split under data/splits/; images stay as files on the grid, Metaflow steps read the catalog by path and pass its sha256 and a query's answer as artifacts, and redundancy is the volume's.

- The design is docs/research/data-catalog.md (task #10, the owner's asks of 2026-10-21); the pure rules are src/schwingnet/catalog.py under the gate; the tool is tools/catalog.py (check, part, build, query, similar, embed, summary, export) on the standard library's sqlite3.
- A new source is one registry entry; a re-ingest is a new shard that supersedes the old one, never a rewrite; a shard is one kind (train, test, review), and the build refuses a train or review shard holding a frozen test person and a test shard holding anyone else.
- The split: a person on data/splits/test-persons.json is test; everyone else is validation where the first 8 bytes of sha256("schwingnet-split|<salt>|<person>") fall below validation_share of the hash space, training otherwise; the salt is in data/splits/rule.json, so adding a person moves nobody.
- The device and exposure facts (modality, device class, make, model, kVp, mAs, pixel size, view band) are columns, so the owner's one-domain hypothesis is measured per device and band, not assumed.
- Nothing in the catalog touches the grid by itself: the first ingest job and build there wait for the owner's word and number; a heavier engine (DuckDB, Parquet, LanceDB) is a pixi feature added by issue, never a server.
