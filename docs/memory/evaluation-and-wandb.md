The witness frames and W&B (#12): every checkpoint is drawn on the same real frames from epoch 0, and runs reach W&B online where the grid's key is found.

- The witness frames: schwingnet.witness chooses them (24 validation C-ArmLSpine frames across L1 to L5, 24 test frames, 2 of each L6 case, 8 evenly spaced frames of each sweep, case134 and case39), tools/witness.py freezes, checks and draws them; the first run on real frames is recorded with `tools/flow.py record --freeze`, which writes data/witness/witness.json, and every later run draws exactly those frames or is refused.
- The trainer draws the validation witness frames at every epoch from epoch 0 (the untrained network) and keeps every epoch's weights under train/epochs/; the evaluator replays the test, transitional and sweep frames over those weights at the version boundary, so the trainer never reads a test row and nothing chooses on test frames. The checkpoint is chosen on the whole validation part, never on epoch 0.
- W&B: tools/wandb_log.py finds the key by name in WANDB_API_KEY, ~/.wandb/token.env (mode 600) or ~/.netrc; online when found, offline under the run's wandb/ folder when the node cannot reach W&B (the start gives up in 60 s), and tools/flow.py pushes each step's offline run from the login node as soon as the step ends; wandb-sync.json and the flow's last line say "W&B NOT PUSHED: why" when it did not reach W&B. Project SchwingNet. wandb is in the train feature of pixi.toml.
- The push, as the locked wandb 0.30 takes it (#252): its sync has no --include-offline and exits 0 when the server refused a run, so a run counts as pushed only by the .wandb.synced mark wandb leaves beside its log; offline it ignores resume="allow", so a step cut and carried on offline is two local runs, pushed together in one `wandb sync --id <run id>-<step>` in the order they started; a log a kill cut mid-record is cut back to its last whole record first (the rest kept in run-<id>.wandb.cut), and nothing is pushed while a trainer holds train/.lock.
- The page: docs/research/evaluation/README.md, written by `python3 tools/eval_page.py write` from docs/research/v1-demo/runs/ and held by scripts/check.sh; it is read on GitHub, never put on Pages, since Pages on a private repository may be public on this plan. Latency comes from evaluate/latency.json, which the latency step (#13) writes.
