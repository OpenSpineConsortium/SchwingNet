The pipeline sandbox: deep learning pipelines built in the browser from typed blocks (docs/sandbox/pipeline-sandbox.html), the owner's asks of 2026-10-30; it plans and requests, and sends no job.

- `python3 tools/pipeline_sandbox.py write` builds the page from tools/sandbox/ (contract.json, the block manifests blocks/<id>.json, the templates templates/<id>.json, engine.js, ui.js, page.css, shell.html) and from tools/experiments_panel.py's reading of src/schwingnet/blocks.py and data/recipes/; `check`, run by scripts/check.sh, fails a stale page, so a change to any of those, a training block or a recipe included, needs `write` and the page committed with it.
- The engine is one plain JavaScript file the page and node both run; tools/pipeline_sandbox.py mirrors it in Python and the test holds the two to the same digests and problems where node is installed.
- A pipeline that maps onto the experiment route becomes the same prefilled experiment issues the experiments panel makes (byte for byte tools/experiments_panel.issue_body), answered by experiment.yml and the gate word as before; any other pipeline is a plan with its job counts and a prefilled issue marked `<!-- schwingnet-pipeline -->` that nothing answers until the pipeline route exists.
- A block is a manifest that meets requirements R1 to R13 (contract.json lists them; `python3 tools/pipeline_sandbox.py check-block PATH` checks one); a block of its own code adds tools/sandbox/blocks/<id>.py with `def run(inputs, params, context)` and tests/test_sandbox_block_<id>.py.
- The pipeline route (pipeline.yml, the word `pipeline <issue>` in the three gates, PipelineFlow under a frozen PREREG, the blocks' run entries and a conformance runner) is planned in docs/research/pipeline-sandbox/README.md, section 8, and waits on the owner's word and job count.
