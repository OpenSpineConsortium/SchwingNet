The gate word `literature <list>` fetches a reading list under grid/literature/ onto the grid with Elsevier's key; Elsevier's files stay on the grid and a Claude session reads them only on the owner's word.

- Keys: symphony-template's grid-accounts.yml action key with name elsevier (organization secrets ELSEVIER_API_KEY and ELSEVIER_INSTTOKEN, one line) and s2 (S2_API_KEY) writes ~/.elsevier/token.env and ~/.s2/token.env through hpcworker's gate word key; no session ever sees a value.
- Fetch: grid/literature.sbatch runs grid/literature_fetch.py as plan, then fetch, under the size rule, into the landing literature_<list> of the data root, 0700, files 0600; PMC open-access copies, Elsevier's API after its entitlement check, Semantic Scholar's open copies; PMC articles outside the open-access subset are never scripted.
- Reading: a Claude session on the grid under the owner's account reads INDEX.md in the landing and the open-access files; Elsevier's files only on the owner's word, since a session sends what it reads to Anthropic's API (INDEX.md marks them); a cloud session reads only the report the word prints (papers and reasons, no text).
- Each send alternates: queue, then print and keep the report; the send after fetches again only what is missing, so an Elsevier paper lands once its access opens (the text-mining amendment of Elsevier's 2026-10-16 e-mail).
- First run (job 40819848, 2026-10-28): 17 of 42 got, mostly as Europe PMC XML since PMC answers 403 to a scripted PDF; Elsevier answered 403 even for the open-access shin2024, so the request was refused before rights were checked: either the token is not bound to the key or the key is not yet enabled for the ScienceDirect APIs, perhaps until the text-mining amendment (ask Elsevier both); Semantic Scholar answered 429 to four keyed lookups, which now get six tries with a doubling back-off that also waits out a Retry-After of up to two minutes.
