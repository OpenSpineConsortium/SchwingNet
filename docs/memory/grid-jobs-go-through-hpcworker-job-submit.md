Every SchwingNet grid job is queued through hpcworker's `job submit` with a class (cpu, batch or gpu) and never an sbatch line of ours, since the site profile knows the partitions and the QoS (issue #77).

The owner's order of 2026-10-21: grid jobs use the lab's existing, tested Slurm knowledge. grid/hpcw.sh is the one helper grid/gate.sh, the run-*.sh scripts and tools/flow.py's slurm mode use: `hpcw_submit NAME CLASS [K=V...] [options] -- SCRIPT` asks the shape with `--check` first, then queues it in <checkout>/grid with the K=V pairs in the job's environment, and prints the job id; `hpcw_after` turns sbatch's dependency text into `--after ID:ok|any`. The grid gate hands gate.sh its hpcworker as HPCWORKER (run through bash, since the clone keeps it 0644); by hand it is found on PATH, and HPCW_DRY=1 prints the submissions. Every CPU job here is batch (reqp with the requeue QoS, requeued on preemption), the version 1 run and the latency GPU jobs are gpu (the latency ones narrowed to gmsap with --partition), and a .sbatch header keeps only --time, --cpus-per-task and --mem; tests/test_gate.py fails on a header or a script that places a job itself. A job's output is in hpcworker's log folder for the project (status reads it with `job log`), not grid/logs/, which keeps the stage reports and GATE_JOBS.txt. Live jobs are still read from squeue, because `job status` reports every job as ended when neither squeue nor sacct answers. The tests use the fake tests/fakes/hpcworker, which logs each queued job as one line with its --after list in sbatch's words.
