Profiling a session: tools/profile.py reads a session's transcript, the same file tools/usage.py reads for the usage trailer, and gives what the session spent as counts alone, for the research programme under docs/research/beyond-cooperation/.

A Claude Code transcript carries the API's own token counts on every call and every tool call with its answer, so what a session spent on context, tool calls, reading and time can be measured afterwards by code, from the file, with nothing installed and nothing sent anywhere. `python3 tools/profile.py TRANSCRIPT --json FILE` writes the record and prints the report: each API call once by its message id, the context call by call with its cached share and compactions, calls by tool with their failures, bytes and seconds, reads and re-reads of files, and seconds in tools (two at once counted once) against seconds outside them, the model's and the harness's. The record never carries a path, a command, a prompt or any text, so it can be committed beside the question it answers; tests/test_profile.py is the definition of every count.

The same counts ride on a session's commits, the programme's step 1: the commit-msg hook of tools/usage.py adds a Symphony-Profile line after the Symphony-Usage line, the profile since the session's last commit (calls, failed, repeated, the files its reads named and re-read with their bytes, the peak context of its calls since, compactions, drops, seconds in tools), counts alone and no tool's name, and a run in Actions keeps the same counts in its usage record; the metrics switch stops both. Step 2 sums them: `tools/metrics.py collect --profile-out`, which the metrics workflow runs, writes PROFILE.json beside METRICS.json on the branch metrics, each pull request's lines and runs summed per work setting and on the coordination block's two sides, with calls, reads and re-reads per profiled merge and the median peak as ratios over 1 where parallel did better; the collector does not read it until the Apps' privacy statement lists its keys, which is the owner's step. Step 3 is docs/research/beyond-cooperation/report.md, one table per question with each arm's run against the baselines and its outcome (tasks landed, MAST modes judged) beside costs per landed task, written by `python3 tools/profile_report.py docs/research/beyond-cooperation` from the records committed there (baseline-DATE.json with its .outcome.json, runs/DATE-ARM/ with outcome.json and *.profile.json); tests/test_profile_report.py fails when the page is stale. The record of tools/profile.py names the harness's own tools and folds every MCP tool into one row, mcp, and any other into other, since a server's name says what a session was connected to; `--tools N` prints the names on the screen only.

The programme measures a way of working before changing it: context compression, fewer tool calls and less code reading are its arms, each read beside whether the work landed and, when it did not, how it failed in MAST's names (arXiv:2503.13657; the record's repeated calls and compactions are its step repetition and loss of history read by code), and no run that spends tokens starts without the owner's word and the number. The first record is docs/research/beyond-cooperation/baseline-2026-10-15.json, the thread that wrote the instrument, taken from a transcript that is not kept, so the tests are its reproducible part; its first API call carried 120,867 tokens before any work: 43,468 read from the prompt cache, the part of the harness's own context an earlier request with the same prefix had written, and 77,397 written for the call, the rest of the harness's context, the project's instructions (about 18,000 tokens), the Project's memory and the thread's first message; every later call carried it all at the cache-read price.
