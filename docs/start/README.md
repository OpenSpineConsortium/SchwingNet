# Start here

This folder is the way in. It says what the five repositories are, which path fits what you want to do, which accounts and tokens each path needs, and the quickest way to see the whole thing work. Every page is a short list of blocks to copy, each with the settings page it touches and what you should see when it worked. [links.md](links.md) has every settings page as one list of links, and [prompts.md](prompts.md) the sentences to paste into a session.

In the blocks, ORG/NAME is your repository (ORG is the user or the organization that owns it) and N an issue's number. Bash blocks run on macOS, Linux or WSL; PowerShell blocks run in Windows itself. On Windows, run the bash blocks in WSL, since the scripts and the hooks need bash and python3.

## The five repositories

| Repository | What it is |
| --- | --- |
| [OpenSpineConsortium/symphony-template](https://github.com/OpenSpineConsortium/symphony-template), internal | The template a project is made from: the instructions, the memory, the board, the workflows and the hooks that every Claude session on the project reads. |
| [OpenSpineConsortium/symphony-protocol](https://github.com/OpenSpineConsortium/symphony-protocol), public | The claim protocol as one Python library with no dependencies; every other repository runs a copy of it, so a rule is written once. |
| [OpenSpineConsortium/coordbench](https://github.com/OpenSpineConsortium/coordbench), public | The benchmark that compares ways of coordinating Claude Code agents on CooperBench's task pairs, this protocol among them. |
| [OpenSpineConsortium/symphony-marketplace](https://github.com/OpenSpineConsortium/symphony-marketplace), public | The Claude Code plugin `symphony`: the skills, the board command and the hooks, for a repository not made from the template. |
| OpenSpineConsortium/symphony-app, private | The GitHub App Symphony, whose token starts a new copy's first workflows and opens the protocol's sync pull requests. |

How they fit: symphony-protocol holds the rules, and its sync workflow carries every merged change to the other four as a pull request that each one's own check decides. A project is made from symphony-template and coordinates through GitHub alone: an issue is a task, the first push of a branch `claude/<issue>` is the claim, the board (the file STATE.md on the branch `board`) is the shared state, and a pull request is the handoff. That is why any number of workers, people's sessions, routines and workers in GitHub Actions alike, on any number of accounts, can work one repository at once without talking to each other: GitHub refuses the second push of a claim branch, so two never hold the same issue, and each claims under a name of its own, its label `worker:<name>` ([WORKERS.md](../agents/WORKERS.md)). [ECOSYSTEM.md](https://github.com/OpenSpineConsortium/symphony-protocol/blob/main/ECOSYSTEM.md) in symphony-protocol draws the map: which modules each repository copies and how a change reaches each.

symphony-template is internal to its enterprise, so only the enterprise's members can open it and press "Use this template". Anyone else comes in through the front door, the public repository [OpenSpineConsortium/symphony-start](https://github.com/OpenSpineConsortium/symphony-start): they install its App on a repository of their own, press Create on the form GitHub sends them to, and within about two minutes a pull request is open there with the whole template filled in (an empty repository) or the protocol alone (one with files), as its README says, once the template's owner has set it up (its README, For the owner); with its Setup App installed on the repository too, the same run applies the settings `scripts/setup-repo.sh` would, so nothing is left by hand, except what the policy of their organization or enterprise holds off, which the pull request names; the files land in their repository and are theirs to read. The other way is a public copy, which the template's owner publishes with `python3 scripts/crowd.py publish-template` ([crowdsourcing.md](../setup/crowdsourcing.md), Part 1, step 2, route A); it publishes the template's files and history, so it is made only with the owner's agreement. Below, TEMPLATE_OWNER/TEMPLATE_NAME is that copy, or OpenSpineConsortium/symphony-template itself for a member; where a step says to make the repository from it, the front door's form does the same for anyone else.

[capabilities.md](capabilities.md) lists everything a project can do today, what sets it apart, and worked examples to hand to someone new.

## Accounts and tokens

Each line belongs to one account: Anthropic's Consumer Terms forbid sharing account credentials, so nothing here is pooled or committed, and no file in a repository holds any of it. A repository's Actions secret stays with its account only while that account's owner is the repository's one writer: any writer can run a workflow of their own that reads it, and every writer's @claude comment runs on CLAUDE_CODE_OAUTH_TOKEN. So the secrets come out of the repository before anyone else gets Write ([team.md](team.md), step 1). In an organization, its owners have admin on every repository it owns, and a base permission of write makes every member a writer, from the moment a repository is made: a copy made there may hold CLAUDE_CODE_OAUTH_TOKEN only when you are the organization's only owner and its base permission is read or none. Otherwise leave out `--token` and @claude ([solo.md](solo.md), steps 3 and 6), or make the copy in an organization you alone own.

| What | Made where | Stored where | Held by | Needed for |
| --- | --- | --- | --- | --- |
| claude.ai sign-in | `claude` (a browser sign-in), or claude.ai | your machine and claude.ai | each person, their own | everything |
| GitHub connection for cloud sessions | https://claude.ai/code, Sign in with GitHub | Anthropic, encrypted with your claude.ai account; never in the session's VM | each person, their own | cloud sessions, Projects, routines |
| The Claude GitHub App on the repository | https://github.com/apps/claude/installations/new | the repository's or the organization's GitHub Apps settings | the repository's admin, once | cloud sessions on the repository (a private one needs it to clone, and any one for the session's push, unless GitHub is connected with `/web-setup`), Projects, routines' GitHub triggers, @claude, the workers in Actions, the coordinator workflow |
| gh sign-in | `gh auth login` | your machine | each person, their own | setup-repo.sh, crowd.py, the claim skill on your machine |
| CLAUDE_CODE_OAUTH_TOKEN | `claude setup-token`, on your machine, or `python3 scripts/tokens.py`, the token wizard, which runs it for you and stores the token unseen ([claude-tokens.md](../setup/claude-tokens.md)) | the repository's Actions secrets, or the organization's for the repositories on its list | one account, one token per repository, only while its owner is the repository's one writer | @claude, the workers in Actions, the coordinator workflow |
| SYMPHONY_CLAUDE_1 to SYMPHONY_CLAUDE_8, and SYMPHONY_CLAUDE_ACCOUNTS, the slots in use | the token wizard, one slot per account of your own | the organization's Actions secrets, seen by the repositories on their list; or one repository's | the owner, whose own accounts the slots are | a benchmark in Actions, one account per job at a time (coordbench's bench.yml) |
| COORDBENCH_CLAUDE_TOKEN | `claude setup-token`, on your machine | Environment variables of your own personal cloud environment | each person who runs the benchmark, their own | coordbench's agents |
| COORDINATOR_TRIGGER_URL and COORDINATOR_TRIGGER_TOKEN | a coordinator routine's API trigger, Generate token, where the repository runs one ([coordinator.md](../agents/routines/coordinator.md)) | the repository's Actions secrets | the routine's account, only while its owner is the repository's one writer | the board waking the coordinator routine when it changes |
| SDLC_APP_ID and SDLC_APP_PRIVATE_KEY | symphony-app's scripts/register.py | an Actions variable and secret: on symphony-protocol, for the sync; on an organization, for its copies' first push, only where the owner alone writes every repository the organization owns, since the visibility that reaches a copy from its first push (all, or private, gh's default) also puts the key into every copy a member makes there, where that member is admin | the owner; the key comes out of a repository others write to | the first workflows of a copy made in an organization only the owner writes to (any other copy runs its init on GITHUB_TOKEN; its Checks start with its first pull request and its Board with the first issue or pull request a person opens); the protocol's sync |
| ANTHROPIC_API_KEY | nowhere | nowhere: keep it unset | nobody | nothing; on your machine it would outrank your sign-in and bill the API |

A cloud session needs no token in its environment for project work: it runs on your own sign-in and reaches GitHub through its proxy. Only the benchmark puts one there, because the agents it starts need it.

## The quickest path, about five minutes

You need Claude Pro, Max or Team, or an Enterprise seat with Claude Code, signed in at https://claude.ai/code with GitHub connected (Sign in with GitHub; on Team and Enterprise an Owner first turns on the GitHub connector at https://claude.ai/admin-settings/connectors), and read access to the template. Branch rules, secret scanning and @claude come later, in [solo.md](solo.md), steps 3 and 6; until then nothing but the session's push guard stops a push to the default branch.

1. Make the repository. A member of the template's enterprise makes it private, in an organization of the enterprise, whose plan already enforces branch rules and offers auto-merge on a private repository: https://github.com/new?template_owner=OpenSpineConsortium&template_name=symphony-template&owner=OpenSpineConsortium&visibility=private, with another organization of the enterprise in place of `owner=OpenSpineConsortium` if that is where you make repositories. An organization's owners write every repository it owns, and an organization secret reaches a copy from its first push, so before you create it read "Accounts and tokens" above: the copy holds no subscription token unless you are the organization's only owner, and the organization must not hold the App's key for all its repositories or all its private ones (the SDLC_APP_PRIVATE_KEY row); if it does, ask an organization owner to limit it to a list of repositories they alone write, or remove it, first. Anyone else makes it from the public copy: https://github.com/new?template_owner=TEMPLATE_OWNER&template_name=TEMPLATE_NAME&owner=@me&visibility=public. Name the repository and create it. You should see the new repository with the template's files.
2. Wait a minute or two, then open https://github.com/ORG/NAME/issues. You should see the issue "Set up this project", opened by the first push's init workflow, and six labels at https://github.com/ORG/NAME/labels.
3. Install the Claude GitHub App on it: in "Set up this project", follow the link "install the app", which usually has your repository already chosen (if not, pick it), and install. You should see Claude at https://github.com/ORG/NAME/settings/installations. On an organization, an organization owner may need to approve it.
4. Open a task at https://github.com/ORG/NAME/issues/new?template=task.yml, for example the title "Task: write the goal" with the goal "docs/project.md says what this project makes, for whom and what done looks like" and the acceptance "bash scripts/check.sh passes and the owner agrees"; the form does not submit without an Acceptance. You should see it labelled todo, as issue #2 in a new repository.
5. Open https://claude.ai/code?repositories=ORG/NAME, paste the prompt below with your issue's number, and send it. Within minutes you should see the branch `claude/2`, a draft pull request saying "Closes #2", and the claim on the board at https://github.com/ORG/NAME/blob/board/STATE.md.

```
Claim issue 2 with the claim skill and carry it to a ready pull request, as docs/agents/PROTOCOL.md says; work on the branch claude/2, not this session's own branch. gh issue and gh pr are refused in a cloud session, so add the labels, post the plan and open the draft pull request with your GitHub tools or gh api. Mark the pull request ready with your GitHub tool update_pull_request (draft false), not gh api, which cannot change a draft; if you have no such tool, comment "finished; ready to mark" on the pull request and stop before you delete the claim file. Do not merge.
```

From there: [solo.md](solo.md) finishes the setup, and [parallel.md](parallel.md) starts several such sessions at once.
