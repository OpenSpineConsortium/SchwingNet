How to read it, as a baseline of this project's own way of working:

- What the session is. A thread of a claude.ai Project in the cloud, started by a brief and carrying 12 prompts in all, the owner's messages, the coordinator's relays and the harness's own notifications delivered as user turns, which the count does not tell apart, with two helper transcripts, the review agent's and its own after a usage limit stopped it and it was resumed, whose calls are in the rows and whose context is not; the harness wrote 361 attachment lines, hook output, reminders and its records of what it loaded, which the growth attribution cannot tell from the tools' answers they came with. The session's conversation was condensed once (the compaction, and the one drop), after a peak of 379,356 tokens; the last call carried 344,769.
- The start. The first API call carried 120,867 tokens before any work: 43,468 read from the prompt cache, the part of the harness's own context that an earlier request with the same prefix had written, and 77,397 written for this call, the rest of the harness's context, the project's instructions (about 18,000 tokens), the Project's memory and the thread's first message; how they divide between the harness's prompt, its tools and the thread's content, the usage does not record. Every later call carried it, which is why 96 percent of the context tokens were cache reads and the uncached input over the whole session was 3,396 tokens. The plan's section 5 says what that costs and what it is the first measure of.
- The time. Of 4,595 active seconds, 560 were in tools, two at once counted once, and 4,035 outside them, the model's and the harness's; the harness counted 1,826 seconds of thinking. The session's own 277,104 output tokens (the record's 458,421 less the helpers' 181,317) over those 4,035 seconds are about 69 tokens a second, which is the model writing: this thread's time went to its own output, thinking and text, and not to its tools. Per tool the seconds are summed and the helpers' calls are in the rows: of the 1,406 seconds in the rows, 661 are the helpers' calls', and the session's own 745 against the 560-second union say its calls seldom ran beside one another.
- The reading. 63 calls named 97 files, 53 of them distinct, 19 of them files the session had read before; 41 calls read part of a file (head, tail, a sed range), the auto-mode instruction to read through the shell at work, and 178 shell commands were filters or here-document consumers (head and tail after a pipe, cat writing a file from a here-document). Of the 581 KB the reads returned, 174 KB came back from calls that only re-read, about 30 percent, which is the most a hashing index (the plan's section 2, last row) could have saved this session before its own cost is counted. 4 of the 265 tool calls repeated an earlier call exactly, MAST's step repetition read by code (the plan's section 3), an upper bound on waste.
- The context. It grew by 273,352 tokens over the session, 189,754 of them attributed to the shell by the session's own calls (the shell's row, 188 calls returning 815 KB, has the helpers' calls in it too); the rest to the notifications, the web and the tool search.
- The failures. Eleven of the 21 failed calls were WebFetch calls to hosts this environment cannot resolve (dev.to, grith.ai, web.archive.org, huggingface.co, alphaxiv.org, neurips.cc, datasets-server.huggingface.co, sites.google.com and mlanthology.org, the last eight while reading about MAST); seven were shell commands, a wrong output path and a syntax slip early on, and later two edit scripts whose assertion did not find the text they were to replace, a rehearsal whose test failed, a test run before its fix and a script of the reviewer's run without its arguments, each found and fixed in the next call; two were the helper's reads of another repository the session's GitHub tools do not reach, and one a reviewer request GitHub refuses on one's own pull request. The one unanswered call is the command that took this profile, whose answer was not yet written when it read the file.

What a baseline of one session cannot say: whether these figures are typical of the project's threads, which the profile trailer of the plan's step 1 answers over every commit, or what they would be under any arm of section 2, which is what the arms are for. And what this record cannot do: be made again, since the transcript it was read from lives in the session's container and is not kept; the tool's tests are the reproducible part, and a kept transcript (coordbench's harness keeps one per run) gives the first baseline that can be regenerated.
