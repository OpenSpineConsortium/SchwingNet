# Symphony beyond cooperation: what one agent spends, and how to spend less

Source: the thread "Symphony beyond cooperation" of the symphony Project, 2026-10-15 and 2026-10-16, on the owner's ask quoted below and the owner's pointer to MAST of 2026-10-16 (section 3); no Claude Doc or artifact is its source. Of the four documents attached to the owner's ask, the package-search report is the one this page uses (section 2), and the taxonomy spec is read from its copy in this repository.

The owner's ask of 2026-10-15 23:35 UTC (item 5 of the message that resumed the project from the 2026-10-15b handoff): a more general use of the Symphony protocol for LLM usage optimization beyond cooperation, "including but not limited to context compression, profiling, decreased tool usage, decreased code reading through hashing/RAG, etc all in a reproducible way with autonomous research continuously", with two pointers, kitaisreal/agentprof and a dev.to article that profiled Claude Code with strace.

This page is that programme: its questions, the outcome side that reads how work fails, the instrument that measures them, the first measurement, the loop that keeps measuring, and what each step costs. The loop of section 6 is designed here and built a step at a time, each step a pull request of its own: the pull request that brought this page (symphony-template#94) brought the instrument, its tests and the first measurement, the next brought step 1, the profile on every commit (symphony-template#104), a later one step 2, its sums per pull request in PROFILE.json (symphony-template#116), and the next step 3, the report, report.md, which tools/profile_report.py writes from the records here. Where the ask forked, these defaults were taken and are said here: a plan with a first reproducible measurement rather than a plan alone; the programme lives in this repository, under docs/research/, with its instrument under tools/ beside the usage trailer it extends; benchmarks on other people's tasks (SWE-bench and the like, the owner's item 6) are the business of repositories like coordbench and are only pointed to from here; and no run that spends tokens starts without the owner's word and the number.

## 1. Why this is Symphony's to do

Symphony's one idea is that coordination state lives in the work itself, in GitHub objects, and is read by code (docs/agents/PROTOCOL.md; the taxonomy spec, docs/checkpoints/2026-10-15b/taxonomy/spec.md, section 3). The same idea applied to cost already exists here: what each session spends rides on its commits as the Symphony-Usage trailer, each Claude run in Actions leaves a symphony-usage-* artifact, and the field metrics add them up per pull request and compare work done alone with work done in parallel (tools/usage.py, tools/economics.py, docs/setup/metrics.md, Economics). Coordination is the first thing Symphony optimized, and the ratios in METRICS.json's coordination block are its measure.

Everything else an agent spends can be measured the same way, from the same records, with the same discipline, and that is the programme:

- The records. A Claude Code session leaves a transcript, one JSON object a line, with the API's own token counts on every call and every tool call with its answer; a run in Actions leaves the Agent SDK's execution file with the same messages. tools/usage.py reads them for the trailer. Nothing more has to be installed or hooked, and nothing is sent anywhere.
- The discipline, from OpenSpineConsortium/coordbench: keep the task, the agent and the scoring fixed and make the thing under study a plug-in, an arm; pre-register the question and the analysis before a run (its bench/cooperbench/PLAN.md); say for every measure whether it is taken as the reference work takes it, equivalently, differently for a reason, or not yet (its PARITY.md); write an audit record per run and leave spoiled runs out of every figure (its audit.json, coordbench#21); have a model judge only when the owner runs it.
- The protocol. A research question is an issue; an epic is planned into tasks by the coordinator; a task is an arm run by a worker, which pushes its results and opens a pull request; the required check runs the tests that hold every measure to its definition; the board shows what is running. The research loop is Symphony's own way of working, applied to measuring itself.

What in the protocol generalizes, piece by piece:

| In the protocol | In the research loop |
| --- | --- |
| One issue is one branch and one pull request, claimed by the first push | One question is an issue; one arm is one branch and one pull request, whose records land with it |
| The board is rendered by code from the issues, the branches and the pull requests, and nobody edits it by hand | The report is rendered by code from the records, the baseline's row first, and nobody edits it by hand |
| What a session spent rides on its commits as the Symphony-Usage trailer, read by the field metrics | What a session's context, calls and reads were rides the same way, as a Symphony-Profile trailer (section 6, step 1), which the field metrics sum per pull request into PROFILE.json (step 2) |
| The required check holds a pull request to the protocol | The required check holds every record to its schema and every measure to the test that defines it |
| The coordinator plans an epic into tasks and settles what a blocked task needs | Each question is an epic, the arms are its tasks, and the findings re-plan it |
| The vendored library is held to its record (tools/VENDORED), and coordbench's PARITY.md says how each measure relates to CooperBench's | Every measure says how it relates to the reference it is compared with, and a definition changes in its test first |

## 2. The questions

Each domain the owner named has a measure a transcript already contains, an arm that would change it, and an outcome that must be read beside it: fewer tokens is trivially reached by doing nothing, so every cost measure is reported with whether the work landed (the pull request merged, its required check green, no reverts; or, on a benchmark, the task's tests passed) and, where it did not, how it failed, in the names MAST gives (section 3).

| Domain | The measures (tools/profile.py) | Baseline | Arms to measure | Better means |
| --- | --- | --- | --- | --- |
| Profiling | Tokens by kind and model; the context sent on each API call, its first, peak, mean and last; the share served from the prompt cache; calls, failures, repeated calls, bytes in and out, seconds and the tokens brought in, per tool; seconds in tools, two at once counted once, seconds outside them, and the harness's own count of thinking | This page's section 5 | None by itself: it is the instrument the other rows use. One arm of its own: the harness's file I/O under strace (section 6, step 6) | A reader can say where a session's tokens, time and context went |
| Context compression | First context, peak, mean, cached share, compactions and drops, growth from tool results | The same | Claude Code's automatic compaction as it is; /compact at milestones; reading through helpers whose transcripts stay out of the main context; results trimmed at the source (head, grep, sed ranges in place of cat); shorter instructions at session start | Lower peak and mean, higher cached share, at the same outcome |
| Decreased tool usage | Calls per tool, failed, unanswered and repeated calls, shell commands by use (read, filter, search, list, git, run) | The same | Rules that batch independent calls and join commands; permission allowlists, so fewer calls wait on a prompt; skills that bundle a procedure (the claim skill); a tool that answers in one call what took several | Fewer calls and failures per landed pull request |
| Decreased code reading through hashing and retrieval | Reads, files named and distinct, re-reads and the bytes they returned, partial reads | The same: its Reads line, where what the calls that only re-read returned is the most an index could have saved that session | An index at session start, one line per file with its size, its content hash and its outline (the functions and headings), kept by the commit hook and read in place of the tree, so that a session reads a file only when it does not know it and reads it again only when its hash has changed; a search-first rule; a retrieval tool that returns the span that matters rather than the file; a code map in CLAUDE.md | Fewer bytes read and re-read per landed pull request, at the same outcome, with the index's own cost counted in |

The arms are hypotheses, not recommendations: the package-search report attached to the owner's ask (a Word document on the orchestration packages, item 6's "naive approach"; not in this repository) recommends retrieval for rules and context compaction on general grounds, and here each is measured before it is adopted. The questions extend the taxonomy spec's section 11, whose R3 (what one coordination step costs) and R7 (what free minutes are worth) are the two cost questions already open there.

## 3. The outcome side: how the work fails, as MAST names it

Every cost measure above is read beside whether the work landed. MAST (the Multi-Agent System Failure Taxonomy of Cemri, Pan, Yang and others, "Why Do Multi-Agent LLM Systems Fail?", arXiv:2503.13657, NeurIPS 2025; the owner's pointer of 2026-10-16) names how it fails when it does not. Built from 150 traces read by six expert annotators (a Cohen's kappa of 0.88 between them) and grown to more than 1,600 traces of seven multi-agent frameworks (secondary accounts name MetaGPT, ChatDev, HyperAgent, AppWorld, AG2, Magentic-One and OpenManus), judged by an LLM annotator built to agree with the annotators, it gives 14 failure modes in three categories. Its dataset, mcemri/MAST-Data on Hugging Face, holds the judged traces (MAD_full_dataset.json, about 200 MB; the message of its latest commit counts 1,642 rows) and a human-labelled subset (MAD_human_labelled_dataset.json, about 2.7 MB); the paper's repository, multi-agent-systems-failure-taxonomy/MAST on GitHub, links the dataset, and the paper says its annotator is released there too. The paper is on arxiv.org and the dataset on huggingface.co, neither of which this environment can reach, so what this section says of them was checked against a secondary copy of the paper's table (roanbrasil/agents-integration-patterns, patterns/FAILURE-MAP.md), the repository's README and quotations of the paper found by search; the paper's Appendix A is the authority where they differ, and the dataset's fields are not described here because they were not read.

| Code | Failure mode | Category | What the records show of it by code, or could |
| --- | --- | --- | --- |
| FM-1.1 | Disobey task specification | Specification | Nothing by code; the required check and the review are the project's reading of it |
| FM-1.2 | Disobey role specification | Specification | For a registered worker, a pull request whose files are outside its area |
| FM-1.3 | Step repetition | Specification | A tool call the same as an earlier one in the same transcript, the same tool with the same input: the record's repeated calls; and the re-reads of files |
| FM-1.4 | Loss of conversation history | Specification | The compactions and the drops the record counts |
| FM-1.5 | Unaware of termination conditions | Specification | A claim idle for 24 hours, which the coordinator releases; a draft never marked ready |
| FM-2.1 | Conversation reset | Inter-agent misalignment | Work after a compaction that redoes work before it: a read of a file again after the compaction |
| FM-2.2 | Fail to ask for clarification | Inter-agent misalignment | Nothing by code |
| FM-2.3 | Task derailment | Inter-agent misalignment | A pull request whose files are outside what its claim listed (the board's Files column against the pull request's files) |
| FM-2.4 | Information withholding | Inter-agent misalignment | A claim whose plan comment was never posted, or a pull request opened late |
| FM-2.5 | Ignored other agent's input | Inter-agent misalignment | A "main moved" comment with no merge of the default branch after it; an overlap notice whose order was not kept |
| FM-2.6 | Reasoning-action mismatch | Inter-agent misalignment | Nothing by code |
| FM-3.1 | Premature termination | Task verification | A pull request marked ready with its check red; a session that ended with tool calls unanswered |
| FM-3.2 | No or incomplete verification | Task verification | A push with no run of the check (bash scripts/check.sh, or the tests) in the session before it; the transcript shows both |
| FM-3.3 | Incorrect verification | Task verification | A check that passed and a revert that followed (the field metrics count the reverts) |

Three things follow for the programme:

- Two modes are measured now, by the instrument of section 4: step repetition as the record's repeated calls (an upper bound, since a `git status` after a change is a repeat and no waste) with the re-reads beside it, and loss of conversation history as the compactions and drops. Each arm of section 2 is read with them: a context-compression arm that lowers the peak and raises the compactions has moved the cost into MAST's FM-1.4, and the report must say so.
- MAST's second category, misalignment between agents, is what Symphony's protocol exists to prevent, and the protocol makes each mode a GitHub object that code can read: the claim's plan, the pull request's files against the claim's list, the "main moved" and overlap comments, the release of an idle claim. That is the coordination counterpart of this page, R3 and R7 of the taxonomy spec's section 11, and the table's right column is the hypothesis for it; it is not measured yet.
- A detector for any further mode is added only with a test against MAST-Data's human-labelled traces: run over the traces labelled with the mode and over those not, with its agreement reported, by code, spending no token. The traces are other frameworks' logs, so each framework needs a reader of its format, and the first is a sample of one framework's; HyperAgent's are a coding agent's and come first. The file is fetched by the owner or by a local session, since the cloud environment cannot reach Hugging Face. MAST's own annotator is an LLM judge, and here a judge runs only when the owner runs it, on their own subscription and never on an API key, as the field metrics' judge does (tools/metrics.py judge codes pull request conversations with CooperBench's App F); MAST's prompt is a second judge for the same harness, giving every pull request conversation its MAST modes beside App F's communication errors, by the owner's hand (section 6, step 7).

## 4. The instrument: tools/profile.py

`python3 tools/profile.py TRANSCRIPT [--json FILE] [--paths N] [--no-helpers]` reads one session's transcript and its helpers' (the subagents' transcripts beside it, as tools/usage.py reads them), or a run's execution file from Actions, and prints a report; --json writes the record. tests/test_profile.py holds every count to its definition on a transcript the test writes, so a change to a definition fails a test before it changes a figure.

What it counts, and how:

- Each API call once, by its message id: a message written as several lines, one per block, carries its usage on each, the input and cache counts the same on every line and the output count as far as the message had got when the line was written (a helper's lines show it growing), so the largest is taken. The context of a call is its uncached input plus its cache writes plus its cache reads; the cached share is the cache reads over the contexts summed; a line whose usage says it sent nothing (an error line) is no call.
- Each tool call once, by its block id, matched to its answer by that id: the answer's size is the text the model saw, a block that is no text (a tool reference, an image) by the size of its JSON; an error is what the harness marked; the seconds in the tool run from the line that asked to the line that answered, and a tool's own line times it, since the harness writes a message's tool lines as it runs them and an answer can come before the message's next line.
- The growth of the context from one call to the next, less the call's own output, is what the calls between them brought in; it is shared among that call's answered tools by the size of their answers, as each tool's context_tokens_estimated. This is an estimate, and its key says so; the record's growth is the whole, shared or not.
- A read is a call of the Read tool or a shell command of cat, head, tail, sed, less, more or nl naming a file; the paths are resolved against the line's working directory, following a cd inside the command; a pattern, a variable or the standard input names nothing, and an option's value (head -n 20, sed -e SCRIPT, nl -w 3) is no file. A re-read is a file named by a read after an earlier read of it in the same transcript. A here-document's body is data, not commands; a reader that names no file is a filter on another command's output or the consumer of a here-document (`cat <<'EOF' > file` writes the file from one); sed editing in place writes and reads for nobody; the shell's keywords (do, then, fi and the rest) and the wrappers that run a command as it is (time, sudo, env, nohup, exec, xargs) are read through to the command.
- A repeated call is one the same as an earlier call in the same transcript, the same tool with the same input, MAST's step repetition read by code (section 3); it is an upper bound on waste, since a `git status` after a change is a repeat and no waste.
- A prompt is a user line that is text and no tool result, no reminder the harness marked as its own and no compaction's summary: the person's messages and whatever else arrives as a user turn, a relay or a notification, which the transcript does not tell apart; an attachment is a line the harness adds beside a response (hook output, a reminder).
- A compaction is the harness's own boundary line or the summary it starts the continued conversation with; a drop is a fall of the context by more than half between two calls, however it came about.
- The active seconds are the gaps between consecutive lines with pauses over five minutes left out, as usage.py counts them. The seconds in tools are the union of the tool calls' intervals, so two tools running at once count once; per tool they are summed, so there each counts. A helper's calls are in the per-tool rows, their calls, failures, bytes and seconds, and in the token totals, while the union, the active seconds, the context and the prompts are the session's own; the record's helpers block says what the helpers added (transcripts, calls, seconds, output tokens), so a reader can take it back out. The seconds outside tools are the active seconds not covered by that union: the model's time, its thinking and its answer, and the harness's own between lines, which the transcript cannot tell apart; the harness's count of the thinking is given beside them.

What it does not see, so that its figures are read right: a file read by git show, python or any program not in the list, or through a redirection (cat < file); a cd in one call that moves a later call, since paths are resolved against the working directory the harness recorded on the line and the harness's shell keeps a cd beyond the call that made it; what a helper read, which counts as a read of its own, its re-reads relative to its own earlier reads; a command behind a wrapper that takes a value first (timeout 10, nice -n 5); a cd inside a subshell, which here moves the next command and in the shell does not; what an image costs, which it counts by its data; the difference between a tool's answer and a system reminder that arrived with it, which the growth attribution cannot tell; and time in a run's execution file, which carries no clock and no session id, so its time measures are empty and its record names no session.

The record carries counts, bytes, seconds, tokens, tool names and model names and never a path, a command, a prompt or a line of the conversation (tests/test_profile.py checks that the fixture's paths, commands and words are absent from it), so a record can be committed here; --paths prints the files read most often on the screen only. Since step 2 (section 6) the record names the harness's own tools, a fixed list (tools/profile.py, HARNESS_TOOLS), and folds every MCP tool into one row, mcp, since a server's name (mcp__github__, a Project's channel server) says what a session was connected to, and any other tool, one an Agent SDK program defines for itself, into another, other; --tools prints the tools called most often by their own names, on the screen only. The baseline of section 5 was taken before the fold and names its MCP tools.

How it compares with the pointers:

- agentprof (kitaisreal/agentprof, Rust) registers PreToolUse and PostToolUse hooks that log every tool call, and reports per-call latency, estimated tokens per tool and the slowest calls, live. profile.py reads the transcript afterwards, so it needs no install, works on a cloud session's and an Actions run's records, and has the API's own token counts rather than estimates; it has no live view.
- The strace article (dev.to, vmitro, early 2026; unreachable from this environment, read through the author's issue anthropics/claude-code#19459 of 2026-01-20, closed as not planned without a maintainer reply) profiled the harness, not the agent: on Claude Code 2.1.x under WSL2 it saw .credentials.json opened 339 times in 181 seconds, the changelog read 683 times in 38 seconds (5.45 MB) and the debug log re-read whole about every 2 seconds. That is a third thing to measure, below the agent's behaviour, and section 6 keeps it as its own arm.
- ccusage and claude-tokens read the same transcripts for billing; claude-tokens' authors say ccusage over-counts by 30 to 70 percent because the same message appears in several files after a resume or a subagent run (a vendor claim, not checked here). profile.py counts each message once by its id, as usage.py does.

## 5. The first measurement

The transcript of the thread that wrote this page was profiled with the tool in its reviewed form on 2026-10-16, while the thread was still at work (the record's ended_at says when, to the second), by `python3 tools/profile.py <transcript> --json baseline-2026-10-15.json`; the record is [baseline-2026-10-15.json](baseline-2026-10-15.json) and the report, with its reading, [baseline-2026-10-15.md](baseline-2026-10-15.md), whose figures scripts/render_baseline.py renders from the record; the folder scripts/ keeps the programme's other helpers too. It is a baseline of this project's own way of working, a cloud session of a claude.ai Project on a repository whose instructions load at the start of every session, with its helpers' transcripts (the review agent's) and one compaction in it, and it is read with that in mind.

One number is fixed by construction and worth stating here: the first API call of that session sent 120,867 tokens before any work. Of them, 43,468 were read from the prompt cache, so they are the part of the harness's own context, its tool schemas and perhaps the fixed part of its prompt, that an earlier request with the same prefix had written; the thread's own content cannot be among them. The other 77,397 were written for this call: the rest of the harness's context, the project's instructions (CLAUDE.md and what it imports, seven files, 72 KB of Markdown, of the order of 18,000 tokens), the Project's memory and the message that started the thread. How the two numbers divide between the harness's prompt, its tools and the thread's content, the usage does not record. Every call after it carried that start, served from the cache at a fortieth of the input price for claude-fable-5-1, which served the session's first calls, and a twentieth for claude-opus-5-5, which served its later ones (tools/economics.py, PRICES: 0.25 against 10 and 0.20 against 4 dollars a million tokens), which is why nearly all of the session's context tokens were cache reads (the baseline page gives the share); so what a session's start costs over a session is its size times the calls at the cache-read price, and its write once. What a session starts with is the first thing the context-compression arms change, and the first thing to measure across the project's sessions. The experiment thread found a heavier shape on coordbench's route, where every bench agent re-reads an inherited prompt of about 80,000 tokens (docs/checkpoints/2026-10-15b/handoff.md, section 2.3).

What the record can show again, and what it cannot: the transcript it was taken from lives in the session's container (~/.claude/projects/<folder named for the working directory>/<session id>.jsonl) and is not kept, so the record is not reproducible from any file in this repository; it is the tool's output on that file at that moment. What is reproducible is the tool: its tests write a transcript of their own and hold every count to its definition, and the same command on the same file gives the same record. The first baseline that can be regenerated will come from a kept transcript, as coordbench's harness keeps one per run (section 6, step 5).

## 6. The loop: measuring continuously, under the protocol

Steps 1 to 3 are built and step 4 is opened; the rest is not. Each step is its own pull request, reviewed and checked, in this order, and none spends a token until step 5; step 7 spends none either, since its judge is the owner's own run.

1. The profile beside the usage, built. The hooks that write the usage trailer (tools/usage.py) write a second line after it on each commit, the session's profile since its last commit, by tools/profile.py: `Symphony-Profile: v1 session=6e4cb20b calls=42 failed=3 repeated=1 reads=12 rereads=4 read_bytes=58210 reread_bytes=9120 peak=181234 compactions=0 drops=0 tool_seconds=95`. Each count is the rise of the record's own (section 4) since that commit: the calls and the reads with the helpers' in them, the compactions, the drops and the seconds in tools the session's own, and peak the largest context of the session's own calls made since, so a peak before a compaction is no later commit's; the session is the usage line's, so the two lines pair up, and a line of its own keeps every reader of Symphony-Usage unchanged. A session that commits through its Bash tool in a copy of the template, with the metrics switch on and no commit-msg hook of the clone's own, so measures itself at no token cost; the record rides with the commit as the usage does, and a cloud session's container may die without losing it. A run in Actions keeps the same counts over the whole run, its helpers' calls in them and their context out, with no seconds, since its execution file has no clock, as the profile block of its symphony-usage-* record, where the workflow copied profile.py, economics.py and the protocol library beside the recorder, as the template's workflows now do. The line names no tool, since an MCP server names its tools, and the metrics switch that stops the usage line stops it. The hook leaves the usage before it reads the profile, so a hook stopped at Claude Code's timeout for a hook still leaves the usage line. A commit whose profile could not be read carries the usage line alone, and the next commit's line counts from the last commit that carried one; where the session's last commit was recorded by a hook older than the line, the next commit carries the usage line alone, since its counts would claim what earlier commits did. The counts kept from one commit to the next live in the clone's common git directory, so a session that commits from two linked worktrees counts nothing twice. On the 10.7 MB transcript of the thread that built it, the hook took about 0.4 seconds before a commit, against about 0.2 for the usage line alone, and about 2 and 4 seconds on synthetic sessions of 3,000 and 6,000 calls with long commands (31 and 62 MB), where the first version, which measured each pause against every tool call, took about 10 and 28. The line is read by the message's last paragraph alone, where the hook puts it, so a line quoted in a commit's body counts for nothing; it is read from a pull request's own commits, never from a squash commit, which moves every commit's trailers into its body.
2. The aggregation, built. tools/metrics.py collect, with --profile-out, which the metrics workflow passes, writes PROFILE.json (schema symphony-profile-sums/1) beside METRICS.json on the branch metrics, from what it already reads for the economics, at no call of its own. Each pull request that ended in the window has a profile where any line or run on it made a call or held any context (one with none, or with only lines and runs of zeros, is unprofiled): the Symphony-Profile lines on its own commits and the profiles of the Actions runs that name it or its claim's issue, as the economics attribute their usage, each count summed and the peak the largest (tools/profile.py, pull_profile). The file sums them per work setting, the eight the breakdown sorts pull requests into, and gives the coordination block's siblings: the same two sides, alone and parallel, with the coordinator's runs that name none of the window's pull requests of people and of the Claude workflows on the parallel side, and four ratios over 1 where parallel did better, calls, reads and re-reads per profiled merge and the median peak (group, ratios, coordination; docs/setup/metrics.md, The profile's sums). A side is divided by its profiled merges alone, as the economics divide by measured merges. The runs' records reach the sums through the Actions cache, whose version 2 keeps each run's profile; a record a version 1 cache kept still counts in the economics, marked old, and is downloaded again for its profile after the new ones while its artifact lasts, and PROFILE.json's actions_runs_unread counts those not yet read again beside those left unread. The tool names in profile.py's record are folded to a fixed list, the harness's own tools by name and every MCP tool as one name, since a server's name can say what a person uses (section 4); PROFILE.json carries no tool name at all. The keys stay in the repository's own record, which the collector does not read, until the Apps' privacy statement lists them (its version 5 is the exhaustive list of what the collector keeps, and a new shared key is listed there, with its site page live, before the collector keeps it); then they join METRICS.json, which is the owner's step and a pull request of its own. Its pull request, #116, landed on 2026-10-17 with its adversarial review's nine findings fixed (the cache kept above, a run or line of zeros no profile, the five behaviours no test pinned now pinned by a world with a look-back run, a run naming nothing, a look-back coordinator run, work beside only open work and a line from before the window, the sums worked out only with --profile-out and after METRICS.json is written, and the unread count); scripts/step_2_undoings.py undoes each part of step 2 in a copy of the tree, 55 in all, and each makes a named test fail.
3. The report, built. [report.md](report.md), which tools/profile_report.py writes from the records in this folder alone, spending no token: one table per question of section 2, the baselines' rows first and then each arm's runs, each row with its outcome (tasks, those landed, the MAST modes judged) beside its costs, which are per landed task, and with the repeated calls and the compactions, the two MAST modes the records measure, beside every cost, as step 7 asks. A baseline is a record baseline-DATE.json with, where its work's outcome is known, baseline-DATE.outcome.json; an arm's run is a folder runs/DATE-ARM/ with an outcome.json (schema symphony-arm-outcome/1: the question it answers, the arm, the tasks, those landed, the modes or null where not judged, and the source) and one *.profile.json per transcript, which is what step 4's tasks commit. `python3 tools/profile_report.py docs/research/beyond-cooperation` regenerates the page, and tests/test_profile_report.py fails the checks when the committed page is not what the records give, so a run's records and its row land in the same pull request. The one baseline, of 2026-10-15, carries its outcome: #94, the work it profiled, merged with its check green; nobody judged its MAST modes.
4. The arms as tasks. Each question of section 2 is an issue labelled epic; the coordinator plans it into tasks, one per arm, with the files each owns, and gives them to a registered worker (docs/agents/PROTOCOL.md, Planning). A task is: run the arm on the fixed task set, commit the profile records and the outcome under runs/<date>-<arm>/ in this folder, and open the pull request; the required check holds the records to the schema. A finding that settles goes to docs/memory/ by the remember skill, in the same pull request. ## 8. Where this stops

This page settles the measures and the order, makes the instrument and builds the loop's steps 1 and 2; it does not build the rest.
