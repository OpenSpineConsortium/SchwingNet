# Reader access: asked for through GitHub, viewed in the browser only

Source: the project thread "Stage the textbook for this project", 2026-10-27, answering the owner's question of 03:12 UTC: "how could i make such that readers can request access through github and be approved for inbrowser viewing only?" Read from GitHub's documentation as the github/docs repository's content and data files stood on 2026-10-27 (docs.github.com is unreachable from a cloud session), from the artifact runtime's type definitions (contract 0.2.90, unchanged in 0.2.91 for every capability named here), from tools/front_door.html, and from the notes of this repository and of OpenSpineConsortium/symphony-template named below. A second reader checked each finding against its source; the corrections it made are folded in.

## The short answer

GitHub has no grant that shows a private repository in the browser and withholds the files: every repository role, Read included, may pull, and anyone who may read may download any branch as a zip. The front door adds no such limit, since it reads with the reader's own GitHub access, and it opens for nobody outside the claude.ai organization that holds the artifact. So "approved for in-browser viewing only" is had only by never giving the reader access to SchwingNet itself: a separate repository holding only what the reader is meant to see, or a service of ours that holds the read for them. A request through GitHub and an approval by the owner can be built in front of either.

## What GitHub can and cannot do

- No view-only role. data/tables/repository-roles.yml gives "Pull from the person or team's assigned repositories" to read, triage, write, maintain and admin. Custom repository roles, on Enterprise Cloud only, start from an inherited role and "You can only choose an additional permission" (about-custom-repository-roles.md), and grants add up (data/reusables/organizations/precedence-for-different-levels.md).
- No switch for downloads. Any branch, tag or commit downloads as a zip or tarball from the Code menu, and the REST archive endpoint needs only Contents read (downloading-source-code-archives.md). The forking policy, off by default for private repositories, governs forks alone. Requiring SSH certificates (Enterprise Cloud) stops Git over HTTPS and unsigned keys but exempts GitHub Apps' user tokens and says nothing of Download ZIP, and restricting OAuth apps leaves GitHub's own privileged apps (Git Credential Manager, GitHub CLI, GitHub Desktop, VS Code).
- Taking access away takes back nothing copied: "the person will still retain any local clones of your repository" (removing-an-outside-collaborator-from-an-organization-repository.md), which matters for unfiled material.
- No request button. A person outside the organization has no built-in way to ask for a repository, a team or the organization: access starts with an owner's invitation, and teams hold organization members only. An issue form on a public repository works as the request, but its text and the requester's login are public, and the author may edit the issue after submitting it.
- Approval can be automated. A label that only Triage and above may add starts a workflow (on issues, types labeled), which invites the issue's author (github.event.issue.user.login, never a login read from the body) as an outside collaborator with permission pull, PUT /repos/{owner}/{repo}/collaborators/{username}, whose default is push. It needs a GitHub App token with the repository permission Administration write, since GITHUB_TOKEN reaches neither collaborators nor members; access goes again by DELETE on the same path. The issue's text reaches the workflow only through environment variables, never interpolated into a script.
- Every reader costs a seat. On Team and on Enterprise Cloud each outside collaborator on a private repository takes a paid seat, counted once across repositories, a pending invitation is billed too, and removing one does not lower the count by itself (content/billing/reference/github-license-users.md). A seat must be free before an invitation goes.
- Access-controlled Pages is Enterprise Cloud only: "A privately published site can only be accessed by people with read access to the repository the site is published from" (changing-the-visibility-of-your-github-pages-site.md). On Team, Pro or Free a private repository's Pages site is public. The site may be published from a separate repository that holds only built pages, so its readers need read on that repository alone; that an outside collaborator with Read counts as such a reader is the natural reading, not stated.

## What the door gives a reader

- An outside viewer gets no connectors. The runtime's capability summary says of mcp that "outside viewers get null", and the door then stops with "This view cannot reach your connectors." (tools/front_door.html, code absent). Outside is anyone who is neither the owner nor a member of the claude.ai organization holding the artifact, invited by email or arriving by a public link. On a personal plan that is everyone else, and the door serves the owner alone: the owner's account was measured on Max on 2026-09-28 (docs/research/beethoven-worker-opening.md), and the plans of the accounts the work moved to on 2026-10-25 are not recorded.
- A reader inside the organization still reads with their own GitHub access, through a custom connector of their own built on a GitHub App's client id and secret, with that App installed on OpenSpineConsortium and allowed Contents read. The door App as specified, "SchwingNet door", only on this account, can be authorized only by members of the GitHub organization (making-a-github-app-public-or-private.md), and its client secret is a credential no reader is handed.
- The artifact cannot take a request itself: an outside viewer never writes the artifact's database, gets no comments, and a page can add nobody (db.d.ts, comments.d.ts, user.d.ts). A request has to live outside the artifact.

## What the repositories already have

- The control panel's Share tab (symphony-template docs/research/sharing-a-repository.md, share-tab-withdraw.md) invites a direct collaborator with read, triage, write or maintain, acting as the signed-in owner through SymphonyBoard's user token, which holds Administration write; it lists, withdraws and changes invitations. Only an administrator of the repository may invite.
- "Ask to join" (site #77, 2026-10-19): a request is an issue whose first line is `<!-- symphony-access: request -->`, on the organization's public front repository, and the Share tab lists open requests with Invite and Decline. Invite on a request gives Write in an organization, not Read.
- The members-only docs site (.github/workflows/docs.yml, tools/textbook_site.py) deploys only when the owner starts it and only where GitHub answers that the Pages site is not public; no deploy is recorded.
- The rules a reader feature meets: nothing of SchwingNet public before the filing, and collaborators kept to OpenSpineConsortium/spine-datasets until then (CLAUDE.md); as few moving parts as possible, no server of ours beyond the stateless sign-in Worker; no credential handed to anyone; a repository never named on the public side of a run; docs.yml only on the owner's call; and the owner's plan of 2026-10-20 to leave GitHub Enterprise, which takes access-controlled Pages with it.

## The routes

1. A reader repository with access-controlled Pages: native, no server. A private repository of the organization holds only the built textbook site, which the owner's Docs run also publishes there. A reader asks through an issue form on the public front repository that names no repository; the owner approves with a label, or with Invite in the Share tab once Invite on a request may give Read; a workflow invites the issue's author with Read on the reader repository alone. The reader signs in to GitHub and opens the site's address. They can clone the reader repository, but it holds only what they can already read. It costs a seat per reader, keeps the organization on Enterprise Cloud, is as fresh as the owner's last Docs run, and leaves requesters' logins public on the front repository.
2. Read on SchwingNet itself: native and live. The Share tab already invites with Read. The reader sees everything live on github.com, and in the door when inside the claude.ai organization, and can clone the code, the records and the unfiled material.
3. A reading service of ours: enforced and live. A small service signs readers in with GitHub for their identity only, checks the approved list, and renders pages from SchwingNet with a read token the reader never holds, so no clone is possible. It is a server of ours with a SchwingNet read token on a public address.

Whatever the route, what a browser shows can be saved or photographed: viewing only stops wholesale copying, not reading.

## Recommendation

Approve no outside reader of SchwingNet before the provisional is filed. After it, the public edition of #196 needs no access control for what its allowlist carries, and route 1 serves what stays confidential while the organization keeps Enterprise Cloud; without it, route 3 is the only one that withholds the files. Whether a reader before the filing needs a confidentiality agreement is a question for the technology transfer office.

## Not measured
