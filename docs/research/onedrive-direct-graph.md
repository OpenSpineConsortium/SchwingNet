# OneDrive on direct Microsoft Graph

Source: the thread "OneDrive on direct Graph", 2026-10-20, restarting part 6.3 of docs/checkpoints/2026-10-19/handoff.md. The owner, 2026-10-19 20:55 UTC: Wayne State approved SymphonyBoard to connect to OneDrive natively, so the administrator consent docs/setup/folders-admin-consent.md asked for is given to the Entra app "SymphonyBoard Folders". The owner's live check passed on 2026-10-20 at 03:50 UTC: the Folders tab said "Connected to OneDrive as Gregory Schwing (business)" and listed the drive, with no request for an administrator's approval.

## What the switch is

One code path for every reader of the owner's drive: the Folders tab, the Notebooks tab and the drive walk all read through Microsoft Graph under the panel's own sign-in (Connect OneDrive, whose refresh token the tab seals into a repository's secret SYMPHONY_DRIVE_REFRESH and the sign-in Worker's /drive/token trades for an access token), The owner, the same day, on seeing it work: "dont expose to the user the ability to do that old way of creating the scan of the onedrive that didnt use natural authetication through microsoft". So the connector walk is retired rather than kept as a fallback: tools/drive_connector.py keeps only the plan and the moves, and the drive-organize skill starts the workflow's Graph walk. No route borrows a signed-in Wayne State or OneDrive session from a page or an extension.

## What was found (2026-10-20)

- The Graph path already exists; the consent was all it waited for. drive-organize.yml's step catalog walks the drive with tools/drive_organize.py over drive_sync.py's Graph client and the sealed refresh token, and writes the same catalog.json the connector walk writes (drive_connector.py builds it with drive_organize.catalog_of), so check, moves and the panel read either alike. The connector was a workaround for the missing consent, as drive-organizer.md's "Connector mode" says.
- A blocker before the first Graph walk on the owner's drive, fixed here: the step catalog force-pushed drive-catalog as one fresh commit holding only catalog.json, TREE.md and digests.jsonl. On the private repository OpenSpineConsortium/onedrive that branch also holds the session's plan.json, moves.json and MOVES.md and the Notebooks tab's notebooks.json and notebooks/, so the first Graph walk would have deleted the proposals and every notebook. The step now commits the new catalog on top of the branch with a plain push, which a branch moved during the walk refuses, and says when plan.json or moves.json came from an earlier catalog.
- Graph throttles a long walk with 429, and a read with 503, naming the wait in Retry-After; the walk named such a folder as unlisted and went on, so a large drive's catalog came out incomplete. drive_sync.call now asks again up to four times after the named wait (ASCII digits only, from 1 to 120 seconds, else 5), any call after a 429 and only a read after a 503, since a write a 503 answered may have been done.
- tools/notebook.py and docx_cite.py never touch the drive; a notebook names files by drive and item id, so the switch changes no notebook, as notebooks.md asked. What changes is who reads: a worker in Actions can now read a notebook's files through drive-sync.yml in the notebook's repository, where before only a session with the connector could.

- The Graph walk now writes what the moves need, as the connector walk did: each item's parent under catalog.json's parents, the drive's top as root (Graph takes root for it), and the folders Microsoft 365's apps keep at the top (Recordings, Microsoft Teams Chat Files and the like) under managed, listed but never read into or moved. drive_connector.py's moves take any OneDrive catalog that names parents.
- The first walks on the owner's drive (2026-10-20). Two stopped at the workflow's own check, since the sealed sign-in had not reached onedrive (the panel's Track saved it elsewhere, then as an organization secret onedrive could not see; site #110 fixed Track). The third got past it, and the sign-in service answered the token trade with 403 and no JSON body. The service's own refusals all carry a JSON error, and it takes a call with no Origin on /drive/token, so the 403 most likely came from Cloudflare in front of it, which refuses urllib's default User-Agent with a plain "error code: 1010". drive_sync.call now names itself in User-Agent, and an answer with no JSON reports Cloudflare's code, as cloudflare_<digits>, so the next refusal says whose it is.
