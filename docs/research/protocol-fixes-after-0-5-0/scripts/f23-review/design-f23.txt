**F23. A comment GitHub lists late stands beside the labels put back.** Status: fixed after 0.5.0 (the owner's decision of 2026-10-13, section 14: the library fix on every finding); found by the second review of F20's fix, which left it in F20's What it leaves, an inference from how GitHub may answer and not a reading of it: GitHub answers the post of the release comment with a 502, or with no answer at all, having written the comment, and lists it only after the run's read of the issue's comments, a write that lands late or a read served before the write reaches it. The re-read then lists no comment, and the run, taking that for a comment GitHub never wrote, put back the labels it took off, so the comment stood beside the label claimed and held the claim for good, as F20 did. The spec's Release now says that a run that fails between the two reads the issue's comments, the comment there making the release whole; that where they list none and GitHub refused the comment, with an answer from 400 to 499, which GitHub gives in place of writing anything, the run puts the labels back; and that where they list none after a server error or no answer at all, either of which may come after GitHub wrote the comment, the run cannot tell whether the comment stands, as where it cannot read them (F20), so it leaves the labels as the release left them, counts no release of its own, and the next run settles it. The library reads it so: github.wrote_nothing says a failed write surely changed nothing only for a 4xx, and github.release_one, after a post whose re-read lists none, puts the labels back only then, and otherwise answers with github.not_listed, which, as github.unsettled does for a refused re-read, brings the snapshot's labels up to date with no release of its own counted (both through github.labels_left). In the harness a Fault may have no status, which the fake answers with the timeout http.client raises, so the adapter reads the call as one with no answer, and a read of an issue's comments may be answered without the comments GitHub wrote in the run and lost its answer to (LISTED_LATE, FakeGitHub.lost); verbs.FAULTS gains comment-late (a 502, the comment written, then a re-read listing none of it), comment-unanswered-late (no answer, the comment written, then the same) and comment-422 (a refusal, nothing written), the last since comment-rate-limited, the one 4xx the faults had, becomes a whole release once the client retries a rate limit (symphony-protocol#40); the oracle quotes the spec's new clauses (SPEC["whole"], SPEC["put back"], SPEC["unsettled"], SPEC["listed late"]); invariants.unread_releases takes in invariants.unlisted_releases, the issues whose release comment GitHub answered with a server error or no answer and whose re-read, answered, listed no comment the post wrote, so labels_put_back holds such a run to putting nothing back, unsettled_left_alone to renaming nothing, and seen takes the comment out of the oracle's view of the page; and a call's status may be None, which the checks read as a failure (invariants.failed).
- **What happened.** Until the fix release_one put the labels back after any failed post whose re-read listed none, so a comment GitHub wrote and listed late stood beside the label claimed: every later coordinator found it, more than 24 hours after the branch's last commit, and skipped the claim as released, while the board, seeing claimed, counted no release and never renamed the branch; only a person's hand, or a push of the holder's, moved it.

- **The choice made.** Leave the labels off after a server error or no answer whose re-read lists none, rather than put them back: GitHub may have written the comment, and labels put back beside a comment that stands hold the claim for good, while leaving them is safe either way, since the next run's read settles it; after a refusal, a 4xx, GitHub wrote nothing, so putting them back is right. The re-read after a 4xx is kept, so a refused re-read still leaves the release unsettled and a release comment someone else wrote meanwhile still makes it whole, as before. No status takes in two more failures, which GitHubError gives none either: an answer that was not JSON, which comes once GitHub has done what it was asked, so it is rightly no refusal, and a call never sent (github.unsent), which a run meets only for a token or a path http.client will not send, at its first call and not at the comment. The run's line for it is new, a rendered string said here as CLAUDE.md asks: `#<n>: release unsettled, the comment failed: <why>; its issue's comments list none yet, though GitHub may have written it before that failure and list it only later; the labels stay as the release left them`; and the line `#<n>: not released, the comment failed: <why>; <labels> put back` now follows only a 4xx. The version stays 0.5.0, which waits for the owner's approval without this fix; the release after it carries the fix.
- **What it costs.** Nothing on a run GitHub answers, or one whose comment it refuses with a 4xx; where GitHub answers the comment with a server error or no answer and the re-read lists none, a run more before the release counts, the next run counting the comment GitHub wrote or releasing the claim again where it wrote none.
- **What it leaves.** Between the run that cannot tell and the next, the issue carries todo alone, or the labels a release leaves on an epic or a blocker, while the board lists the claim as held, the clerk deals it as F20's What it leaves says, and a holder who pushes in that window keeps the claim with its labels off, as F20 leaves it. A comment GitHub lists only after the next run's read too is taken for none by that run, which releases the claim again, so the issue carries two release comments, which does no harm. The canary does not reach the case, which needs GitHub to answer a write with an error and list it late.
