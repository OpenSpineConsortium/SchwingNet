Source: the thread "Build a deep learning pipeline sandbox" (it began as "Plan evaluating latent shape priors against explainable metrics"), 2026-10-30, on the owner's words of 15:12 UTC, "i need that artefact to display just like that as an html with actions tied to button clicks in a github repo ... id like to be able to load new modules and run analysis on the grid by building deep learning pipelines on a web browser with lots of flexibility", the owner's yes to this repository at 15:14 UTC, and the owner's specification of 16:16 UTC, quoted in section 1. The artefact is bordercall's research_notes/latent-shape-prior-evaluation/pipeline.html (the private page https://claude.ai/artifact/8mfLZEEQupfs1wnGFKrASc), whose look the sandbox keeps. Confidential, this repository only.

## Where it stands

Built: the page docs/sandbox/pipeline-sandbox.html, generated by `python3 tools/pipeline_sandbox.py write` from the block manifests under tools/sandbox/blocks/ (32 blocks), the templates under tools/sandbox/templates/ (6 pipelines), the contract tools/sandbox/contract.json, the engine tools/sandbox/engine.js and the interface tools/sandbox/ui.js; `python3 tools/pipeline_sandbox.py check` runs in scripts/check.sh and fails a stale page or a manifest that breaks the rules of section 7. Open the page from a clone in any browser, with no server; the private claude.ai edition is made by `python3 tools/pipeline_sandbox.py artifact --out PATH`.

Live: a pipeline that maps onto the experiment route (section 5) becomes the prefilled experiment issues the experiments panel already makes, so it runs today on the owner's click, one GPU job per request. Planned: every other pipeline compiles to a plan with its job counts and a prefilled pipeline issue that nothing answers yet; the grid side that would run it is section 8 and waits on the owner's word. No grid job was sent by this work.

## 2. From today's Metaflow pipeline to blocks

Today a block is one field of src/schwingnet/blocks.py, a training choice that `--block KEY=VALUE` names (docs/research/experiment-framework.md). The sandbox widens the word to every step of the programme: a block is one step with typed inputs and outputs, a manifest that says what it takes, what it gives, what it costs and what runs it today. Each launched flow of flows/registry.txt and each gate word of grid/gate.sh is one block or a few, and the eighteen training fields become the params of the blocks that use them (augment, normalise, denoise, samples, the classifier's architecture, the trainer's optimiser, schedule, sampler, loss weights and selection, the prior head's weight).

The stages are fixed and are the prediction's grammar: source, prepare, split, augment, model, train, calibrate, select, evaluate, analyse, report.

A pipeline made only of live blocks runs today; one with any other block is a plan until section 8 is built.

## 3. Types, and how a block adapts to the data

Every port carries a type record: kind (data, model, checkpoint, metrics, report), the ordered axes (N samples, T time, C channels, D, H, W, F features, K points, P coordinates) with the sizes that are known, the dtype, the target (none, level, mask, points, value) and its class count, the split parts present, whether the person key rides along, the modality, the licence, the sources upstream, the model family, the spatial rank and whether it is trained. A block states the pattern each input accepts (any of kind, rank, time axis, axes it needs, dtypes, targets, split or unsplit, parts it needs, modality, trained) and how each output follows from an input, by ops: set a field, set or drop an axis, add one, narrow the licence by a recipe, and so on.

That is how the architecture adapts: a model block's output type keeps the data's axes and sizes, so the network is resolved from what reaches it. With a grey 64 by 64 frame catalog the classifier reads "a resnet18 whose 2-D stem takes 1 channel(s) of 64 x 64; head of 27"; fed colour frames at 224 it reads 3 channels and 224 by 224, with no edit. A model and the data it was built for stay one linear chain, so growing a pipeline to the right always pipes one output into one input.

The claim of genericity is held to the code, not written over it. Each block that takes data or a model says which spatial ranks, time axis, channel counts and sizes it takes today, and why where it takes less than all of them (the classifier takes 2-D frames of any channel count and any size through adaptive pooling, grey tiled to 3 channels; the 3-D classifier and a time axis are planned). The check feeds every block the contract's probes (2-D grey 64, 2-D colour 224, 3-D grey 96, 2-D clips of 16 frames, a table of 32 features) of each rank it claims, each probe given the targets the block asks for and, for a block that takes data not split yet, no parts; a block that claims a rank must accept the probe and compute every output with no problem (requirement R8). So a claim of shapes is tested while a block may still say what its data must mean: masks for morphometry, unsplit data for a split. The probes run in the engine today; running the code itself on them is the conformance runner of section 8.

## 4. Holding to the right of a node, and the prediction

The grow zone of a card is the band from 6 to 260 pixels right of its right edge and 30 pixels above and below it. The anchor is the nearest left node: of the cards whose right edge is left of the pointer and whose band holds it, the one whose right-edge middle is nearest. When the pointer rests there for 140 ms a ghost card shows the top prediction 72 pixels right of the anchor, with a ring that fills over 480 ms and then commits the node: a new node of that block, its first input fed from the anchor's first output, selected, with the types, the plan and the job counts recomputed. Beside the ghost a strip shows the top five predictions with the reason for each; the wheel or the arrow keys move along it, keys 1 to 5 commit one at once, a click commits, Escape cancels. A press and hold works the same on a touch screen, and Shift with the right arrow opens the ghost for a focused card from the keyboard. One hold makes one card, so holding again further right grows the chain one step at a time.

It stays fast because the pointer never touches the page's layout: the cards' rectangles are cached and rebuilt only after a layout change, the pointer is read once per animation frame, and a commit redraws only what changed. Measured in a headless Chromium on 2026-10-30 with about 30 cards on the board, a pointer move cost about 0.03 ms and a commit 2 to 8 ms of script, most of it the engine's propagation and compile, with the next frame painted about 10 ms after the commit, inside one 16 ms frame.

The prediction is a rule, not a learnt model, so it is the same for everyone and can be read. The candidates are the blocks with an input that accepts the anchor's output type. Each is scored by how often the templates and the viewer's own history go from the anchor's block to it (the history counts twice and stays in the viewer's browser), by the stage grammar (the next stage the pipeline lacks scores highest, the same stage lower, an earlier stage lowest), with a bonus for a stage the pipeline lacks entirely and a penalty for a block already on the board (except evaluation, analysis and report blocks, which a pipeline often has several of). The reason shown is the strongest term, for example "after Train, the templates go to Evaluate held out (3 of 4)".

## 5. What a pipeline becomes: the digest, the plan and the request

A pipeline is a small JSON spec: nodes (a block, its version, its params, and the values it varies over) and edges (an output port to an input port), with the card positions beside it. Its canonical form fills every default, sorts the nodes and edges, writes numbers in plain decimals and keys in order with no spaces, and its SHA-256 is the pipeline's digest, the same in the page's JavaScript and in tools/pipeline_sandbox.py, which the test holds to the bit. The digest names a pipeline the way tools/run_code.py names a run by its code.

Compiling a pipeline tries the experiment route first. It applies when every block is one an experiment request can carry, with exactly one catalog, one classifier and one trainer, every node reachable from the catalog, and every value within the route's limits (resnet18 only, crop size 64, 1 to 200 epochs, hours above 0 and at most 48, no float in exponent form). Then each combination of the varied values is one request whose issue body is byte for byte what tools/experiments_panel.py writes, so the existing path answers it: .github/workflows/experiment.yml checks it and answers with the gate word schwingnet-experiment-<issue>, the owner's click sends it, and grid/experiment-driver.sbatch runs flows/launch.py experiment under docs/research/experiments/PREREG.md, one GPU job that trains and evaluates. The template screen_arms, augment varied over none and strong and the optimiser over adam and adamw at 20 epochs, is the owner's rule of 02:46 UTC that every arm is a block screened in parallel on short runs: four requests, four GPU jobs.

Otherwise the route is the pipeline route, and the page says why the experiment route did not apply. The plan lists each compute node with its class, its submissions, its tasks and its hours: a varied param fans the arms out downstream until a select node joins them, an array block sends its arms as one array job, and a block that runs inside its upstream job (the held-out evaluation inside the training job) adds its hours there. The totals per class are the job count the owner's word is given on. The page's request button opens a prefilled issue whose body carries the marker `<!-- schwingnet-pipeline -->`, the digest, the job counts and the canonical spec; nothing answers it until section 8 exists, and the issue says so.

## 6. Transparency, reproducibility and scaling

Transparency. Every source is a block with a data card: where the data came from, where it lives, how many, the person key, the split, what is held out, the licence, and the repository files those facts are read from. The lineage rides on every type to the end of the pipeline: the sources upstream, the licence (a recipe cut narrows it, joining two inputs takes the more restricted), whether the person key survives and which split parts are present. Only evaluation and report blocks may read the test part, and a block that reads a part its data lacks is refused, so a pipeline cannot select on test or train across the split by accident. Every block says what runs it today and which files implement it.

Reproducibility. A pipeline is named by its digest; each block has a whole version (the owner's rule) and the spec records it; every param is written with its default filled, so a later change of a default cannot change an old pipeline silently. Each block declares its determinism: exact, seeded (naming the param that seeds it), or declared, saying what varies and why that is tolerated. A run still goes through flows/launch.py under a frozen PREREG with its CLAIM and REFORMS report (docs/memory/every-deep-learning-job-runs-on-a-launched-flow.md); the sandbox adds the digest in front of it, not a second way to run.

Scaling. The fan, the combinations and the job counts per class are computed before anything runs and shown as tiles: GPU submissions, GPU tasks, GPU-hours, CPU submissions. The limits are the contract's: 60 nodes, 120 edges, 64 combinations, 1,000 array tasks. Nothing on the page sends a job: the size rule, the gate and the owner's word stay where they are.

## 7. Importing a block

The page's Import a block dialog takes a manifest pasted or chosen as a file, checks it against the requirements with the same engine the repository runs, lists every problem with its code, and adds a block that passes to the palette, kept in that browser only and marked "imported, not in the repository". `python3 tools/pipeline_sandbox.py check-block PATH` makes the same check from a clone, and the repository's own blocks pass it in scripts/check.sh. The format a block is written in, field by field with a worked example, is block-format.md in this folder. The requirements, which the dialog shows beside the text:

| | Requirement |
|---|---|
| R1 | Identity: the manifest format, an id of lowercase letters, digits and underscores, a whole version, a title, a stage, a one-line summary, what it does, a glyph from the contract's list. |
| R2 | Ports: named inputs and outputs of the shapes above; a source has no input and every other block at least one; at least one output; every op and reference names a param or port that exists. |
| R3 | Params: a choice, an int, a float, a bool, a set or a list of names, each with valid bounds and a valid default; names unique. |
| R4 | Rules: conditions between params, each naming params that exist, with the sentence shown when it fails. |
| R5 | Reads: the split parts it reads; the test part only in evaluation and report. |
| R6 | Job: its class (none, cpu or gpu), hours per task, CPUs, memory, whether it rides in its upstream job and whether its arms go as one array. |
| R7 | Determinism: exact, seeded by a named param, or declared with what varies and why. |
| R8 | Genericity: the ranks, time axis, channels and sizes it takes, why where it takes less, and the probe test of section 3. |
| R9 | Needs: the libraries it uses, from the contract's list. |
| R10 | Code: existing (the files it names exist), own (its code and test files exist, the code with a docstring and `def run(inputs, params, context)`), or planned (no code on this branch; its status is then planned, or pending when it is built on an unmerged pull request). |
| R11 | Today: what runs it now, stated truly (live, a word, a flow, a pending pull request by number, or planned). |
| R12 | Text: ASCII only, no control characters, the canonical manifest at most 16,384 bytes. |
| R13 | Data card: a source block fills every field of its card and names the files its facts come from. |

To make an imported block runnable: put its manifest at tools/sandbox/blocks/<id>.json, its code at tools/sandbox/blocks/<id>.py and its test at tests/test_sandbox_block_<id>.py, run `check-block` on it and open a pull request. A pipeline that uses it runs only after that pull request merges and only on the pipeline route of section 8, since the experiment route carries only the trainer's own blocks.

## 8. The grid side, waiting on the owner's word

A pipeline issue needs five pieces to run, each a pull request and none built here:

1. .github/workflows/pipeline.yml, answering a pipeline issue as experiment.yml answers an experiment: it checks that the asker may write, compiles the spec again with tools/pipeline_sandbox.py, refuses on any problem or a digest that differs from the issue's, records the request, and answers with the plan, the job counts and a gate word.
2. The word `pipeline <issue>` in the three gates that pass a word to the grid: grid/gate.sh here, scripts/grid-accounts.sh in symphony-template and grid_gate.sh in hpcworker, as `totalseg complete` was taught to them on 2026-10-30.
3. flows/pipeline.py, a PipelineFlow in flows/registry.txt, started by flows/launch.py under a frozen docs/research/pipeline-sandbox/PREREG.md: one step per node in the order the engine gives, a foreach over the arms, a join at each select node, each step calling its block's code through `run(inputs, params, context)` with the digest and the lineage stamped on every output.
4. That entry for every block whose code exists, as thin wrappers over tools/train.py, tools/evaluate.py and the launched flows, and the widenings the blocks' notes name (a 3-D classifier from MONAI's 3-D networks, a time axis for the clips).
5. A conformance runner that runs each block's code on the contract's probes, tiny and on the CPU in the required check, and once on a grid GPU, so the genericity a manifest claims is proved by its code.

The grid work in it, the conformance run on a GPU and the first pipeline run, waits on the owner's word and the number of jobs, under the size rule.

## 9. What is not true yet

- Only the experiment route runs; every other pipeline is a plan with its job counts.
- A type checks kinds, axes, sizes, dtypes, targets, parts, modality and lineage, not what an image shows: a type that matches does not make a pipeline sensible.
- The prediction is a rule over six templates and the viewer's history, not a learnt model; it gets better as templates are added.
- An imported block lives in one browser until its pull request merges.
- The template latent_prior rebuilds only the part of pipeline.html the blocks reach: the gold tier 3 CTs, morphometry and naming, the anomaly-aware split, the annealer screen over four schedules and two seeds as one array, selection on validation and the held-out evaluation. pipeline.html's arms A to E, its smoke runs, the full run's seeds and the 2-D landmarks have no block yet, so the template's job counts (GPU 2 submissions, 9 tasks, 97 GPU-hours; CPU 3 submissions, 37 hours) are the sandbox's, not the page's.
- The page is not on the members-only site: docs.yml runs only on the owner's call, and tools/textbook_site.py would need a step that copies docs/sandbox/.

## 10. Decisions taken in the owner's place

- The home is this repository (the owner's yes of 15:14 UTC): the page under docs/sandbox/, its generator and check in tools/, the blocks and templates as JSON under tools/sandbox/, so a block is reviewed by pull request like any other change.
- The page sends no job and starts no workflow: its buttons open prefilled issues, the route the experiments panel already uses, and the owner's click on the gate word stays the only way a job is queued.
- Thirty-two blocks to start, one per step of today's flows and words, with their status stated as it is; the 2-D classifier's genericity claimed only as far as the code goes.
- One flat type record for every port; a model keeps the type of the data it was built for, which is what lets it adapt.
- Whole versions for blocks; the licence order of data/recipes/ from commercial to research-internal, then uncut; limits of 60 nodes, 120 edges, 64 combinations and 1,000 array tasks.
- Plain JavaScript and the Python standard library only, no font, script or style from outside, so the page opens from a clone and as a private claude.ai page alike.
