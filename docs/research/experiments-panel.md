# The experiments panel: every recorded run by its data input, its blocks and its outcome, and how a figure asks the page around it to act

Source: the thread "Textbook: Claude integration and artifact edition", 2026-10-24, issue #242, on the owner's words of 20:34 UTC that day: "ok please make sure there is an interactive artefact correlating a data input, workflow blocks chosen, and loss/accuracy/model/reproducibility report/WandDB online records" and "make sure i can trigger new combinations of data and blocks interactively, either by drop down ui, or claude prompt to trigger it to run on the grid". This note says what the panel reads and shows, why its data is inlined, why a run request is an issue, and the messages a figure framed in the book exchanges with the page around it, which the storage planner's panel and every later panel follow. The triggers, issue #248 on the same day: the issue form, the workflow that answers a request with the exact command and the gate word and records it, the gate word that runs it, the artifact edition's Run as me and the Claude prompt path, are sections 3, 4, 6 and 7.

## 1. What the panel reads and shows

tools/experiments_panel.py reads every folder with a RUN.json under docs/research/, the ledger's docs/research/v1-demo/runs/ among them, and nothing that is not committed: RUN.json, train/checkpoint.json, train/metrics.jsonl, train/MODEL.md, evaluate/results.json, evaluate/latency.json, split-check.json, reforms.json, claim.json, REPORT.md, wandb-sync.json, PROVENANCE.json and NOTE.md where each exists, the ledger docs/research/v1-demo/LEDGER.md, the recipes under data/recipes/ and the blocks of src/schwingnet/blocks.py. It reads blocks.py from the source with ast rather than importing it, because the package imports beartype and the required check runs without the locked environment; the test holds the two readings equal where the package can be imported.

For each run it gives, in one row and one expandable record: the data input (the catalog by version and sha256; the recipe and the sources trained or validated on from PROVENANCE.json where the run wrote one, else the sources the result rows' strata name, and the bank the run's note or ledger row names; a run on the synthetic bank is marked, since it measures the workflow and not SchwingNet); every block with its value, version 1's default spelled out where a run named none, as schwingnet.blocks.from_record reads a checkpoint from before the blocks; the epochs, the seed and the parent; the training loss and validation accuracy of every epoch; the accuracy of every stratum with its 95 percent Wilson interval, the all-levels test row as the headline; the latency where one was measured; the model as its card gives it (the architecture line; no card records a parameter count yet, so that cell says not recorded; the checkpoint's sha256); the reproducibility fields (the commit, the clean-tree flag, the split flags, the REFORMS and CLAIM tallies, the report's verdict, the path of RUN.json and the exact flow command that reproduces the run from what RUN.json records); and the W&B links, or offline with why, or not logged for a run made before W&B.

The page filters by data input and by each block, draws the test and validation accuracies with their intervals, the loss curves on a logarithmic axis, and a correlation view that groups the chosen measure by the value of one block, with the group's mean; with two runs that share every block it shows one group and says so. Its Run a new combination panel lists the recipes and every block's choices from the same files, says every way a choice does not hold in the trainer's own words (weight decay with adam, sources without a by-source samples choice, a prior weight without the prior, epochs outside 1 to 200), and shows the exact command. The static experiments.svg beside the page is the accuracy chart alone, for the chapter's image line and for a reader with no script. scripts/check.sh runs `python3 tools/experiments_panel.py check` and fails when the committed page, record or image differs from what the records give, so a pull request that records a run must rebuild the figure, as the evaluation page and the reports are held.

Today the panel shows two runs, a767a466f5c1 and cd37124c487d of 2026-10-21, both version 1 with no block named, both dry runs on the synthetic bank: 556 of 556 and 430 of 431 test crops right, best validation epochs 2 and 4, neither online on W&B (one made before W&B, one with no key in the container). The page says so at the top: every number on it is a record of the workflow, not a measurement of SchwingNet.

## 2. Why the data is inlined

The book shows an interactive figure inside an iframe with sandbox="allow-scripts" and nothing else (tools/textbook_site.py, figure_block): the figure's script may run, but the frame has an opaque origin, may not read the site's pages or storage, may not open a window and may not navigate the page around it. A page that fetched its data would have nothing to fetch it from under that sandbox, and a page served with the site that read the site's files would need an origin the sandbox withholds. So the tool writes the data into the page as one JSON constant and the page draws from it with inline script and inline SVG; the page loads no script, no stylesheet and no font from anywhere, and the same file opens from a clone with no server. The cost is a page rebuilt on every recorded run, which is what the currency check asks for anyway, and a size that grows with the runs: 47 KB today, of which the data is a quarter, so a hundred runs is under a megabyte.

The sandbox has a second consequence: a link inside the figure cannot leave it. GitHub and W&B refuse to be shown in a frame, a new window is refused by the sandbox, and the top page may not be navigated. So when the figure finds itself framed it hands every link to the page around it, and that page shows the link where a person can click it; opened on its own, the figure's links are links. Section 4 gives the messages.

## 3. Why a run request is an issue

The owner's rule is that no grid job runs without his word and the number of jobs (docs/project.md), so a button in a figure cannot queue a run, and a figure cannot know who presses it. An issue is the one thing a figure can ask for that leaves a record, names the person who asked, can be answered by a workflow running main's code and can be acted on by the owner from wherever he reads GitHub. Request this run therefore opens a prefilled issue labelled experiment whose body carries the combination as lines a workflow reads (section 5); the workflow validates each value against the committed lists, answers with the exact flow command, the gate word that queues it and the owner's exact click, and labels the issue owner-act when it must wait for that click. A requester without write access gets the refusal only, as the figure re-run workflow already does. The same lines are what the Claude prompt path writes when the Ask box's answer names a combination, so the two ways of asking meet in one issue and one record.

Built under #248, the answer is .github/workflows/experiment.yml with tools/experiment_run.py as its clerk, on an issue opened or labelled experiment and on Run workflow (the dispatch Run as me makes, whose inputs recipe, epochs, seed, hours and blocks the workflow turns into an issue of its own before answering it, so a dispatch leaves the same record as a press of Request this run). The workflow runs main's checkout, never the issue's text as code: tools/experiments_panel.py parse_request reads the panel's `key: value` lines or the form's `### key` sections and nothing else of the body, bounding every value to 80 characters of letters, digits and . _ , - and every whole number to nine digits before it is compared with anything, and check_request holds the recipe to data/recipes/, each block to src/schwingnet/blocks.py and the trainer's rules (weight decay with adamw, sources with a by-source samples choice, per_person with cap-per-person, a prior weight with the prior) and the epochs to 1 to 200. It answers once, counting its own marker comments, with the normalised request, the exact flow command, the command the grid runs, the gate word `schwingnet-experiment-<issue>` and the owner's click (symphony-template's grid-accounts.yml, action `job`, or `bash ~/SchwingNet/grid/gate.sh experiment <issue>` from the grid's shell), labels the issue owner-act, and records the admitted lines as `<issue>.request` on the branch experiments by a fast-forward commit, refusing to write where the branch holds any other file. A request from someone whose author association is not owner, member or collaborator gets the refusal and nothing else; a request that does not hold gets every problem with the known list, and nothing is recorded.

The branch exists because of what the login node is: grid/gate.sh runs there under bash alone, with git, hpcworker and the coreutils, no python and no GitHub API, so a combination cannot reach it as a command-line argument through the gate's `schwingnet-<word>[-<id>]` shape, and the gate cannot check it against the blocks module. The word `experiment <issue>` therefore fetches `<issue>.request` from the branch with git, which the login node has, checks each line's shape in bash (the four settings once each, every block line one KEY=VALUE word in the request's charset, at most 40 lines of at most 120 characters), needs version 1's inputs as the v1 word does, and submits one GPU job, grid/experiment-driver.sbatch, which runs `tools/experiments_panel.py check --request` inside the container against the checkout's own blocks module before tools/flow.py runs with the request's recipe, blocks, epochs, seed and hours on the catalog version grid/v1-version.sh chooses. Three readings of the same lines, each against what its place can hold: the workflow against the lists, the login node against the shapes, the container against the lists again at the commit that runs. Two lists stand between the Run workflow page and this word, each admitting the words it knows and no other: symphony-template's scripts/grid-accounts.sh, which turns the job name the owner types into the gate's word, and hpcworker's tools/grid_gate.sh, which passes a SchwingNet word on to this gate. symphony-template #459 and hpcworker #45 add `experiment` to both, beside #252's sweep and bank; the gate's own clone of hpcworker takes its change once the owner sends the job word `update`, and the shell route works without either.

## 4. The messages between a figure and the page that embeds it

A figure framed in the book or in the artifact edition speaks to the page around it with window.parent.postMessage(payload, "*"); the figure cannot name the parent's origin, since it does not know where it is shown, and the parent must never trust the origin of what it receives, since a sandboxed frame's messages arrive with origin "null". The rule on both sides:

- The parent accepts a message only when event.source is the contentWindow of one of its own figure iframes, never by origin, and answers that source frame with event.source.postMessage(reply, "*"). A script of the page itself is no figure frame, so the parent also exposes window.schwingnetDispatch(request), the same dispatch as a promise of {ok, error}, and window.schwingnetConnector(), a promise of the connector or null; the artifact edition's Ask box uses the two.
- The parent acts only on the repositories it allows, OpenSpineConsortium/SchwingNet and OpenSpineConsortium/spine-datasets; a request naming any other is answered ok false with the error "repository not allowed". It starts only the two workflows whose run is a request that the owner's own act completes, experiment.yml on SchwingNet (it answers an issue and queues nothing) and storage.yml on spine-datasets (it opens a pull request the owner merges); a dispatch naming any other workflow of either repository is answered ok false with the error "workflow not allowed", since a figure is framed content and some figures are exported artifacts.
- Where the page has no connector (the Pages site, a viewer outside claude.ai, window.claude absent or claude.use("mcp") resolving null), a request is answered ok false with the error "no connector", so the figure shows its fallback: the link and the text to paste. The answer comes within about two seconds where window.claude never appears and within six whatever the lookup does, one lookup shared by every request of the page and never made twice once it has settled, since a figure waits only so long for an answer (the storage planner's panel eight seconds) before it shows its fallback.

The message types:

- schwingnet.open, figure to parent: {type, href, label}. A link the figure cannot open under its sandbox. The parent shows it where a person can click it (the site shows a bar at the foot of the page; the artifact edition may do the same); it never opens a window on its own, since a message handler holds no user gesture and a browser would refuse the popup.
- schwingnet.experiment, figure to parent: {type, command, recipe, blocks, named, epochs, seed, hours, issueUrl, title, body, ok, problems, repo, workflow, ref, inputs, label, fallbackUrl}. The combination the experiments panel names, sent on every change; blocks is every part with its value, named the KEY=VALUE words that differ from version 1, ok whether the choice holds and problems why not, and the last six fields are the dispatch the parent may offer for it (repo OpenSpineConsortium/SchwingNet, workflow experiment.yml, ref main, inputs {recipe, epochs, seed, hours, blocks} as strings, fallbackUrl the prefilled issue). The parent shows Request this run from issueUrl and, where it has a connector, Run as me, which dispatches those fields when the viewer presses it; it is an alias of schwingnet.dispatch handled by the same code, with the dispatch made on the viewer's press rather than on arrival.
- schwingnet.dispatch, figure to parent: {type, repo, workflow, ref, inputs, label, fallbackUrl}. A request to run a workflow now as the viewer, through the viewer's GitHub connector (the actions_run_trigger tool: owner, repo, workflow_id, ref, inputs). Answered with schwingnet.dispatch.result, {type, label, ok, error}, error a message or code when ok is false.
- schwingnet.read, figure to parent: {type, id, repo, path, ref}. A request to read a file of an allowed repository as the viewer (the get_file_contents tool; a base64 body decoded before it is answered). Answered with schwingnet.read.result, {type, id, ok, text, error}. The storage planner's panel reads PLAN.json at ref storage-feed of OpenSpineConsortium/spine-datasets this way to refresh its snapshot.

The capability the artifact edition of #236 and #277 declared for this was {"sample": {}, "mcp": {"servers": [{"server": "GitHub", "tools": ["actions_run_trigger", "get_file_contents"]}]}}, with {"sample": {}} alone where the publish refused the connector's entry. The edition was never published, since the Artifact tool publishes only what Claude has read whole, and the reader that takes it to claude.ai (#294, docs/research/textbook-as-an-artifact.md) declares the project's files and sample and no connector (tools/textbook_publish.py CAPABILITIES), so there Run as me answers "no connector" and every figure shows its fallback, as on the Pages site. A figure that asks for nothing but links needs only schwingnet.open; a figure that acts names its repository and workflow in the dispatch and carries a fallbackUrl, so that a viewer with no connector still has a way. The connector's two calls are made as the viewer, in the viewer's own browser, and nothing of them passes through this repository: the dispatch is actions_run_trigger with method run_workflow, owner, repo, workflow_id and ref from the message and every input as a string; the read is get_file_contents with owner, repo, path and ref, answered with the file's own text whatever shape the runtime hands back (the API's base64 envelope, decoded as UTF-8; the server's content blocks, the file's resource before the text block that says it was downloaded; or a plain string), so a figure parses the text as it would the file. What a viewer sees who presses Run as me without the connector granted to the page is the result's error and the prefilled issue, never a silent nothing; and a dispatch starts no grid job, since the workflow it starts only answers an issue.

## 5. The request body

The experiments panel's issue body, and the body the Claude prompt path writes, is:

```
<!-- schwingnet-experiment -->
recipe: none
epochs: 20
seed: 1
hours: 4
block: architecture=resnet34
block: augment=box-jitter,intensity
```

followed by prose and the command the lines name. The marker is the first line; recipe is a name under data/recipes/ or none; epochs is a whole number from 1 to 200 (tools/experiments_panel.py EPOCHS_MOST); seed is 0 or more; hours is the training job's wall time, above 0; and each block line is one KEY=VALUE word as tools/flow.py takes it, only for a part that differs from version 1. The issue form of the triggers issue renders its fields as "### key" headings with the value below, and the workflow's validator reads both spellings, so a request from the form, from the panel's prefilled link and from the Claude prompt path is one record.

## 6. The Claude prompt path

The owner's second way of asking was "claude prompt to trigger it to run on the grid". The Ask Claude box of the artifact edition (tools/textbook_artifact.py ASK_JS) answers from the page's text on the viewer's own account; its rules now ask that when the reader asks for a run, the answer end with one line of its own, `experiment: recipe=<name> epochs=<n> seed=<n> hours=<h> KEY=VALUE ...`, the panel's defaults where the reader names none, and no such line otherwise. The box reads that line into the request of section 5 (a word that is not KEY=VALUE in the request's charset is dropped, since the workflow would refuse it anyway), shows Request this run, the prefilled issue, and, where window.schwingnetConnector resolves, Run as me, which dispatches experiment.yml with the same five inputs through the page's dispatcher. The box checks only the shape of each word: the workflow checks the values against the lists and answers with them when one is unknown, so a reader who asked for a block the page never named gets the list to choose from, on the issue, rather than a run of something else. The research loop, .github/symphony/research.md, works an open experiment issue from a person with write access before anything else: reads it, says what the answer leaves open, and records the run once its files are in the repository; it never sends the gate word, which is the owner's click.
