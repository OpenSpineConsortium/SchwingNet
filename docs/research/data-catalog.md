# The frame catalog: an extensible data flow for the fluoroscopic level detector

Source: the thread "SchwingNet video demo plan", 2026-10-21, the owner's asks of 00:54 UTC (incorporate the grid handoff of SchwingNet #27; design the extensible data flow on the premise that spines share one structure and exposure is the noise that tells a lateral film from a C-arm frame from a cone-beam projection; index it so a run queries for what it needs instead of loading files by the millions) and 01:05 UTC (the database framework must work natively with Metaflow, suit imaging data and support RAID). It is task #10 of the plan (retraining-plan.md, version 2) and the design behind data/registry/, data/splits/, src/schwingnet/catalog.py and tools/catalog.py. Confidential, this repository only.

## The premise, stated so it can be measured

A vertebral column has one structure whatever imaged it: the same bodies in the same order, the same pedicles, the same endplate pairs, the same transitional variants. What differs between a digital lateral film, a mobile C-arm spot frame, a fluoroscopy frame and one projection of a cone-beam sweep is the physics that wrote the structure onto the detector: tube voltage and current, detector type, pixel pitch, field of view, collimation, scatter, the view angle, and the vendor's post-processing. The owner's hypothesis is that these are nuisance: a model that sees the structure can be made to ignore them, and the images of every device can be mapped into one common domain where the detector trains once.

The catalog is built so that hypothesis is a measurement and never a belief. Every nuisance factor the record names is a column of the frame's row: the modality (xa, rf, cbct_projection, dx, cr, render), the device class (mobile C-arm, fixed C-arm, cone-beam gantry, film, synthetic), the make and model where known, the kVp, the mAs, the pixel size, the view angle folded into a band (frontal, lateral, oblique), and the source. A run that trains on one device and tests on another is one query per side. A run that measures the mapping into the common domain asks for the same levels from two devices at the same angle band and compares what the encoder makes of them: the cosine of their embeddings, kept in the catalog's embedding table per model version, is the first instrument, and the per-level accuracy by device and exposure band is the second. The spinesurg-ct-nnunet handoff already found that detection, not physics, is the binding constraint on the reported stack (HANDOFF_PHYSICS.md: detection costs about sixty points where realistic physics costs eleven to twenty-eight); the catalog lets the new stack re-measure that claim per device instead of inheriting it.

## What already exists, and what is built on it (native first)

- spinesurg-ct-nnunet data_platform/ has the layout every source already follows on the grid, `$RS/data/<source_id>/{raw,converted,derived,labels,meta}`, 211 source cards in sources.json, and a holding index, db/SCHEMA.sql built by build_index.py into `$RS/data/_index/holding.sqlite` (tables source, subject, item, annotation, split, lineage), which also loads in DuckDB. Its realxray adapter already writes one `meta/<stem>.json` per frame with case, device (make, model, kvp, mas, detector), view (gantry_deg, lat_from_ap_deg), px_mm, boxes with levels, split and source image. The catalog extends that model rather than replacing it: the same key rule for persons (spine-program 10_data_platform_grid PATIENT_IDENTITY_SPEC, metadata first and file name last; tools/patient_keys.py), the same per-frame facts, and a SQLite file beside the holding index.
- beethoven-research's splits.py is the split check: SplitLevel names the identity level per corpus (patient, study, cadaver, source_volume) and `disjoint` fails when a test person appears in training. The registry carries each source's identity level so that check runs on the catalog's answer before any training step.
- The leak checks of the old record (LEAKAGE.md: store key, pixel key, item key, CHK-6 perceptual hashes, CHK-7) run on the shards as the ingest step, and their verdicts are rows, not prose.
- The grid holds the bytes: C-ArmLSpine under /rs/rs_grp_oschome/go2432/data/carmlspine, the sweeps' projections under realxray/carmlspine_sweep, AASCE and VinDr as SchwingNet #27 put them there with their line endings fixed. Nothing is copied into a database; the catalog points at the files.

## The storage choice: Metaflow, imaging data and RAID

The owner's requirement of 01:05 UTC is answered by what Metaflow is. Metaflow has no database of its own for a user's data: a flow's steps pass Python objects as artifacts, which it pickles into its datastore (a directory on a local or shared filesystem, or an S3-compatible bucket), and it stores its run metadata in that same datastore or in a metadata service. So "natively works with Metaflow" means two things, and the catalog meets both:

1. A step reads and writes the catalog as a file by path and passes what identifies it as artifacts. The `ingest` step writes a shard directory on the grid (files plus MANIFEST.json) and sets `self.shard = name` and `self.manifest_sha256`; the `catalog` step rebuilds the SQLite file from every manifest and sets `self.catalog_path` and `self.catalog_sha256`; `train` runs a query and sets `self.selection`, the list of (shard, path, sha256) rows it will read, which Metaflow stores as the step's artifact, so `resume` and a later audit read the same rows. No step holds a connection open across steps and no step depends on a server.
2. The catalog is a single file in a format Metaflow's own tooling and every notebook read without a service: SQLite from Python's standard library, the same engine as the holding index, which DuckDB opens in place (`ATTACH 'catalog.sqlite' (TYPE sqlite)`), which pandas and polars read, and which a Metaflow card can summarize. Where a columnar copy serves a scan better (every frame's kVp and level over millions of rows), `tools/catalog.py export` writes JSONL now and Parquet once pyarrow or DuckDB enters pixi.toml as a feature in a change that re-locks on purpose (.claude/rules/writing.md: a dependency is an issue first); Parquet is the columnar format DuckDB, Lance, pandas and polars read natively, and a Metaflow step passes a Parquet file by path as it passes anything else.

Imaging data never goes into the database. A frame is a file in a shard on the grid, named by its content hash; the catalog holds its facts, its hash and its path. That is how every large imaging catalog that lasts is built (the holding index, MONAI's and nnU-Net's dataset JSONs, Hugging Face's and WebDataset's shard manifests): the bytes are immutable blobs in a filesystem that is good at blobs, the index is small and rebuildable, and a training step streams the bytes its query named. Embeddings, which are vectors and not images, do go in the catalog: one row per frame per model version, as a BLOB of float32, loaded by `embed` into a fresh copy of the file that is renamed into place (so the sha256 a step passed on still names the file it read, and the new file has a new one), with the brute-force cosine of src/schwingnet/catalog.py as the ranking rule over the training and validation parts only, unless a query names the test part. At the counts the plan expects for 2 November (hundreds of thousands of frames at most) a brute-force scan over a float32 table is seconds; when the catalog outgrows it, LanceDB, a file-based vector store that lives on the same volume with no server, is the candidate, added by issue as a pixi feature, and the schema above is what it would import.

RAID is a property of the volume, not of the database, and the catalog is designed so that any volume serves it. The grid's /rs volume is CephFS, which stores every object replicated or erasure-coded across OSDs (Wayne State's pool settings are not recorded here; the owner can ask C&IT for the pool's replication factor or erasure profile, which is the number that answers "how redundant"). A database that "natively supports RAID" is one that is a plain file on a POSIX filesystem and makes no assumption a redundant volume breaks: SQLite is that (one file, fsync on commit, WAL off for a file on a network filesystem, which is why the builder writes a fresh file beside the old one and renames it into place rather than writing in place), and so are JSONL, Parquet and shard directories. A server database (PostgreSQL, a vector service) would also sit on the volume, but it would need a daemon the login node may not run and a compute node cannot keep, and it would make the catalog depend on a process instead of a file; so none is used. The second half of redundancy is that the catalog is derived: `tools/catalog.py build` rebuilds it from the manifests and the two split files, byte for byte when its inputs are the same (the file carries no clock, and the test says so), and the manifests are append-only and content-hashed, so a lost or corrupted catalog file costs a rebuild and never a byte of data; the shard directories are the one thing to back up, and they are already on the replicated volume with the corpora themselves. A copy of the catalog file beside each training run's record (Metaflow's artifact of its sha256, the file itself in the run directory) gives every result the exact index it read.

What this rules out, each with its reason: a hosted database (no server of ours, and nothing of the data leaves the grid); storing pixels in the database (blobs in SQLite or Postgres defeat the filesystem's replication and the training loader's streaming); a dependency on an S3 endpoint (Metaflow's S3 datastore would work against a Ceph RGW if Wayne State offers one, which is not yet known, and the local datastore on the same volume needs nothing); a format only one library reads.

## The shapes

Three JSON shapes under version control, one SQLite shape derived from them.

- data/registry/<source>.json, the registry entry (schwingnet.catalog.RegistryEntry): the source id, its identity level (what a split must not share), its person-key rule in words, the access statement and determination (nothing clinical enters without it, BUILD_PLAN's G4 row), its modality and device class, the regions it covers, its grid root, and its shards (name, manifest path, kind, superseded_by). A new dataset is one new file and one ingest; a re-ingest adds a shard that supersedes the old one, and the old manifest is never rewritten.
- MANIFEST.json in each shard directory on the grid (ShardManifest): schema version, the shard's name `<source>/<ingest date>-<12 hex of the content hash>`, its kind (train, test, review), the ingest date, the code commit, what it supersedes, and one Item per frame: path within the shard, sha256, the person's study-local pseudonym, modality, device, exposure, angles, acquisition date where allowed, and labels (level, box in the unit square, labeller). The shard's content hash is the sha256 over its items' hashes in path order, so two ingests of the same bytes name the same shard. A shard is one kind and never a mix, so a training loader that names a train shard can never read a test person, and the builder refuses a train shard that holds a frozen test person.
- data/splits/test-persons.json and data/splits/rule.json: the frozen test persons with why each is frozen (the three real L6 persons of C-ArmLSpine and the two demo sweeps), and the rule for everyone else: `hash = first 8 bytes, big-endian, of sha256("schwingnet-split|" + salt + "|" + person)`, validation where that hash is below validation_share times 2 to the 64, training otherwise (schwingnet.catalog.part_of). The split extends: a person added next month gets the same answer as if present on day one, and no earlier person moves. The salt is in the file so the rule is reproducible and in nobody's head.
- catalog.sqlite (tools/catalog.py schema): build (the schema version, the code commit, the split rule's salt and share, and the sha256 of the test-persons and rule files it was built from, so a later run can tell which frozen list a catalog knew), source (from the registry), shard (name, kind, ingest date, code commit, what it supersedes, the manifest's path and sha256, its count), person (key, source, part, the split hash, how many frames), item (one frame: shard, path, sha256, person, part, modality, device_class, make, model, detector, kvp, mas, px_mm, lat_from_ap_deg, gantry_deg, view, acquired, label_count; keyed by shard and sha256, so the same bytes may sit in a train shard and a review shard), label (item, shard, level, region, transitional, box, labeller) and embedding (item, model, dim, vector). Indexes on the columns queries narrow by. The build writes a fresh file and renames it into place, refuses a train or review shard holding a frozen test person, a test shard holding anyone else, a shard loaded beside the shard it supersedes, and a manifest whose name is not what its source, date and content hash say.

## What a run asks

A query is a schwingnet.catalog.Query, every field a set that narrows one axis, turned into one parameterised WHERE clause by `where_clause`, so a person key or a source id is never spliced into SQL. A query that names no part reads training and validation; the test set is read only by a query that names it, and the contract on `where_clause` says so, so no trainer reads a test frame by forgetting a flag. The answers below are the plan's use cases; each is one command of tools/catalog.py and one artifact of a Metaflow step.

- The lumbar training set of every device but the one under test: levels L1 to L5 and sacrum, part train, every modality but xa.
- Every lateral frame of a transitional person for the rare-class review: levels T13 or L6, view lateral, to a review shard (the parts left unnamed, so training and validation).
- The frames a device-shift measurement pairs: the same levels, the same view band, kvp band 70 and 80, device class mobile_c_arm on one side and film on the other.
- The frames nearest a witness frame in a model's embedding space, to see what the encoder thinks is alike: `similar --model <version> --item <sha256> --k 24`.
- Who is in the test set and why, and the count of frames per part per level per source, which is the number every result row carries beside its confidence interval.
