## 1. The question, and what a reviewer would ask of the answer

How far are FleXray's synthetic DRRs from real X-rays, plain film and intra-operative fluoroscopy, and is that distance larger than the distance between two real corpora? And does this project's own rendering of FleXray's recipe reproduce FleXray's? A map alone answers neither: t-SNE draws clusters for any two sets with a consistent difference, however small, and its distances between clusters mean nothing. So the maps are drawn, as asked, and every claim is carried by a test with an interval and a calibration:

- a classifier two-sample test (C2ST): a classifier trained to tell the sets apart, scored out of fold with every person wholly on one side of each split, its AUC with a person-cluster bootstrap interval and a person-level permutation p-value;
- a kernel test: the unbiased MMD with a Gaussian kernel at the median distance, with a person-level permutation p-value;
- the generative-model distances, Frechet distance and KID, read in each space's first 64 principal components (FD64, KID64) so that every space is compared at the same dimension and with a stable covariance;
- precision, recall, density and coverage (Naeem et al. 2020), which say whether the synthetic images lie inside the real manifold and how much of it they cover, the two ways a renderer can fail;
- silhouette and neighbour purity of the groups, the share of each group's neighbours in each family, and which real corpus a classifier trained on the real corpora alone calls each synthetic group;
- the calibration: each group with at least 40 persons split in two by person, and every test run on the two halves, where it must find nothing. A split-half AUC whose interval excludes 0.5 means the pipeline leaks and the corresponding real-versus-synthetic number is not read.

### 2.1 The segmenter block

Which segmentation model's masks label a CT is a part of the recipe like any other, `segmenter`, with the values `spineps` (the default: the production runs) and `moose` (only when replicating FleXray's own dataset); TotalSegmentator is not a value, by the owner's word. One pure module, src/schwingnet/segmenters.py, is the home of the names, the two alphabets, the ids and the maps between them; the render blocks (src/schwingnet/render_blocks.py) and the training blocks (src/schwingnet/blocks.py, which record it for the anomaly route's pack stage, tools/anomaly_pack.py, to choose with --block segmenter=VALUE once that stage imports this module; as this is written it spells the VerSe alphabet itself, with a note naming this module) import it, and the torch side that reads a mask file by scheme is tools/render_blocks.py, so no block module spells a label itself.

- SPINEPS writes the VerSe alphabet: C1 to C7 are 1 to 7, T1 to T12 8 to 19, L1 to L5 20 to 24, L6 25, the sacrum 26, the coccyx 27 and T13 28. The canonical vertebral names are vertebra_c1 to vertebra_c7, vertebra_t1 to vertebra_t13, vertebra_l1 to vertebra_l6 and sacrum; the coccyx has no canonical name.
- MOOSE's stored ids are FleXray's configs/datasets/MOOSE.yml stored_labels, 0 to 117, lowercase names, copied into the module as a literal and held equal to the file by a test: vertebra_l6 is 83, hip_left and hip_right 84 and 85, sacrum 86, and there is no T13. FleXray's protocol all_structures_flexray_v4 keeps 97 of the 117 stored names, aliased into its 60 model labels (left and right merged, the ribs by number), and drops 20: vertebra_l6, rib_left_13, rib_right_13 and seventeen soft-tissue names.
- A label volume written for either scheme carries MOOSE stored ids, which is exactly what FleXray's own code reads (its TrainingLabelProjection over the dataset's stored labels), so FleXray's own remap sees the same labels under both segmenters. L6 is in the volume as 83 and dropped by that remap, as in FleXray's own training; the thirteenth ribs likewise as 44 and 57; both are recorded as dropped in the manifest. T13 and the coccyx have no MOOSE id, so they are left out of the volume and recorded as unsupervised with their raw values; so is the trachea, which moosez's organs model labels and MOOSE never stored.
- SPINEPS is never run anywhere (its production array is not approved): only existing masks are read, from the data root's spineps folder, whose layout is not recorded, so the locator walks it for `*_seg-vert_msk.nii*` and takes the first file, in sorted order, whose name before `_seg-vert` names the subject (s0011, sub-s0011 or s0011_ct); a mask on another voxel grid than the CT is passed over with its reason. The segment subcommand refuses `--segmenter spineps` with the owner's reason.
- MOOSE masks exist nowhere on the grid, so one GPU job makes them (bench flexray_drr_seg, section 7): moosez's Python entry on exactly the CTs the study chooses, with the five CT models whose labels MOOSE stores (organs, cardiac, peripheral bones, ribs, vertebrae; the lungs model repeats the organs model's lobes and the muscles and digestive models label nothing MOOSE stores), its models read from the fetched weights and never downloaded, its outputs under the data root's moose in moosez's own layout, `<moose>/<subject>/`, where the locator reads each model's file by the model's region word in its path. The moose label volume merges the five models' multilabel files in that order, soft tissue first and the vertebrae last, so where two models' masks overlap a bone wins over soft tissue and a vertebra over a rib; a model whose file is missing is recorded, and at least one must be there.
- The manifest records, for each subject, the scheme, the mask files by name only, the MOOSE ids present with their names, the dropped names present, the unsupervised values seen and the models missing.

A render takes a third value, `none`, which is a render choice alone: it is not in src/schwingnet/segmenters.py's SEGMENTERS, the training blocks or the experiments panel, which need masks, and the render blocks allow it only with a recipe that reads no label (src/schwingnet/render_blocks.py, reads_labels: the crops drawn by inverse label frequency, the isocentre on a structure or a vertebra and the lognormal attenuation each read one). The owner asked on 2026-10-27 whether the comparison needs a segmentation at all, and it does not, since a DRR's pixels are a projection of the CT. nanodrr scatters each ray sample into the channel of its label, the background's 0 among them, and fxr.drr's render_drr sums the channels, so a label volume splits the sum and changes no pixel; with the attenuation off the blocks engine passes no label at all. The masks enter only through what FleXray's recipe does with them, the crops weighted by the structures they hold with an empty crop dropped, the isocentre on a structure's centroid and the factors a structure takes; and through this study's own code, the CT choice and the pairs that compare segmenters. tests/test_flexray_render.py holds it: test_the_raw_recipe_draws_the_same_pixels_with_no_masks and test_the_blocks_engines_image_of_a_view_is_the_same_under_none_and_the_masks (a raw-recipe view is the same under none, moose and spineps), test_render_drr_with_a_label_volume_draws_the_cts_projection_alone, test_physical_ct_keeps_every_planned_crop_and_aims_at_the_crops_centre, and test_a_recipe_that_reads_labels_is_refused_under_none_before_anything_is_written.

The study's choice of CTs: the render groups on one CT folder render the same CTs, chosen once in the salted order among the CTs that have masks under every segmenter those groups name whose masks are read, and the plan and the summary say how many CTs had each. Segmenter none names no segmenter (schwingnet.domain_gap.segmenters_named), so a folder whose groups are all on none chooses among every CT. A group whose segmenter's masks are not read, because their folder is not there, holds fewer CTs' masks than the five persons a group needs to be tested (as a segment job that stopped on one of its first CTs leaves it), or a run by hand left them out with --skip-masks, is skipped with that reason in its own record while the other groups on the folder render, and the CTs are chosen without those masks. A folder that holds more is read, and the choice is made among the CTs it covers, so a segment job cut short a little later still holds every render group to few CTs, fewer again once a group passes some over, and the mask-free groups with them; no cutoff avoids that without splitting the CTs the render twins share, so the segmentation job's report is read before the study word is sent, and a MOOSE run that ended short goes back to the owner. The segment job's plan, made before any MOOSE mask exists, chooses among the CTs with SPINEPS masks, which is the same choice once the job has made MOOSE masks for all of them and a smaller one, said in the summary, where it has not. The groups on none require no masks, so the plan's choice with them is the one it made for job 40799505, and a test holds it unchanged (tests/test_domain_gap_run.py, MaskFreeRenderTest).

### 2.2 The render recipes, the two engines and the six pairs

A render is a configuration of named blocks (src/schwingnet/render_blocks.py). DEFAULT is FleXray's released MOOSE recipe in every part with the project's own segmenter: the CT clipped to -1000 to 2000 HU and held as float16 as FleXray's packs are, every voxel at or below -900 HU set to air as its loader does, axial 256-slice crops in the volume's own slice plane at the 50 percent overlap the released packs were made with (the choice flexray-axial; flexray-axial-min is the fewest crops), crops drawn by FleXray's inverse-label-frequency weights (tau 0.5, the crop taking its largest class weight), the pose drawn from FleXray's MOOSE profile (the gantry over the full orbit, the tilt within 30 degrees, the source within 100 mm across and 500 to 900 mm away, the detector 1150 to 1250 mm away with 1.25 to 2.25 mm pixels), the isocentre a structure's centroid drawn without replacement, a cone beam nine times in ten and orthographic otherwise, each structure's attenuation multiplied by a lognormal factor (mode 1, sigma 1, within 0.1 to 4) on half the renders, each render min-max scaled, 4 views a CT on a 256-pixel detector with 500 samples a ray, segmenter spineps. FLEXRAY is DEFAULT with segmenter moose, FleXray's recipe to the bit, the replication's; PHYSICAL is DEFAULT with the attenuation randomisation off; PHYSICAL_CT, the preset physical-ct, is PHYSICAL from the CT alone, its crops drawn uniformly, its isocentre the volume's centre, which under an axial crop is the crop's centre, and segmenter none, every planned crop kept since none is dropped for holding no structure; FLUXRAY_RAW is section 2.3. Two engines run a configuration: `blocks`, this project's tools/render_blocks.py, one function per named choice with FleXray's fxr.drr primitives underneath for the pose draw and the rendering; and `flexray-runtime`, FleXray's own code for every step (its crop planner and packer, its crop weights, its label remap at the released model's protocol, its SegmentationDRRRuntime from its MOOSE training profile, its scaling), which takes only the choices FleXray's code makes and refuses the rest in words before rendering, and takes both segmenters, since each hands it MOOSE stored ids. It takes segmenter none only under pose fluxray-grid, where it builds the request from fxr.drr's primitives and reads no label, and refuses physical-ct (ENGINE_PRESETS), since its runtime reads labels under FleXray's own pose profile. The seed of a view comes from the salt, the subject and the view alone, never from the engine or the group, so two groups on one folder that differ only by their attenuation block share every crop, isocentre and pose, and the reference engine seeds FleXray's own generators from the same number; its draws differ where its code differs, which is the point of the test. Each view is written as a 16-bit grey PNG with its row in manifest.json (the crop, the isocentre's label and point, the pose with its SDD, pixel size and grid index, the attenuation factors drawn, the seed), and a second call under the same settings reuses every view already on disk, so a job cut short carries on.

The six pairs the summary reads (tools/domain_gap.py, REPLICATION_PAIRS), each isolating one thing:

- flexray_replica against flexray_reference: our blocks against FleXray's own code under the same MOOSE labels, the replication test; it gets the word of section 4 and is the study's verdict.
- fluxray_raw against fluxray_raw_reference: FluXray's raw-render recipe through our blocks against FleXray's primitives; the second worded pair.
- flexray_drr_ct against flexray_drr: what the labels' aiming does, the crops weighted by the structures they hold and the isocentre on a structure, with the attenuation off in both. As in the segmenter pair, the crops, isocentres and poses are not shared, since the two recipes draw them differently. Added on 2026-10-27, before any number was seen.
- flexray_drr against flexray_replica: the attenuation randomisation, since they share crops, isocentres and poses.
- flexray_spineps against flexray_replica: the segmenter, the production labels against the replication's, on the same CTs and seeds. The crops, isocentres and poses are not shared, since FleXray's recipe draws them from the label volume before the pose: a crop holding no structure is dropped, the crop is drawn by its label classes, the isocentre over the structures the crop holds, and the pose after those draws from the same generator (tools/flexray_render.py, BlocksEngine.view; the order is FleXray's own and the replication test holds it). So the pair isolates the labels and everything the labels decide, which is what changing the segmenter changes in a production run.
- fluxray_raw_reference against fluxray: the FLUX edit, with the pose recipe held the same. The earlier pair flexray_reference against fluxray confounded the pose recipe with the edit and is dropped.

### 2.3 FluXray's raw-render recipe, from the paper

FluXray's raw renders were not FleXray's online training profile. They are 90 fixed poses a CT, y in 650, 900 and 1150 mm, z in -300, -200, -100, 0, 100 and 200 mm, alpha in 0, +45, -45, +90 and -90 degrees, x 0, beta and gamma 0; the detector 1250 mm from the source with 0.6 mm pixels and 1024 x 1024 pixels; the isocentre the volume's centre; the whole volume, not a crop; the attenuation fixed, that is the randomisation off; each render min-max scaled. So FLUXRAY_RAW names crop whole, crop_sampler uniform, pose fluxray-grid (one of the 90 poses drawn uniformly a view, as a FluXray training draw takes one of a subject's poses, the SDD and the pixel size fixed by the choice and both recorded in the manifest with the pose's index), isocentre volume-centre, projection cone, attenuation off, scale minmax, segmenter moose, 4 views, a 1024-pixel detector. The recipe reads no label, so the groups fluxray_raw and fluxray_raw_reference take it with segmenter none since 2026-10-27 and their pixels are the same with masks or without; the preset keeps MOOSE's labels for a replication of the dataset with its masks. What FluXray then did and the raw recipe stops before: FLUX.2 klein 9B edited each render (4 steps, bfloat16, guidance 1), pixels whose raw DRR was below 0.05 were set to 0, a paired-difference filter dropped about 4 percent of the edited renders per pose, and the released images are the edits at 1024 resized to 512, by the paper (docs/research/flux-realism/README.md records the stored images at 256 by 256); the fluxray group carries those as released. Every image of the paper, X-ray or DRR, was clipped to its own 0.5 and 99.5 percentiles and min-max scaled, which is the study's own decoding of every group (section 3), so the clip is applied once and alike to every group. FleXray's runtime cannot draw the grid, since its PoseSampler knows fixed presets and random ranges, so under fluxray-grid the reference engine builds the request with the explicit pose through fxr.drr's primitives (compute_isocenter at the volume's centre, DRRRenderRequest with the rotation, the translation, the fixed SDD and pixel size, render_drr, scale_rendered_images) and honours exactly FLUXRAY_RAW's parts.

## 3. From file to feature

Every image, synthetic or real, takes the same path: decoded to floats (DICOM through its modality LUT, MONOCHROME1 turned bone-bright, a cine's middle frame; 16-bit PNG and TIFF at their depth), windowed to its own 0.5 and 99.5 percentiles as the bank does and as the paper did to every image, cut to the centre square of 0.9 of its shorter side and resized to 256 with an area filter. Cutting a square rather than padding one keeps a pad's flat border, which only non-square images would carry, from telling the corpora apart; resizing everything to 256 makes the resolution step the same for the 1024-pixel raw renders, FluXray's release (512 by the paper as section 2.3 reads it, 256 as docs/research/flux-realism/README.md records the stored images) and the real corpora alike.

Three feature spaces, so that no finding rests on one encoder's view:

- flexray: FleXray's flagship member (flux0375) at its own preprocessing, the spatial mean of the input to the last instance norm of its deepest encoder block. The output of an affine instance norm has the norm's learned shift as its spatial mean for every input, so pooling the block's output would give one vector for every image.
- imagenet: torchvision's ResNet-18 with ImageNet weights, its 512 pooled features, the conventional FID-style space.
- physics: handcrafted measures a renderer gets wrong first: the intensity histogram, the radial power spectrum's shape, the gradient histogram, the noise (a robust spread of the Laplacian at two scales and their ratio), local contrast, the shares near black and near white, the share of strong edges.

Fluoroscopy is often shown bone-dark and DRRs bone-bright, which any encoder separates at once. The primary reading is therefore inversion-invariant: each space's feature of an image is the mean of its features of the image and of its inverse. FleXray's space is also read as stored, as a secondary reading, to show how much of the gap polarity alone carries.

## 4. The analysis, and what was fixed before any number was seen

Per space: features standardised; the maps (PCA, t-SNE at perplexity 30 on PCA-50, UMAP with 30 neighbours on PCA-50, and LDA, which is supervised and labelled so), each but LDA with its trustworthiness against PCA-50, from at most 600 images a group; every synthetic group against each real group and against each pooled real family (300 images from each testable real group, so no one corpus outweighs the rest); every pair of real groups; pooled fluoroscopy against pooled film; the six pairs of section 2.2; the split-half nulls. The classifiers are logistic regression (scaler, PCA to 64, C 1) and 15 nearest neighbours, five person-grouped folds stratified by label; 1,000 bootstrap draws; 100 permutations of the C2ST against each family, 1,000 of the MMD everywhere. A group with fewer than 20 decoded images is left out, and one with fewer than five persons is plotted and never tested. Benjamini-Hochberg runs over every MMD p-value of a space and over its C2ST permutation p-values.

## 5. Limits known before the run

- The corpora differ in more than their realism: anatomy (cervical films, a hip phantom, cephalograms, abdomen), devices, eras and formats (JPEG re-exports, 16-bit scans, DICOM). A real-versus-real AUC near 1 is the expected baseline for many pairs, which is why the gap ratio and the words compare the synthetic distance with the real-real one rather than with chance.
- The FleXray-recipe renders follow FleXray's own pose profile, mostly frontal arcs over a wide field, and the raw FluXray renders its 90 fixed poses; the real spot frames are narrow and centred on the lumbar spine. The map shows the gap the renderers' own settings make, not one tuned to match the held frames.
- The replication's CTs are TotalSegmentator v2.0.1's, not the ENHANCE-PET 1.6k volumes FleXray's MOOSE dataset was made from; the masks come from moosez 3.2.2 on the moosez-v.3.1.3 release's model weights, and which moosez version labelled FleXray's dataset is not stated in the code read here. moosez's library entry, by its source (moosez 3.2.2, moose()), writes each model's file as clin_CT_<region>_segmentation_<input stem>.nii.gz straight into the output folder it is given, reoriented to the input; moosez was never run in this container, so the locator matches a model's file by its region word anywhere in the path below the subject's folder, the tests hold that layout and the CLI's both, and the segment subcommand's plan is what the tests hold.
- The moose label volume merges the five moosez models' outputs in a precedence this project fixed, soft tissue first and the vertebrae last (src/schwingnet/segmenters.py), so a voxel two models claim is the later model's. FleXray's paper says only that its CTs went through the MOOSE-Z pipeline and nothing of how overlaps were resolved into one stored-id volume, so a replication gap at the costovertebral and hip-femur overlaps is read against this project's precedence, not FleXray's.
- The SPINEPS folder's layout is not recorded, so the locator walks the whole folder once and matches by name; a CT whose SPINEPS mask is on another voxel grid, or has no mask under either segmenter, is not among the chosen CTs.
- flexray_drr_ct aims at the crop's centre where FleXray aims at a structure's centroid, and draws its crops uniformly where FleXray weights them by the structures they hold, so it is FleXray's physics on this project's aim and not FleXray's render; the pair with flexray_drr measures what that difference does. Where a crop holds little anatomy at its centre, the view shows it as it is, which FleXray's recipe would have dropped or aimed elsewhere. The FluXray raw groups aim at the volume's centre as the paper did, so for them none changes nothing.
- Persons are files in seven groups; their within-group test splits are by file.
- DeepFluoro has six specimens, so its intervals are wide.
