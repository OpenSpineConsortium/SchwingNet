# Deviations from PREREG.md

Source: the thread "Compare synthetic FluXray against real fluoroscopy", 2026-10-27. Every departure of the study from its pre-registration (PREREG.md beside this file), dated, with its reason, in the order it was decided. None was decided after a number of the study had been read.

1. 2026-10-27, 14:47 UTC. The render groups hold 27 CTs, not the 250 the design planned (README section 2). The segmentation job, Slurm job 40799505, ended at exit 0 having run MOOSE on the 27 CTs its plan chose: the plan chooses among the TotalSegmentator v2.0.1 CTs with a SPINEPS mask on their own grid, and 27 had one. Asked whether to send the study on those 27, to run the mask-free groups at 250 first, or to hold for new segmentation jobs, the owner chose "Send it now on the 27 CTs". Each render group's tests therefore stand on 27 persons, so its intervals are wider than planned, and a group under five persons after a render passes CTs over is plotted and never tested, as the design already says.

2. 2026-10-27, 17:51 UTC. The analysis runs as units claimed by the tasks of a Slurm array on the H200 nodes, in place of one process on one GPU job: one prepare job (render, plan, images, features and each reading's head), an array of tasks that claim the units, and one merge job that assembles results.json, the figures and the summary. The owner's word was "cancel and shard requesting h200 / see the beethoven protocol for doing so". No statistic, constant, seed or reading changed: each unit is one contrast, null, structure measure or map, run with the study's seed of 0 from the same head, and tests/test_domain_gap_array.py holds the array's results.json equal to the one-process run's on the same inputs, apart from the run record, both in a process of one BLAS, OpenMP and torch thread. On the grid each unit runs in a worker process of one thread, which a unit run again in a process of one thread matches to the bit (the same tests). A process of many BLAS and torch threads sums in another order, since how BLAS splits a product among its threads changes the order of its sums (a product of the study's z64 with its transpose comes out differently with one, two, three and four threads): that moves the float32 measures in their seventh digit, and with four threads the one-process run and the array did not always agree in the last digit of a float64 silhouette, so the V100 send's numbers, had it written any, would have differed from the array's there, as tools/domain_gap_stats.py's opening already says of a GPU.

3. 2026-10-27, 17:52 UTC. The study's first send, Slurm job 40802322 (sent 14:48 UTC at commit 38e5533, on a V100 with 4 CPUs), was cancelled on the owner's word after about three hours, while it was still in its analysis. It wrote features and no results.json or summary, and no number of it was read. Its feature files are rewritten by the new prepare job wherever one does not load whole.

4. 2026-10-27. The run now writes a record the design did not ask for, which changes no number: PREREG.md's hash is checked by the first line of every step of the job (exit 90 on a mismatch), every results.json carries a `_run` block (job, task, host, time, commit and whether the tree was clean, the script's and the code's hashes, the arguments, the inputs' hashes, the pre-registration's hash and the seed), the summary opens with five record lines, and PROGRESS.txt says what each stage and task is doing, as the owner asked at 17:53 UTC ("make sure you are logging").

5. 2026-10-27. The mask-free groups, flexray_drr_ct among the primary endpoints and the two FluXray raw groups on segmenter none, were added on the owner's question of 04:15 UTC, before the first send and before any number; README sections 2.1, 2.2 and 4 record them, and PREREG.md includes them, since it restates the design as the first send ran it. They are listed here because they came after the design's first writing of 2026-10-25.

6. 2026-10-27. The Lab Recipe asks that each bar come from a published value or a power calculation. The study's bar of 0.6 on the AUC's lower bound was fixed by the design on 2026-10-25 (commit 080e175) and the MMD's q of 0.05 for the replication on 2026-10-26 (d917c30), as conventions, before any number; neither was taken from a published value or a power calculation, and the report says so beside the words.

7. 2026-10-27. The Lab Recipe's rule 14 asks for a decision gate between a timing run and a production array. No separate timing run is made: the prepare job is the array's own first step and writes the units' list with each unit's cost, so the array's tasks start only once it has ended, and a task that finds no list exits 0. The first array's own progress, read during the run, stands in for the timing run.

8. 2026-10-27. PREREG.md section 5, restating README section 1, words the pipeline's failure as a split-half null whose AUC interval excludes 0.5. The study's code has flagged a split-half null by its MMD permutation test instead since its first version (commit 080e175, 2026-10-25), and the first send ran that code: a null is flagged where its MMD's Benjamini-Hochberg q over the space's split-half nulls is below 0.05, and an AUC interval above 0.5 is counted beside it and flags nothing by itself, because the C2ST's bootstrap interval holds the trained classifiers fixed and is too narrow for a few dozen persons, while the permutation test is exact under a person-level null. That is the rule the study applies: where a group's null is flagged, every contrast the group is a side of in that space is not read, the sentence being PREREG.md's ("the split-half null of <group> in <space> found a difference, so its contrasts are not read"); the summary's calibration lines name each flagged group and the report marks a flagged primary endpoint not read. A group of fewer than 40 persons, each render group on the 27 CTs among them, has no split-half null. PREREG.md stays as frozen; this item is the departure. Found by the review of the sharding on 2026-10-27, before any number.

9. 2026-10-28, 00:23 UTC. The array has 16 shard tasks in place of 4, and its three jobs run on any card of the grid's gpu class in place of the H200 nodes alone, on the owner's words "can i run mroe jobs and shard it to more gpus like 16 so the damn parallelism churns through it? also make sure there is realtime logging in the CLAIMS/REPORT" and "you can drop the requirement for h200 unless its a memory problem". Memory on a smaller card is measured for prepare alone: the first send, Slurm 40802322, ran its render, images and features on a 16 GB V100 (Tesla V100-SXM2-16GB) and was cancelled in its analysis (item 3). A shard uses its card only for the MMD's permutations, but its sixteen workers each open their own context on the one card, which no run has measured on a small card; so an MMD test the card has no room for runs with numpy on the CPU (tools/domain_gap.py, mmd_where_it_fits), its permutations numpy's draws under the same seed either way, the unit is never failed for the card's size, its result file names the backend it ran on, and the run log names each unit sent to the CPU. The six jobs sent at 22:01 UTC (prepare 40812341, the array 40812342 and the merge 40812360) were still waiting in gmsap's queue, having done nothing. No statistic, constant, seed or reading changed: a unit is the same contrast whichever task claims it and on whichever card, tests/test_domain_gap_array.py holds the array's results equal to the one-process run's, and each task names its card, so the record says which cards the units ran on. The MMD's permutations run on torch where a card is there, so a unit's MMD p may differ in its last digits between card models, as a GPU's sums may (DEVIATIONS.md, item 2). The six jobs were cancelled at 01:01 UTC on the owner's tap of "Send 18 jobs, any GPU" (00:57 UTC), before any of them started. The run now also writes a run log, which changes no number: every step's lines with their times, its newest in the status word, at most 50 lines in the bench report, every quarter mark kept and, before any routine line, every failure the 50 lines can hold (the first and the last of them where they cannot), and the CLAIM report's section Run log; and each step waits on the tool in the background, so the TERM job submit sends the batch shell two minutes before the time limit reaches the tool, whose own line then says how it ended.
