## 1. The question

For one combination of training blocks and data recipe that a person asked for on an issue labelled experiment, how accurately does the level stage trained with it name each vertebral body on the held-out real frames the catalog holds, per level, per source and in the transitional stratum, over the truth boxes; one row of the experiments panel, read beside version 1's row on the same frozen test persons.

## 2. Population and inputs

- The configuration: the request, the lines `recipe`, `epochs`, `seed`, `hours` and any number of `block: KEY=VALUE`, as experiment.yml recorded them as `<issue>.request` on the branch experiments before the run, and as the gate fetched them when the owner sent the word. The request is the run's registered configuration: it is written before the run, held by its bytes in the launcher's key (flows/experiment.py, key_reads), and checked in the job against this checkout's blocks module and recipes before any frame is read (`tools/experiments_panel.py check --request`), so a request that no longer holds trains nothing. A block the request does not name is version 1's choice (src/schwingnet/blocks.py), and a request that names none is version 1's training to the bit.
- The catalog: the version grid/v1-version.sh chooses, as for version 1 (the newest that holds both of C-ArmLSpine's parts and every C-ArmLSpine shard at the head of its chain, with a split-check marker for the test persons and the rule as they are now), split-checked again in the job before any frame is read; the request's recipe, where it names one, cuts the catalog as data/recipes/ says (tools/licences.py). The run names the catalog by its sha256 in RUN.json and the recipe and sources in PROVENANCE.json.
- The test persons: data/splits/test-persons.json (sha256 4c57462fb8d4fa4591fb73d10e506957b5f00f66c25c2e7f07731f2f073cb59d) under the split rule data/splits/rule.json (sha256 4f26dbc75ea43b3cb8605204b343e6144f9e99b027654e6f126158e4ba3634c3), the same for every request and for version 1.
- The weights: the ImageNet ResNet-18 file resnet18-f37072fd.pth, named by its sha256, from which every requested combination starts, as version 1 does. The grid holds no ImageNet file for another architecture, so a request whose `architecture` block names another is refused before any frame is read, in the job and again in the flow's start, and waits for its file.
- Exclusions: none beyond the split rule and the recipe's cut. The test part is never read by the trainer; FluoroCap and the leaked banks are in no catalog shard (retraining plan, section 3.2).

## 3. The measurements

The same as version 1's (docs/research/v1-demo/PREREG.md, section 3), since the run is tools/flow.py run with the request's words:

- Per epoch, epoch 0 included: the training loss and the validation accuracy with its interval, per level, per source and for the transitional stratum, in train/metrics.jsonl; the validation witness frames drawn whole.
- The kept checkpoint: the epoch with the best measure the request's `select` block names (version 1's accuracy unless it names balanced-accuracy) on the whole validation part, never on the witness frames alone and never epoch 0.
- On the test part, read once after training: naming accuracy over the truth boxes as correct of n with its 95 percent Wilson interval and the persons behind it, over all levels, per level and per source, the transitional stratum apart and never pooled; the confusion matrix; the test witness frames over every kept epoch, which choose nothing.
- Every number stamped with the run id, the commit, the clean-tree flag and the catalog's sha256 (RUN.json); the blocks in train/checkpoint.json and train/MODEL.md; and the run's CLAIM 2024 and REFORMS report (tools/report.py), written after its last step and checked by the flow's end step.

## 4. The hypotheses and their bars

None is tested, as the owner chose on 2026-10-29 at 03:23 UTC. A requested combination is one point of the loop that optimises the blocks (experiment-framework.md, section 1); its numbers are estimates, each with its interval and its n, read beside version 1's on the same test persons. No bar is set, no published value applies, and no power calculation was made. A bar the owner sets later, for a request or for a set of them, is a new PREREG with its own freeze.

## 5. What counts as failure

- The request does not hold at the job's commit: the job ends before the launcher starts, with the check's words in its report, and nothing is trained.
- The request names an architecture with no ImageNet file on the grid: the job ends before the launcher starts with "architecture=<name>: no ImageNet file for it on the grid, so the request waits for one", and nothing is trained.
- The words the flow is given differ from its request's lines (recipe, epochs, seed, hours or blocks), or the request file's bytes change during the run: the flow fails at its start, or its verdict is 1 with the line "the request file changed during the run", so a run never trains one configuration and records another.
- The run cannot be run or recorded: a dirty tree, a split that is not disjoint, a catalog, weights or request file whose bytes are not the ones the record or the key names, or a step that exits other than 0 once retried. The flow fails, the launcher exits other than 0, and the run's progress page shows the step that failed with its last line, "tools/flow.py run exited <code>: <its last line>" where tools/flow.py failed; no number of it is quoted.
- tools/flow.py ended without finishing the run: the verdict is 1, with the line "<run>: no FINISHED.json, so tools/flow.py did not finish the run" on the page.
- The run's CLAIM 2024 and REFORMS report, as tools/flow.py left it, is not what the run's files give, or cannot be written or does not check once written: the verdict is 1, with one of these lines on the page: "<run>: NOT CURRENT as the run wrote it, so written anew; why: <the check's words>", "<run>: NOT CURRENT as the run wrote it, and not written anew; why: <the check's words>", "<run>: NOT WRITTEN at the end; why: <the tool's words>" or "<run>: NOT CURRENT once written at the end; why: <the check's words>". A stale report is written anew where the tool can write it, so the folder holds the current one; the verdict stays 1.
- A stale report of work done before this Metaflow run began, a run resumed after tools/flow.py had finished, is no failure: it says only that tools/report.py or its inputs changed since, which no key names. It is written anew with the line "<run>: written anew under the report tool as it is now, its work done before this run began; <its counts>; it was not current, why: <the check's words>".
- A checkout that moved during the run: the run is not used and the word runs it again (grid/experiment-driver.sbatch).
- An item the report counts as missing is shown and is not a failure of the run; `tools/report.py check --complete` stays the gate before any number is published (docs/research/run-report.md).

## 6. The analysis plan

The checkpoint is chosen on the validation part before the test part is read, and the test part is read once, after training. The next combination to request is chosen from the validation part, as the ledger reads it (`tools/block_sweep.py ledger`, which never reads evaluate/results.json); no requested combination is chosen over another, or over version 1, by its test numbers, since a choice made on test persons counts as seeing them (retraining plan, section 4), and a combination chosen that way would need test persons it never saw. Every interval is a Wilson interval on the person-keyed n. Per-level and per-source rows are description; a level with too few test persons to carry an interval is reported with its n and never pooled to reach one. Nothing is read blind, since no person reads an image. The run's verdict is computed by flows/experiment.py from the run's end and its report, so no reader chooses it.
