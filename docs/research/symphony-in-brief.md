## TL;DR

Symphony lets many Claude Code workers share one GitHub repository, each issue held by one worker at a time, using only GitHub's own objects: issues are the queue, a branch is the lock, and a pull request is the only way work lands.

- **How it works.** A worker claims issue N by being first to push the branch `claude/N`; GitHub refuses a second push of that name, so only one worker can hold it. The worker opens a draft pull request at once, and its work lands only by a merge with the required check green.
- **What keeps it tidy.** A board, rebuilt as issues, pull requests and branches change and every six hours, shows who holds what and which open work touches the same files. A coordinator step in that same run frees claims idle for 24 hours and tells overlapping work which lands first; Claude splits large requests (epics) into tasks.
- **What it guarantees.** Bookkeeping safety: one holder per issue, releases only when due and never half done, no commit made unreachable and no finished work released by the board or the coordinator, and forbidden pushes refused when the guard can read them. On main today 12 of its 17 guarantees are checked, by exhaustive search of small worlds and by tests (checked, not proved), 2 hold only if commit dates are honest, 1 is known broken (repeat overlap notices) and 2 are partly checked or not yet.
- **What it does not promise.** That the code is right beyond the repository's own tests, that work ever finishes, or that parallel work beats one agent.
- **Against CooperBench.** CooperBench's pairs work blind in separate containers, talk only by messages and merge once at the end; Claude Sonnet 4.5 fell from 47.1% alone to 25.8% as a pair. Symphony is the opposite design, shared and visible work merged continuously, like the authors' later, unreviewed shared-git (56%) and team (62%) runs. Whether Symphony beats them is not measured yet: coordbench's pre-registered 50-pair run has not happened.

## How it works

Every rule lives once, in the dependency-free Python library symphony-protocol, and each repository that follows it runs a vendored copy ([README.md:3](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/README.md#L3)). A worker is a person's Claude Code sessions, a routine on a Claude account, or a worker in GitHub Actions, each under its own name and label `worker:<name>` ([PROTOCOL.md:7-9](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L7-L9)). One piece of work moves through six steps:

1. **Queue.** Work is a GitHub issue labelled `todo`; an `epic` is a larger request that Claude plans into tasks ([PROTOCOL.md:3](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L3), [13-19](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L13-L19)).
2. **Pick.** The worker reads the board and takes, in order, an issue given to it by label, an unclaimed blocker or the next unclaimed `todo` issue, the last two from its area if it has one; never an epic. It notes which open work changes the same files ([PROTOCOL.md:25](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L25)).
3. **Claim.** It pushes a new branch `claude/N` whose one commit adds a claim file naming the worker, the plan and the files to touch. GitHub refuses a second push of the same name, so a second claimant is turned away and picks another issue ([PROTOCOL.md:29](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L29), [33-47](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L33-L47)).
4. **Work in the open.** It opens a draft pull request with "Closes #N" at once and pushes often. If main moves on in a way that stops the merge, because the repository requires up-to-date branches or the two conflict, the board says "main moved". The worker then merges or rebases main in; the one forced push allowed is a lease onto its own claim ([PROTOCOL.md:55](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L55)).
5. **Finish.** The pull request deletes the claim file, passes the required check and is marked ready. The owner merges, or GitHub auto-merges for a worker set to; the merge closes the issue ([PROTOCOL.md:59](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L59)).
6. **Release.** An unfinished claim with no commit for 24 hours is freed. Its claim labels come off and `todo` goes on unless the issue has `todo`, `epic` or `blocker`; then a comment says why, whose it was and what the branch holds; then the branch is renamed to `released/N-<sha>`, so the work is kept and the issue is listed again ([PROTOCOL.md:67-69](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L67-L69)).

[The doc shows a figure here, one issue's claim lifecycle in five states. It does not export to Markdown.]

A second worker's push of the same branch is refused, so it picks another issue. The board's run, started by GitHub events and every six hours, is what says "main moved" and makes the 24-hour release.

Three pieces run around those steps, all plain code on the repository's own token with no Claude usage, except the planning:

- **The board.** STATE.md on the branch `board`, rebuilt on every issue and pull request event, every branch made or deleted, every push to main and every six hours ([PROTOCOL.md:3](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L3)).
- **The coordinator.** Inside the board's run it releases idle claims and tells each piece of overlapping work, once, the order to land in: a blocker first, then work marked ready, then the work that began first ([PROTOCOL.md:73](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L73)). Planning epics, settling blocked tasks and integrating finished epics is Claude's job, in coordinator.yml ([WORKERS.md:25-30](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/docs/agents/WORKERS.md#L25-L30)).
- **The fences.** A Claude Code hook, the push guard, refuses forbidden pushes before they run; GitHub's branch protection stands behind it; and CI's protocol check fails a pull request that breaks the rules ([PROTOCOL.md:104-107](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L104-L107)).

The same rules also run as a merge gate over other worlds: GitHub's API, a bare git repository (the benchmark's arm) or memory, for tests ([PROTOCOL.md:79-99](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L79-L99)).

## What it guarantees

Symphony's 17 guarantees are safety properties of its bookkeeping, each restating one sentence of the spec ([GUARANTEES.md:3](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/GUARANTEES.md#L3)). On symphony-protocol's main today (b5f098d, after F15 and F16 merged this evening), 12 hold, 2 hold only if commit dates are honest, 1 is known broken, 1 is partly checked and 1 is not checked.

What "checked" means here:

- The library's own code runs against a fake of GitHub that keeps state, with scripted workers, not Claude; an oracle written from the spec's words, importing nothing from the library, judges every step ([DESIGN.md:14-18](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/DESIGN.md#L14-L18)).
- A breadth-first search tries every interleaving of small worlds: two workers on one issue to depth 5 (about 29,500 states), three workers to depth 4, and every fault kind from a due claim. None found a violation ([GUARANTEES.md:12](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/GUARANTEES.md#L12), [README.md:50](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/README.md#L50)).
- 59 deliberately broken copies of the rules (mutants) are each caught, which shows the checks bite ([mutants.py:446-639](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/mutants.py#L446-L639)).
- This is bounded checking of small worlds, not a proof. The deeper searches and the real-git world are the deep lane, [symphony-protocol#21](https://github.com/OpenSpineConsortium/symphony-protocol/pull/21), still unmerged ([README.md:72](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/README.md#L72)).
- Nothing after release 0.4.1 is released. The template already runs F4, F7, F12 and F14 ahead of release ([VENDORED:1](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/tools/VENDORED#L1)); F9, F13 and F15 reach it with the next release. F16 needs no code there, since 0.4.1 already behaves as the spec now says, only new wording in the template's docs at that sync ([README.md:69](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/README.md#L69), [DESIGN.md:857](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/DESIGN.md#L857)).

## What it does not guarantee

Symphony guarantees how work is shared, not that the work is good, finished or faster.

- **Correct code.** Work lands when the repository's own required check is green, so quality is only as strong as that check ([PROTOCOL.md:86](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L86)). Tasks can each pass while the merged whole fails, which is why the coordinator re-checks main after an epic's last task ([WORKERS.md:29](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/docs/agents/WORKERS.md#L29)).
- **Progress.** Nothing promises an issue gets done: a stalled claim can sit 24 hours before release, and finished work waits for review however long it takes ([PROTOCOL.md:67](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L67)).
- **Speed or success from parallel work.** Unmeasured so far; see the CooperBench section.
- **Semantic conflicts.** Overlaps are found by file name only, from claim files and pull request files; two changes to different files can still break each other ([PROTOCOL.md:73](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/spec/PROTOCOL.md#L73)).
- **Fair idle times.** Idleness is read from the commit date, which whoever pushes sets, so a worker can keep a claim alive or let one lapse early by its clock (F8, open).
- **Protection from someone with write access.** The push guard is a hook in a worker's own Claude Code, so a push made from anywhere else meets only GitHub's branch rules. The release gate's own write-up says it does not hold against anyone who may write to the repository, and lists the settings not yet made ([README.md:177-184](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/README.md#L177-L184)).
- **Four spec rules with no check at all yet:** a second pull request closing a claimed issue, a claim commit holding only the claim file, an epic's tasks going only to a worker whose area fits (the planner's code does not check areas) and work waiting behind a blocker ([DESIGN.md:144-150](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/DESIGN.md#L144-L150)).

## Against the original CooperBench work

CooperBench tested the opposite of Symphony's design, and coordbench is built to compare the two on CooperBench's own task pairs, but its real run has not happened yet.

[CooperBench](https://arxiv.org/abs/2601.13295) ("Why Coding Agents Cannot be Your Teammates Yet", January 2026) has 652 tasks from 12 repositories in 4 languages; each task is one repository state and two features with hidden tests ([research.md:23-25](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/docs/research.md#L23-L25)). Its pairs did markedly worse than one agent doing both features ([research.md:33-38](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/docs/research.md#L33-L38)).

|  | CooperBench's Coop setting | Symphony, and coordbench's sdlc arm |
| --- | --- | --- |
| Who does what | Each agent is handed one feature | Workers claim issues from a queue; in the benchmark each feature is an issue |
| Workspace | Own container and branch; neither sees the other's code | One shared remote; every claim, plan and draft pull request is visible |
| Channel | Free-text messages only, at most 100 actions per agent | The board, claim files and pull requests, with messages too |
| Integration | Two patches merged once, at the end | Continuous: "main moved" notices, and a gate that lands only a clean merge with main as it is now |
| Score | The merged code passes both features' hidden tests; for the paper's numbers, a conflicting merge was retried as a union merge, then by a learned resolver | CooperBench's own scorer at commit 63b9d44, which on a conflict tests the first agent's patch alone, unlike the rule behind the paper's numbers |
| Result | Claude Sonnet 4.5: 47.1% solo, 25.8% as a pair; GPT-5: 48.3% and 28.1% | Not measured yet |

Sources for the rows: [research.md:28-36](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/docs/research.md#L28-L36), [coordbench README.md:120-130](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/coordbench/README.md#L120-L130), [PARITY.md:87-122](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/PARITY.md#L87-L122).

What else the paper found, and what it did not test ([research.md:39-57](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/docs/research.md#L39-L57)):

- Messaging neither helped nor hurt success; it cut merge conflicts and took up to 20% of steps.
- More agents did worse: 68.6% with 2, 46.5% with 3, 30.0% with 4, on 46 tasks.
- It never tested a shared workspace, so its result is that agents talking blind do worse, not that collaboration hurts.
- The authors' later ablation (one model, 50 pairs, one seed, not peer reviewed) did test one: messages only 26%, solo 48%, a shared git remote 56%, a team with a lead and a shared task list 62%. Symphony's design is those last two: shared branches, plus a coordinator that plans epics the way the team's lead did ([WORKERS.md:27](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/docs/agents/WORKERS.md#L27), [34-42](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/docs/agents/WORKERS.md#L34-L42)).

coordbench's run is pre-registered ([PLAN.md](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md)): 50 pairs from 20 tasks, five arms (sdlc, solo, coop, coop-git, team), Claude Sonnet 5.5 for every agent, 120 minutes per agent, one seed ([19-49](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L19-L49)). The primary test is sdlc against coop on CooperBench's own pass verdict, by an exact McNemar test ([89-112](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L89-L112)). At 50 pairs it can detect a gap of about 25 points; a 10-point gap will show only as an estimate with its interval ([128-134](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L128-L134)). The paper's own numbers came from other models and harnesses, so they sit beside coordbench's for orientation only ([138-142](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L138-L142)).

## Against other agent coding work

Symphony's closest relative is Anthropic's C compiler experiment, which claimed tasks the same way, through git; what sets Symphony apart is that its coordination rules are written down and checked, and what it lacks is any outcome data.

| Setup | How work is split and claimed | How work is merged and checked | What it showed |
| --- | --- | --- | --- |
| [SWE-bench](https://arxiv.org/abs/2310.06770), with systems such as [SWE-agent](https://arxiv.org/abs/2405.15793) and [Agentless](https://arxiv.org/abs/2407.01489) | One agent, one issue; nothing to split | One patch, judged by hidden tests | One agent's skill on real issues; a fixed localize, repair and validate pipeline was the best open-source result on SWE-bench Lite in July 2024 (27.3%, $0.34 an issue) |
| [MetaGPT](https://openreview.net/forum?id=VtmBAGCN7o), [ChatDev](https://arxiv.org/abs/2307.07924) | Role agents (product manager, architect, engineer; CEO, CTO, programmer) follow a set procedure to build one program | Inside one process, by documents and chat between roles | Roles and procedure for one small program; no concurrent writers to one repository, so no claims or merges to solve |
| [CooperBench](https://arxiv.org/abs/2601.13295) | Each of two agents is handed one feature | Isolated, messages only; two patches merged once, judged by both features' hidden tests | Pairs reached about half of solo's success |
| [Anthropic's C compiler](https://www.anthropic.com/engineering/building-c-compiler), February 2026 | 16 agents; a task is claimed by committing a lock file to a shared git repository, and git makes the second claimant pick another | Each agent merges the others' work and pushes straight to the shared repository; tests, and later a CI pipeline | Nearly 2,000 sessions and $20,000 built a 100,000-line compiler that builds Linux 6.9 on three architectures; 16 agents gained nothing on one giant task, the Linux kernel, until a GCC oracle let them split it |
| [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams), experimental | A lead session and teammates on one machine share a task list; claiming uses file locking | Teammates message each other; hooks can gate quality; two teammates editing one file overwrite each other | Best when teammates work independently; for sequential or same-file work one session does better, and tokens grow with each teammate |
| [Anthropic's multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), June 2025 | A lead agent hands research subtasks to subagents | The lead combines their results | Beat a single agent by 90.2% on an internal research eval; such systems use about 15 times the tokens of a chat, one agent about 4 times; token use alone explained 80% of the variance on BrowseComp; most coding work is less parallel than research |
| Cursor's long-running agents, January 2026 (from memory: cursor.com is blocked here, so not re-read) | Hundreds of agents; flat self-coordination with locks stalled, and optimistic writes made agents timid | Planners write tasks, workers finish them without talking to each other, a judge decides whether to go on | A planner and worker split worked where locks alone did not |
| Symphony | Any worker claims a GitHub issue by the first push of a branch; a coordinator plans epics into tasks | Draft pull requests, "main moved" notices, a merge only with the required check green | Coordination rules model-checked; outcomes not measured yet |

[MAST](https://arxiv.org/abs/2503.13657) ("Why Do Multi-Agent Systems Fail?") is a taxonomy of why multi-agent LLM systems fail, released with a dataset of over a thousand annotated traces; it studies failures rather than offering a setup, so it has no row.

Where Symphony sits:

- **Same lock, made durable and shared.** The C compiler's lock was a file in one bare repository that every agent's container mounted; Symphony's is a branch on GitHub, so sessions, routines and Actions on different accounts can share it. The post describes no timeout for a lock whose holder stops; Symphony's 24-hour release is one.
- **Answers to known failures, untested.** Leases answer Cursor's locks held too long, and planning an epic into tasks that own disjoint files answers the compiler's one giant task and agent teams' same-file overwrites. Whether they work is exactly what coordbench has not measured yet.
- **Checked rules are the distinctive part.** None of the other setups publishes guarantees about its coordination layer: the compiler post calls its harness "a very early research prototype", and the agent teams docs list known limitations around task coordination.
- **Outcomes are the missing part.** Every other row reports success, cost or both; Symphony reports neither yet.

## What is not measured yet

No number yet says whether Symphony makes agents finish more work, or cheaper work, than any alternative; four things would start to.

1. **The benchmark.** coordbench's pre-registered run: 50 pairs under five arms, sdlc against coop first. The survey that fixed the pairs is done (tag survey-1, [PLAN.md:19-27](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L19-L27)), and a real dispatch waits on the owner's setup steps ([README.md:185-207](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/README.md#L185-L207)). The one real pair on record is a smoke run of the coop arm, which did not pass and says nothing about Symphony ([first-real.html](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/first-real.html)).
2. **A second seed.** One seed at 50 pairs separates only large gaps; a second seed on the pairs where arms disagree is the planned follow-up ([PLAN.md:128-134](https://github.com/OpenSpineConsortium/coordbench/blob/5e4860e4a2157f4ef14397f877fd9c3dccd81a14/bench/cooperbench/PLAN.md#L128-L134)).
3. **Live GitHub.** The canary checks what no local world shows, such as two pushes of one claim at the same instant; its first run waits on adopting the canary repository ([README.md:66-70](https://github.com/OpenSpineConsortium/symphony-protocol/blob/b5f098d3851b24e2611bb5474c964c5695e28c86/validation/README.md#L66-L70)).
4. **Real projects.** The field metrics are built to set work done alone beside work done in parallel, with what each cost, in adopted repositories ([WORKERS.md:59](https://github.com/OpenSpineConsortium/symphony-template/blob/8f69c4056e98c6ef3549496209a1239e6d1b65ec/docs/agents/WORKERS.md#L59)); no results are reported here.

Matched budgets matter when these run: in Anthropic's research system token use alone explained 80% of the variance, so an arm that spends more can look better for that reason alone ([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)).
