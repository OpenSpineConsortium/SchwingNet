# The textbook as a claude.ai artifact: why the book goes to claude.ai, and from where

Source: the textbook thread of 2026-10-24 (issues #233 and #236), the owner's decision card of 18:15 UTC and the change of plan of 18:42 UTC, and the same thread's decision cards of 2026-10-25 at 02:52 UTC (issue #277) and 04:28 UTC (issue #294); the measurements were taken from the cloud session's container on 2026-10-24 and 2026-10-25 and are quoted here, with no transcript.

## The question

The owner asked on 2026-10-24 for the artifacts themselves in the book, interactive, not screenshots (#233), and then for the book itself to live on claude.ai with Claude inside its pages (#236). Two ways were open: bring the live claude.ai artifacts into the members-only Pages site, or take the book to claude.ai as one artifact. Which of the two is possible decided the design.

## The finding: a live artifact cannot be framed from anywhere else

On 2026-10-24 the cloud session fetched the headers of a live artifact page from this container with curl. The page answers `content-security-policy: frame-ancestors 'self' chrome-extension://fcoeoabgfenejglbffodgkkbkcdhcgfn chrome-extension://dngcpimnedloihjnnfngkgjoidhnaolf`, and the artifact's own content is served from a per-artifact frame origin, `<uuid>.frame.claudeusercontent.com`, which the claude.ai page frames. A browser obeys frame-ancestors before it renders, so a page on any other origin, the Pages site included, gets a blank frame; the two extension ids name Anthropic's own browser extensions, which a web page cannot borrow. Nothing a repository holds, no token, no header and no proxy of ours, changes that, and the project keeps no server. Grade: Measured, by the header read on that day; it holds until claude.ai changes its policy.

So #233 embeds the exported copies under artifacts/ in the Pages site, in sandboxed iframes, and #236 goes the other way round: the whole site, with the exported pages inside it, is published as one multi-page artifact, where the exported pages are pages of the same artifact and open as themselves.

## Where the publish may run

Three places were tried or weighed.

- A cloud session, publishing with its Artifact tool. On 2026-10-24 the session's safety guard refused the publish of the built edition as data exfiltration, even with the owner's decision card in the conversation: the edition is the whole confidential book, and a guard that reads a hundred megabytes of patent material leaving a repository for a hosted page refuses it whatever the person says. A retry from the cloud on the owner's own words was not tried.
- The owner's machine, by a slash command a session runs there, the first plan of #236. It works, and it puts the republish after each merge in a person's hands or a routine's.
- A GitHub Action, the owner's choice at 18:42 UTC: on every push to main that changes the book, from a session anthropics/claude-code-action runs on the repository's Claude token, the subscription token already kept for the synthesis reads (the one exception to the rule that no Claude credential is kept anywhere, the owner's choice of 2026-10-23). Nobody is present, nothing of the book is read by a person, and the artifact lands in that account's gallery, private until shared.

What the Action cannot prove before it runs: that claude-code-action's headless session carries the Artifact tool at all. The tool is part of Claude Code's cloud and desktop surfaces; whether a `claude -p` run in Actions under a subscription token has it is answered by the first run. The prompt tells the session to print ARTIFACT_TOOL_MISSING if it does not, the helper fails the run on that line, and nothing is recorded, so a missing tool costs one failed run and the design falls back to the owner's machine.

## What the first run found, 2026-10-25

The owner's Run workflow at 01:42 UTC (run 40151692244) built the edition, planned three batches (442 files) and started its session, Claude Code 2.1.299, which claude-code-action v1.0.249 runs through the Agent SDK with the Artifact and Read tools allowed and the user's settings alone. The session answered ARTIFACT_TOOL_MISSING in one turn: the tool was not among its tools, allowed or not. Nothing was published and nothing recorded. Grade: Measured.

Claude Code's own documentation gives the reason (code.claude.com/docs/en/artifacts.md, section Availability, read on 2026-10-25): artifacts need a session backed by a claude.ai account on a paid plan, the Anthropic API as the provider, an organization without CMEK, HIPAA or zero data retention, and a surface that carries them, the CLI, the desktop app, Claude Tag or a remote-control session the person started; they are off by default in the Agent SDK, the GitHub Action, MCP-server contexts and `claude -p` run from one's own scripts. The settings reference says `enableArtifact: true` is the same as leaving the key unset, so no setting turns the tool on where the surface leaves it off, and claude-code-action's action.yml has no input for it. So no workflow publishes the book, from this repository or any other. Grade: Documented, and agreeing with the measurement.

What can publish it is a Claude Code session signed in to the owner's account: on the owner's computer, the first plan of #236, or a scheduled task on that account, whose cloud sessions run in auto mode and may publish an artifact once the classifier allows it (code.claude.com/docs/en/routines.md). A publish that declares runtime capabilities, as the edition's first publish does for the Ask Claude box, is asked of the person, or in auto mode put to the classifier, which refused this publish in the cloud session of 2026-10-24; a new artifact published in answer to a prompt the person types needs neither (artifacts.md, When Claude Code asks before publishing). Which of the two is the owner's choice, put on a decision card on 2026-10-25.

## The route chosen, 2026-10-25

The owner chose on that card, at 02:52 UTC, to publish from the owner's computer: one command, run in a clone of the repository on a computer where Claude Code is signed in to the account that keeps the book, a new edition whenever the owner wants one, never automatic (#277). `python3 tools/textbook_publish.py local` does every step but the publish itself. It fetches main, reads the record from the branch textbook-artifact into a small bare repository of its own in the work folder, and stops where the book's inputs at main's head are the ones already published. Otherwise it builds the site and the edition with that commit's own builders, in a worktree made in the work folder, plans the batches, writes the prompt to prompt.txt and opens Claude Code in the work folder on one line that sends it to the prompt. The session publishes with its Artifact tool, writes its marker lines to answer.txt, the one file it may write, and tells the person to type /exit; the command then records the edition, a fast-forward commit on the branch from that bare repository, and prints the link.

Why the pieces are as they are. The work folder sits beside the clone and never inside it, so the session there loads none of the repository's instructions, hooks or settings, as the Action's session ran with the user's settings alone. The record leaves from a repository of its own because the clone's pre-push hook runs the gate on the checked-out tree and refuses to push any other commit, and the record's one file is no part of that tree. The builders run in UTF-8 mode, as on CI, since the owner's computer may run Windows, whose default encoding is another. Where Claude Code is not found, or with --no-launch, the folder is left ready and the command prints the two steps to take by hand: the line typed in Claude Code there, then `local --record`. With --anyway it publishes an edition whose inputs are already published. The workflow went with the choice, since no run of it could publish. Grade: Measured for the steps, against a bare repository standing in for GitHub (tests/test_textbook_publish.py), and for a dry run of the build from main on 2026-10-25 (453 files, 108.5 MB, three batches, 9.4 seconds); the publish itself is measured by the owner's first run.

## The reader, chosen 2026-10-25

The owner chose at 04:28 UTC, on a decision card, a reader over this project's files (#294): what Claude publishes is one small page it reads in full, and the book stays in the files of the Claude project the textbook thread belongs to, from where the page reads it when it is opened, with the viewer's own access, through the artifact runtime's files capability. Nothing of the book is in the page or in the artifact's versions, and a viewer who cannot open the project's files reads nothing.

How it works. A thread of the project, whose files are mounted at /mnt/project-files, runs `python3 tools/textbook_reader.py stage` after the book changes on main: it builds the site and the edition with main's own builders, as the publish did, packs the edition into two files, book-<commit>.bin, every file of the edition one after another in the order of their paths with the text gzipped where that is smaller, and book-<commit>.json, which says where each file lies, its type and its sha256, copies both into textbook/ of the project's files, reads each back after a pause, since the folder is a network mount, and writes the pointer CURRENT.json last, so a reader never finds an edition half copied. The edition before stays, so a reader open on it reads on until it is reloaded, and older ones are removed once they are an hour old. A stage whose book inputs are the ones the pointer names copies nothing. The page, tools/textbook_reader.html, 39 KB in 838 lines of ASCII, declares the files capability for this project and sample. Opened, it finds textbook/CURRENT.json among the project's files, reads the index, and takes each page's bytes by its span, a page with its stylesheet, pictures and figures in a few reads. It shows the book's own pages in a frame of its own origin that it hands its window.claude, so their Ask Claude box and the search of the book work as they did on the edition, what they pass to sample made again in the reader's own realm, since a runtime that checks what it is given by instanceof would refuse a frame's own arrays and abort signals, and the figures and exported artifacts sealed, in sandboxed frames with their files inlined, as the Pages site frames them; it keeps at most 64 MB of what it read and lets the oldest go. Where it cannot serve the viewer it says why: no files capability on this page, access declined, no access to the project's files, no copy staged, a copy of another format, or a copy replaced while it was read. `python3 tools/textbook_publish.py local` now publishes the page: it takes the page from main's commit, stops where that page and its capabilities are the ones already published, and opens Claude Code on a prompt that has it read the page whole and then publish it, recording the link on the branch textbook-artifact. The page is published again only when it changes, never when the book does.

The reader declares no connector. The edition declared the GitHub connector's two tools behind a figure's Run as me (docs/research/experiments-panel.md, section 4); in the reader a figure's Run as me answers "no connector", and the figure's prefilled issue and the workflow's link stand in, as they do on the Pages site.

Grade: Measured against a stand-in of claude.ai's runtime in Chromium (tests/reader_stand_in.py, tests/test_textbook_reader_browser.py), with the real edition of main at ac9afa3, built at 04:19 UTC on 2026-10-25: 453 files, 108.7 MB unpacked and 86.0 MB packed, 41 of them exported artifact pages, the largest file 10.6 MB; the front page came up in about 0.3 seconds from four reads, and a chapter, its figures, the storage panel of chapter 22, an exported artifact's page, the dark theme and a phone's width were driven there. The stand-in follows the runtime's documented contract (the files capability's types of contract 0.2.90: a listing of at most 500 entries a page, reads of at most 25 MiB, errors by code); how claude.ai's own frame and runtime behave beyond it is measured only by opening the reader there.

## Why an Action was the first plan, and why a schedule beside it

This was the design until 2026-10-25 and is kept as the record of it; the workflow is gone (The route chosen, above). The repository is the source of the book, and the artifact is a copy that must not fall behind it, so the copy is republished by the thing that knows when the source moved. A push to main that changes the book starts the run; a merge GitHub's auto-merge makes starts no workflow, because automerge.yml arms it with the workflow token, and most of this repository's pull requests merge that way, so a schedule every half hour is the fallback that catches them, as synthesis.yml runs daily for the same reason, and docs.yml did until the owner made it run only on the owner's call on 2026-10-25. The schedule is kept cheap by a fingerprint: the sha256 of git's listing of the book's inputs at the commit (the chapters and figures, artifacts/ with the synthesis's records, the site's and the edition's code, the stylesheet, CODEOWNERS), kept in the record, so a scheduled run that finds the fingerprint already published stops before building. The day is capped (TEXTBOOK_PUBLISHES_PER_DAY, 12, at most 50) and the switch TEXTBOOK_ARTIFACT set to off stops it.

The record is the metrics branch's pattern (a commit built from the files alone, never replacing a branch that holds other files) with one change: each commit is a fast-forward on the branch's head, so the branch's history is the publish log and the day's publishes are counted from it, which needs no run list and no marker artifact. The session itself holds a read-only token and the Artifact and Read tools alone; the job that writes the record runs no session.
