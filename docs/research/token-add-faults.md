# Add Token faults of 2026-10-18

Source: the project thread "Add token faults" (greg's report of 2026-10-18, relayed by the coordinator), with the Control panel sign-in thread's diagnosis. Read from issue #222 and the logs of the Token workflow's runs 1 to 7 on this repository, and from `claude setup-token` 2.1.302 run in a cloud container behind tools/token_run.py's own pseudo-terminal with a made-up code, which no account can redeem.

## 1. A repository whose adoption is not merged

Ashley's repository, aschehr/OpenSpineToolbox-S1fix-2Dprojection, had its adoption pull request open, so its default branch had no .github/workflows/token.yml. The page opened an issue there, then the dispatch answered 404, and the page's hint told her to "pick symphony-template in the Repository box", which is the wrong advice for someone adding a token to her own repository.

The fix (site pull request "Tokens: say to merge the adoption first, and never strand Add Token"): the page reads `GET /repos/{repo}/actions/workflows/token.yml` before it opens the issue, so such a repository gets no stray issue, and on 404 says the workflow comes with the adoption and to merge the adoption pull request first, linking the open one from the branch symphony/adopt where there is one.

## 2. Add Token stuck after the dialog was closed

greg's press opened issue #222 and started run 39165163409, which posted the sign-in link at 20:51:01, 18 seconds after the run began. The page never showed the Sign in button, and Add Token did nothing afterwards. Three things in symphony-panel.js combined:

- GitHub answers an issue's comments with `Cache-Control: private, max-age=60`, so the browser served the page's first, empty read of the comments for up to a minute: the link could reach the page as much as a minute after the run posted it.
- Close only hid the dialog, and the poll went on for up to 15 minutes with the Add button disabled. Pressing Add Token opened the settings form, which cleared the dialog, so the sign-in view the poll drew into was no longer on the page; its Save and sign in then returned at once on the disabled button, and nothing showed.
- Nothing could stop the poll.

The same pull request reads the comments at an address of its own each time, so no cached answer is served; remembers the sign-in under way, so Add Token (or Renew) shows its dialog again instead of a dead form; and adds a Stop this sign-in button, which ends the poll, closes the issue as not planned and frees Add Token. The stop is hidden once the sealed token has arrived, so it never cuts the save of the secret short. An adversarial review of the change found that a stop which waited for the call on its way could wait for good, since the page leaves a call unanswered once it has signed out, so the stop frees Add Token at once and a sign-in begun before a sign-out is let go; the Add Token tile reads Sign-in waiting while one is under way; the dialog names the repository and says when another sign-in holds it; a 404 first asks whether SymphonyBoard reaches the repository at all; and a workflow Token that is turned off is said so, with its page, before any issue is opened.

## 3. Why runs 1 to 6 printed no token

Every run posted its sign-in link within about 15 seconds. Then:

| Run | Issue | What happened |
| --- | --- | --- |
| 1, 3, 4 | 187, 195, 196 | no code came within ten minutes |
| 2, 5, 6 | 189, 201, 202 | the code reached claude, which showed it as 92 asterisks, and printed nothing more within the 60 seconds the run waits |

Runs 1, 3 and 4 fit fault 2: the page drew its sign-in where nobody saw it, or a second press (runs 3 and 4 began 33 seconds apart) left one of them waiting.

Runs 2, 5 and 6 are not settled. What is known:

- The code's length, 92, is a 48-character code, the `#` and the 43-character state, so the page passed it whole.
- In the container, the same script's paste and Enter reach claude 2.1.302: a made-up code of that shape draws "OAuth error: Request failed with status code 400. Press Enter to retry." within seconds, with TERM set, with TERM unset, with TERM=dumb and with CI=true. A wrong or used code would have said so in the runs' last words; they show no error and no "Long-lived authentication token created successfully!" either. So claude neither refused the code nor finished within the minute, or it drew something the run did not keep.
- Inferred, not yet measured on a runner: GitHub's runners set no TERM, and with TERM unset claude draws only the cells that change, words separated by cursor moves (`\x1b[20G`) in place of the letters already on the screen. A token drawn over earlier text in that mode would reach tools/token_run.py in pieces that tokens.Masker's whole-token shape does not match, so it would be counted as no token and a piece of it could pass the mask. The runs show no sign this happened, since even the success line is missing, but it is a reason to give claude a TERM.

On the owner's word of 2026-10-18 ("just fix it so she and other collaborators can add their tokens"), tools/token_run.py now gives claude TERM=xterm-256color where the runner sets none; whether that was the cause is for the next real run to show. The rest stays proposed: in .github/workflows/token.yml set `TERM: xterm-256color` for the step, and on failure have tools/token_run.py report counts alone (bytes claude printed after the Enter, whether claude was still running, whether the mask holds a tail back), never text, so the owner's next run either works or says which of these it was.

## 4. A 403 writing a slot on a personal repository

Later on 2026-10-18 Ashley's Add Token answered 403 "Resource not accessible by integration" with the hint for an organization. On a personal account's repository the slots are the repository's own secrets and variables (slotPlace in symphony-panel.js), and Save and sign in writes the variable SYMPHONY_CLAUDE_SETTINGS before anything else. symphony-app's manifest.json grants the App the repository permission Secrets (write) and the organization's Secrets and Variables, but no repository Variables (actions_variables), so that write is refused on every personal repository, whoever presses. Inferred from the manifest, since no session can read the App's live settings. The site (pull request 68) now names the repository permissions in the hint for a personal repository; the App needs the repository permission Variables: read and write added in its settings, and each personal installation's owner accepts the new permissions.

## 5. The first token minted, and who may write the pool

Run 8 of the Token workflow (issue #228, started 22:00 UTC on 2026-10-18 by the owner, before the TERM change merged) posted its sign-in link, took the code and sealed the token, and the page saved it as slot 1. So runs 2, 5 and 6 did not fail for want of a terminal type alone, and the minting works as built; the TERM change stays as a guard.

Ashley's 403 has a cause no App setting removes: the Tokens page writes a slot as the person signed in, and GitHub lets only an organization's owners write its secrets and variables, and only a repository's administrators its own. She is neither an owner of OpenSpineConsortium nor a collaborator on symphony-template, which the page's old 404 hint told her to pick (inferred: the page's error does not name the repository). ## 6. A collaborator's token into the organization's pool

The owner chose on 2026-10-18 ("Yes, free slots") to let someone who may write to an organization's repository, but is not an owner of the organization, add their own Claude token to its pool. Since GitHub refuses such a person every write of an organization secret or variable, the Token run does the writing itself: the page dispatches token.yml with `store: pool` and no key, and the workflow's job store, in the environment token-store, mints the SymphonyBoard App's installation token for the organization (organization secrets and variables, write) and runs tools/token_run.py with it. The script, once the token is minted, lists the organization's secrets and puts the token into the first slot of SYMPHONY_CLAUDE_1 to 32 that holds none, visible to the repository the run is in; adds the slot to SYMPHONY_CLAUDE_ACCOUNTS; marks it in SYMPHONY_CLAUDE_SETTINGS with the person as its owner and a new id; and posts only the slot's number on the issue. It never writes a slot that holds a token, and a settings variable that is not JSON by slot is left for an owner to mend rather than written over. Neither the run's GITHUB_TOKEN nor the App's token reaches claude's environment.

What holds it to that, after an adversarial review of the change on 2026-10-18:

- The job's script is the default branch's only where the environment token-store allows the default branch alone, which an owner sets (Settings, Environments); otherwise anyone who may write could dispatch the workflow from a branch of their own with a script that does anything the App's token allows.
- The environment fences the script, not the App's key. SDLC_APP_PRIVATE_KEY is an organization secret that ci.yml and template-init.yml read outside any environment, so anyone who may write to a repository it reaches can already run a branch workflow that uses it, and the App's organization secrets permission, which this change uses and the manifest already lists, makes that a way to overwrite any slot. The pool is only as safe as the key: the fix is the key held as an environment secret of token-store and not reachable elsewhere, or a separate App for this job; that is the owner's choice, and until it is made the store adds no exposure the key did not have.
- The App's token is minted only after claude has gone, since a process can read its parent's environment however the child's is trimmed: the sign-in step holds the token in a file of the runner's temporary folder readable by the runner's user alone, the next step mints the App's token, and the store step reads the file, deletes it, and stores the token; a last step deletes it whatever happened. The checkout keeps no credential in .git/config.
- The App's token carries every permission the installation has, since actions/create-github-app-token v3 has no input for the organization's variables.
- A run that stops before the script can say why (the App's token refused, the environment withholding the job, an install that failed) posts the failed mark from a step that runs on failure, and a repository in crowd mode answers through a job of its own, so the page hears at once instead of after fifteen minutes; an error the script did not foresee is posted by its kind alone.
- The slot is asked for once more just before the write, so a slot another run took since the list is never written over; the window left is the moment between that read and the write. SYMPHONY_CLAUDE_ACCOUNTS is read back after the write and written again where an owner's page took the slot away at the same moment.
- An owner whose membership GitHub would not show keeps the owner's path on the page.
- Not fixed, and older than this change: the page takes the first sealed comment by github-actions[bot], and any workflow someone who may write runs can comment as that bot, so a branch workflow could answer an owner's sign-in issue with a token of its own choosing, which the page would save. The key's inputs are visible in the run's page, so a nonce passed the same way would not help; it needs the run's own identity checked, for the owner's decision.
- A collaborator can change or remove their own slot's settings from the page only as an owner can today, so the page shows them the slot as theirs and leaves its settings to an owner.

## 7. One token per person, lent where they choose

The owner asked on 2026-10-19 for a person's token to belong to the person, not to the repository they pressed Add Token in, and to be lent to as many or as few repositories as they like and taken back at any time. GitHub has no per-person secret that Actions can read: a user's own secrets are Codespaces secrets, which no workflow sees. An organization secret whose visibility is "selected" carries its own list of repositories, and that list is a lend list, so a person's token is one slot of the organization's pool whose settings name them as its owner.

- Add Token in a repository first asks whether the person already owns a slot; if so the run lends that slot to the repository (adds it to the secret's list, and to the lists of SYMPHONY_CLAUDE_ACCOUNTS and SYMPHONY_CLAUDE_SETTINGS so the workers there read the slot) and makes no new token. The App's token for that look is revoked by the script before claude starts. Only when the person owns none does the sign-in run and store a new token, lent to that repository alone.
- Your token on the page asks the run where the token is lent, takes it back from one repository, or deletes it, each a short run with no sign-in that touches only the slot whose settings name the person who started it. The run posts the repositories by id, never by name, and the page names those the person can see.
- A repository of another organization or of a personal account cannot see an organization's secret, so a token there is a second token, made by a second sign-in; Claude gives an account as many setup tokens as it asks for.
- An owner of the organization still sees and changes every slot directly, as before.

An adversarial review of this change found no way to reach another person's slot, and these, now fixed: the look step fails, and the sign-in after it is skipped, where the App's token cannot be revoked before claude starts; a deletion clears the owner's mark before the secret, and a new token is marked as its person's before it goes in, so no free slot is ever left marked as someone else's; a slot keeps the account's numeric id beside the login, since a login passes to whoever takes it after a rename or a deletion; a slot or variable an owner set to private repositories only is said so rather than reported as lent everywhere; a second sign-in at the same moment makes no second token; and the page runs one Your token action at a time and reads the tiles again after it.

## 8. Lending from outside: members, strangers, a public front repository

Thread "Add token fixes", 2026-10-19. The owner asked that lending be open to members of an organization or enterprise and not only to collaborators, that anyone be able either to ask to join or simply to lend a token "without any say in how it is used", that both be possible from the Symphony extension without ever seeing the control board, and that a public front repository in an organization take the tokens that the organization's private repositories then run on.

What already holds. The Tokens page never asked for collaborator status: it asks GitHub whether the signed-in person may push to the repository, which a member of the organization or of a team has through the organization's base role as a collaborator has by name. The board itself needs nothing new to stay out of a stranger's sight: every page reads the repository with the person's own token, and a private repository answers nothing to someone without access.

What stops a stranger today is GitHub, not the page: a workflow dispatch is taken only from someone who may write, and the lend and manage jobs run on a dispatch. So a person with no role can open an issue on a public repository and nothing else. The design turns that around and makes the issue the whole interface.

### The issue is the interface

- The front repository is a public repository of the organization that carries the template's token.yml (the organization's own copy of the template, or a repository adopted for the purpose). A lend is an issue opened there whose first line is `<!-- symphony-token: lend -->`; a list or deletion of one's own token is an issue whose first line is `<!-- symphony-token: manage -->` with the action on its second line. The workflow starts on `issues: opened` as well as on a dispatch, with the issue's author as the actor. The run posts the sign-in link as a comment, the person presses it on the issue page itself, signs in on claude.ai, and pastes the code back as a comment, which only the author's comment counts as; the run stores the token and closes nothing it did not open. No page of ours is needed: GitHub's issue page shows the link and takes the code.
- The Symphony extension's part is a button, "Lend my Claude token", on the organization's or the front repository's page, which opens GitHub's new-issue page with the title and the marked body filled in (github.com/OWNER/REPO/issues/new?title=...&body=...), the person pressing Submit; and, on an issue the run has answered, a button that opens the sign-in link, as the extension already turns an install link into a button. The extension holds no token and calls no API, as its privacy statement promises; the issue page is GitHub's. A second button, "Ask to join", opens the same page with the access request's mark (Asking to join, below, built on the site first). Both ship as an extension release, which a merge to its main submits to the Chrome Web Store, so the extension's privacy statement takes the two buttons first.
- The run's job in the environment token-store holds the App's key and runs on an issue anyone may open. That is the step the session's safety check refused to write without the owner's own words; the owner gave them on 2026-10-19 ("Yes that's fine, it can start on an issue anyone can open"), and token.yml now starts its pool jobs on `issues: opened` with the issue's author as the actor, the marks above deciding which job, the run closing the issue when it is done, and a bare code pasted on the issue counting as the page's marked one does. The worst a stranger can do is fill the organization's free slots with their own tokens, which an owner deletes from the Tokens page, and start runs that cost the organization Actions minutes, which GitHub's own spam limits bound. In crowd mode the job still never runs.

### Lending without any say

- A lender who wants no say lends to the organization, not to a repository (the issue's second line says `organization`): the run stores the token in a free slot marked as theirs, with `"keeping": "organization"` in its settings, and lends it to the repositories a standing list names, the organization variable `SYMPHONY_LEND_TO`, a comma list of repository ids that an owner sets once from the Tokens page ("new lent tokens run on these"; a list that is not ids stops the run with a word for the owner). The front repository need not be on it; the private ones are. The run, which holds the App's token, adds those ids to the slot's secret and to the two variables' repository lists, so the workers in the private repositories read the slot on their next run with nothing done by hand (the owner's rule: no per-person steps). With no list yet the token is lent nowhere, for an owner to place.
- Such a lender is told only that the token is in the organization's keeping: the run posts `organization` in the lent mark's place for the ids, for a new token and for one of theirs that a no-say lend touched, since the lender cannot see the private repositories and should learn nothing of them from a list. Delete still works for them, since the token stays theirs: the slot's settings carry their login and numeric id, and the manage run touches only that slot. Built in the template beside this note (token_run.py: request, no_say, standing_list, Keeper.mark_keeping); the Tokens page's words for it and the owner's box for the standing list are the site's next change.
- A repository of the organization that has no workflow Token of its own, as one adopted for the protocol alone has not (the owner met this on 2026-10-19 pressing Add Token on the grant's repository, which answered that token.yml was not there), takes a token all the same: the Tokens page looks for a repository of the organization that carries the topic symphony, that the person may push to and that has the workflow, opens the issue there and dispatches the run with the input `lend_to`, the id of the repository it shows, and the run lends the token there (token_run.py: lend_target). The id is checked against the organization through the App's token, and so is the lender's right to write there, which a dispatch on that repository would have needed, so nobody plants a token in a repository that is not theirs; and only a dispatch carries it, so an issue-started run lends only to its own repository. The grant's repository gets no workflow of its own, since its files are not Symphony's to carry.
- A lender who wants a say (a collaborator of some repository) keeps section 7's path: Add Token in the repository they are focused on lends there alone, and Your token lists and takes back by repository.
- An owner sees every lent slot on the Tokens page with its lender's login, lends it to more private repositories or takes it off one (the slot's repository list is an owner's to write through the page already), and deletes it.

### Asking to join

A request to join is an issue whose first line is `<!-- symphony-access: request -->`, opened by the person asking; the Share tab lists the open ones at the top with Invite and, on the card's X, Decline, and either closes the issue with a word, which GitHub tells the author. Built on the site on 2026-10-19 beside this note: the Share tab shows "+ Ask to join" to someone it refuses to show the people to, and the Tokens page's Add Token offers the same to someone without write. In an organization, Invite gives Write on that repository; an owner who wants the person on the private work invites them there, or into the organization from GitHub's own page. Collaborator status is what shows the board: nothing hides it on purpose, and a private repository hides itself.

### What the review of the privacy statement found, 2026-10-19

The control panel's sign-in thread had the Apps' privacy statement version 30 reviewed against the pool's code, and five findings came to this thread; the owner, asleep, asked that the recommended fixes be taken. Each is a pull request of its own.

- A revoke or a delete took the token off a repository and left the two variables SYMPHONY_CLAUDE_ACCOUNTS and SYMPHONY_CLAUDE_SETTINGS on it, so a repository that no longer ran on anyone's token still read every lender's login and account id. Now a revoke, and a delete for each repository the slot reached, take the two variables off a repository that no other slot reaches (Keeper.reached_by_another, unlend_variables), a slot on in every repository or in the private ones counting as reaching it. The variables' values still show in the logs of a public repository's runs wherever a workflow hands them to a step through env, since GitHub prints a step's env and masks secrets alone, and a repository's GITHUB_TOKEN cannot read an organization variable at run time; what they show is each lender's login, account id and model settings, which the Tokens page shows to anyone with write access already. Keeping them out of the logs would mean a secret in the variable's place, which the page could not read back; that is a design question for the owner, not a fix.
- A delete wrote the owner's mark away first and the secret last, so a run cut short between the two left a token nobody owned and its lender could no longer delete. The secret now goes first; a mark left on an empty slot is harmless, since own_slot needs the secret too and the next store writes the mark over, and a store that takes the freed slot between the two keeps its own mark, since the delete removes the mark only while its id is the deleted token's and takes the slot off the accounts list only while no secret is in it again. A second review found that a delete or a revoke run from a repository the token never reached put that repository on the two variables' lists, through the write that changes their value, and that the reach was read once for each repository, about 65 calls each; the value is now written without touching the lists, and the other slots' reach is read once a run. A store keeps its order, the mark before the secret, for the reason its comment gives: a token is never in a slot under another's mark.

### Keeping, and what the App's token can be narrowed to, 2026-10-19

Two more findings of the review of the Apps' privacy statement version 30, taken as recommended while the owner slept.

- A token in the organization's keeping was still lent by a plain lend to the repository its lender picked, and its lender could still revoke it from a repository, though mark_keeping's word is that only delete stays theirs. Now a plain lend of a kept token lends nothing more and answers "organization", a lend with no say still places it where the standing list says, and a revoke of it is refused with a word that delete is still theirs.
- The review asked that token.yml's three App tokens be narrowed to organization secrets, organization variables and issues. GitHub's App permission list (the REST description's app-permissions schema, read on 2026-10-19) names organization_secrets but no permission for an organization's variables, so a token narrowed by permission-* inputs would lose the variables the run writes, as token.yml's comment on the store step already says. The steps stay as they are: the look's token is revoked before the sign-in, the store's is minted only after claude has gone, and both live in the environment token-store. Narrowing waits until GitHub names the variables permission for a token request.
