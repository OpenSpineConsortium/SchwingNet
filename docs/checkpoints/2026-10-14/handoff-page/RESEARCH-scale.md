# Scale requirements: research of 2026-10-13

## Requirement 1

Requirement 1: every pull request an autonomous worker makes (a worker in Actions, the coordinator, a routine) must pass a required beethoven-qa gate before it merges and must come with beethoven-qa's evidence report for a person to review. It must also be possible to tell such a pull request from a person's.

### Recommended design

One required check, named `qa`, on every pull request into the default branch, a person's and a worker's alike. It runs beethoven-qa from beethoven-qa's own repository at a pinned commit and leaves the evidence report where both a person and a worker can read it. Nothing is decided by classifying the author; the report only says who opened the pull request.

1. beethoven-qa (built under its own gate, released as v6.0.0 and tagged; today only v1 to v3 are tagged). Add a composite action (action.yml at the repository root) and a command `python -m beethoven_qa qa`, offered as a new export in interface/INTERFACE.json.
   - Setup: the action installs pixi 0.81.0 by its sha256, then beethoven-qa's own locked qa environment at Python 3.12, from the action's directory. A composite action is the only way a caller reaches the provider's files (chrome-store-release-kit release-kit.yml:24-27).
   - Lanes, over the caller's checkout against the pull request's base (HEAD^1):
     (a) The repository's own test command, the action's one input, must exit 0. With no command named, the check fails ('no tests named').
     (b) The supply-chain group over .github/workflows/.
     (c) readability, design, duplication and security over the Python files the change adds or changes. Only new or worse findings block, and no table is needed.
     (d) Coverage of at least 80% of the new Python lines, where the tests run in the qa environment.
     (e) The CrossHair/Z3 gate, only where a [tool.beethoven-qa] table names a contracted package. A full consumer runs its own `pixi run --locked report` instead.
   - Every other lane is reported 'not applicable' with its reason, never 'passed'. Vendored files listed in a VENDORED or ORIGIN record are measured in the repository that writes them, not in each copy.
   - Output: report.md goes to $GITHUB_STEP_SUMMARY, headed by the pull request's author and kind. Every blocking finding becomes an `::error file=...,line=...::` annotation, which GitHub shows on the diff and serves through the check-runs API a worker reads with gh. The whole folder is kept as the artifact evidence-report.
   - It names no secret, starts no Claude Code, deletes nothing, and takes no input that loosens a limit.

2. symphony-template, and through the front door every adoption in both modes.
   - New file `.github/workflows/qa.yml`:
     - triggers: pull_request (opened, synchronize, reopened, ready_for_review) and workflow_dispatch;
     - `permissions: contents: read`, and a concurrency group per ref that cancels the stale run;
     - one job `qa`: actions/checkout@v7 (fetch-depth 0, persist-credentials false), then `uses: OpenSpineConsortium/beethoven-qa@<full commit> # v6.0.0` with `test: bash scripts/check.sh`.
   - Rulesets: ruleset-main.json, ruleset-org.json and ruleset-crowd.json require `qa` beside `check`.
   - protocol.yml and add-worker.yml dispatch qa.yml beside ci.yml.
   - The `check` job stays as it is, with no dependency.
   - Docs: claude-action.md, WORKERS.md, the Finish section of PROTOCOL.md, and one memory fact.

3. symphony-start.
   - adopt.py brings qa.yml in mode existing too, with the repository's own test command as the input.
   - scripts/setup.py keeps a required-checks rule naming `qa` in mode existing. Today it removes that rule.
   - The README says the check downloads pixi and its locked packages from conda-forge and PyPI, and sends nothing anywhere.

4. What a person does.
   - Per pull request, nothing. Before merging a worker's pull request ('lands': 'owner'), or afterwards ('auto-merge'), they open the qa run summary and read the report.
   - Once: answer the decisions below. While beethoven-qa is private, set its Actions access to 'Accessible from repositories in the organization'.
   - On each repository set up before this change: add `qa` to the ruleset by hand, then after its first run pin it to GitHub Actions (integration 15368).

How the report tells who made a pull request. Author claude[bot] means a worker in Actions or the coordinator. Any other author is a person's account; behind it, the claim file's '- Worker:' line and .github/symphony/workers/<name>.json, both written by the worker itself, separate a routine from the person's own session.

The rule this waives is the template's .claude/rules/writing.md:6, 'No new dependencies', for exactly one dependency: beethoven-qa's qa action pinned to a full commit, with the pixi environment its lock fixes, used only by the job `qa`. Open it as the issue the rule asks for. The same line's 'pinned to a major tag' still stands if a beethoven-qa release lets its supply-chain group accept a major tag for GitHub's own actions and anthropics/claude-code-action (decision 4); otherwise that wording is waived too.

### Decisions for the owner

- Require qa on every pull request, or only on autonomous workers'? Recommended: every pull request. GitHub cannot scope a required check by author, a skipped required job counts as passing, and routines, @claude and sessions open pull requests under your login. The report still names who opened each one.
- Waive .claude/rules/writing.md:6 'No new dependencies' for one dependency: beethoven-qa's qa action pinned to a full commit, with its locked pixi environment downloaded inside that one job? Recommended: yes, through the issue the rule asks for. The template's code and its `check` job keep the rule.
- Keep beethoven-qa private, or make it public with a licence? Recommended: public under MIT, like the adoption files, if the gate is to cover symphony-protocol, coordbench, symphony-start, symphony-marketplace, the site and adopters. If it stays private, the gate covers only the organization's private and internal repositories, and the README must say adopters get none of it.
- Action pins: which gives way, the template's major tags or beethoven-qa's full-commit rule? Recommended: a beethoven-qa release accepts a major tag for GitHub's own actions (actions/*, github/*) and for anthropics/claude-code-action, and keeps blocking every other unpinned action. The template's rule then stands, and no repository needs a bump pull request each time GitHub moves a runtime (the SHA-pinned checkout v4.4.0 already runs on a deprecated Node 20). The alternative is full-commit pins everywhere, bumped by hand.
- Which Python should the qa environment use? beethoven-qa pins 3.11 and Symphony's code needs 3.12. Recommended: a second locked qa environment in beethoven-qa at 3.12, leaving the engine's 3.11 environment alone.
- What happens where beethoven-qa has nothing to measure? Recommended: report the lane 'not applicable', never 'passed'. A repository that names no test command fails the check. A protocol-only adoption names its test command when it is adopted.
- Should autonomous Python code need contracts and the symbolic gate? Recommended: only in repositories that opt in with a [tool.beethoven-qa] table naming a contracted package. Everywhere else, the code standards plus coverage of new lines.
- Must a person approve an autonomous pull request before it merges? Recommended: no required approval. A solo owner can never approve their own pull requests, and these arrive under your login. The qa check decides the merge; the report serves whoever merges or audits.
- Extend beethoven-qa beyond Python? Recommended: yes for readability (lizard: complexity, lines, parameters) and duplication (jscpd) on TypeScript, JavaScript, Go and Rust, using tools already in its lock. Security and coverage stay Python-only until a tool is chosen.
- Pin the qa check's source to GitHub Actions (integration 15368)? Recommended: yes, once Actions has reported the check, both in the organization ruleset and by hand on each repository. The Setup App's single run cannot do this.
- Keep the strict 'branch must be up to date' policy at scale? Recommended: keep it. If merges pile up behind long qa runs, use GitHub's merge queue (public organization repositories, or private ones on Enterprise Cloud), with merge_group added to the qa triggers.
- Add qa to the CooperBench arm? Recommended: keep it out of coordbench's parity arms, which have no required check by design. If wanted, measure it as a separate arm, with the difference stated in PARITY.md.

### Risks

- Every pull request downloads pixi and the locked packages from GitHub releases, conda-forge and PyPI. An outage of any of them turns every pull request's qa check red, and nothing merges until it recovers or a person lifts the requirement.
- Vacuous passes: measured, four groups 'pass' over zero files. Unless the qa command reports 'not applicable' and its tests pin that behaviour, a green check means nothing on a non-Python repository.
- Until the qa environment moves to Python 3.12, coverage fails every template pull request (44 test failures measured under 3.11).
- Pins drift. A full-commit pin is never updated, so it falls behind the runner: the Node 20 warning on the pinned checkout, and ubuntu-latest moving to Ubuntu 26 from 2026-10-19. Adopters keep whatever pin they were adopted with.
- GitHub Free does not enforce a private repository's ruleset, so qa is only advice there.
- Rollout order: protocol-only adoptions require no check today. A default worker in Actions turned on before qa is required would auto-merge with nothing run. Existing rulesets are skipped by setup-repo.sh, so they must be updated by hand.
- A qa check whose source app is not pinned can be turned green by any writer posting a commit status, including a session on a person's token.
- Throughput: the strict up-to-date policy plus long lanes (symbolic takes 26 min on a 2-core runner) serialises merges, and concurrent jobs are capped (Team 60, Enterprise 500).
- The 5.0.0 report job failed on GitHub's runner for a cause that was inferred, not proven, and it ran for about 30 minutes. The qa action inherits that until it is measured on the runner.
- Vendored code: tools/sdlc_protocol would be measured in every copy. One measured finding is guard.refusal with cognitive complexity 32. Unless such code is measured upstream, a sync pull request blocks on code no copy may edit.
- Symphony's workers in Actions run Claude Code on a token, which Beethoven's repositories forbid. beethoven-qa can be the gate, but it must never host workers.
- The report's routine-versus-person line rests on the worker's own claim file. It informs the reader and must never decide anything.
- While beethoven-qa is private, every caller depends on its Actions access setting, and the organization's public repositories can never call it.

### Alternatives rejected

- Make every Symphony repository a full beethoven-qa consumer (pinned copy, pixi.toml and lock, the kit, contracts). The gate fails any package with nothing to prove, and Symphony's 49 Python files carry no contracts. The kit's automerge.yml arms auto-merge on every pull request opened ready, and its rulesets.yml needs a personal access token; both clash with the draft-first claim protocol, the per-worker 'lands' setting and the no-settings-as-code decision. Every update needs a person's gh sign-in. beethoven-qa itself gives standard-library repositories 'the repository half only' (CONSUMING.md:26-31).
- Require the gate only on workers' pull requests. Rulesets cannot condition on the author, and a skipped required job reports success. Routines, @claude and a person's sessions all open pull requests under the person's login, so exactly those would pass ungated. The only marker that separates them, the claim file's Worker line, is written by the worker and deleted when the pull request is marked ready.
- Use an organization ruleset workflow ('Require workflows to pass') as the only mechanism. It is Enterprise Cloud only, and a private workflow runs only on private repositories, so it reaches neither the public organization repositories nor any adopter. It could be layered later over the organization's private repositories, where workers cannot edit it.
- Use a reusable workflow (workflow_call) in beethoven-qa instead of a composite action. The required check would then be named '<caller job> / <called job>' with the second half defined in beethoven-qa, so a rename there strands every caller's ruleset. A called workflow reaches its own files only through composite actions anyway.
- Use GitHub Code Quality or code-scanning rules. They are paid (a per-committer fee plus AI credits; code scanning on private repositories needs Code Security), which goes against 'Prefer GitHub's native, free features; no API billing', and they are not beethoven-qa.
- Re-implement beethoven-qa's limits in the template's standard-library Python. That makes a second copy of every limit that drifts from the first, and it is still not beethoven-qa.
- Run beethoven-qa only inside the worker's session (the coaching hook, gate-until-green). The worker runs it and can ignore it, so it is advice, not a gate. It may be useful later to shorten the fix loop.
- Post the report as a pull request comment. That needs pull-requests: write on a job that runs the pull request's code, plus logic to find and update the comment, and it fails on forks. The job summary and annotations need no permission.
- Have a webhook service post the check, the way symphony-app posts sdlc/protocol. GitHub hosts no always-on compute a webhook can reach, so it is one more service to keep running.
- Fold beethoven-qa into the existing `check` job. That avoids a ruleset change in mode new, but a download outage would then break the template's dependency-free check, and mode existing has no `check` job to fold into.

### Risks

- Schedules are best effort. Measured here, they ran hours late and dropped most slots. Every cron in the design is affected: the workers' pickup after their rounds, the board's fallback, metrics and the collector, the weekly protocol update, the coordinator's tidy and the canary itself. A public repository's schedules also stop after 60 days without activity.
- claude-code-action@v1 and the CLI it installs change almost daily, so a regression reaches every adopted repository on the same day. The canary detects such a regression; it does not prevent it.
- Every Claude run depends on the Claude GitHub App and on Anthropic's OIDC token exchange. That App's permission set can change, and an installation keeps its old permissions until an owner approves the new ones.
- Pull requests opened with GITHUB_TOKEN now need approval before their CI runs. Whether the dispatched 'check' satisfies the ruleset beside an approval-pending run is not yet measured.
- REST API 2022-11-28 ends about 24 months after 2026-03-10, around March 2028. Two breaks already wait in the code (the 204/202 uninstall check and merge_commit_sha), and calls that send no version change behaviour when GitHub's default version moves.
- GITHUB_TOKEN gets 1,000 requests an hour per repository (15,000 on GHEC), shared by the board, the clerk, tidy and metrics, and the board keeps no budget. Many workers in one repository can exhaust it, so a large-scale test should measure board runs and requests per hour.
- The canary's reset moves a default branch by force. It must refuse every repository id but the canary's, and it is the one place where the rule against force-pushing a default branch is set aside, for a fixture.
- The canary's worker leg spends the owner's plan and can be flaky on model behaviour. One red run is a signal to look, not proof of a break.
- Browser-only steps cannot be exercised by any workflow: the two Apps' Setup URLs, 'Redirect on update', the state parameter through two hops and the form's prefill. A person has to walk through them after each change.
- Every adopted repository's required check clones the public library at its VENDORED commit. Renaming symphony-protocol, making it private or rewriting its history would break every user's merges.
- Until it is pinned, the 'check' requirement can be met by any App with Checks write, the Claude App included.
- Usage is parsed from formats Anthropic does not document, in continue-on-error steps, so it fails silently. The canary must assert a non-zero record.
- Without the update path, adopted repositories keep 1,755 lines of copied workflow YAML that only Dependabot (major tags) and protocol.yml (the library alone) can change.
- A strict up-to-date rule with many workers makes every landing re-run CI on all the other open pull requests. The merge queue is not available to repositories owned by personal accounts.

### Alternatives rejected

- Deploy the webhook server, in a container or on the approved Cloudflare service, for the sdlc/protocol check run. Rejected: it duplicates the required 'check' (tools/check_protocol.py); it puts the App's private key and the webhook secret on a host that needs uptime and a redelivery job, since GitHub never redelivers; it receives every installation's events; and a ruleset that required it would block every pull request while it was down.
- A webhook for installation events that dispatches the sweep. Rejected: it needs the same host, the key and a token that may dispatch workflows, while the Setup URL chain already brings every installer to the form.
- Keep the sweep as it is. Rejected: it ran 8 times in about 50 hours against a ten-minute cron; its cost grows with every adoption, since it rescans adopted repositories; and it opens pull requests and issues in repositories nobody named.
- A stand-in Claude through ANTHROPIC_BASE_URL (a fake Messages API in the job). Rejected for now: how the CLI behaves against a fake is not yet measured; the wire format would become a moving part of ours; it cannot catch model or prompt drift; and the Beethoven repositories forbid an ANTHROPIC_BASE_URL gateway.
- A stand-in executable through path_to_claude_code_executable. Rejected: the action drives the CLI through the Agent SDK's stream-json control protocol, which a stand-in would have to speak.
- A scripted fake worker step in workers.yml. Rejected: it tests everything but the action and the CLI, and its pushes with GITHUB_TOKEN would neither start CI nor carry the Claude App's identity.
- Public reusable workflows called by every adopted repository. Rejected: it would publish the template's workflows against the decision that the template stays private; 'secrets: inherit' works only within one organization or enterprise (workflow-syntax.md:1606-1608); and every user's run would depend on that repository while it runs.
- Pin claude-code-action to a full SHA in users' copies. Rejected for now: 248 v1 releases and 25 CLI bumps in four weeks would mean a weekly pull request in every repository, whose check never exercises the Claude workflows; revisit once the update path exists.
- Make the merge queue the default. Rejected: GitHub offers it only for organization-owned public repositories and private repositories on GHEC (data/reusables/gated-features/merge-queue.md).
- Fold every issue-triggered workflow into one file. Rejected: it saves some skipped runs but gathers all their write permissions in one place.
- Pin runs-on to ubuntu-24.04. Rejected: it postpones the move to Python 3.14 and is retired later anyway; a weekly leg on ubuntu-26.04 shows the change first.
- Drop the Setup App and leave the settings to scripts/setup-repo.sh. Rejected: the owner decided that one press applies them, and the ruleset with its required check, which the Setup App applies, is what makes 'it passes' enforceable.
- Shorten the crons, or add more of them. Rejected: GitHub delays and drops scheduled runs under load (documented, and measured here).

### Risks

- 42 pairs detect only large gaps (about 26 to 30 points at 80 percent power), so a null result there does not show the arms are equal. Report intervals, not verdicts.
- Token leak: an agent that prints its environment writes the token into its stream and session files, and a public repository's artifacts are downloadable by anyone signed in. The scrub must land before the first real run.
- Usage limits mid-pair waste the partial work of both agents and leave Error pairs to rerun after the window resets. Concurrency above two sessions per token, and use of one token from many runner IPs, are not yet measured.
- The two largest flash images (4.19 and 4.11 GB compressed) may not fit a 14 GB runner with the overlay. Free the runner's preinstalled toolchains or leave those 3 pairs out, decided in PLAN.md.
- The runner's open network differs from the cloud session's. Agents' Bash can still fetch upstream code (only WebFetch and WebSearch are off, as in CooperBench), so runs from the two environments must not be pooled, and config.json records which one ran.
- Drift during a run: pin ubuntu-24.04 (ubuntu-latest moves to 26.04 in November 2026), CooperBench 63b9d44 and the Claude Code version. The vendored protocol must not change mid-benchmark.
- As a non-root runner user, the hub loses the git reflog and the team arm its task mirror. Run the runner with sudo -E, or the team arm silently differs.
- GitHub limits: 256 jobs per matrix (5 arms on 50 pairs is 250; adding sdlc-watch needs two dispatches); 100 pending jobs per concurrency group (with fewer than three accounts, split the dispatch); concurrent-job limits depend on the organization's plan, which this session cannot read.
- Running the arms of a pair one after another can carry order effects. Rotate the arm order by pair index.
- Setup-tokens expire after a year. The workflow's preflight should name each label whose secret is missing or empty, never a value.
- The sdlc arm under-represents Symphony 0.4.0 (no coordinator plan, no overlaps, no required check), so its result speaks for the claim protocol, not the whole product.
- Terms of service: Anthropic's page recommends an API key for organization-shared secrets. The owner decided to use their own subscriptions knowing this; it must not extend to anyone else's credentials.

## Requirement 3 (the owner, 2026-10-13)

Requirement 3 (the owner, 2026-10-13): paste the setup-tokens of all of the owner's own Claude accounts once, and have the Claude runs of every Symphony repository in the owner's organization spread across those accounts automatically, moving off an account when it nears or hits its plan limit, the way cswap's auto mode does on one machine, so that CooperBench benchmarks can later run on Symphony at scale. The limits: tokens live only in GitHub's secret store, never in a file, a log, an argv or a commit. Subscription tokens only: no API key and no usage credits. Shared state uses GITHUB_TOKEN alone. Never a Beethoven repository, and never a contributor's credential.

### Recommended design

The pool, in GitHub's own stores: one organization secret per account, SYMPHONY_CLAUDE_<NAME> (NAME is the owner's short label in A-Z and 0-9, for example MAX1), holding that account's `claude setup-token` token, with repository access set to 'Selected repositories'. One organization variable, SYMPHONY_CLAUDE_ACCOUNTS, with the same access, lists the names in order; it holds no secret. Nothing else is new: no server, no webhook, no branch writes, no cross-repository token. A repository without the variable has a pool of one, its existing CLAUDE_CODE_OAUTH_TOKEN, so it behaves exactly as today. Default workers registered at adoption take whichever pool their repository has.

The paste: symphony-template scripts/accounts.py, written with the Python standard library and gh, run by the owner in their own terminal and never in a Claude session.
- `add NAME` explains the pool and the terms question once and asks for yes. It then runs `gh secret set SYMPHONY_CLAUDE_NAME --org ORG --visibility selected --repos <pooled list>` with the terminal attached, so gh's own masked prompt takes the token and gh encrypts it locally. The script never reads, prints, stores or forwards the value, and never uses --body. Last, it adds NAME to the variable with `gh variable set`.
- `sync` recomputes the pooled list and sets every pool secret's and the variable's selected repositories through the REST API, without touching any value. It admits only repositories that carry the topic symphony, are private or internal, are not in crowd mode, have the owner as their only writer (collaborators?permission=push), and have a push ruleset keeping .github/workflows/** to the owner. It never admits a Beethoven repository (names starting beethoven, hpcworker, the study repositories). Each refusal says why. It warns when a token nears its year.
- `list`, `pause NAME` (out of the variable, secret kept) and `remove NAME` complete it.
The owner runs sync after each new repository.

The rule: symphony-protocol gains sdlc_protocol/accounts.py, pure and clock-injected, behind `python3 -m sdlc_protocol accounts observe|pick`. It is vendored into the template, with a shim tools/accounts.py beside team.py, and into coordbench, which can deal benchmark arms to accounts the same way.
- observe(messages) reduces an execution file to the last rate_limit_event and the result's error kind: rejected, allowed_warning, overage, authentication_failed or account_on_hold, or a missing token.
- pick(pool, records, legs, now, run number, tried) gives each leg one secret name:
  - a rejected account is out until its resetsAt plus 60 s (cswap's reset slack);
  - a dead account is out for 6 hours, an account on overage until its reset;
  - a near account (allowed_warning, Claude Code's own warning thresholds in the role of cswap's 90 percent) is used only when no account without a record is left;
  - legs spread over the rest by rotation on the run number (cswap's best strategy);
  - names in `tried` are skipped, and a worker file's account note is honoured when it names an available pool account;
  - names must match ^(CLAUDE_CODE_OAUTH_TOKEN|SYMPHONY_CLAUDE_[A-Z0-9]{1,30})$, so no other secret can be routed into a session.
- When every account is out, the leg does nothing and its summary names the first reset.

The record: each repository's Actions cache, with GITHUB_TOKEN alone.
- Each observation is one tiny cache entry keyed symphony-account-<NAME>-<status>-<until>-<run>-<attempt>-<worker>.
- Entries are immutable, so parallel legs never overwrite each other.
- One REST call reads them back, with the data in the keys: GET /repos/{repo}/actions/caches?key=symphony-account-&ref=refs/heads/<default>&sort=created_at&direction=desc.
- An entry is never restored, so it is evicted 7 days after it is written, which is never before the reset it records.
- Each repository learns an account's state once per window on its own. No organization-wide record is possible with GITHUB_TOKEN alone.

The workflows, workers.yml first:
- The registry job (no secret, actions: read) adds the pick and outputs {worker: secret name}.
- The work job becomes a caller of a new reusable workflow, .github/workflows/claude-session.yml, with the same matrix and concurrency. It passes exactly one secret: `secrets: claude_token: ${{ secrets[fromJSON(needs.registry.outputs.accounts)[matrix.worker]] }}`. GitHub evaluates that mapping before any runner exists, so the session's runner holds one account's token.
- claude-session.yml has two jobs:
  - claude (cache-mode: read; CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 with bubblewrap installed; CLAUDE_CODE_RETRY_WATCHDOG never set) runs today's steps: team.py next, the action and the usage record. It then runs observe on the execution file, from a copy of the tool made before the session. If the account was rejected or dead and work is left, it dispatches workers.yml again for the same worker and round, with this account added to tried. GITHUB_TOKEN may start workflow_dispatch, and the chain ends once every account has been tried.
  - ledger (needs claude; cache-mode: write; no secret, no checkout) checks the outputs (a name from the pool, a status from a fixed set, an until no more than 8 days ahead) and saves the one entry.
- A session cut off mid-run is carried on by its claim branch, as the protocol's 'push often' already provides; it is not resumed.

Around it:
- The crowd guard refuses SYMPHONY_CLAUDE_ACCOUNTS.
- The board may print one line per account from the same keys.
- The coordinator and @claude move onto claude-session.yml after the workers. That workflow is also the natural piece for the central versioned Symphony Action, since a called workflow takes its caller's variables and secrets.
- The control panel, later, shows the pool's state and links to GitHub's own secret page. It never takes a Claude token.

What the owner does: for each account, run `claude setup-token` while signed in as that account, then `python3 scripts/accounts.py add MAX1` and paste into gh's prompt. Run `sync` after each new repository. Keep usage credits off on every pooled account. Run add again when a token nears its year.

### Risks

- Anthropic may enforce its terms on every pooled account at once, without prior notice. Several subscriptions run around the clock by unattended workers is not the 'ordinary, individual usage' the advertised limits assume. The 2026-11-12 Usage Policy names services that route requests through consumer subscriptions.

- A leaked setup-token stays valid for up to a year. Deleting the GitHub secret does not revoke it; revoking means signing that account out everywhere.
- Each repository learns an account's state on its own, so several repositories each waste one start (about a runner minute) per spent account per window. Those minutes count on private repositories.
- Records can be lost or poisoned: by cache eviction, by eviction at the 10 GB cap, or by a background process faking the execution file. The checks bound the damage to a skipped account for at most 8 days or one failed start.
- Not yet measured:
- whether secrets[...] with a computed name works in a call's secrets mapping;
- whether a run under every threshold emits a rate_limit_event;
- whether every response carries per-window utilization;
- whether cache-mode: write behaves as documented on issues-triggered runs.
- Usage credits left on bill quietly past the plan limit. The run only notices afterwards, through the overage fields.
- A limit reached mid-session loses the work since the last push; the next round on another account carries the claim on.
- Limits on parallel sessions per subscription account are not documented. GitHub caps concurrent jobs at 60 on Team and 500 on Enterprise.
- The pool variable and the secrets can drift, for example a deleted secret that is still listed. The leg then gets an empty token and records the account as missing; it never falls back silently to the main account.
- A model-family limit (Opus or Sonnet) spends an account only for that family. A worker whose file names no model is treated as blocked by any family limit.
- GitHub's newer cache restrictions could change. The record would then degrade to failover-only through the tried chain, which stays correct but wastes more starts.

### Alternatives rejected

- A dynamic secrets[...] lookup inside the Claude step. The runner would then hold every secret the repository can see: every pool token, and others such as SDLC_APP_PRIVATE_KEY.
- One static step per account, each behind an if:. The job names every token, so every token reaches the runner.
- secrets: inherit into the called workflow. It passes every secret.
- Polling usage the way cswap does. A setup-token can only make model requests, and the usage endpoint needs the profile scope. A probe session would spend usage and send Claude Code's whole system prompt.
- An organization variable or a repository variable as the spent record. GITHUB_TOKEN has neither Variables permission. Writing them would need an App key or a personal token with organization write in every repository.
- A branch as the record. Parallel legs race on git pushes, the ruleset needs exemptions and the history grows. It stays a workable fallback.
- Artifacts as the record. The name filter is exact-match, so reading needs downloads through storage redirects.
- Environment secrets per repository with a default-branch deployment policy. They contain branches better, but every token must be pasted once per repository, because GitHub has no organization-level environments.
- An organization-wide ledger on a server. The Cloudflare sign-in service is stateless by decision, and the App's webhook server is not always running.
- cswap auto on the owner's machine publishing readings to an organization variable. It is a moving part that sleeps with the owner's laptop. Kept as a possible later accelerator.
- Each account running its own routines. This is Anthropic's own feature and needs no pasted token, so it is the cleanest on terms. But routines are made by hand per account and repository, no API creates them, and they do not switch when an account is spent. Kept as the fallback if Anthropic objects.
- An API key, which Anthropic recommends for secrets shared across repositories. It breaks the template's subscription-only rule and Beethoven's no-API-key rule.
- CLAUDE_CODE_RETRY_WATCHDOG=1. A run on a spent account would wait out the window on a paid runner.
- Pasting through the control panel. Symphony's own code would then collect a Claude credential, which the legal page forbids developers to do.
- Copying cswap's full logins to GitHub. They are refresh-token lineages that rotate; only setup-tokens belong in a CI secret.
