# A generic QA gate on what GitHub provides

## Recommended gate (before verification)

Principle: the judge lives where the worker cannot edit it, every language meets the same questions, and every verdict comes from a tool or GitHub, never a model. Three layers.

1. Settings, no workflow file (an organization security configuration plus rulesets, applied once by Symphony Setup or scripts/setup-repo.sh). (a) Code scanning default setup with CodeQL, suite extended; maintainability and reliability queries added for the whole organization with the custom property github-codeql-extra-queries='+security-and-quality', still with no workflow. Default setup finds the languages, adds new ones as they appear, scans every PR to the default branch with incremental analysis and keeps CodeQL current (github/docs setup-types.md:18-23,38; repository-properties.md:61; workflow-configuration-options.md:352; incremental-analysis.md:25). Copilot Autofix stays on: single suggestions, no AI credits, no verdict. (b) Secret scanning with push protection. (c) Dependabot alerts and security updates, and a dependabot.yml for the github-actions ecosystem. (d) The default-branch ruleset Symphony already ships (docs/setup/ruleset-main.json, ruleset-org.json), extended: pull_request; required_status_checks, strict, with check, dependency-review and qa, each pinned to integration_id 15368 (GitHub Actions) so a token cannot satisfy them with a commit status; code_scanning {tool: CodeQL, alerts_threshold: errors, security_alerts_threshold: high_or_higher}, which also blocks while an analysis is missing or running; bypass_actors empty. Where Code Quality is bought: code_quality {severity: errors}, and code_coverage once it leaves preview. On Enterprise Cloud the same as an organization ruleset, plus a workflows rule naming a central qa.yml by repository_id, path and sha, so no PR can change the gate (REST rule schemas in github/rest-api-description).

2. One workflow per repository, GitHub's own actions and the runner's tools only (no pixi, no pip, pinned runner label ubuntu-24.04). Job check (Symphony's, unchanged): bash scripts/check.sh, the repository's own tests, linter and type checker in its own language (scripts/check.sh:25), plus check_protocol.py for claude/<N> PRs. Then a stdlib step 'runner linters on changed files': shellcheck --severity=warning for *.sh, *.bash, *.sbatch; yamllint -d relaxed for *.yml and *.yaml; python3 -m py_compile for *.py; node --check for *.js, *.mjs, *.cjs; the generalized suppression and skipped-test refusal (noqa, nosec, type: ignore, shellcheck disable, yamllint disable, eslint-disable, @ts-ignore, NOLINT, pytest.skip, it.skip and the like) on added lines; the download-digest rule on workflows via yq; each tool's version recorded; a changed file of a type nothing checks is listed as unchecked. It writes qa.json (and SARIF for upload-sarif, category qa-lint, where code scanning exists) and uploads it. Job dependency-review: actions/dependency-review-action with fail-on-severity: high, fail-on-scopes: runtime, comment-summary-in-pr: on-failure (public repositories, or private ones with Code Security). Optional per repository, coverage: when the tests emit Cobertura or lcov, a stdlib step computes the share of new executable lines run (beethoven-qa's 80% rule, now language-neutral); with Code Quality, also actions/upload-code-coverage@v1.

3. The report, in a workflow the PR cannot edit: qa-report.yml on workflow_run of the workflow above, which always runs the default branch's copy (events-that-trigger-workflows.md, workflow_run; branch-requirement.md:1), on ubuntu-slim with stdlib Python and gh only. It treats downloaded files as data, reads the PR's check runs, the code scanning alerts for refs/pull/N/merge where code scanning exists, the dependency review result and qa.json, flags any change to .github/, scripts/check.sh, tests or tool configuration as 'this PR changes its own gate', and writes one sticky PR comment, a job summary, a check run named qa with annotations (50 per request) and the JSON as an artifact, attested with actions/attest where available. A renamed or deleted CI workflow means no qa check, so the PR stays blocked: fail closed.

Pass and fail, the same for every language. PASS only when (1) check exited 0; (2) for every CodeQL language present the analysis of the PR head completed and no open alert on added or edited lines is an error or a high or critical security alert; (3) no newly added runtime dependency carries a high or critical advisory or a malware advisory; (4) no secret was pushed and no open secret alert was introduced; (5) the runner linters report no error or warning in changed files of their types and no suppression or skipped test was added; (6) where the repository opted in, at least 80% of new executable lines ran. A tool that did not run, a missing analysis or a missing result is FAIL, never a pass (beethoven-qa's exit 2 rule, and the code_scanning rule's own conditions, merge-protection-rulesets-conditions.md). A language nothing analyses (R, LaTeX, notebooks, PHP, HCL, most of shell beyond shellcheck) is held to (1) and (3)-(5) only, and the report names it 'not statically analysed'. This is the same baseline GitHub applies to third-party coding agents on its own platform: CodeQL, secret scanning and an Advisory Database check of new dependencies for High or Critical and malware (content/copilot/concepts/agents/about-third-party-coding-agents.md:66-76).

beethoven-qa lanes that stay, and only for: CrossHair/Z3 and the contract check, the readability, design and duplication groups, in the Python repositories that adopted icontract and carry beethoven-qa (beethoven-qa, beethoven-agents, the research pipeline), outside the generic gate, the symbolic lane nightly or with --module; the new-line coverage rule, the suppression and skipped-test refusal and the download-digest rule, rewritten in stdlib and language-neutral, inside the generic gate; the Scorecard CLI as a weekly report; boundary in the Beethoven repositories. Dropped from the generic gate: pixi and conda-forge, the pinned copy and vendor-check, ruff, mypy and pytest as gate lanes (they move into each repository's check), bandit and zizmor wherever CodeQL runs.

Workers' pull requests: every claim branch claude/<N> targets the default branch, and rulesets match the base branch, so the gate holds every worker PR whatever its head name; strict keeps the branch current; check_protocol.py inside check already holds the claim protocol. A worker in Actions must open and push its PR with an App token (claude-code-action's, workers.yml:93-134) or a person's token: PRs made with GITHUB_TOKEN start approval-required runs only, and ruleset workflows never run for them (actions-do-not-trigger-workflows.md; troubleshooting-rules.md:65).

Cost in minutes. Public repositories: nothing on standard runners (billing github-actions.md:24). Private and internal (2 vCPU, Linux $0.006 a minute, every job rounded up to a whole minute; actions-runner-pricing.md:14): check about 1-3, CodeQL one job per language (not measured here; a few minutes each for a small repository), dependency review 1, report 1 on ubuntu-slim at $0.002, so roughly 6-12 billed minutes a push for a Python plus workflows repository, against beethoven-qa's measured 28 min 45 s gate job and about 29 min report job (58 or more billed minutes) plus six standards jobs never timed on a runner. At Team's 3,000 included minutes that is about 250-500 pushes a month instead of under 50; at Enterprise Cloud's 50,000, about 4,000-8,000.

## Reporting channels

Five native channels, none needing a dependency. (1) The Security tab, through code scanning: CodeQL results and any SARIF 2.1.0 file uploaded with github/codeql-action/upload-sarif (inputs sarif_file, category, wait-for-processing; the job needs security-events: write) become persistent alerts with rule, severity, CWE tags, the commit that introduced them and a recorded dismissal (who and why). On a pull request, an alert whose lines are all among the added or edited lines appears as an annotation in Files changed, inside a 'Code scanning results / <tool>' check that fails on error, high or critical, and as a pull request review in Conversation. Limits: 10 MB gzipped per file, 20 runs per file, 25,000 results per run of which the top 5,000 are kept, 1,000 locations per result, 1,000,000 alerts. Public repositories free; private and internal need Code Security. beethoven-qa's SARIF already carries partialFingerprints and external/cwe tags, so it could be uploaded as it is where code scanning exists; it is not uploaded today (beethoven-qa docs/STANDARDS.md:127-129). Sources: github/codeql-action upload-sarif/action.yml; github/docs content/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts/triage-alerts-in-pull-requests.md:27,35,51; content/code-security/reference/code-scanning/sarif-files/sarif-support.md:40-44,61-66,103; data/reusables/code-scanning/sarif-limits.md. (2) Check-run annotations: from workflow commands (::error file=...,line=...::) at most 10 error, 10 warning and 10 notice annotations per step and 50 per job (actions/toolkit docs/problem-matchers.md:7-11); from the Checks API with checks: write, 50 annotations per request, appended by further updates, and a Markdown summary of up to 65,535 characters (github/rest-api-description, Create a check run); both show in the Checks and Files changed tabs. (3) Job summaries: Markdown appended to GITHUB_STEP_SUMMARY, grouped per job on the run's summary page one click from the PR's check, 1 MiB per step and at most 20 step summaries shown per job (github/docs content/actions/reference/workflows-and-actions/workflow-commands.md:797-819,935). (4) Pull request comments: one sticky comment kept up to date by a job with pull-requests: write; GitHub's own actions already do this (dependency-review-action comment-summary-in-pr, README.md:127; github-code-quality[bot] for coverage and quality findings, set-up-code-coverage.md:153-168). It is the one channel that outlives the Actions retention, and claim branches live in the repository, so the token can write. (5) Artifacts: immutable since upload-artifact v4, 90 days by default, settable to 1-90 days on public and 1-400 days on private and internal repositories (actions/upload-artifact README.md:299,344-360; github/docs data/reusables/actions/about-artifact-log-retention.md:13-16). Since 2026-10-01 check suites, check runs, commit statuses and workflow runs expire under the same retention (about-artifact-log-retention.md:1-6; checks-and-statuses-retention-scope.md), so annotations and summaries are a view, not a record. The report's provenance: actions/attest signs a subject such as report.json with Sigstore, verifiable with gh attestation verify; public repositories on every plan, private and internal on Enterprise Cloud only (actions/attest README.md:34-41; data/reusables/gated-features/attestations.md). What the reviewer reads: the sticky comment, with the verdict on each question and links to the alerts, the check runs and the artifact; the Security tab and the checks hold the detail; the artifact holds the full JSON.

## Decisions for the owner

- Code scanning on the private and internal repositories workers change: buy GitHub Code Security for them (per active committer; App bots are free), make them public, or accept that private ones get no CodeQL and keep bandit (Python) and zizmor (workflows) there, which are dependencies Symphony's rule does not allow.
- Secret scanning on private repositories: buy Secret Protection, or rely on Symphony's own SECRET_SHAPES check (sdlc-template tools/check_docs.py:41) as the only secret gate there.
- Coverage: buy Code Quality for its PR findings and coverage rule, or keep beethoven-qa's new-line rule in a stdlib Cobertura/lcov reader; GitHub's rule gates aggregate coverage or its drop, not new lines, and is in preview.
- What 'for human review' requires: an advisory report Greg reads before merging (spine-program's rule: only Greg merges), or a required approval. An approval cannot be given on PRs opened under Greg's own login (authors cannot approve their own, github/docs data/reusables/repositories/request-changes-tips.md:9), so a required approval implies workers commit and open PRs under an App or machine identity.
- Identity and bypass: keep bypass_actors empty everywhere (Symphony's rulesets are; beethoven-qa .github/rulesets/main.json:5-9 lets OrganizationAdmin bypass always) and decide whether sessions keep acting as an organization owner, who can also dismiss code scanning alerts directly under delegated dismissal.
- Allow or forbid the AI-credit features (agentic autofix, Code Quality AI findings, AI Scan, Copilot code review) under 'no API billing'; if allowed, a budget with a hard stop, and none of them in pass or fail.
- Which beethoven-qa groups block in the Python repositories that carry it: readability, design and duplication have no native equivalent and partly in-house limits (WMC 50, NOC 10, RFC 50 'chosen here'); blocking, report-only, or dropped.
- Where the gate lives: per-repository workflow files that adoption copies (a worker's PR can edit them), a default-branch workflow_run reporter (the PR cannot edit it, but can still edit ci.yml and scripts/check.sh), or an Enterprise Cloud organization ruleset workflow pinned to a commit of a central repository (no PR can edit it).
- Action pinning: Symphony pins GitHub's actions to major tags (actions/checkout@v7, anthropics/claude-code-action@v1); turning on 'Require actions to be pinned to a full-length commit SHA' would stop those runs until they move to SHA pins kept fresh by Dependabot, or to workflow lockfiles (preview).
- Runner label: pin ubuntu-24.04 (system Python 3.12.3, Symphony's floor) or follow ubuntu-latest, which becomes Ubuntu 26.04 with Python 3.14.4 in November 2026; Symphony's ci.yml runs the runner's own python3.
- Retention: raise the private repositories' Actions retention toward 400 days if check runs and annotations must stay as evidence, or treat the sticky PR comment and code scanning alerts as the record.
- Cadence of the CrossHair lane in the Python Design-by-Contract repositories: every PR (26 min on a 2-vCPU private runner), changed modules only (--module), or nightly.

## Risks

- A worker can change its own judge: pull_request runs use the merge commit's workflow files and scripts (github/docs events-that-trigger-workflows.md, pull_request: GITHUB_SHA is the merge commit), so a worker PR can rewrite ci.yml, scripts/check.sh or the tests, and any GitHub Actions job can create a check run with a required name, so integration_id 15368 does not tell workflows apart. Only an Enterprise Cloud ruleset workflow pinned by sha, a push ruleset restricting .github/** and scripts/** for workers (Team and up), or a required human approval closes this; GitHub holds its own coding agent's workflow runs for approval for the same reason (data/reusables/copilot/cloud-agent-workflow-run-approval-default.md).
- Symphony's required check 'check' names no source app (sdlc-template docs/setup/ruleset-main.json:31, ruleset-org.json:36): any person or integration with write access can set a commit status named check to success (available-rules-for-rulesets.md:178), including a session holding the owner's token.
- Sessions acting as an organization owner can bypass rulesets that list OrganizationAdmin (beethoven-qa .github/rulesets/main.json:5-9, bypass_mode always) and dismiss code scanning alerts directly even with delegated dismissal (delegated-alert-dismissal.md:15-16); Code Quality's 'Dismiss finding' unblocks a merge (catch-issues-before-merge.md:79), and who may dismiss it is not documented on the pages read.
- Diff-line rule: code scanning shows an alert on a PR, and merge protection counts it, only when every line of the alert is among the added or edited lines (sarif-support.md:61-66; merge-protection.md:41); a beethoven-qa function finding uploaded as SARIF and anchored at an untouched def line would not block, where beethoven-qa's anchor matching blocks a function made worse.
- Preview pieces change without notice: the code_coverage rule, the secret merge rule, workflow lockfiles, AI Scan and Code Quality's AI findings are public preview (restrict-code-coverage.md:14-15; data/reusables/secret-scanning/merge-protection-public-preview.md; data/reusables/actions/workflow-lockfiles-preview.md; ai-powered-security-detections.md:13-14); keep them out of the blocking set.
- Fail-closed side effects: the code_scanning rule blocks while analysis is missing or running, and the code_quality rule blocks when analysis fails, for example when Actions minutes run out (data/reusables/code-scanning/merge-protection-rulesets-conditions.md; available-rules-for-rulesets.md:242-246); on a private-repository quota a month of heavy lanes can freeze every merge.
- Evidence expiry: since 2026-10-01 check suites, check runs, commit statuses and workflow runs follow the Actions retention, 90 days by default, at most 90 on public and 400 on private and internal repositories (data/reusables/actions/about-artifact-log-retention.md:1-16; checks-and-statuses-retention-scope.md).
- Runner drift: ubuntu-latest becomes 26.04 in November 2026 (Python 3.14.4, Node 24, shellcheck 0.11.0, clang 20-22) and the image is rebuilt weekly under a label (Ubuntu2404-Readme.md:3,11; Ubuntu2604-Readme.md:19-27,295); Symphony's ci.yml uses the runner's python3, so its 3.12 floor stops being what CI tests.
- Truncation: 10 error, 10 warning and 10 notice annotations per step and 50 per job from workflow commands (actions/toolkit docs/problem-matchers.md:7-11); 50 annotations per Checks API request and a 65,535-character summary (github/rest-api-description, Create a check run); 1 MiB per step summary and 20 summaries per job (workflow-commands.md:935); SARIF 25,000 results per run with the top 5,000 kept and 10 MB gzipped (sarif-limits.md; sarif-support.md:103). A first scan of an old repository will be cut.
- PRs made with GITHUB_TOKEN start approval-required runs only, other GITHUB_TOKEN events none, and ruleset workflows never run for them (data/reusables/actions/actions-do-not-trigger-workflows.md; troubleshooting-rules.md:65): a worker that opens its PR with GITHUB_TOKEN never gets a green required check without a person's click.
- The workflow_run reporter runs with write tokens over artifacts made by PR code, the artifact-poisoning pattern CodeQL's actions queries flag (data/reusables/code-scanning/codeql-query-tables/actions.md); it must parse downloaded files as data, escape Markdown, and never execute or check out PR code.
- Language blind spots: CodeQL covers ten languages and Actions workflows; shell, R, LaTeX, notebooks, PHP, HCL and Dockerfiles get only AI Scan, advisory and gated (codeql-languages-bullets.md; ai-powered-security-detections.md:30,45,52); spine-program alone tracks 522 .py, 72 .sh and 117 .tex files (git ls-files count of /home/user/spine-program), so most of its non-Python code would be reported as not statically analysed.
- Dependency-graph blind spots: no pixi or conda ecosystem is listed (dependency-graph-supported-package-ecosystems.md:28-58), so beethoven-qa's conda-forge and PyPI toolchain is invisible to Dependabot and dependency review.
- A documentation inconsistency to test before relying on it: about-github-advanced-security.md:66 shows dependency review 'No' for a public repository without Code Security, while data/reusables/gated-features/dependency-review.md, billing github-advanced-security.md:55 and the action's README.md:29 say public repositories have it.
- The Scorecard action is a third-party container image (ghcr.io/ossf/scorecard-action:v2.5.0, action.yaml:61), does not support GitHub Enterprise repositories and treats pull_request as experimental (README.md:42,46); it cannot be the PR gate.
- Cost today: beethoven-qa's CI is at least 58 billed minutes a push on a private repository (gate job 28 min 45 s, beethoven-qa .github/workflows/ci.yml:36-38; report job about 29 min, docs/REPORT.md:167) plus six standards jobs, each downloading pixi and installing the locked environment, never timed on a runner (docs/STANDARDS.md 'Not yet measured'); at Team's 3,000 minutes that is under 50 pushes a month across all repositories. CodeQL's own minutes in the recommended gate are not measured here either.
- Turning on the SHA-pinning Actions policy before re-pinning stops every Symphony workflow pinned by major tag (data/reusables/actions/actions-use-policy-settings.md; sdlc-template .github/workflows/ci.yml uses actions/checkout@v7).

## Each beethoven-qa lane against its native equivalent

- **symbolic gate, check 1: contracts present and nothing hidden (python -m beethoven_qa gate)** (Python only (imports the package; icontract decorators; pytest and unittest skip forms)): Every public function of the package named in [tool.beethoven-qa] carries icontract @require/@ensure; every .py file imports as a module without exiting; no '# crosshair:' directive, no public coroutine, no contracted pydantic model, no empty package. It also refuses suppression comments the standards' tools read (# noqa, # type: ignore, # nosec, # pragma: no cover, jscpd/zizmor/complexipy/lizard markers) and skipped or xfail tests, in the package and where pytest collects. Native: None for contracts. For suppressions GitHub works differently: no page under content/code-security documents an inline suppression comment for code scanning (grep for 'codeql[', 'lgtm[', 'suppression comment', 'alert suppression' found nothing); an alert is closed by a recorded dismissal (actor and reason), and delegated alert dismissal makes writers request it, while organization owners and security managers still dismiss directly. Nothing native refuses skipped tests or tool-specific disable comments (shellcheck disable, yamllint disable, eslint-disable, @ts-ignore, NOLINT). Availability: Delegated alert dismissal on github.com for code scanning, secret scanning and Dependabot alerts; it presupposes code scanning, i.e. a public repository or Code Security. Keep beethoven-qa for it: True.
- **symbolic gate, check 2: CrossHair + Z3 (pixi run --locked symbolic)** (Python only (CrossHair executes Python under icontract)): That no input meeting a function's preconditions violates a postcondition, 20 s per condition, one CrossHair process per target, failing on a precondition no input can meet. Mostly a bounded search: 13 of 165 conditions confirmed over all paths, 152 not confirmed within the bound, on 5.0.0's tree (14 min 3 s on 4 cores); 26 min on GitHub's runner, gate job 28 min 45 s. Native: None. CodeQL is query-based pattern and data-flow analysis; no GitHub feature or preinstalled tool checks pre- and postconditions. Private-repository standard runners have 2 vCPU/8 GB against 4 vCPU/16 GB for public ones, which fits 26 min on the runner against 14 min on a 4-core session (an inference, not measured). Availability: Not a GitHub feature; runs wherever the pinned pixi environment runs. Keep beethoven-qa for it: True.
- **lint (ruff check src tests && ruff format --check src tests)** (Python): Ruff's rules and formatting under the repository's own ruff settings. Native: CodeQL's security-and-quality suite adds maintainability and reliability queries for every CodeQL language (advanced setup, or default setup plus the organization property github-codeql-extra-queries='+security-and-quality'); GitHub Code Quality runs CodeQL quality rules on pull requests for C#, Go, Java, JavaScript, Python, Ruby and TypeScript, posts them as github-code-quality[bot] comments and can block with the 'Require code quality results' rule. For other file types the runner has shellcheck 0.9.0, yamllint 1.38.0, clang-format/clang-tidy 16-18, PSScriptAnalyzer 1.25.0 and rustfmt 1.10.0. Ruff is not on the image; nothing native checks formatting. Availability: CodeQL: public repositories free, private/internal with Code Security. Code Quality: Team or Enterprise Cloud only, per active committer, plus Actions minutes; AI features draw AI credits. Keep beethoven-qa for it: False.
- **typecheck (mypy src, strict)** (Python): Static types of the package. Native: None: CodeQL does not type-check and GitHub has no type checker. The runner's toolchains type-check by compiling: Node.js 22.23.3 with npm for tsc from a repository's devDependencies, Go 1.24-1.26, Rust 1.99, Java 8-25, .NET 8-10. Availability: Runner tools on every plan; they are the repository's own check, not a GitHub service. Keep beethoven-qa for it: False.
- **tests (pytest -q under typeguard's import hook)** (Python): The repository's tests pass; typeguard checks annotations at run time inside the test enclave. Native: None: GitHub runs what the workflow runs and the required check is the job's conclusion. - Two critical CodeQL queries in the default suite fire on privileged jobs:
  - `actions/untrusted-checkout/critical` (9.3) fires when a job `git fetch`es the PR ref and then runs steps (`UntrustedCheckoutQuery.qll:303-345`).
  - `artifact-poisoning/critical` (9.0) fires when a job downloads artifacts into the workspace; downloads to `RUNNER_TEMP` or `/tmp` are exempt (`ArtifactPoisoningQuery.qll:261-290`).
  - Under a `high_or_higher` rule on a public repository, a naively written reporter would block its own PR.
- GITHUB_TOKEN is limited to 1,000 API requests an hour per repository, 15,000 on Enterprise Cloud (`data/reusables/rest-api/primary-rate-limit-github-token-in-actions.md:1`). `pulls/{n}/files` returns at most 3,000 files.
- shellcheck reads `.shellcheckrc` unless given `--norc` (`shellcheck.1.md:77-79,300-302`). yamllint reads `.yamllint` from the working directory or a parent unless given `-c` (yamllint `configuration.rst:14-24`). A PR can add either file, so the gate must pass explicit settings.
- Node's coverage honours `/* node:coverage disable */` comments (Node v22 `test.md:483-509`), so the refusal list must include them.
- GitHub has path-based required reviewers (preview, organization repositories), code-owner review, and by default one extra approval for unattributed Copilot PRs (`available-rules-for-rulesets.md:119,131-167`). All three need an approver other than the PR's author.

## D. Is the recommended gate the simplest generic one?

No. The settings layer is right. But the design carries three required checks, a PR-side lint job, an artifact handoff and an attestation. On the private repositories workers mostly change, Code Security is off, so all of that shrinks to `check` plus a few checks that read the PR as plain text. On top of that, conditions (2), (3) and (4) cannot be checked as written (A6-A8), and (5) can be forged by the PR (A19). What I would change:

1. **Two required checks, both pinned to `integration_id` 15368: `check` (unchanged) and `qa`.**
   - Drop the `dependency-review` job.
   - The reporter calls `GET /repos/{owner}/{repo}/dependency-graph/compare/{base}...{head}` where dependency review exists.
   - It calls `/advisories?type=malware&affects=...` for added dependencies everywhere.
   - Dependabot alerts and malware alerts stay on for every repository, free.

2. **`qa` is the only judge, running from the default branch (`workflow_run` on ci completion).**
   - It reads the PR only through REST (`pulls/{n}/files` patches, `contents?ref=<head_sha>`) and never checks out or executes PR code. That means no `qa.json`, no artifacts and no attestation in the first version.
   - It fails on:
     - Suppressions and skipped tests added in the diff, from an extended list: `codeql[`, `lgtm[`, `node:coverage`, istanbul and c8 ignores, `#[ignore]`, `t.Skip`, `@Disabled`, `nolint`, `rubocop:disable`, plus the research's list.
     - Secret shapes in added lines, using Symphony's `SECRET_SHAPES`.
     - Any change on a `claude/*` branch to `.github/**`, `scripts/check.sh`, CODEOWNERS or linter configs.
     - Changed shell files (including `.sbatch`) under `shellcheck --norc --severity=warning`.
     - Python that does not compile, and JavaScript that fails `node --check`.
     - Workflows that do not parse in yq, that grant write at the top level, or that run a download without a digest check.
   - It folds in the native results where they exist: code scanning alerts on the PR ref, including those dismissed during the PR and by whom.
   - Each question gets one of three answers: pass, fail, or not available here. A tool that should have run and did not is a fail.

3. **Scope the native settings so they cannot block repositories that lack them.**
   - CodeQL default setup and the `code_scanning` rule only on `visibility:public`, or on repositories where Code Security is bought.
   - Delegated alert dismissal on.
   - The secret-scanning merge rule only where Secret Protection exists (spine-program has it now).

4. **Report through one check run and one sticky PR comment.** The check run summary holds up to 65,535 characters and annotations go up in batches of 50. Skip job summaries, artifacts and attestations at first. The reporter takes about a minute on ubuntu-slim (about $0.002 a push), well inside slim's 15-minute limit.

5. **The precondition the research understates: workers must not push or open PRs as an organization owner.**
   - Owners can edit rulesets and dismiss alerts directly (`delegated-alert-dismissal.md:16`), so against a misbehaving worker the gate is only advisory.
   - With a worker identity (an App token with contents, pull-requests and checks write, and no administration), Greg's merge can become a required approval, because the author would no longer be Greg (`request-changes-tips.md:9`). Code-owner review of gate files then works too.

6. **beethoven-qa: keep it as the Python Design-by-Contract specialist; do not make it generic.**
   - If complexity and duplication limits are wanted in every language, lizard alone covers cyclomatic, NLOC, parameters, cognitive complexity and duplicates in 26 languages.
   - It is one dependency (plus pygments and pathspec), so it is Greg's call against Symphony's no-dependency rule. Start it as advisory.

7. **Runner.** Run `check` on `ubuntu-24.04`, or keep `ubuntu-latest` and add `actions/setup-python` with 3.12, which is already cached on 26.04 (`Ubuntu2604-Readme.md:190`).
