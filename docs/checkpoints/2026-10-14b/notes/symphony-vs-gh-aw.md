# Is Symphony a hand-rolled standard work queue? Symphony against gh-aw

Written 2026-10-14 from the files, not from memory: github/gh-aw at d06e087 (2026-10-13; the docs under docs/src/content/docs/, the Go package pkg/workqueue), githubnext/gh-aw-workshop at d8c57ab, GitHub's docs source for Copilot dynamic workflows (github/docs, content/copilot/), OpenSpineConsortium/symphony-protocol at 3e98b88 (0.4.1 plus the F12 fix), and symphony-template main at 1dda21d. Every load-bearing sentence names its file and line.

## The answer in short

1. Yes, a worker queue can be a standard GitHub pattern, and gh-aw documents four of them plus a native one. 2. Yes, Symphony's claim protocol is a lease-based work queue built on GitHub's own objects, and its core is textbook. 3. No, it cannot be imported today: gh-aw's queue only takes workers that are gh-aw workflows in Actions, runs Claude only on an API key or Copilot billing, and its queue shipped last week with a spec that calls itself a proposed design. 4. You are building two things: a standard queue, whose plumbing gh-aw also has, and a coordination protocol for independent Claude Code sessions, people and routines sharing one repository with no credential of theirs held anywhere, which gh-aw does not have and does not claim to.

Recommendation: keep building the protocol and the 0.5.0 queue as planned, take the two cheap wheels now (queue: max, since merged in #70, and a workflow linter in check.sh), and treat gh-aw as the thing to measure against on the canary once its Claude engine takes a subscription token or you decide to pay for API or Copilot inference for Actions workers. Switching to gh-aw's queue or to Copilot dynamic workflows ends Symphony's stated purpose, coordination of Claude Code agents, so that is a product change, not an import.

## 1. Can worker queues be represented in a standard GitHub pattern?

Yes. gh-aw's WorkQueueOps page lists five: a native `tools.work-queue` ("a Git-backed queue with fair scheduling, task dependencies, and Claim-scoped effects") and four "lightweight alternatives", issue checklists, sub-issues, cache-memory and repo-memory (patterns/workqueue-ops.md:8). The native queue "stores immutable tasks and lifecycle events in work-queue.jsonl on a dedicated Git branch. A trusted producer submits tasks, a dispatcher requests assignments, and workers process them" and "the agent does not choose which task receives a Claim" (:27). "A Claim authorizes one attempt at a task" (:29). It "supports Git storage only. Issues and pull requests can be dependency nodes, but they are not queue-storage backends" (:64).

The alternatives are what Symphony's shape resembles most, and the page says what they lack: "Checklist progress markers do not provide native fair scheduling, Claim authority, or verified dependency graphs. The concurrency group serializes runs in that group, but does not protect against other workflows or humans editing the issue" (:112).

## 2. Is this what Symphony is doing?

Yes, in the sense that matters. Symphony's queue is "GitHub Issues on the repository" and its lock is "the first push of a branch: GitHub refuses the second push of the same name, so two workers can never hold the same issue" (symphony-protocol spec/PROTOCOL.md:3). Map it onto queue vocabulary:

- The lease is the branch claude/N; the lease holder is the claim file's Worker line.
- The visibility timeout is 24 hours by the head's committer date (spec:67).
- Requeue is the release: labels off, a marked comment, the branch renamed to released/<issue>-<sha> so the name is free and the work is kept (spec:67, the Release section).
- The idempotent consumer is the HTML marker on every coordinator comment, so a second run posts nothing twice (spec:73).
- The fencing token is the claim file the push guard reads before a lease push, which closed F7 (spec:55; validation/DESIGN.md:792).
- Fair dispatch is the dealing of one run's workers so "no two race for one claim" (spec:77), which F4 is about (DESIGN.md:776).

So the F-list reads like the bug list of any queue built on a store that is not a queue: a release half applied (F1), a lost notification under a concurrency group (F12), a clock the producer controls (F8), two names for one key (F5). gh-aw's own operator reference has the same genre of trouble in its "Synchronization and recovery" section: "locks never expire or get stolen" (reference/work-queue.md:310), "Automatic crash recovery that can safely clear these fences is not implemented" (:319-321), and "Reservations remain until exact termination or definitive nonlaunch evidence exists" (:422). GitHub is not a queue, and both projects pay for that.

## 3. Can it just be imported from some GitHub package?

Not today, for three reasons that are each in the files.

- Who may be a worker. gh-aw's workers are gh-aw workflows compiled into Actions: "Workers must require an assignment" through frontmatter (patterns/workqueue-ops.md:38), "Publish approved AW workers and enable work-queue" (guides/deploy-work-queue.md:13), and "Human status-label changes alone cannot establish cancellation or Result" (reference/work-queue.md:259). Symphony's worker "is anything that claims issues: a person's sessions, local or in the cloud, with whatever helpers they start; a routine on someone's Claude account; or runs in GitHub Actions" (spec:7). The cloud sessions in this very project are workers; in gh-aw they cannot be.
- The credential. "CLAUDE_CODE_OAUTH_TOKEN is not supported by GitHub Agentic Workflows. Provider-based OAuth authentication (such as billing through a Claude Teams or Claude Max subscription) is not supported" (reference/auth.mdx:219; engines/claude.md:22). The Claude engine takes ANTHROPIC_API_KEY, Anthropic workload identity federation, or Copilot's proxy on an organization Copilot subscription (engines/claude.md:18-35). Your durable decision is "no API billing: Claude in CI runs on a subscription OAuth token" (symphony-template CLAUDE.md:38) and crowd mode's rule is that "the project never holds anyone's credential" (:41).
- Maturity. The native queue shipped in v0.91.6 the week of 2026-10-12 (blog/2026-10-12-weekly-update.md:34). Its specification opens with "This is the intended experience of the proposed design, not a feature already implemented" (specs/work-queue-specification.md:23) and ends with eleven "Research limits and unresolved engineering questions", among them "The current Git backend's freshness/ref semantics must be validated under actual concurrent publication" (:2956-2970). Its Go package is about 22,600 lines, most of them tests, so it is serious work, but it is a week old.

What could be imported, as a matter of fit: the run plumbing around a worker (section 6 below), if the credential decision changed. The protocol could not, because nothing in gh-aw knows about a person's session.

## 4. What am I doing: hacking together a standard work queue?

Partly. The queue core is standard, as section 2 shows. What is not standard, and what the queued 0.5.0 work is mostly about, is the coordination layer across workers that gh-aw does not model:

- Workers outside Actions with no credential held by the repository (spec:7, 9).
- A lock that GitHub itself enforces for every kind of worker, by refusing a second push of the name (spec:3), and a fence against git's own lease behaviour (F7, DESIGN.md:792).
- "main moved" told by state once per commit of the default branch, so a worker learns it must bring main in whichever run finds it (spec:55; F12 at DESIGN.md:817). gh-aw's queue delivers effects through safe-outputs, whose `update-branch` and rebase advice are delivery steps (reference/safe-outputs-pull-requests.md:150, 194-196); nothing tells a worker that its branch has fallen behind.
- Overlaps: which open work touches the same files and in what order it should land (spec:73; F2, F13).
- The idle release with its undo and its rename, and the stuck-claim recovery still queued.
- A validation harness that checks the library against an oracle written from the spec's text, with mutants proving the checks bite (validation/DESIGN.md, Summary at line 12; known.json lists F2, F4, F9, F13 and F14 as the red traces still open).

gh-aw's spec says its own liveness and fairness claims "need independent deviation/liveness evidence and conformance checks" (specs/work-queue-specification.md, section 10 item 4). Symphony's harness is the thing that gives that evidence for Symphony's rules. That is not reinvention; it is the part neither side can skip.

## 5. The concurrency page

gh-aw's "Concurrency Control" is GitHub Actions' own `concurrency:` key, filled in by the compiler: per-workflow groups keyed on the workflow name plus the issue, pull request, branch or label, cancel-in-progress only for pull request events, `queue: max` emitted by default where cancel-in-progress is off, and a per-engine group `gh-aw-{engine-id}` so one agent job runs per engine (reference/concurrency.md:9-30). It serializes runs. Symphony uses the same key at the same layer: board.yml has `group: board` and `cancel-in-progress: false` (symphony-template .github/workflows/board.yml:86-88) and pull request #70, merged on 2026-10-14 as cb83274, added `queue: max`, the key gh-aw's compiler writes by default; gh-aw writes it on groups keyed per issue, pull request or ref (reference/concurrency.md:16-26, opt out with `features.group-concurrency-queue: false`), so it corroborates the key, not the board's shape, one group for the whole repository. The claim and lease model is a layer above, and the pattern page says a concurrency group "does not protect against other workflows or humans editing the issue" (patterns/workqueue-ops.md:112).

## 6. The compile step, and static analysis

What `gh aw compile` does: it "extracts the YAML frontmatter, validates it against the workflow schema, validates expression safety (only allow-listed GitHub Actions expressions), and resolves imports" (reference/compilation-process.md:20), builds the jobs, pins every action to a SHA, and writes a `.lock.yml` (:50-58). Optional scanners are actionlint, zizmor, poutine and yamllint; `gh aw validate` runs them all without emitting; `--strict` refuses write permissions, unpinned actions and wildcard network domains (setup/cli.md:340-404). One advisory check reads the prompt and warns when it names a tool the allowlist denies (compilation-process.md:22).

What it does not do: "This layer constrains what components may be loaded and how they may be connected, but it does not constrain runtime behavior" (introduction/architecture.mdx:429), and "the markdown body is loaded at runtime, you can edit instructions without recompilation" (compilation-process.md:14). The agent's instructions are not compiled, and nothing at compile time checks that two workers cannot take one task or that a claim is released. That is the class of bug Symphony's harness exists for.

Symphony's equivalent: scripts/check.sh runs the docs check, the vendored-hash check, the workers registry check and 561 unit tests, and the library's harness checks the protocol against an oracle. Nothing lints or security-scans the eleven hand-written workflows. That is a real gap and a cheap one: actionlint and zizmor are standalone tools ci.yml could run without gh-aw, subject to the no-new-dependencies rule, which says such a proposal is an issue first (.claude/rules/writing.md:6).

## 8. What adopting gh-aw looks like, from the workshop repository

githubnext/gh-aw-workshop at d8c57ab carries 22 markdown workflows, one shared guidelines file they import, and 22 lock files; q.md is 304 lines and its q.lock.yml 2,065, and the workflows directory is about 50,000 lines in all. Every lock file's first line records the compiler (v0.88.4), strict mode and the engine (`"agent_id":"copilot"`), and its manifest pins seven container images per run: the firewall agent, api-proxy and squid, the MCP gateway, github-mcp-server, a node image and alpine (q.lock.yml:1-2). Every one of the 22 workflows declares `copilot-requests: write`, with no engine key, so the engine is the default, Copilot, so inference is billed to the organization's Copilot plan (reference/auth.mdx:108); 20 of the 22 run on a schedule, one on a slash command, and none uses the work queue. aw.json schedules a weekly auto-upgrade of the compiler, and the compiler generates its own maintenance workflow. The owner's steps are `gh extension install github/gh-aw`, `gh aw init`, `gh aw compile` after every frontmatter change, and the secrets each lock file lists (GH_AW_GITHUB_TOKEN, GH_AW_GITHUB_MCP_SERVER_TOKEN, GH_AW_CI_TRIGGER_TOKEN). This is a heavier footprint than Symphony's eleven workflows, in exchange for the sandbox, the pins and the safe-outputs.

## 9. Copilot dynamic workflows

A dynamic workflow is not gh-aw. It is a Copilot CLI and Copilot App feature in public preview, behind `--experimental`: "a program that defines how a task is carried out", written as an `extension.mjs` in a session, a personal directory or `.github/extensions/`, run by the CLI in the background of a chat session or from a script with `copilot workflow run` (github/docs content/copilot/concepts/agents/dynamic-workflows.md; how-tos/use-copilot-agents/use-dynamic-workflows.md). It is Copilot's version of the orchestration this very answer was produced with: Claude Code's Workflow tool has the same shape, phases, parallel subagents, limits, pause and resume.

What it requires and where it runs: a Copilot plan ("available to users on all Copilot plans except Copilot Pro and Pro+ subscribers on existing annual plans"), AI credits, and the host is wherever the CLI runs, your machine or a CI runner you supply with `COPILOT_GITHUB_TOKEN`; GitHub hosts nothing. The agents are Copilot's; Claude models may be picked through Copilot, but Claude Code is not the agent. Guardrails: limits on concurrent subagents, total subagents, active time and approximate AI credits; subagents inherit the session's permission grants and prompt for more in an interactive session, while `copilot workflow run` "does not display permission approval prompts" and denies what was not granted up front; and "An extension can also run its own code directly, outside these permission prompts".

What it is for: orchestration inside one run by one orchestrator. Symphony's protocol is coordination between runs: independent sessions, people and routines, across hours and accounts, on one repository. A dynamic workflow does not know another session exists. So Symphony's workers would gain nothing from it that Claude Code's own Workflow and Agent tools do not already give a session today, and the purpose, coordination for Claude Code agents, does not survive a switch to Copilot-run workflows, because the agent would no longer be Claude Code.

## 10. The two choices, and what survives of 0.5.0

Keep building. Everything queued survives: F4 (dealing, draft symphony-protocol#23), F14, F9, F13, F2, F8, the stuck-claim recovery, harness steps 7 and 8, and 0.5.0 in the last library pull request, in the order protocol-fixes.md gives. Add two cheap items: merge #70 (queue: max, the key gh-aw's compiler writes by default, on narrower groups; merged on 2026-10-14 as cb83274) and open an issue for actionlint and zizmor in check.sh. Keep the Phase 3 rails as planned; gh-aw's credit and rate limits are compiler features you cannot take without the compiler.

Adopt gh-aw as the workflow layer and keep only what it cannot do. Precondition: change the credential decision, to ANTHROPIC_API_KEY, Anthropic WIF or Copilot billing for Actions workers, since the subscription token is refused. Then workers.yml, claude.yml and coordinator.yml's Claude runs become compiled gh-aw workflows with safe-outputs, the sandbox and the pins; the Phase 3 rails collapse to frontmatter; the Phase 6 QA gate's run side is threat-detection and staged mode. The protocol library stays whole, because a gh-aw worker that claims an issue still claims by pushing claude/N like any worker, so F4, F14, F9, F13, F2, F8, the stuck claim and the harness all survive unchanged; only F4's template half (the dealing job in workers.yml) is re-expressed in gh-aw's dispatcher or dropped, and the Phase 4 runtime design shrinks, since the compiler becomes the runtime for Actions workers. Cost: the owner's sessions and crowd contributors still run on their own accounts and are still outside gh-aw, so two worker kinds exist; and your repositories take on gh-aw's upgrade cadence (weekly in the workshop) and its lock files.

Stop and switch to gh-aw's native queue or to Copilot dynamic workflows. Loses the person's sessions as workers, the subscription-token model, crowd mode, and Claude Code as the agent in the Copilot case. The 0.5.0 queue would be abandoned, not finished, and the product would be a different product.

## Recommendation

Keep building. Take the two cheap wheels now. Write the credential fact and the maturity fact as a Decision line so the question is not reopened each week, and put "measure gh-aw's worker lane on the canary" on the list for the day its Claude engine takes a subscription token or you choose to pay for inference in Actions. This note changes no plan; the choice is yours.

## 11. Addendum: Copilot as coordinator, Claude Code as workers, and four checks

The owner's last variant: Copilot-coordinated dynamic workflows that invoke Claude sessions. Checked against the files:

- Which secret each gh-aw engine needs. The Claude engine has three routes: ANTHROPIC_API_KEY as a repository secret; Anthropic workload identity federation, which stores no secret but is still API-billed; and Copilot inference, `engine: claude` with `model: copilot/<claude model>` and `permissions: copilot-requests: write`, where "no PAT, COPILOT_GITHUB_TOKEN secret, or ANTHROPIC_API_KEY is required", inference is billed to the organization's Copilot plan, and the default sandbox holds the GitHub credential (engines/claude.md:18-35; auth.mdx:108, 123). The Copilot engine takes the same `copilot-requests: write`, else a fine-grained PAT in COPILOT_GITHUB_TOKEN; OAuth user tokens are rejected at activation (engines/copilot.md:17-18; auth.mdx:138, 159). So Claude Code can be gh-aw's agent with no credential stored, at the price of an organization Copilot subscription with centralized billing.
- Whether gh-aw's pattern prevents double claims, recovers stale claims and tells main moved. The native queue prevents double claims by granting Claims from one dispatcher ("the agent does not choose which task receives a Claim", patterns/workqueue-ops.md:27); the lightweight alternatives do not ("do not provide ... Claim authority", :112). Stale claims: "locks never expire or get stolen" (reference/work-queue.md:310), a reservation is released only on "exact termination or definitive nonlaunch evidence" (:422), and "Automatic crash recovery that can safely clear these fences is not implemented" (:321), so there is no time-based release like Symphony's 24 hours. Main moved: no file in pkg/workqueue outside tests mentions a branch behind, rebase or mergeable (grep over pkg/workqueue/*.go); the landing mechanics live in safe-outputs as delivery steps, `update-branch` merging the base in, a rebase left to the author, `auto-merge`, and an experimental `merge-pull-request` that refuses the default branch (reference/safe-outputs-pull-requests.md:150, 194-196, 251-254; reference/frontmatter-full.md:9962-9965), so the notice to the worker and the order by file are absent; the mechanics are not.
- Where Symphony's workers run and who holds the credential. A person's sessions run where the person is, local or cloud, and a routine on that person's account (docs/agents/WORKERS.md:7-10). But GitHub does hold a Claude credential in the default mode: the workers in Actions and @claude run on "the secret CLAUDE_CODE_OAUTH_TOKEN, from one account's claude setup-token" (docs/project.md:41; workers.yml:134; claude.yml:65). Only crowd mode holds nobody's credential (CLAUDE.md:41). So "GitHub holds only state" is true of the protocol and of crowd mode, not of the template's Actions workers.
- Whether a dynamic workflow can dispatch to a Claude session outside Actions. It runs where the Copilot CLI runs and can "run commands, use tools, or call other services" (dynamic-workflows.md, About), so on a host with Claude Code installed and signed in it could shell out to `claude -p`, and it can write GitHub state that Symphony's board then dispatches. gh-aw can also run a packaged dynamic workflow inside an Actions job (engines/copilot.md:69). There is no native hand-off to a session elsewhere; outward dispatch is whatever the host and its tokens allow, which is what the board already does with issues and labels.

Model as coordinator against rules GitHub enforces. Symphony already splits these: releases, overlaps, dealing and the board are code in the board's run on GITHUB_TOKEN; only epic planning is Claude (spec/PROTOCOL.md:67, 73, 77); and the lock is GitHub refusing a second push of claude/N (spec:3), which no model holds. A dynamic workflow is also code with agents inside it ("Everything is defined in code: the steps, when to involve agents"), but it is one program on one host for one run, with limits on its own subagents and no view of a session it did not start. Put Copilot in the coordinator's seat and the guarantees that survive are exactly the ones GitHub enforces, the claim lock and the required check, which are Symphony's; the lease release, overlaps and main moved would have to be rebuilt inside the workflow or kept in Symphony's board. Opinion, ahead of nothing now since the evidence is in: use dynamic workflows, or Claude Code's own Workflow tool, inside a worker when one run needs fan-out; keep the coordination between workers in the protocol.

## 12. At scale: the most GitHub-native way to test coordination

The owner's question on 2026-10-14: the most GitHub-native, and therefore least likely to break at scale, way to do autonomous programming in order to test coordination ability at scale; GitHub may store the Claude credentials. The limits cited are in gh-aw-vs-symphony.md section 4.

First, the credential point sharpened: storing a credential is not the constraint. gh-aw refuses the subscription token by design (reference/auth.mdx:219) and its three Claude routes are Anthropic API billing by key, Anthropic API billing by workload identity federation, or Copilot billing through `copilot-requests: write` on an organization Copilot plan (engines/claude.md:18-35). So putting the Actions workers on gh-aw moves their cost off the subscription plan; it does not matter where the token sits.

| Symphony's protocol on gh-aw-compiled workflows | Still Actions; adds a compiler, lock files, pinned actions, a sandbox and safe-outputs | The compiler's churn (five releases in a week) and lock regeneration on every upgrade; the per-engine default of one agent job per engine until overridden; the same board rate limit, unchanged; API or Copilot billing per worker run | The same as above for the protocol, plus gh-aw's per-run audit and OTel; only the Actions workers change |
| gh-aw's native work queue | A JSONL ledger on a branch, Claims from one dispatcher, dependencies, fairness | Its own words: a proposed design, "cannot promise indefinite growth", writes stop when rate limits are exhausted, a dead worker's reservation holds until an operator cancels it; workers only in Actions | Throughput and fairness of a dispatcher-fed queue of Actions workers; not humans, not sessions, no overlaps, no main moved |
| Copilot dynamic workflows | GitHub's own product, but hosted by the CLI on one machine | One host; public preview behind an experimental flag; approximate credit limits; no view of a session it did not start | Fan-out inside one run: subagents, credits, time; not coordination between workers |

The answer, in the owner's terms: the most GitHub-native state and lock are the ones Symphony already uses, issues and git refs, which predate Actions and do not churn; the most GitHub-native run plumbing is plain Actions, which Symphony uses, with gh-aw's compiled layer as a better-hygiene option that adds a weekly-moving dependency and a billing change. The native work queue is the least stable candidate today, and dynamic workflows are not a multi-worker system. The thing that breaks first in a scale test of Symphony is the board's token budget, which is a known, bounded fix (a budget in board.py, an App installation token with 5,000 an hour, and sharding by repository, since the protocol is per repository); RESEARCH-scale.md:239 already names it as the first measurement a large test should take.

## 13. What the verification pass added

A second, independent reading (five readers, three comparers through correctness, replaceability and skeptic lenses, one merge) reached the same four answers. It added these, each re-read on the checkouts:

- Standing. gh-aw is "an open-source GitHub CLI extension from GitHub" "built and maintained by the GitHub Next team", and its README says "Use it with caution, and at your own risk" (gh-aw about.md:11, 28; README.md:55). It is not a platform primitive.
- One lock, never two. A gh-aw worker is bound to one Actions run, "(run_id, run_attempt=1)" (specs/work-queue-specification.md:1110-1111; pkg/workqueue/lifecycle.go:516), and only `dispatch_next` may create Claims (spec:883). Moving the Actions leg onto gh-aw's native queue while sessions still claim by branch would put two claim authorities on one issue, against spec/PROTOCOL.md:3 and guarantee G1. So a migration keeps the branch push as the one lock for every worker and uses gh-aw, if at all, as the compiled run layer, not as the dispatcher.
- The dispatcher credential. gh-aw's dispatch "requires contents: write alongside actions: write on the trusted dispatch credential" (reference/work-queue.md:138-143), which a migration plan has to place.
- Dependencies. gh-aw specifies a task DAG with Issue and pull request gate nodes ("an issue predecessor needs fresh evidence that it is completed; a pull request predecessor needs evidence that it was actually merged", reference/work-queue.md:414-418) and admission checks for cycles (spec:1886). Symphony's dependency rules are its least-checked part: work waiting behind a blocker (U4) and the coordinator's planning by area (U3) have no invariant (validation/DESIGN.md:145-148); the overlap landing order is checked (G7, validation/properties.py:191-207), but F13 leaves open whether "the oldest" is the lowest number or the earliest work (DESIGN.md:822-826). That is the one place gh-aw's design is ahead on substance rather than plumbing.
- An attempt budget. gh-aw retries a failed attempt "within a finite attempt limit" and cancels the Work at exhaustion (spec:715-717); Symphony's release and re-claim name no limit (spec:67-69; claims.py:238-252), so an issue can be claimed, idled and released indefinitely. No finding records a harm from it, "no missed work" was the owner's aim, and spend is capped by the daily run limit, so it is not a 0.5.0 item; it is a question for the owner after 0.5.0.
- The evaluation itself. No document in either repository had considered gh-aw, GitHub Agentic Workflows or any outside queue (grep over both trees: nothing). Record this evaluation as a memory fact in the next protocol-fixes pull request, with the trigger for re-checking: gh-aw's Claude engine accepting a subscription token, or the owner choosing API or Copilot billing for Actions workers.

### Verdicts from the claim-by-claim pass

The pass finished after this note was delivered: 12 claims, each read by a refuter against both source trees, and 28 capability mappings, 24 of them re-verified (two groups' verifiers did not run). No verdict in the table changed and the recommendation stands. Five sentences were imprecise and are corrected above:

- `queue: max`: gh-aw's compiler writes it by default on groups keyed per issue, pull request or ref, not on one group for a whole repository as the board's is, so it corroborates the key, not the shape (section 5, section 10).

- The dispatcher's scopes: workers.yml already grants contents: write and actions: write on GITHUB_TOKEN (gh-aw-vs-symphony.md, section 6).

Two readings the pass added without changing a verdict: F4 is a wasted run, never a double claim, since the push lock still holds (DESIGN.md:777-779), and its fix is one dealer per run rather than gh-aw's serialized racing dispatchers; and a repository made from the template takes the library's newest `v*` tag, a release or not (symphony-protocol README.md:180; protocol.yml:8), which docs/memory/protocol-changes-come-from-symphony-protocol.md already records.

## 14. The last verification round, and what it did not reach

On 2026-10-14 a second round re-checked the six capability mappings and two claims the usage limit had skipped. Five mappings finished; each kept its verdict, with these corrections:

- The rails row was wrong on one point: "none while main is red" has a counterpart, `skip-if-check-failing` (reference/frontmatter-full.md:984-989), and in Symphony that cap is a Phase 3 decision not yet built in workers.yml.
- @claude carries over as is: gh-aw takes plain triggers with a top-level `if:`, so the mention need not become a /command.
- The dependency rule (.claude/rules/writing.md:6) allows GitHub's own actions, and github/gh-aw-actions is published by GitHub, so whether gh-aw breaks the rule is a ruling for the owner, not a given. What the rule clearly does not cover is the `gh aw` CLI, the sandbox's container images and gh-aw's exact SHA pins in place of major tags.
- Adding a worker costs more on gh-aw: a worker is a file under .github/workflows/, so the pull request that adds one needs the workflows permission, which GITHUB_TOKEN cannot hold, plus its compiled lock file. Symphony's worker JSON sits outside that folder. gh-aw's per-Work `worker_profile` is where area dealing would go.
- A 90-minute worker needs two limits raised on gh-aw: `timeout-minutes` and the agent job's own 60-minute default.
- The required check needs a token decision: a pull request a gh-aw agent opens or pushes with the default GITHUB_TOKEN starts no CI run, so Symphony's required check would not report on it unless another token (GH_AW_CI_TRIGGER_TOKEN, a PAT or an App) pushes.
- Cost accounting is a wheel gh-aw has: per-run usage artifacts, cross-run reports inside Actions through the `agentic-workflows` tool, episodes that total an orchestrated run's cost (reference/cost-management.md:66-76, 444), and a daily-cap ledger on a repo-memory branch. Symphony's usage artifact, list-price estimate and run cap are partly reinvented; its 30-day aggregates by work setting, its alone-versus-parallel ratios and its name-free record are not in gh-aw.
- Precision only: several line numbers in the capability map were off by a few lines; no verdict rested on them.
