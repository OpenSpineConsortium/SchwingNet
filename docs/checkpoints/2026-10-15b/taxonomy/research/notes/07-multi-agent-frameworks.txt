# 07 Multi-agent orchestration frameworks, interoperability protocols and parallel coding-agent tools (as of 2026-10-15)

Scope: where Symphony (claims, board, workers and coordinator for Claude Code agents, living in a GitHub repository and run on GitHub Actions) sits among agent frameworks, agent protocols and tools that run several coding agents at once. Star counts are GitHub search API values read on 2026-10-15 through the session's GitHub search tool; versions come from PyPI, npm and git tags read the same day. Clones used: /tmp/claude-research/07/ (ccpm, beads, spec-kit, mcp-spec, a2a, openai-symphony, aeon, backlogmd) and /tmp/claude-research/07/readmes/ (raw READMEs fetched from raw.githubusercontent.com).

## Takeaways

- The field splits into four layers that barely overlap: in-process agent frameworks (CrewAI, LangGraph, Microsoft Agent Framework, AG2, OpenAI Agents SDK, Claude Agent SDK), wire protocols (MCP, A2A, Agent Client Protocol), local parallel-session managers (claude-squad, Conductor, Crystal/Nimbalyst, Sculptor, Container Use, uzi, vibe-kanban) and work-queue coordinators for coding agents (openai/symphony, CCPM, Beads/Gas Town, paperclip, Orbi, cyrus, Contrabass). Symphony belongs to the fourth layer and is the only one found whose coordinator and board run as GitHub Actions jobs on the repository itself.
- None of the general frameworks coordinate through a forge. Their state lives in process memory, a checkpointer database (LangGraph, MAF), a hub with a write-ahead log (AG2 1.0 Network) or a Flow state object (CrewAI); none runs as a CI job by design. They are libraries to build agents with, not protocols for many independent agent sessions sharing one repository.
- Claude Code itself now has five ways to run agents in parallel (subagents, agent view, agent teams, Projects, dynamic workflows). The one with claims, agent teams, uses a file-locked task list under ~/.claude/tasks on one machine, inside one session, is experimental, and does not run under claude -p, so it cannot run in CI. Symphony's claim protocol is the cross-session, cross-account, cross-machine layer those features lack.
- Name collision: openai/symphony (27,697 stars, Apache-2.0, created 2026-02-26) is an issue-tracker-driven orchestrator for Codex with its own "claim" states. It is the closest conceptual neighbor and shares the product name. Its claims live in one daemon's memory; Symphony's live in git refs on GitHub.
- Every single mechanism Symphony uses has prior art: branch creation as an atomic lock (terraform-backend-git, 2020; shogo82148/actions-mutex, 2020; ben-z/gh-action-mutex, 2022; DND-IT/action-lock, 2026, which even expires a lock by the commit date of its ref, as Symphony's 24-hour release reads the committer date of the branch head), lock files in a shared git upstream for parallel Claudes (Anthropic's C compiler, 2026-02-05), idle-claim release on a forge (zulipbot: one week idle, then 3 days, then unassign), and leases in general (Gray and Cheriton, SOSP 1989; Kubernetes Lease). No tool found combines them into one work-queue protocol for agents.
- Atomic claims elsewhere are atomic only inside one store: Beads (one Dolt database, "first claim wins"), paperclip (one server, "atomic task checkout"), NEEDLE (one SQLite queue), Claude Code agent teams (one machine's file lock). Symphony's atomicity comes from the forge's ref update, which every account and machine shares, at no server cost of its own.
- Leases with timeouts exist in MCP coordination servers (mcp_agent_mail file reservations with ttl_seconds; swarm-protocol heartbeats every 10-15 min; Concord stale-claim flags), but they are advisory and need a server process; Symphony's release is enforced by the board workflow and visible as labels, comments and a renamed branch.
- GitHub's own agent products confirm the Actions-native direction: Copilot cloud agent runs on a GitHub-hosted Actions runner (ubuntu-latest) by default, and Copilot, Claude and Codex coding agents on GitHub consume Actions minutes plus AI Credits. Actions is free on standard hosted runners for public repositories, so Symphony's board and coordinator cost nothing to run on a public repository; the Claude work itself still draws on a Claude subscription.
- Churn is high: AutoGen is in maintenance mode (successor MAF 1.0 on 2026-04-02), AG2 1.0 dropped the classic API (2026-07-27), MCP 2026-07-28 removed sessions and the initialize handshake, IBM's ACP merged into A2A and archived, AGNTCY's ACP spec archived, vibe-kanban's company shut down (2026-04-10), Crystal deprecated (2026-02), MetaGPT's open source has had no PyPI release since 2025-03-09. A protocol defined on GitHub primitives (refs, labels, issues, Actions) is less exposed to that churn than one built on any of these.

### Q1b Claude Code's own parallel features (code.claude.com, read 2026-10-15)

- Claude Code lists five ways to run several tasks at once: subagents, agent view, agent teams (experimental, off by default), Projects (public beta on Pro and Max) and dynamic workflows; worktrees, cross-session messaging and /batch (5 to 30 worktree-isolated subagents) support them. "Agent teams don't isolate teammates in worktrees." [Verified] https://code.claude.com/docs/en/agents
- Subagents: definitions in .claude/agents/, ~/.claude/agents/, managed settings, --agents or plugins; `isolation: worktree` runs one in a temporary worktree branched from the default branch; nesting up to three layers (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH); 20 concurrent subagents by default (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS). [Verified] https://code.claude.com/docs/en/sub-agents
- Agent teams: enabled by CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1; a lead, teammates, a shared task list and mailboxes; "Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously"; tasks pending, in progress, completed, with dependencies; state at ~/.claude/teams/{team}/config.json, ~/.claude/teams/{team}/inboxes/{agent}.json and ~/.claude/tasks/{team}/, "never uploaded"; limits: one team per session, no nested teams, lead fixed, no resumption of in-process teammates, "Task status can lag". "In non-interactive mode with the -p flag, including Agent SDK sessions, Claude doesn't spawn teammates." [Verified] https://code.claude.com/docs/en/agent-teams
- Agent teams cost: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode". [Verified] https://code.claude.com/docs/en/costs (section Manage agent team costs).
- Dynamic workflows: a JavaScript script with agent(), parallel(), pipeline(); up to 16 concurrent agents by default (1 to 256 via CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS), 1,000 agents per run, 4,096 items per parallel()/pipeline(); available in claude -p and the Agent SDK; resumable within a session; saved under .claude/workflows/. [Verified] https://code.claude.com/docs/en/workflows. [Inferred] a Symphony worker in Actions could fan out inside one job with a workflow, but workflows give no cross-job claim.
- Cross-session messaging (v2.1.224+): ListAgents/SendMessage between a user's sessions; same machine over a per-session Unix socket or named pipe, other machines and cloud sessions through Anthropic servers via Remote Control; plain text, at most 100 held messages, at most 50 queued, refuses about 1 million characters. It is per user; it carries no claim or lock. [Verified] https://code.claude.com/docs/en/cross-session-messaging
- Projects (claude.ai/code): one conversation that starts threads, usually cloud sessions; "A cloud thread works on its own branch and opens a pull request"; project memory with a MEMORY.md index; instructions up to 16,000 characters; "The enforced limit is 200 new threads per day across your projects"; Pro and Max only, not Team or Enterprise yet. [Verified] https://code.claude.com/docs/en/claude-projects (saved output lines 7, 52, 291-292, 412). [Inferred] Projects coordinate threads of one account; Symphony coordinates sessions of many accounts through the repository, which matches the project's own decision that "the repository is what is shared" (/home/user/symphony-template/CLAUDE.md, Durable decisions).
- anthropics/claude-code: 151,043 stars; proprietary licence ("All rights reserved", Commercial Terms); npm 2.1.300 on 2026-10-14. [Verified] /tmp/claude-research/07/lic/anthropics_claude-code.txt; https://registry.npmjs.org/@anthropic-ai/claude-code.

### Q2 Which are closest to Symphony's model, and exactly where each differs

Symphony's model for reference: queue = GitHub Issues labelled todo; claim = first push of branch claude/N whose first commit adds docs/agents/claims/N.md ("GitHub refuses the second push of the same name"); release after 24 hours with no commit by the committer date of the head (labels off, then a release comment, then the board renames the branch to released/N-<sha>); board = STATE.md on branch board, rewritten by .github/workflows/board.yml on every issue, pull request and branch event and every six hours; the coordinator is a step of that workflow on GITHUB_TOKEN, while planning of epics is Claude in coordinator.yml; workers of one Actions run are dealt from one look (tools/team.py deal). [Verified] /home/user/symphony-template/docs/agents/PROTOCOL.md lines 3, 29, 37, 49-51, 59; .claude/skills/claim/SKILL.md lines 8-16.

- openai/symphony. Same: issue tracker as queue (GitHub Issues is one adapter), per-issue workspace, policy file in the repo, explicit claim and release states, stall detection. Differs: one daemon is the only authority and keeps claims in memory, so two orchestrators on one tracker are not coordinated; runs on a host, not in CI; Codex app-server only; no board artifact beyond a status surface; restart clears blocked state. [Inferred] from SPEC.md lines 16-150, 635-850.
- CCPM. Same: GitHub Issues as the record, epics decomposed into sub-issues, labels for state, worktrees, the repository's files as context. Differs: claim is an assignee plus a label, which two agents can both set (no atomic primitive); one worktree per epic shared by several streams; no idle release; the user's main session is the coordinator; nothing runs in CI. [Inferred] from execute.md lines 130-210.
- Orbi. Same: GitHub Issues with a dispatch label, branch per issue, independent review, merge gate, blocked label. Differs: one local runner on a 5-minute systemd/launchd timer; the claim is a local branch and worktree, pushed only at closeout, so it is not a distributed lock; AGPL-3.0. [Inferred] from orbi-build_orbi.md lines 58-82.
- Beads and Gas Town. Same: a claimable "ready" frontier, atomic claim, dependency unblocking, a merge slot and a merge queue, data carried on a git ref (refs/dolt/data). Differs: atomic only inside one Dolt database; across machines the claims merge after the fact; release is manual; coordinator (Mayor, Witness, Deacon) is a local process; needs Dolt. [Inferred] from the Beads and Gas Town findings above.
- Claude Code agent teams. Same: shared task list, self-claim of the next unblocked task, dependencies, a lead that plans. Differs: one session, one machine, one account; file lock on ~/.claude; experimental; not available in claude -p, so not in CI; no worktree isolation; state never uploaded. [Inferred] from the agent-teams page.
- Anthropic's C compiler harness (16 agents). Same: no central orchestrator, claims are files synchronized through a shared git upstream. Differs: lock files on the shared main line, so collisions surface as merge conflicts; no lease; no board; Docker containers on one host. [Inferred] from https://www.anthropic.com/engineering/building-c-compiler (fetched).
- DND-IT/action-lock. Same: GitHub ref creation as the atomic primitive (HTTP 422 when it exists), staleness from the commit date of the ref's SHA (stale_threshold 600 s), runs in Actions. Differs: a generic mutex for CI jobs, released by deleting the ref; no work queue, labels or board. [Verified] /tmp/claude-research/07/readmes/DND-IT_action-lock.md lines 1-66.
- Backlog.md. Same: board rendered from files in the repository, including branches active in the last 30 days; one task per agent session and one PR per task. Differs: no claim primitive; local CLI; no release. [Inferred] from the Backlog.md findings.
- mcp_agent_mail, swarm-protocol, Concord. Same: leases with TTL or heartbeat, stale-claim detection. Differs: advisory, state in a server process (SQLite plus Git, or a hosted service), not in the forge; trust-based identity. [Inferred]
- Copilot cloud agent and Agent HQ. Same: GitHub-native, runs on Actions runners, starts from an issue, ends in a pull request. Differs: a person assigns the agent; one agent per task; no peer claim protocol or lease; billed in AI Credits; one vendor's control plane. [Inferred] from the github/docs findings.
- aeon. Same: Actions-native schedule, state in git and issues, subscription token accepted. Differs: one agent's skills, no claims between workers. [Inferred]
- [Inferred] No neighbor found combines all of: an atomic forge-side claim, a lease measured from repository state, a release that keeps the work (rename to released/N-sha), a board rendered by CI from repository state, a coordinator that is a CI step on GITHUB_TOKEN, and workers on different Claude accounts. ### Q3 Prior art: git ref creation as a distributed lock, and lease-based claims on a forge

- terraform-backend-git (plumber-cd, created 2020-04-12, 336 stars): "State locking would be based on branches, as creating a new branch is atomic operation. To acquire a lock - it would mean to push a branch named locks/${file}. The branch would need to have a file ${file}.lock added and committed to it ... If pushing the branch fails with error saying that fast forward push is not possible - that would mean something else already acquired the lock ... To unlock - would mean to simply delete that remote branch." No stale-lock expiry is described in the README. This is the same shape as Symphony's claim (branch plus a claim file in its commit). [Verified] /tmp/claude-research/07/readmes/tbg.md lines 340-380; grep for expire, timeout, stale, force-unlock returned nothing.
- shogo82148/actions-mutex (created 2020-12-27, archived, 23 stars): pushes a commit with a random string to branch actions-mutex-lock/<key>; "If the pushing succeeds, it means that no concurrent jobs run." [Verified] shogo82148_actions-mutex.md lines 82-101; GitHub search.
- ben-z/gh-action-mutex (created 2022-03-26, 91 stars): spinlock where "test-and-set functionality is provided by Git, where a git push can only succeed if the commit to be pushed is a fast-forward of what's on the remote"; motivated by GitHub Actions concurrency keeping "a queue of length 1". [Verified] ben-z_gh-action-mutex.md lines 23-56.
- DND-IT/action-lock (created 2026-02-20, archived, replaced by DND-IT/tamci): refs/locks/<name>; "A ref can only be created once - if it already exists, the create call returns 422"; "If a lock has been held longer than stale_threshold seconds (based on the commit date of the SHA), it's automatically removed and re-acquired"; default 600 s. [Verified] DND-IT_action-lock.md lines 3-66.
- Anthropic, "Building a C compiler with a team of parallel Claudes" (Nicholas Carlini, 2026-02-05): "Claude takes a lock on a task by writing a text file to current_tasks/"; "If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one"; "I don't use an orchestration agent"; 16 agents in Docker containers with the repo at /upstream; nearly 2,000 sessions, 2 billion input and 140 million output tokens, just under $20,000. [Verified] https://www.anthropic.com/engineering/building-c-compiler
- Other small projects treat a pushed branch as a held claim (marcelusfernandes/agentic-setup issue #157, "reconcile and claim read a codex/task-<n> branch as a held lock", repo created 2026-09-05, 0 stars). [Reported] search result title and snippet; repository existence Verified by GitHub search.
- Leases as a concept: Gray and Cheriton, "Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency", SOSP, December 1989. [Reported] search (courses.cs.duke.edu PDF mirror). Kubernetes Lease objects: every kubelet heartbeat updates spec.renewTime on a Lease; also used for leader election. [Verified] https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/architecture/leases.md lines 12-30.
- Lease-based claims on a forge for human contributors: zulipbot ("@zulipbot claim" assigns and labels "in progress"; after a week without updates it asks the assignee; with no reply in 3 days it "will automatically remove the issue's current assignee(s) and the in progress label"). [Verified] https://raw.githubusercontent.com/zulip/zulip/main/docs/contributing/zulipbot-usage.md lines 16-86. apb7/unassign (Probot app, ping then unassign, e.g. 7 and 10 days) and an Apache Burr pull request reporting that bot comments reset an inactivity clock. [Reported] search "GitHub action unassign issue after days of inactivity".

## Claims worth verifying

- "GitHub refuses the second push of the same name" (PROTOCOL.md line 3; claim skill line 8). What git actually refuses is a non-fast-forward update: a second worker whose commit descends from the holder's tip (for example after fetching claude/N and committing on it) would be accepted. The fast-forward rule, plus the protocol's instruction to branch from the default branch, is what gives exclusion, exactly as terraform-backend-git and gh-action-mutex describe. A strictly create-only claim would be `git push --force-with-lease=claude/N: origin claude/N` (empty expected value) or the REST create-ref call (422 when the ref exists, as DND-IT/action-lock uses). The vendored push guard fences only --force-with-lease onto claude/N by reading the claim file on both sides (/home/user/symphony-template/tools/sdlc_protocol/guard.py docstring lines 1-45) and lets through what it cannot judge, so a plain fast-forward push onto another worker's claude/N would pass both the guard and GitHub; it would leave the holder's claim file in place, so the claim itself is not stolen, but "never push to another worker's branch" rests on the rule, not on a refusal. [Inferred] Worth an adversarial test.
- The name "Symphony" collides with openai/symphony (27,697 stars, Apache-2.0), which is also about claiming issues for coding agents; search and positioning risk.
- A2A v1.0 date: primary CHANGELOG says 2026-03-12; secondary sources say January, March or April 2026. Whether A2A sits under the AAIF or a separate Linux Foundation project is unresolved.
- Microsoft Agent Framework GA: PyPI shows 1.0.0 on 2026-04-02; secondary sources say April 2 or 3.
- "Approximately 7x more tokens" for agent teams holds "when teammates run in plan mode" only; do not quote it as a general multiplier.
- paperclip shows 102,621 stars seven months after creation; a check against star-inflation or a hosted-product user base would help before citing it as adoption.
- Beads has no claim lease or timeout: based on a grep of docs/ only; the Go source was not read.
- terraform-backend-git has no stale-lock expiry: based on its README only.
- Copilot cloud agent billing after June 2026 (AI Credits instead of premium requests) comes from the current github/docs page plus secondary sources; the transition date is Reported.
