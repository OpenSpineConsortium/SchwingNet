# Beethoven launcher: what it is and how it works (research notes 04)

Written 2026-10-15 from the local clones (each checked equal to its GitHub main with git ls-remote the same day: hpcworker 3b22e70 of 2026-10-07, beethoven-extension a239ae5 of 2026-10-15, beethoven-sites 83f34e8 of 2026-10-08, beethoven-base a8e545d of 2026-10-09, beethoven hub cb41b4a of 2026-10-09), the public site clone, Anthropic's and GitHub's own documentation fetched today, and web searches. Grades: Verified = primary source opened by me; Reported = secondary source or search summary only; Inferred = my reasoning from cited facts. Paths are relative to /home/user unless absolute.

## Takeaways

- What it is: Beethoven (the launcher) puts a student's own Claude Code session, running as an ordinary Slurm batch job on a compute node of their university's cluster, inside claude.ai/code and the Claude phone app. Two pieces do the work: hpcworker (bash 4.2 + Python 3.6 framework on the cluster, framework VERSION 18) and the Beethoven Chrome MV3 extension (20.0.0), a launcher and diagnostics panel that talks to one origin, the university's Open OnDemand (OOD) portal. Everything else (site modules, beethoven-base, the access service, the VS Code and Desktop editions) is support.
- The mechanism is Anthropic's own shipped feature, not a hack: `claude remote-control` runs under tmux inside an Apptainer image in the job, registers with api.anthropic.com over outbound HTTPS and polls for work; claude.ai becomes the window. No inbound port, no API key, no vendor relay, no Claude credential touched by the vendor. The design replaced an earlier claude.ai fetch-interception design that the project's own research report rejected on Consumer Terms grounds.
- Category (Inferred): a bring-your-own-subscription, no-admin-install agent launcher for HPC; a "phone/web front end for a supervised coding agent inside a batch job". Nearest neighbors are center-run module installs of Claude Code/Codex used from a login-node or OOD terminal, VS Code tunnels inside Slurm jobs, OOD Interactive Apps, Anthropic's Claude Science SSH hosts (desktop-to-login-node, sbatch per job) and Anthropic's self-hosted environments (Team/Enterprise beta). No search found any other tool that launches Remote Control from an sbatch job through OOD.
- What is unique (Inferred from cited facts): (1) runs entirely on surfaces every OOD 3.x/4.x site exposes without administrator help; (2) nothing persistent on the login node, one sbatch per action, polling >= 60 s, designed to the strictest of 12 sampled site policies (Wayne State: 20-process cap, VPN-only portal, CentOS 7); (3) the worker queues its own successor before wall time so it stays on; (4) a 17-check probe/diagnostics model that explains each failure in one sentence; (5) a data-only site-module layer so a new university is a JSON pair, not code.
- GitHub role: GitHub is Beethoven's development, CI, release and distribution substrate, not its runtime. All five launcher repositories checked are private (verified by API today), so the "free unlimited Actions minutes for public repositories" argument does not apply to Beethoven as it stands: its hosted-runner minutes draw on the organisation's private quota (2,000 min/month on GitHub Free for organizations, 3,000 on Team). Its cluster-side CI lane runs as Slurm jobs on the grid itself and posts GitHub commit statuses, which consumes no Actions minutes because GitHub's runners cannot reach the VPN-only grid.
- Contrast with Symphony (Inferred): Symphony runs Claude in GitHub Actions on a `claude setup-token` subscription token; Beethoven forbids exactly that (no setup-token, no CLAUDE_CODE_OAUTH_TOKEN, "no CI that runs Claude Code on a key or a token"), because Remote Control needs a full-scope `claude auth login` sign-in and the project's rule is that the vendor never handles a Claude credential. The two share the Chrome Web Store release kit and the GitHub-as-plane habit, not the Actions runtime.
- Cost: the student pays for their own Claude Pro or Max (Remote Control usage shares the plan's one limit with chat); the university pays compute through its normal allocation; the vendor runs only a Cloudflare Worker (access check) and static pages; the Trial Edition is free of charge and no paid edition exists.
- Status and licence: pre-release, proprietary ("All rights reserved"; "Private and proprietary"), vendor Gregory Schwing trading as OpenSpineConsortium; one deployment (Wayne State, site `wayne`, lab `oschome`); Chrome Web Store listing public since 20.0.0 (2026-10-11/13) but every worker still needs the vendor's per-account approval; written approval from Wayne State C&IT and a written answer from Anthropic are stated preconditions of any paid edition.
- Binding constraints are policy, not technology: Wayne State's AI guideline ("All AI tools must first be approved by C&IT; third-party AI bots are not approved for use at this time"), no BAA on a personal plan, Remote Control unavailable under ZDR or the HIPAA configuration, transcripts stored on Anthropic's servers while connected. Beethoven answers with supervised mode by default, a restricted-folder refusal, disclosure at every start and a rule that patient data never leaves the grid.
- Documentation drift to watch: hpcworker/README.md still says extension 10.0.0, framework VERSION 8, agreement version 7 and privacy version 8, while the code says framework 18 and the extension's texts say agreement 14 / privacy 15; the extension README places the access service in beethoven-vscode while hpcworker's README says it moved to beethoven-access on 2026-10-07; the research report's heading says a "six-call adapter" while its body specifies eight calls.

### 2. The mechanism (Remote Control from a Slurm batch job, OOD, outbound HTTPS, own sign-in)

- Data path diagram: browser/phone <- outbound HTTPS only, from the job -> api.anthropic.com; extension -> https://ondemand.<university>.edu -> login node -sbatch-> compute node (tmux > apptainer exec > claude remote-control), job writes status.json, connection.json, rc.log to shared storage read back through OOD Files [Verified] beethoven-extension/README.md:86-101; hpcworker/README.md:55-70.
- The job, in order: node-local temp, XDG_RUNTIME_DIR fix, per-job token, status.json (starting), `claude auth status` "never the credential", "queue its own successor so the worker is always on (one successor per link, started by the scheduler when this job ends; a stop file ends the chain)", start `claude remote-control` "inside the container under a pseudo-terminal (tmux, or `script` with a held-open pipe)", parse session name and link from rc.log into connection.json, heartbeat, leave cleanly on SIGTERM [Verified] hpcworker/framework/jobs/worker.sbatch.tpl:1-14; launch line at :287-317.
- Consent handling: Claude Code's own `"remoteDialogSeen": true` and `hasTrustDialogAccepted` are the only keys read from its config; a marker file the panel writes on the student's acknowledgement is the fallback, and the job answers y once from either record [Verified] hpcworker/framework/jobs/worker.sbatch.tpl:16-24; marker paths `$HOME/.beethoven/claude/.beethoven-remote-consent` (and the older .ashley- name) are a product-layer field [Verified] hpcworker/framework/profiles/wayne.json (consent_markers); beethoven-sites/README.md:16.
- Anthropic's Remote Control, today: "available on Pro, Max, Team, and Enterprise plans. API keys are not supported. On Team and Enterprise, an Owner must first enable the Remote Control toggle"; "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine. When you start Remote Control, it registers with the Anthropic API and polls for work."; `--capacity` default 32; workspace trust prompt exits with "Workspace not trusted" when stdin/stdout is not a terminal (why tmux is needed); server mode "gives up after roughly 10 minutes" offline; `--continue` resumes "for about four hours after the server stopped"; setup-token and CLAUDE_CODE_OAUTH_TOKEN "can only make model requests" and cannot establish Remote Control; unavailable with CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, DISABLE_GROWTHBOOK, a non-Anthropic ANTHROPIC_BASE_URL, Bedrock/Agent Platform/Foundry [Verified] https://code.claude.com/docs/en/remote-control (fetched 2026-10-15).
- Launch history: announced 2026-02-24/25 as a research preview for Max, "coming soon" to Pro; TechRadar at launch said not for Team or Enterprise, which today's docs supersede [Reported] TechRadar "Anthropic reveals Remote Control..." https://www.techradar.com/pro/anthropic-reveals-remote-control-a-mobile-version-of-claude-code-to-keep-you-productive-on-the-move ; Gigazine https://gigazine.net/gsc_news/en/20260225-claude-code-remote-control .
- Sign-in stays in Anthropic's flow: the extension opens Anthropic's sign-in page, the student signs in and pastes the code into the panel; "The code is typed once into the sign-in sitting running on a compute node and is not kept"; "the sign-in must complete through Anthropic's own flow, so the extension opens the page and takes the code from you, and never reads it from an Anthropic page or from your clipboard" [Verified] beethoven-extension/README.md:125-135. Rule source quoted in the report: developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" [Verified as quoted] hpcworker/docs/RESEARCH_REPORT.md:5.
- No credential handling: "no `setup-token`, no `CLAUDE_CODE_OAUTH_TOKEN`, no reading of Claude Code's credentials file, no multi-account rotation"; the framework reads `claude auth status` and two yes-or-no keys [Verified] beethoven-extension/README.md:157-164; hub rule "No API key anywhere ... no CI that runs Claude Code on a key or a token, no usage credits" and "Never a Claude credential" [Verified] beethoven/CLAUDE.md:22-27.
- OOD surfaces chosen for version stability: Shell WebSocket frames `{"input": ...}` "identical in v2.0.32, v3.0.3, v3.1.14, v4.1.0 and v4.2.5"; Files JSON routes; Active Jobs JSON; OOD has no public API ("It's not on our roadmap to open any API"); OOD at "over 2,100 organizations worldwide" [Verified as the report's claims, sources not re-opened] hpcworker/docs/RESEARCH_REPORT.md:29, 31, 33, 35.
- Login-node etiquette: "one `sbatch --parsable` through the shell, then the shell is closed"; the sign-in sitting holds the shell up to 10 + 10 minutes, panel closes after 15; "Scheduler-facing calls never faster than once a minute" [Verified] beethoven-extension/README.md:202-207.
- Supervised by default: `--permission-mode default` "so that every command is approved from the app, which is what Utah, NERSC and USC require" [Verified] hpcworker/docs/RESEARCH_REPORT.md:106.
- First field proof: Remote Control registering from an sbatch job under a pseudo-terminal "answered yes at 02:22 UTC on 2026-09-29 ... job 40496445 on `asx15`"; a worker at 09:55 UTC (job 40501099, asx1) reported `loggedIn: true`, plan `max`, and registered [Verified as internal record only] beethoven-extension/README.md:228-240. The report had said "No published account shows it under `sbatch`" [Verified] hpcworker/docs/RESEARCH_REPORT.md:17.

[Verified] openspineconsortium.github.io/beethoven/killlist.json.
- Rejected alternative: the earlier design (a MAIN-world window.fetch patch on claude.ai forging Anthropic's SSE stream) fails on the Consumer Terms (automated access, reverse engineering, interference; suspension "at any time without notice"), on Chrome service-worker lifetimes, and functionally [Verified as the report's argument] hpcworker/docs/RESEARCH_REPORT.md:3-7.

## Claims worth verifying

- Remote Control works from an sbatch job under tmux at all, and survives preemption or requeue: the only evidence is the project's own record of jobs 40496445 and 40501099 on 2026-09-29 (beethoven-extension/README.md:228-240); requeue survival is stated untested (RESEARCH_REPORT.md:106).
- "Twelve of twelve sampled clusters fit": eleven Slurm, one LSF, and the PBS/LSF adapters are fixture-tested only (pbs.sh:2-4, lsf.sh:2-3); portability beyond Wayne State is a design claim, not a measurement.
- OOD Shell WebSocket framing "identical" from v2.0.32 to v4.2.5 and OOD at "over 2,100 organizations": from the report, sources not re-opened here (github.com HTML and openondemand.org were not fetched).
- The Chrome Web Store listing is public and installable "with no invitation needed" (index.html:689; reviewers.html:238): chromewebstore.google.com was not reachable from here.
- Access-service behaviour (ten most recent installations, e-mail on a new one, one installation per account) lives in beethoven-access, which this session could not read (403).
- The vendor receives nothing but the approval check (PRIVACY.md:357-372): a code audit of the extension and the Worker would confirm it.
- Remote Control plans: today's docs say Pro, Max, Team, Enterprise; launch coverage (TechRadar, Feb 2026) said Pro/Max only; Gigazine described sessions as "end-to-end encrypted", which conflicts with the docs' statement that the transcript is stored on Anthropic servers while connected.
- Center policy quotes (CHPC, NERSC 2026-08-19 hook, USC, TACC) are taken from the report of 2026-09-28; policies of this kind move monthly.
- GitHub's self-hosted runner fee: postponed in December 2025; status for late 2026 not confirmed by a GitHub primary source beyond the docs page saying self-hosted is free.
- Wayne State C&IT approval status: no document here says it was granted; the pilot treats Beethoven as a "third-party AI bot" until it is.
