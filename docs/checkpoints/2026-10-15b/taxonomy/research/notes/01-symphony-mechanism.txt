# Symphony as built: what it is, its mechanism, the GitHub primitives it rests on, what it costs, how mature it is

Research worker notes, 2026-10-15. Local clones read at: symphony-template 15d3f22 (2026-10-15), symphony-protocol a3a5b4d (2026-10-15, equals remote HEAD), symphony-start e14903d (2026-10-13, equals remote HEAD), symphony-marketplace 5f6be11 (2026-10-14, equals remote HEAD), coordbench 5028999 (2026-10-15), openspineconsortium.github.io 8656487 (2026-10-15). File paths are relative to the named repository; line numbers are at those commits. Grades: Verified (primary source opened by me), Reported (secondary source or search summary), Inferred (my reasoning from cited facts).

## Takeaways

- Symphony is a coordination protocol plus its reference implementation that turns one GitHub repository into the shared state machine for any number of Claude Code workers (a person's sessions, routines on claude.ai, legs of a GitHub Actions matrix): issues are the queue, the first push of `claude/N` is the lock, the file STATE.md on the branch `board` is the shared blackboard, and a pull request plus the required check `check` is the handoff. There is no server of its own; everything is 11 workflow files, a stdlib-only Python library (6,783 lines) and Claude Code hooks.
- Most of the machinery is deterministic code on the workflow's own GITHUB_TOKEN (board, idle-claim release, overlap notices, dealing work to workers, protocol check, tidy, metrics). Claude runs in only three workflows (claude.yml, the `work` job of workers.yml, four jobs of coordinator.yml), all through anthropics/claude-code-action@v1 on one subscription OAuth token, CLAUDE_CODE_OAUTH_TOKEN; a worker with nothing to do starts no Claude session.
- It is GitHub-native to an unusual depth: it rests on about 30 GitHub primitives, including concurrency `queue: max` (a GitHub feature of 2026-05-07), branch rename closing the head branch's pull request, single-commit state branches force-pushed by commit-tree, the GITHUB_TOKEN no-retrigger rule as loop prevention, `workflow_dispatch` as the one self-trigger, App Setup URLs chained with `installation_id`, and environments with required reviewers as a release gate.
- Cost story: in a public repository, standard-runner Actions minutes are free and unlimited and rulesets, required checks, auto-merge, code owners and secret scanning are free on every plan, so the only bill is the Claude plan (Pro $17 a month annual or $20 monthly; verified on claude.com/pricing 2026-10-15). A private repository on GitHub Free gets 2,000 minutes a month and no enforced gate at all.
- The subscription-token-in-Actions choice is both a differentiator and the largest exposure: GitHub's own Agentic Workflows (gh-aw) refuses CLAUDE_CODE_OAUTH_TOKEN by design; Anthropic's docs support it but tie it to one person's subscription and recommend an API key for a shared secret; every worker in Actions shares that one account's five-hour window.
- Maturity: very young and very heavily tested. The library's first commit is 2026-10-10; six tags v0.1.0 to v0.4.1 in four days (v0.4.1 on 2026-10-13); 22 first-parent merges since v0.4.1 are unreleased, and the template vendors them ahead of release. I ran the suites: 1,379 library tests pass in 236 s, 581 template tests in 103 s. A validation harness (spec-derived oracle, exhaustive interleavings up to 18.8 million states, 29 mutants, git as oracle for the push guard) found 19 defects; 18 are fixed, F8 awaits the owner.
- Not built yet: the "rails before any worker runs unattended" (Phase 3: the 10-runs-a-day cap, the `qa` required check, a required check pinned to GitHub Actions as its source), the public runtime, the control panel, the account pool, the canary's first run and any real CooperBench run of Symphony. The plan says "Private repositories only until Phase 3".
- The public pitch (site, READMEs) sells "a team of Claude Code teammates on your repository" and "three presses"; it never mentions GitHub Actions, free minutes or cost. Several internal documents are stale against current GitHub behavior or the repositories (the June 2026 change to GITHUB_TOKEN pull requests, the removed sweep.yml, the release step without its approval).

### 1. What Symphony is, as a component list

Workers ... share a repository by claiming an issue as a branch `claude/<issue>`, working in the open on a draft pull request, and landing only what merges cleanly with the default branch as it is now." [Verified] symphony-protocol README.md:3.

### 2. The mechanism

- Claim: push a new branch `claude/N` from the default branch whose first commit adds only `docs/agents/claims/N.md` (worker, plan, files to touch, issue link); N is one to nine ASCII digits, no leading zero (`claude/03` is no claim). [Verified] symphony-template docs/agents/PROTOCOL.md:29; tools/sdlc_protocol/claims.py:22 (PREFIX "claude/"), :79 (NUMBER regex `0|[1-9][0-9]{0,8}`).
- The lock is git's refusal of a non-fast-forward: "The second `git push -u origin claude/N` is refused, because the branch exists and the push is not a fast-forward of it". PROTOCOL.md:3 phrases it as "GitHub refuses the second push of the same name". [Verified] docs/start/parallel.md:101; PROTOCOL.md:3. The two phrasings differ: a second push that fast-forwards the first (built on a fetched claude/N) is accepted by git; the claim file, the push guard and the protocol check cover that case. [Inferred]
- Announce: labels `claimed` + `worker:<name>`, every other worker's label taken off, plan posted as a comment; draft PR at once with "Closes #N". [Verified] PROTOCOL.md:31-37; .claude/skills/claim/SKILL.md steps 6-7.
- Board: STATE.md on branch `board`, exactly one commit, built from the rendered file alone with `git hash-object`, `mktree`, `commit-tree` and force-pushed, so the default branch never carries a board commit and default-branch rules never block it; rewritten only when content changed; sections Claims, Open pull requests (clean/behind/conflicting/blocked/unknown), Overlaps, Queue, Given to workers, Blockers, Recently merged (last 5). [Verified] .github/workflows/board.yml:13-19, 147-163; docs/agents/STATE.md:5, 11-30.
- Board triggers: push, create, delete, pull_request (opened, synchronize, reopened, closed), issues (opened, edited, closed, reopened, labeled, unlabeled), schedule `17 */6 * * *` as fallback, workflow_dispatch; permissions contents/pull-requests/issues write; concurrency group `board` with `cancel-in-progress: false` and `queue: max` so a merge's four events are not cancelled (finding F12). [Verified] board.yml:68-100.
- Release of idle claims (the coordinator's code half, in the board's own run, no Claude): a claim whose head's committer date is more than 24 hours old is released unless finished (in-review label, PR marked ready, or a draft whose author's latest comment starts "finished; ready to mark"); labels off first (todo put on when none of todo/epic/blocker), then a comment whose first line is `<!-- sdlc-coordinator: claim-released -->` saying why, whose, what the branch holds and the plan; labels put back if the comment fails; then the branch is renamed `released/<issue>-<short sha>`, which frees the name and closes the PR. [Verified] PROTOCOL.md:49-51; claims.py:26 (IDLE_AFTER 24 h), :30, :46, :53; spec/PROTOCOL.md:67-69 (symphony-protocol).
- Overlaps: every file more than one piece of open work changes, with landing order blocker first, then ready work, then the oldest (by when GitHub recorded the push that made the branch, since F13); each piece told once in a comment `<!-- sdlc-coordinator: overlap <numbers> -->`. [Verified] PROTOCOL.md:55; symphony-protocol spec/PROTOCOL.md:73; coordinator.py:37.
- Coordinator's judgement half: coordinator.yml runs Claude to plan an issue labelled `epic` into tasks with owned files and interfaces (returned as JSON; tools/team.py writes the plan and opens the tasks as sub-issues labelled todo + worker:<name>), settle a task labelled `blocked`, integrate when the last task closes, and run the coordinator prompt weekly (cron `29 5 * * 1`). [Verified] .github/workflows/coordinator.yml:1-58; docs/agents/WORKERS.md:25-30.
- Worker kinds: (a) a person's sessions, named by GitHub login or SYMPHONY_WORKER, no file needed; (b) a routine on someone's claude.ai account; (c) a worker in GitHub Actions run by workers.yml. Routines and Actions workers are registered by `.github/symphony/workers/<name>.json` (name, runs actions/routine/session, about, area globs, lands owner/auto-merge, model, max_turns 1-500, rounds 1-50, account note, never a credential), added by the "Add a worker" issue form whose workflow opens the PR. [Verified] docs/agents/WORKERS.md:7-15; .github/symphony/workers/README.md.
- Dealing: workers.yml's first job lists Actions workers and runs `tools/team.py deal` once for the whole run from one look (fix F4), then one matrix leg per worker (concurrency group per worker) re-checks and runs Claude only for move carry/take; after a successful session a leg re-dispatches itself with workflow_dispatch up to `rounds` (default 6). Triggers: cron `43 */6 * * *`, issues labeled (todo, blocker, worker:*), workflow_dispatch. [Verified] .github/workflows/workers.yml:1-56, 72-137, 300-321.
- Push guard: a PreToolUse hook on Bash that exits 2 to refuse a push to the default branch or `board`, any `--force`/`-f`, a `+` refspec, `:` and `*` refspecs, `--all/--branches/--mirror`, a misnamed claim like `claude/03`, `--force-with-lease` outside one's own claude/ branch, and (F7, after 0.4.1) a lease onto a claude/ branch whose claim file names another worker; it lets through what it cannot parse, leaving GitHub's rules as second fence. [Verified] tools/sdlc_protocol/guard.py:1-60, :517 (other_holder), :550 (refusal); .claude/rules/board.md; symphony-marketplace README.md:14-21.
- Required checks: the ruleset file requires a PR (0 approvals), blocks force push and deletion, and requires status check `check` with strict up-to-date policy; it names no integration, so any source satisfies it. CI job `check` runs scripts/check.sh (check_docs, vendoring verify, workers check, unittest) and, on PRs, tools/check_protocol.py (claim file present while draft, gone when ready, body closes the issue, head in this repository). The `qa` check is planned, not built. [Verified] docs/setup/ruleset-main.json; .github/workflows/ci.yml:70-115; scripts/check.sh:10-23; CLAUDE.md decision "Every pull request an autonomous worker makes passes a required QA gate ... (not built yet)".
- GitHub's own docs confirm the unpinned-source exposure: "Any person or integration with write permissions to a repository can set the state of any status check in the repository ... you can select an app as the expected source". [Verified] github/docs content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets.md:179.
- Versions move by vendoring, not install: tools/VENDORED records release, commit and sha256 per file; check.sh fails on a hand edit; CI clones symphony-protocol and compares byte for byte. The template's record reads "sdlc-protocol 0.4.1 53e232f..." though 53e232f is main after v0.4.1 (F18), i.e. ahead of any release. [Verified] tools/VENDORED:1; tools/sdlc_protocol/__init__.py:19; git ls-remote tags (v0.4.1 at 485d470); docs/memory/MEMORY.md line on protocol changes.

### 4. What runs where and what it costs

### Current GitHub behavior that bears on the design (checked 2026-10-15)

- `queue: max` is real: up to 100 pending runs per concurrency group; cannot combine with `cancel-in-progress: true`. [Verified] github/docs data/reusables/actions/actions-group-concurrency.md:15-20; changelog 2026-05-07 "GitHub Actions concurrency groups now allow larger queues" [Reported] (search result, https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues).
- GITHUB_TOKEN rule changed: "pull_request events with the opened, synchronize, or reopened activity types: when a workflow using GITHUB_TOKEN creates or updates a pull request, the resulting pull_request event creates workflow runs in an approval-required state"; feature flag on fpt and ghec, "currently rolling out on dotcom". Symphony's headers still say "neither a push nor a pull request made with GITHUB_TOKEN starts a workflow" (add-worker.yml:13-15; protocol.yml:19-20). [Verified] github/docs data/reusables/actions/actions-do-not-trigger-workflows.md; data/features/actions-github-token-pull-request-approval.yml. Changelog "Bot-created pull requests can run workflows if approved", 2026-06-11 [Reported] (https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/).
- "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." Symphony's crons are fallbacks, so a quiet public copy loses its six-hourly board fallback, weekly protocol intake and daily metrics after 60 idle days. [Verified] github/docs data/reusables/actions/scheduled-workflows-disabled.md; consequence [Inferred].
- Renaming a branch: "If the renamed branch is the head branch of an open pull request, this pull request is closed"; a branch covered by a ruleset can be renamed only by an admin. Matches the release design and docs/setup/github.md:16. [Verified] github/docs renaming-a-branch.md:4, 19, 31.
- GitHub Actions holds potentially malicious workflow runs for approval on public repositories (changelog 2026-07-28). Not checked against Symphony's workflows. [Reported] (search result, https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/).
