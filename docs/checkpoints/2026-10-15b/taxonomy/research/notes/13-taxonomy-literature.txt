## Takeaways

- The axes that recur across 2024-2026 agent taxonomies are: architecture or components (profile, memory, planning, action; brain, perception, action), communication or control structure (centralized, decentralized, layered or hierarchical, shared message pool), interaction type (cooperative, debate, competitive, coopetition), autonomy (by the human's role), environment (sandbox, physical, none), memory and temporal continuity, and application domain. Cost and compute payer appear in practitioner and vendor sources (token multipliers, Actions minutes) but in none of the academic taxonomies read here.
- Autonomy has converged on SAE-style 0-5 ladders: Hassan et al. (SE 1.0 to SE 5.0, mapped explicitly to SAE levels; Claude Code, Devin, Jules and Codex placed at Level 3 "Goal-Agentic"), Shapiro (Level 0 to Level 5 "Dark Factory", 2026-01-23), and Feng, McDonald and Zhang, whose five levels are defined by the user's role (operator, collaborator, consultant, approver, observer). Anthropic (2026-02-18) defines no levels and measures autonomy empirically (turn duration, auto-approve rate, interruptions).
- No academic or analyst taxonomy found has an axis for "where the agent's compute runs and who pays for it". This is the gap where Symphony's GitHub Actions nativeness (standard runners free in public repositories) and Beethoven's HPC batch placement (institution's allocation) are distinctive; it should be an explicit axis.
- Industry categories moved from "assistant" to "agent" in 2025-2026: Gartner's 2025 Magic Quadrant was "AI Code Assistants" (September 2025); a secondary source reports a May 2026 "Magic Quadrant for Enterprise AI Coding Agents" with GitHub, OpenAI, Cursor and Anthropic as Leaders (needs verification). Thoughtworks Radar Vol 34 (Apr 2026) put Claude Code in Adopt, "Team of coding agents" in Assess, "Coding agent swarms" in Caution, and named "agent-native project memory and task tracking" (Beads) a new category.
- The CNCF landscape (commit 150352e3, 2026-10-15) has a top-level "AI Agent" category with 11 subcategories (Agent Framework, Agent Tool, Evaluation, Guardrail, Knowledge Graph, Protocol, RAG, State and Memory, Structured Output, Vector Database, Workflow Orchestration) but no subcategory for coding agents or agent coordination; GitHub Actions sits in App Definition and Development / Continuous Integration and Delivery among 63 entries.
- Malone and Crowston's definition ("coordination is managing dependencies between activities") and its four dependency families (shared resources, producer/consumer, simultaneity, task/subtask) map one-to-one onto agent coordination: claiming an issue is shared-resource allocation, blockers and task dependencies are prerequisite constraints, pull requests are transfers, required checks and specs are usability standards, landing order and merge queues are simultaneity, epics are task/subtask decomposition.
- Symphony is best classed as a hybrid concurrency scheme: a pessimistic, create-once claim on the issue (first push of claude/N wins, GitHub refuses the second) with a lease-like idle release (24 h) and a fence on forced pushes, plus optimistic integration of the code itself (private branch, validation by the required check, merge, rebase on "main moved"). Anthropic's C compiler harness (2026-02-05) independently used the same idea (lock files in current_tasks/ synchronized through git). Beethoven's super-master lease is a textbook Gray and Cheriton lease with a Chubby/DDIA fencing token.
- Symphony's board, issues, labels, branches and claim files act as a blackboard and as stigmergic marker traces in the shared medium; Heylighen-style stigmergy (work leaves a trace that prompts the next action) is the closest classical frame for a coordinator that lives in the repository rather than in a running process.
- For Beethoven's research side, the Workflows Community terminology (Suter et al., FGCS 174:107974, 2025; five axes, 23 WMSs classified) and the GI/de-RSE guideline (Kind, Use, TRL, application class 0-3, building on Hasselbring et al. 2024) are the ready-made schemes; Yu and Buyya (2005) supplies the five classic elements (workflow design, information retrieval, scheduling, fault tolerance, data movement).

## Findings

### 1. Axes that recur across taxonomies

- Sapkota, Roumeliotis and Karkee contrast Generative AI, AI Agents and Agentic AI along: Definition, Autonomy Level, Task Complexity, Collaboration, Learning and Adaptation, Applications (Table I); Initiation Type, Goal Flexibility, Temporal Continuity, Learning/Adaptation, Memory Use, Coordination Strategy, System Role (Table II); and five further "critical dimensions": core function and goal, architectural components, operational mechanism, scope and complexity, interaction and autonomy (Tables V to IX). Agentic AI's coordination strategy is "Hierarchical or decentralized coordination" and its memory "Shared episodic/task memory". arXiv 2505.10468 v1 of 2025-05-15; peer-reviewed in Information Fusion 126 (2026) 103599, doi 10.1016/j.inffus.2025.103599. [Reported] Full-text mirror https://raw.githubusercontent.com/Miyan0Shiho/arxiv-auto-collector/HEAD/2025-W20/AI%20Agents%20vs_%20Agentic%20AI_%20A%20Conceptual%20Taxonomy_%20A.md lines 860-912, 988-1016, 1111-1180; journal details from https://raw.githubusercontent.com/nbremner/llm-research-wiki/HEAD/wiki/sources/unreviewed/2026-sapkota-ai-agents-vs-agentic-ai.md
- Guo et al. (IJCAI 2024, arXiv 2402.01680) position LLM multi-agent systems on four dimensions: agents-environment interface (Sandbox, Physical, None), agent profiling (Pre-defined, Model-Generated, Data-Derived), agent communication (paradigms Cooperative, Debate, Competitive; structures Layered, Decentralized, Centralized, Shared Message Pool, the last from MetaGPT; content), and capability acquisition (feedback types, adjustment strategies); applications split into problem solving and world simulation. [Reported] Text mirror https://raw.githubusercontent.com/thanhbn/arxiv-downloader/HEAD/agent/2402.01680-Large_Language_Model_based_Multi-Agents-_A_Survey_of_Progress_and_Challenges.txt lines 125-140, 216-245, 273-320; the five paper streams are on the authors' README https://raw.githubusercontent.com/taichengguo/LLM_MultiAgents_Survey_Papers/HEAD/README.md [Verified for the README]
- Tran et al. (arXiv 2501.06322, 2025-01-10) characterize collaboration by five dimensions: actors, types (cooperation, competition, coopetition), structures (peer-to-peer, centralized, distributed), strategies (role-based, model-based, rule-based in the paper), and coordination protocols. [Reported] Abstract mirror https://raw.githubusercontent.com/ATOM00blue/machine-learning-library/HEAD/corpus/papers/2501.06322.md
- Single-agent architecture frames: Wang et al. (arXiv 2308.11432) construct an agent from Profile, Memory, Planning and Action modules; Xi et al. (arXiv 2309.07864) from brain, perception and action; Luo et al. (arXiv 2503.21460, 2025) organize the field into construction, collaboration, evolution, tools, security, benchmarks and applications. [Verified] Authors' READMEs: https://raw.githubusercontent.com/Paitesanshi/LLM-Agent-Survey/HEAD/README.md lines 51-60; https://raw.githubusercontent.com/WooooDyy/LLM-Agent-Paper-List/HEAD/README.md line 35; https://raw.githubusercontent.com/luo-junyu/Awesome-Agent-Papers/HEAD/README.md lines 15-48
- Liu et al., "Large Language Model-Based Agents for Software Engineering: A Survey" (arXiv 2409.02977), classify along two perspectives: SE tasks (requirements, code generation, static checking, testing, debugging, release, end-to-end development and maintenance) and agent architecture (planning, memory, perception, action; multi-agent roles and collaboration mechanism; human-agent collaboration by phase). [Verified] https://raw.githubusercontent.com/FudanSELab/Agent4SE-Paper-List/HEAD/README.md lines 1-70
- Yang et al., "A Survey of AI Agent Protocols" (arXiv 2504.16736), classify protocols on two dimensions: context-oriented versus inter-agent, and general-purpose versus domain-specific (MCP context-oriented general; A2A, ANP, Agora inter-agent general; agents.json, LMOS, Agent Protocol domain-specific). [Verified] https://raw.githubusercontent.com/multi-agent-systems-failure-taxonomy/MAST/HEAD/taxonomy_definitions_examples/definitions.txt (repository head 2025-07-23). ### 2. Autonomy levels and agentic software engineering roadmaps

- Feng, McDonald and Zhang define "five levels of escalating agent autonomy, characterized by the roles a user can take when interacting with an agent: operator, collaborator, consultant, approver, and observer" (arXiv 2506.12469, cs.HC, v1 2025-06-14, v2 2025-07-28; Knight First Amendment Institute). [Reported] https://raw.githubusercontent.com/sailfish009/paper/HEAD/2025.06.17.txt lines 271-274. A secondary note says the paper maps GitHub Copilot Agent and Gemini Deep Research to L3, Devin and SWE-agent to L4, and proposes "autonomy certificates" and "assisted evaluations". [Reported] https://raw.githubusercontent.com/BobYeger/state-of-agents/HEAD/sources/Levels%20of%20Autonomy%20for%20AI%20Agents.md
- Hassan, Li, Lin, Adams, Chen, Kashiwa and Qiu (arXiv 2509.06216, 2025) define SE 3.0 as "Agentic Software Engineering", a duality of SE for Humans and SE for Agents, two workbenches (Agent Command Environment, Agent Execution Environment), new artifacts (Merge-Readiness Packs, Consultation Request Packs, BriefingScript, LoopScript, MentorScript, Version Controlled Resolutions), and six levels mapped to SAE J3016: Level 0 Manual Coding (SE 1.0), Level 1 Token Assistance (SE 1.5), Level 2 Task-Agentic (SE 2.0, Copilot, CodeWhisperer), Level 3 Goal-Agentic (SE 3.0, Devin, Claude Code, Jules, Codex), Level 4 Specialized Domain Autonomy (SE 4.0), Level 5 General Domain Autonomy (SE 5.0). The mirror titles it "Foundational Pillars and a Research Roadmap", not "...and Research Directions". [Reported] Full-text mirror https://raw.githubusercontent.com/averkij/top_papers/HEAD/assets/json/2509.06216.json (abstract and section "Start")
- Shapiro's practitioner ladder (2026-01-23): Level 0 manual, 1 discrete delegated tasks, 2 pairing, 3 human as manager and reviewer of diffs, 4 human as PM and spec author, 5 "Dark Factory" where humans neither write nor review code; he claims most organizations top out at Level 3 (unsubstantiated per the reviewer). [Reported] https://raw.githubusercontent.com/lhl/realitycheck-data/HEAD/analysis/sources/shapiro-2026-five-levels-dark-factory.md
- Anthropic, "Measuring AI agent autonomy in practice" (2026-02-18): autonomy is "the degree to which an agent operates independently of human direction and oversight", treated as emergent from model, oversight and product; no formal levels; Claude Code 99.9th-percentile turn duration rose from under 25 to over 45 minutes between October 2025 and January 2026; median turn about 45 s; full auto-approve rises from about 20% of sessions for new users to over 40% by about 750 sessions; interruptions from about 5% to about 9% of turns; internal human interventions per session fell from 5.4 to 3.3. [Verified] https://www.anthropic.com/research/measuring-agent-autonomy
- He, Treude and Lo, "LLM-Based Multi-Agent Systems for Software Engineering: Literature Review, Vision and the Road Ahead" (arXiv 2404.04834, v4; TOSEM) exists as a roadmap; its text was not read here. [Reported] https://raw.githubusercontent.com/litlfred/cat-harness/HEAD/library/arxiv-2404.04834v4/README.md

### 6. Classical coordination concepts and how they map onto agent coordination

- Malone and Crowston, "The interdisciplinary study of coordination", ACM Computing Surveys 26(1):87-119, 1994: "coordination can be seen as the process of managing dependencies among activities"; the processes analyzed are those "for managing shared resources, producer/consumer relationships, simultaneity constraints, and task/subtask dependencies". [Reported] Abstract mirror https://raw.githubusercontent.com/yiren-liu/coquest/HEAD/backend/paper_graph/data/venue_txt/348_.txt
- Their Table 1 pairs each dependency with processes: shared resources with first come/first serve, priority order, budgets, managerial decision, market-like bidding; producer/consumer split into prerequisite (notification, sequencing, tracking), transfer (inventory management, just in time) and usability (standardization, ask users, participatory design); simultaneity with scheduling and synchronization; task/subtask with goal selection and decomposition; task assignment is itself a shared-resource problem. [Reported] https://raw.githubusercontent.com/AlexKapadia/AutoFirm/HEAD/docs/research/A1-multi-agent-orchestration/06-malone-crowston-coordination-theory/SUMMARY.md ; a 2009 operationalization uses the same four processes (Hossain, Construction Management and Economics 27:25-39) https://raw.githubusercontent.com/zhongyunshun/cm_topics/HEAD/Cleaned_TXTs/481.txt lines 56-62
- Mapping to agents (Inferred from the above and the cited systems): shared resource = an issue or task that only one worker should take (Symphony's first push of claude/N is first come/first serve; the coordinator's worker:<name> label is a managerial decision; Claude Code teammates self-claim; Salemi et al.'s agents "volunteer", which is market-like bidding); prerequisite = blocker label, task dependencies ("a pending task with unresolved dependencies cannot be claimed"); transfer = the pull request, Hassan's Merge-Readiness Pack, a mailbox message; usability = standards (AGENTS.md, CLAUDE.md, required checks, Beethoven's interface standard); simultaneity = landing order, merge queues, "main moved" rebases, Slurm scheduling; task/subtask = epics, orchestrator-workers, planners and sub-planners. Sources: /home/user/symphony-template/docs/agents/PROTOCOL.md lines 3, 27, 43-59; https://code.claude.com/docs/en/agent-teams
- Blackboard architecture: Hearsay-II (Erman, Hayes-Roth, Lesser and Reddy, ACM Computing Surveys 12(2):213-253, 1980) with "a global, hierarchical data structure (the blackboard)", independent "knowledge sources" that monitor it and contribute partial solutions, and "a control mechanism that opportunistically determines which knowledge source to activate next" (Nii, AI Magazine 7(2), 1986). LLM revivals: Salemi et al. (Google Cloud AI Research, arXiv 2510.01285, 2025-09-30) report 13-57% relative gains in end-to-end task success over master-slave and RAG baselines; Han and Zhang (arXiv, 2025-07) select acting agents by blackboard content until consensus. [Reported] https://raw.githubusercontent.com/Miyan0Shiho/arxiv-auto-collector/HEAD/2025-W40/LLM_based%20Multi_Agent%20Blackboard%20System%20for%20Inform.md lines 1-40, 532-545, 588-590, 669-671; https://raw.githubusercontent.com/sailfish009/paper/HEAD/2025.07.03.txt lines 1031-1034
- Shared message pool (MetaGPT) is the publish-subscribe form of the blackboard in Guo et al.'s structure axis. [Reported] Guo mirror lines 311-315
- Stigmergy: coined by Grasse (1959) for termite nest building; Theraulaz and Bonabeau (1999) split quantitative from qualitative stigmergy; Parunak (2006) sematectonic versus marker-based; Heylighen (2016, Cognitive Systems Research 38) generalizes it ("A process is stigmergic if the work done by one agent provides a stimulus that entices other agents to continue the job") to Wikipedia and open source; Crowston and colleagues studied stigmergic coordination in FLOSS teams, with the code as the medium. [Reported] https://raw.githubusercontent.com/LeeHengYu/mediator-coevo/HEAD/related-literature/multi-agent-llm-mediator/_agent_findings/06_stigmergy.md lines 9-31; https://raw.githubusercontent.com/graphwork/wg/HEAD/docs/research/organizational-patterns.md lines 13, 37-39
- Tuple spaces: Gelernter, "Generative communication in Linda" (1985): processes communicate through a shared tuple space with out (insert), in (withdraw a matching tuple, blocking until one exists) and read; a tuple "has an independent existence in TS" until withdrawn, so communication is decoupled in space and time. Mapping (Inferred): a task queue where in() is an atomic claim; GitHub's refusal of a second push of the same branch name gives exactly one successful withdrawal per issue. [Reported] https://raw.githubusercontent.com/simbo1905/the-morning-paper-archive/HEAD/content/2015/02/generative-communication-in-linda.txt
- Leases: Gray and Cheriton, "Leases: An efficient fault-tolerant mechanism for distributed file cache consistency", 12th SOSP (1989) pp. 202-210, cited by Chubby. A lease "is similar to a lock with a timeout", must be renewed, and passes to another holder when the old one stops renewing; safe use needs fencing tokens (Chubby calls them sequencers). [Reported for Gray and Cheriton's content] Kleppmann, DDIA 2nd edition ch. 9, https://raw.githubusercontent.com/Vonng/ddia/HEAD/content/en/ch9.md lines 833-837, 1088-1100, 1156-1167, ref 73 at line 1791
- Chubby (Burrows, OSDI 2006): coarse-grained advisory reader-writer locks ("they conflict only with other attempts to acquire the same lock"), session leases renewed by KeepAlives, a "lock-delay" before a failed holder's lock can be re-claimed, and sequencers checked by servers to reject delayed requests; Chubby's sessions "reduce the overhead of leases [9] in the V system". [Verified] Paper PDF in https://github.com/papers-we-love/papers-we-love distributed_systems/the-chubby-lock-service-for-loosely-coupled-distributed-systems.pdf (pdftotext lines 229-250, 805-815, 913-915)
- Optimistic versus pessimistic concurrency: Kung and Robinson (ACM TODS 1981) run each transaction in three phases, read (writes go to a private workspace), validation, write, betting that conflicts are rare; pessimistic two-phase locking acquires locks before access and risks blocking and deadlock. Mapping (Inferred): a git branch is the private workspace, the required check and merge are validation, a conflict means rebase and retry. [Reported] https://raw.githubusercontent.com/fengsxy/paper_reading/HEAD/cs202/10_OCC.md sections 1-2.1
- Evidence from agent practice: Cursor (2026-01-14, as excerpted in the template's own history) found a shared file guarded by locks failed (agents held locks too long or failed holding them, and "twenty agents fell to the throughput of two or three") while pure optimistic concurrency made agents "risk-averse"; separate roles (planners, workers, judge) worked. [Reported] /home/user/symphony-template/docs/history/crowdsourcing/research.md lines 119-127, 155
- Anthropic's C compiler run (Carlini, 2026-02-05): 16 agents, each in a Docker container cloning a bare upstream repository; "Claude takes a 'lock' on a task by writing a text file to current_tasks/"; "If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one"; no orchestration agent; nearly 2,000 sessions over two weeks, 2 B input and 140 M output tokens, just under USD 20,000, a 100,000-line compiler that builds Linux 6.9 on x86, ARM and RISC-V. [Verified] https://www.anthropic.com/engineering/building-c-compiler
- Claude Code agent teams (experimental, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1): a lead, teammates, a shared task list (pending, in progress, completed, with dependencies) and per-agent JSON mailboxes; "Task claiming uses file locking to prevent race conditions"; one team per session, no nested teams, local files under ~/.claude/tasks/. ### 7. Scientific workflow and research software taxonomies

- Yu and Buyya, "A Taxonomy of Workflow Management Systems for Grid Computing", Journal of Grid Computing 3(3-4):171-200, 2005 (doi 10.1007/s10723-005-9010-8), rest on five elements: workflow design, information retrieval, workflow scheduling, fault tolerance and data movement, and classify 13 grid WMSs including Pegasus and Kepler; a 2017 review calls it the only true hierarchical taxonomy among workflow "taxonomies", most being controlled vocabularies. [Reported] https://raw.githubusercontent.com/jayjaybillings/thesis/HEAD/docs/_posts/2016-12-21-yu-and-buyya-2005.markdown ; https://raw.githubusercontent.com/jayjaybillings/thesis/HEAD/docs/_latex/compExam/src/workflows-review.tex lines 75-136
- Suter, Coleman, Ferreira da Silva and 23 co-authors, "A Terminology for Scientific Workflow Systems", FGCS 174:107974 (2025), arXiv 2506.07838: five axes, Workflow Characteristics (flow task/iterative/data; granularity; coupling tight/loose; dynamicity; domain specific/agnostic), Composition (schema ad-hoc/standard, API, GUI; abstract/intermediate/concrete/implicit; flat/hierarchical), Orchestration (planning static/dynamic/event-driven; execution runner/resource manager/serverless), Data Management (batch/pipelined/partitioned; file/streaming/in-memory/network; local/shared/distributed/replicated storage), Metadata Capture (prospective/retrospective provenance; monitoring; fault handling and user intervention); 23 WMSs classified; the group counts over 300 WMSs. [Verified] Working group's site https://raw.githubusercontent.com/workflowscommunity/workflowscommunity.github.io/HEAD/page_terminology.html and .../_working_groups/terminology.md ; corroborated by https://raw.githubusercontent.com/aiidateam/aiida-website/HEAD/src/blog/2025-06-24-wf-terminology.md
- Hasselbring, Druskat, Bernoth, Betker, Felderer, Ferenz, Lamprecht, Linxweiler and Rumpe, "Toward Research Software Categories" (arXiv 2404.14364, 2024): a multi-dimensional categorization with a template, and "role-based, developer-based, and maturity-based categories". [Reported] arXiv RSS mirror https://raw.githubusercontent.com/ehijano/rss_fetch/HEAD/rss_data/cs.SE/2024-04-22_cs.SE.xml
- The GI and de-RSE template guideline (January 2025, doi 10.18420/2025-gi_de-rse; English version) categorizes research software by Kind (MSD modeling, simulation and data analytics; PoC; Ctrl embedded control; Tool; User apps, "a detailed categorization can be found in [HDB+24]", that is Hasselbring et al.), Use (technical infrastructure, specialist infrastructure, growing, individual, demonstration), TRL 1-9, and application classes ApC0-ApC3 (from the DLR guidelines, 2018), each class raising required measures. [Verified] https://raw.githubusercontent.com/gi-ev/RSE-software-entwicklungs-leitlinien/HEAD/docs/RSE_Leitlinien_Softwareentwicklung-en-US.md lines 1-10, 513-560, 628-670, 1531

### 8. Proposed axes for classifying agent software, from models to domain workflows

Twelve axes; each lists its categories, where it comes from, and where Symphony (S) and Beethoven (B) fall. All placements are [Inferred] from the local files cited in section 6.

1. Stack layer. Categories: L0 model; L1 single-agent harness (Claude Code, Codex CLI); L2 agent framework or SDK; L3 coordination and orchestration layer; L4 execution platform (sandbox, CI, HPC scheduler, hosted agent service); L5 domain workflow or application. From: CNCF's split of AI Agent, Inference and AI Native Infra; Sapkota's Generative AI / AI Agent / Agentic AI; Anthropic Managed Agents' harness versus sandbox (2026-04-08, https://www.anthropic.com/engineering/managed-agents). S: L3 on L4 (GitHub). B: L4 (HPC bridge) and L5 (beethoven-research).
2. Autonomy, by the human's role. Categories: operator, collaborator, consultant, approver, observer (Feng et al.), cross-walked to Hassan L0-L5 and SAE J3016; measured by turn duration, auto-approve and interruption rates (Anthropic). S: sessions at collaborator to approver; registered workers with "lands": "auto-merge" approach observer, bounded by the required check. B: student sessions operator to collaborator; engine runs approver.
3. Control topology. Categories: single agent; centralized orchestrator-workers; hierarchical planners and sub-planners; layered; decentralized peer-to-peer; shared-medium (blackboard, message pool, ledger). From: Guo, Tran, Sapkota, Anthropic patterns, Cursor's roles. S: shared-medium with a coordinator (planner) in coordinator.yml and self-claiming peers. B: hierarchical masters and satellites under one lease holder.
4. Communication medium and protocol. Categories: direct messages (mailbox, A2A); context protocol (MCP); shared blackboard or task list; stigmergic traces in the work artifact (code, issues, branches); tuple space. From: Yang et al., Guo, Gelernter, Nii, Heylighen. S: GitHub objects as blackboard and traces; no agent-to-agent chat. B: engine store and bus.
5. Concurrency control over shared work. Categories: partitioning only (file ownership, as Claude Code's guidance "Break the work so each teammate owns a different set of files"); pessimistic lock; lease (lock with expiry, renewal, fencing); optimistic (private copy, validate at merge, retry); hybrid. From: Kung and Robinson, Gray and Cheriton, Chubby, DDIA, Cursor, Carlini. S: hybrid (create-once claim plus 24 h lease plus optimistic merge). B: lease with fencing token.
6. Dependencies managed (multi-valued). Categories: shared resource, prerequisite, transfer, usability, simultaneity, task/subtask. From: Malone and Crowston Table 1. S: all six (claim; blocker and Overlaps order; pull request; required check; landing order; epics). B: shared resource (accounts, lease), task/subtask (task graph), simultaneity (Slurm).
7. Execution environment. Categories: developer machine; vendor cloud session or hosted agent service; CI runner (GitHub Actions, GitLab CI); HPC batch job; self-hosted server or Kubernetes; with isolation sandbox / container / none. From: Guo's environment interface, Thoughtworks sandboxing, Suter's execution (runner, resource manager, serverless), GitHub docs. S: Actions runners plus each worker's own session. B: Slurm compute node in Apptainer.
8. Trigger and lifetime. Categories: interactive session; event-driven (issue, PR, comment, push); scheduled; batch; long-running loop (Ralph loop) or durable execution. From: Suter's planning (static, dynamic, event-driven), claude-code-action's interactive versus automation modes, Thoughtworks on durability. S: event-driven with a 6-hourly schedule as fallback (PROTOCOL.md line 3). B: batch job.
9. State and memory. Categories: stateless; context window; session log; project memory files; shared work ledger (issue tracker, board, Beads); provenance (prospective, retrospective). From: Sapkota (memory, temporal continuity), Wang (memory module), CNCF State and Memory, Beads, Managed Agents' append-only session log, Suter's metadata capture. S: git and GitHub as durable ledger, docs/memory/ as shared memory. B: engine store, STATUS.md and session files.
10. Cost model and compute payer, with licence. Categories: inference paid by metered API, by each person's subscription, or bundled in a vendor seat; compute paid by the user's machine, the vendor, free CI minutes for public repositories, or an institution's HPC allocation; licence open, open core, source-available, proprietary. From: GitHub billing and limits, Claude Code GitHub Actions costs, Anthropic's 15x multi-agent token figure, the CNCF landscape's licence field. No academic taxonomy carries this axis. S: Actions free on standard runners in public repositories (bounded by 6 h jobs and 20 concurrent jobs on Free), inference on contributors' own subscriptions; protocol and plugin MIT. B: institution's cluster time, student's own subscription.
11. Verification and governance. Categories: none; self-check; LLM judge; deterministic gates (tests, linters, required checks, formal proof); human merge approval; external certification. From: MAST category 3, Thoughtworks feedback sensors, Hassan's Merge-Readiness Packs, Feng's autonomy certificates, GitHub Agentic Workflows' safe outputs. S: required checks "check" and "qa" plus owner or auto-merge. B: beethoven-qa contracts and CrossHair/Z3 gate (/home/user/beethoven-qa/README.md lines 1-8).
12. Domain, artifact and maturity. Categories: SE task (Liu et al.: requirements, code, testing, debugging, release, end-to-end); scientific workflow (Suter's domain specific or agnostic); research software Kind, Use, TRL and application class (GI guideline after Hasselbring); general business process. S: end-to-end software development and maintenance. B: research software, Kind MSD, application classes 1-2, research automation.
