## Takeaways

- The 2026-10-14 work placed Symphony against one main neighbor, GitHub Agentic Workflows (gh-aw: a Markdown-to-Actions compiler plus a native Git-backed work queue), and two lesser ones (Copilot dynamic workflows; "Copilot as coordinator, Claude Code as workers"). Across 20 Symphony capabilities gh-aw had 2 "as-is in part", 7 "weaker", 11 "no"; Symphony reinvents fully only the run rails (daily caps, skip while main is red).
- Its framing, still sound on 2026-10-15: Symphony's queue core is a textbook lease-based work queue on GitHub objects (issue = task, first push of claude/N = lease, 24 h by committer date = visibility timeout, released/<issue>-<sha> = requeue), and what is not standard is coordination between independent workers of every kind (a person's local or cloud sessions, routines, Actions workers) across hours and accounts, with GitHub itself enforcing the lock by refusing a second push of a ref name.
- Decision (owner, 2026-10-14 10:03-10:05 UTC): keep the Symphony protocol and its 0.5.0 queue; Candidate A, a standard-library Python compiler of Symphony's own that regenerates all 11 workflows byte for byte, after 0.5.0; gh-aw only as a measured pilot (Candidate B, a self-defined `claude -p` engine on CLAUDE_CODE_OAUTH_TOKEN) on the canary after 0.5.0. The owner refused Copilot inference outright ("without losing the absolutely solo usage of a claude substription token").
- The deciding fact is billing, not storage: gh-aw still says on 2026-10-15 that "CLAUDE_CODE_OAUTH_TOKEN is not supported ... it will be ignored" (auth.mdx:219; engines/claude.md:22). Its Claude routes are an Anthropic API key, Anthropic workload identity federation (still API-billed), or Copilot inference billed to an organization's Copilot plan.
- What moved since 2026-10-14: gh-aw shipped 7 more tags in 3 days (v0.91.9 on 2026-10-12 to v0.92.0 on 2026-10-14 21:17 -0700), so about 12 releases between 2026-10-08 and 2026-10-14; its queue is still "the proposed design", locks "never expire or get stolen", and crash recovery "is not implemented", but its Unreleased changelog adds queue bootstrap defaults (concurrency 16, pending limit 4,096, three attempts with 30 s backoff), so it now has the attempt budget Symphony lacks.
- GitHub now sells its own agents running on Actions: Copilot cloud agent (renamed from "coding agent" by March 2026; 59-minute session cap; one branch, one pull request per task; one repository), Copilot automations (schedule, issue-opened and pull-request triggers; not available in public repositories), and third-party Claude and Codex coding agents (the press calls this Agent HQ; public preview), all billed in AI Credits at $0.01 each since GitHub's 2026-06-01 move to usage-based billing, plus Actions minutes.
- Public-repository economics are confirmed on 2026-10-15: standard GitHub-hosted runners are free in public repositories and for self-hosted runners; private quotas are 2,000 (Free), 3,000 (Pro, Team), 50,000 (Enterprise Cloud) minutes a month, hard-stopped without a payment method; concurrent jobs 20 Free, 40 Pro, 60 Team, 500 Enterprise. Symphony's pitch is the combination nobody else ships: free compute (public repository) plus flat-rate inference (a Claude subscription) plus a lock GitHub enforces.
- Two constraints the earlier work did not cite: GitHub's Additional Product Terms bar using GitHub-hosted runners for "any other activity unrelated to the production, testing, deployment, or publication of the software project associated with the repository" and bar offering "the Actions product or service ... for commercial purposes"; Anthropic's Claude Code legal page says OAuth is "designed to support ordinary use" and Pro/Max limits "assume ordinary, individual usage", and the GitHub Actions page advises an API key, not an OAuth token, for a secret shared across repositories.
- The readiness research (2026-10-14) lists what is unmeasured: board-run API calls and duration in a real repository, issue-to-claim time, any real claim-to-PR or PR-to-merge figure, canary run times (never run live); the library has no request budget and no retry on 403/429 or Retry-After (still none at a3a5b4d); one subscription token is shared by every Actions worker. Since then the harness record shows every open finding fixed on main (validation/known.json: as_built [], red []), but the version is still 0.4.1 and 0.5.0 waits for the owner.

### 2. What was decided and why

- Answer in short: worker queues can be a standard GitHub pattern; Symphony's claim protocol is one; it cannot be imported because gh-aw's queue takes only gh-aw workflows in Actions, runs Claude only on an API key or Copilot billing, and shipped the week of 2026-10-12 as "a proposed design"; Symphony builds a standard queue plus a coordination protocol gh-aw "does not have and does not claim to" [Verified, as the note's text] (symphony-vs-gh-aw.md:7).
- Recommendation: "Keep building", take two cheap wheels (`queue: max` on the board group, merged as #70 / cb83274 on 2026-10-14; a workflow linter), and measure gh-aw on the canary once its Claude engine takes a subscription token or the owner pays for API or Copilot inference [Verified, as the note's text] (symphony-vs-gh-aw.md:9, 108, 116).
- Switching to gh-aw's queue or Copilot dynamic workflows "ends Symphony's stated purpose, coordination of Claude Code agents", a product change, not an import [Verified, as the note's text] (symphony-vs-gh-aw.md:9, 112).
- Status: the owner approved both queued decisions on 2026-10-14 (decision cards 10:03 and 10:04 UTC, "yes, yes" 10:05 UTC): Candidate A after 0.5.0's fixes, the gh-aw pilot on symphony-protocol-canary after the owner releases 0.5.0; PR 1a (30 `uses:` pinned to commits) prepared and parked as /mnt/project-files/plans/candidate-a-pr-1a-pins.patch [Verified, as the plan's text] (/home/user/symphony-template/docs/checkpoints/2026-10-14b/plans/gh-aw-migration-plan.md:7-14).
- Why Candidate A: it compiles all 11 workflows and changes no behaviour (first output equals the committed file byte for byte); gh-aw can compile only the 3 Claude-running workflows and only through a self-defined engine it calls an unsupported sample; gh-aw "requires an engine and has no engine-less form", so it cannot take the 8 deterministic workflows [Verified, as the plan's text] (gh-aw-migration-plan.md:20-26, 97).
- Candidate B's costs, per the plan: threat detection must be off (it runs only on built-in engines, which bill Copilot or an API key); a push or pull request made with github.token starts no workflow run, so the required check needs a dispatched ci.yml run; 2 rows lost, 14 changed, 3 unmeasured, against A's "same" in every row [Verified, as the plan's text] (gh-aw-migration-plan.md:99-103, 110, 147).
- One lock rule for any migration: gh-aw's Claims come only from `dispatch_next` and bind one Actions run, so running Actions workers on `tools.work-queue` while sessions claim by branch would make two claim authorities and break guarantee G1; gh-aw may be the run layer only [Reported, prior note] (gh-aw-vs-symphony.md:85).
- The note recommended recording the credential and maturity facts as a Decision line and a memory fact; neither CLAUDE.md, docs/memory/ nor .claude/session.md mentions gh-aw on 2026-10-15 [Verified: grep for "gh-aw", "agentic workflows", "candidate a" found nothing] (/home/user/symphony-template/CLAUDE.md; docs/memory/; symphony-vs-gh-aw.md:116, 161).
