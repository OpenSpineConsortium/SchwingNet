## Takeaways

- CooperBench (Stanford + SAP Labs, arXiv 2601.13295, PDF 2026-01-27; ICLR 2026 workshop poster) is 652 two-feature tasks from 12 repositories in 4 languages; its "curse of coordination" is that two agents splitting a pair pass far less often than one agent doing both: Claude Sonnet 4.5 307/652 (47.1%) solo against 168/652 (25.8%) coop, GPT-5 315 against 183, under OpenHands v0.54 with messaging only, isolated containers and a 100-action cap.
- The curse is a property of the isolated, messages-only setting, not of multi-agent work as such: CooperBench's own later ablation (codex + gpt-5.5, flash 50 pairs, one seed, 2026-05-19) has coop 26%, solo 48%, coop+git 56%, team (lead, task list, scratchpad) 62%, and concludes "most multi-agent value = a shared code substrate, not the orchestration". Symphony's design (shared remote, claims, pull requests, a merge gate) sits on the side of that result that beats solo.
- coordbench (OpenSpineConsortium, public) is a plug-in harness that holds CooperBench's tasks, scorer and Claude Code fixed and swaps the coordination "arm": solo, coop, coop-nocomm, coop-git, team (CooperBench's own, prompts word for word), sdlc (Symphony's claim protocol decided by the vendored symphony-protocol gate) and sdlc-watch; an xblossom arm (team + four prompt rules) exists outside the tree and has not produced results yet.
- Preliminary 8-pair step (2026-10-15, claude-sonnet-5-5, Claude Code 2.1.300, 45 min per agent, one seed): solo 5/8, coop, sdlc, coop-git and team each 6/8; every exact McNemar p = 1.000; coordination gap -12.5 points for every two-agent arm (the paper's Claude had +21.2). No curse appeared, so the step cannot show the protocol removing one.
- What the protocol did on those 8 pairs: 16 claims, 16 PRs, 16 merges at first attempt, 0 gate conflicts, fewest messages (3.8 per pair, 8.8% of tool calls against coop's 6.1 and 17.6%), the same estimated cost as coop ($1.30 per pair, $1.73 per verified result) but the slowest median wall time (529 s against coop 335 s, solo 219 s), with 2,306 of 7,375 agent-seconds (31%) blocked in wait_for_message.
- Two agents cost about twice one agent's tokens under every setting (1.9-2.5x by medians); about 95% of input is prompt-cache re-reads of each agent's own transcript, and in this route a fixed ~78-82K-token inherited prefix is 74-79% of input (figures conflict across the notes), so absolute dollars are the route's, not a standalone agent's.
- A convincing result needs far more than 8 pairs: the pre-registration's 50 pairs detect a gap of about 25 points (my simulation: power about 0.87 at one-third discordant pairs), not 10 (power about 0.17); a 10-point gap needs roughly 170-270 pairs, plus several seeds, a task-cluster-aware test, and the 10 blocking harness defects found by the review fixed first.
- The nearest published competitor on the same benchmark is Claim Plane (Apache-2.0, 0.56.3): static pre-write admission raised CooperBench pair pass from 23.3% to 50.0% (+26.7 pp, 95% CI 9.6-60.0) on 30 pairs x 3 seeds, but by serializing 96.7% of executions; no speedup claimed.
- GitHub Actions nativeness is real in the benchmark itself: bench.yml runs each (pair, arm) as one job on ubuntu-24.04 in a public repository, where standard runners are "free and unlimited" (4 CPU, 16 GB RAM, 14 GB SSD, 6 h per job, 256 matrix jobs, 20 concurrent jobs on the Free plan); the only paid input is each account's Claude subscription window.

## Findings

### 1. What CooperBench is

- 652 tasks from 12 open-source libraries in Python, TypeScript, Go and Rust, built by eight co-authors; each task gives two agents one feature each on the same repository state; features are compatible but "potentially conflicting"; 77.3% of tasks have conflicting ground-truth solutions [Verified] PAPER lines 112-115, 227-234.
- Dataset composition: 199 features in 52 task sets, 652 pairs; Table 3 sums 34 PRs, and coordbench notes the text, the column and App A.2 disagree (34 vs 32 vs 52) [Verified] PAPER lines 1328, 1342-1343; CB-PARITY "Open questions" (Table 3 bullet).
- Current code (63b9d44) has 652 pairs over 30 tasks; subsets: lite 100 pairs/26 tasks, flash 50 pairs/20 tasks/11 repos (uniform from lite, seed 42), core 10, flash_10 10, team3_250 (250 triplets) [Verified] CBCODE dataset/subsets/*.json.
- Gold-conflict share at 63b9d44: 499 of 652 (76.5%) against the paper's 77.3% [Verified] S8-REP "Dataset" section, lines ~280-282 (computed by coordbench from CBCODE dataset/gold_conflict_report.json).
- Setting: agents run in separate Docker containers/VMs, communicate only by a message tool (SQL-backed, delivered into the next step's prompt), are capped at 100 actions ("we do not observe performance gains ... from raising this number"), and their two patches are merged once at the end with git merge-file; a small learned resolver handles superficial conflicts [Verified] PAPER lines 235-262, 371-380.
- Models: GPT-5, Claude Sonnet 4.5 (via GCP), MiniMax-M2, Qwen3-Coder-30B-A3B-Instruct, Qwen3-30B-A3B-Instruct-2507 (two Qwen via vLLM), all under OpenHands v0.54 [Verified] PAPER lines 371-373, 465-467.
- Headline counts, Table 5 (k of 652, solo/coop): gpt-5 315/183, claude 307/168, minimax 236/91, qwen coder 141/87, qwen 41/30; retention AUC_coop/AUC_solo 0.64, 0.60, 0.46, 0.63, 0.68, pooled 0.59 [Verified] PAPER lines 1511-1524. The website and Table 6 give claude coop 169 and gpt-5 182 (conflict with Table 5) [Verified] S8-REP "Pass rates" note line ~29; CB-PARITY Open questions.
- The gap is stated three ways: "30% lower" (abstract), "around 50% lower"/"25% success" (intro, blog), "41% of Solo capability is lost" (App C pooled retention) [Verified] PAPER lines 64-70, 136-139, 1496; BLOG1 line 41. coordbench's report says "The abstract's '30% lower' follows from none of the paper's numbers"; its derived Claude gap is 21.2 points (45% relative), pooled 46% relative [Verified] S8-REP "Coordination gap" paper line.
- Gap is largest at middle difficulty ("mid-difficulty crisis") [Verified] PAPER lines 485-491; BLOG1 line 56.
- Scaling agents: 68.6% with 2, 46.5% with 3, 30.0% with 4, on 46 tasks from 3 task sets, model not named [Verified] PAPER lines 529-536.
- Communication: with vs without the message tool is not significantly different in success, but significantly reduces merge conflicts; up to 20% of steps go to messages (Claude 20.0% of events) [Verified] PAPER lines 545-566; S8-REP "Communication" paper line.
- Failure causes (Table 2): expectation 42%, commitment 32%, communication 26%; the blog says expectation is 63% of failures (conflict, flagged by coordbench as an open question) [Verified] PAPER lines 738-752; BLOG1 line 127; CB-PARITY Open questions (Table 2 bullet).
- Emergent success behaviours: role division, resource division ("I will modify ONLY lines 68-84"), negotiation; the authors call orchestration scaffolding "a workaround, not a solution" and bet on native ability, while inviting orchestration submissions ("We are happy to be proven wrong") [Verified] BLOG1 lines 167-201, 205-209, 224-228.
- Git follow-up (blog, Feb 2026): giving agents a self-hosted git server raised coop by +1.53 (Gemini 3 Flash, OpenHands SDK: 27.76% vs 26.23%, solo 48.60%), +2.91 (Flash, Mini-SWE: 15.18 vs 12.27, solo 25.20) and +1.38 (Gemini 3 Pro, Mini-SWE: 21.78 vs 20.40, solo 36.80), "not statistically significant"; it adds five failure patterns (impatience, destructive overwrites, broken commits, git disasters such as force pushes, blame hallucination) [Verified] BLOG2 lines 41-138, 140-186.
- Team-harness ablation (CooperBench docs, generated 2026-05-19, codex + gpt-5.5, flash 50 pairs, Docker, one seed, unreviewed): coop 13/50 (26%), solo 24/50 (48%), coop+git 28/50 (56%), team baseline 31/50 (62%), team minus scratchpad 15/50, minus task_list 20/50, minus mcp 30/50, minus auto_refresh 30/50, minus protocol 35/50; median task time solo 2m50s, coop 3m02s, coop+git 3m42s, team 3m56s; eval policy identical -> naive 3-way merge -> lead's patch alone (no union, no member fallback) [Verified] ABL (text extracted); REPORTPY lines 98-100 encode the same 24/13/28/31.
- Framework comparison on the 10-pair core subset, team setting: mini_swe_agent_v2 6/10 ($13.37), openhands_sdk 4/10 ($31.90), claude_code with claude-sonnet-4-5 5/10 (~$8.5), codex 5/10 [Verified] CBCODE docs/BENCHMARK_RESULTS.md lines 1-50.
- Venue: listed as an ICLR 2026 workshop poster (Workshop on Multi-Agent Learning ...), 2026-04-27, under the earlier title "CooperBench: Benchmarking Cooperation in Coding Agents" [Reported] WebSearch: iclr.cc/virtual/2026/10018462. CooperBench code is MIT [Verified] CBCODE README.md "License".

### 2. The arms coordbench compares, and how each coordinates

- coordbench holds task, agents and scoring fixed and makes coordination a plug-in "arm", a Claude Code plugin plus a hub that serves the arm's tools over MCP/HTTP; drivers are headless Claude Code in containers (claude-cli) or the orchestrating session's own subagents (session) [Verified] CB-ARMS lines 1-28.
- solo: one agent implements both features; nothing shared [Verified] CB-ARMS line 34.
- coop: one agent per feature, messages only (CooperBench's Coop; coop-send, coop-broadcast, coop-recv; pull delivery, as 63b9d44's claude_code adapter) [Verified] CB-ARMS lines 35, 42-72; CB-PARITY Decisions item 2.
- coop-nocomm: coop with messaging banned (CooperBench --no-messaging); left out of the pre-registered run to save usage [Verified] CB-ARMS line 36; CB-PLAN lines 31-39.
- coop-git: coop plus a shared bare git remote `team` the agents push to and merge from (the blog's "Curious case" setting); its prompt tells each agent to merge peers' branches before writing its patch [Verified] CB-ARMS line 37; S8 lines 189-193.
- team: a lead and members, a shared task list with an atomic claim under the run's lock, typed requests, a scratchpad volume, and a working wait_for_message (CooperBench's own at 63b9d44 always timed out because of a Redis key-prefix mismatch, which coordbench documents) [Verified] CB-ARMS lines 38, 73-118.
- sdlc (Symphony): an issue per feature, an exclusive first-come claim (on GitHub the first push of claude/<issue>; here an in-memory check-and-set under the run's lock), a branch and pull request on the shared remote, mark_ready, and a merge gate that merges into main only when the branch merges cleanly with current main and otherwise answers "main moved" (merge main in, never rebase); decided by the vendored symphony-protocol gate (bare_git adapter) [Verified] SDLC-ARM lines 1-40; CB-ARMS lines 120-139.
- sdlc gate policy: `gate.Policy(bring_main_in=gate.MERGE, who_merges=gate.GATE, required_check="", remote="team")`, i.e. the gate runs no tests; each agent is told to submit patch.txt from the integrated main once its PR merges [Verified] SDLC-ARM lines 99, 288, 421-430. The harness review confirms the gate runs no tests and that naming a required check would block every merge [Verified] REVIEW lines 19-23.
- sdlc-watch: sdlc plus a peer_pull_requests tool (shared files, whether two branches merge cleanly by git merge-tree, lines both added) and habits of early drafts and frequent pushes; not in the step [Verified] CB-ARMS lines 40, 141-160.
- xblossom (outside the tree): CooperBench team mode plus one prompt section with four moves: facts filed under /workspace/shared/facts/<git hash-object>, a disjoint file plan (FILES.md, PLAN.md, REQUESTS.md), open tasks claimed by coop-task-claim (CAS; loser exits 2), and certificates in done notes (patch path, git diff --stat, test command and exit code); the team prompt is an exact prefix of the xblossom prompt, so a difference is the moves' effect [Verified] XB-ARM lines 3-85. It was approved at 17:24 UTC and a 12-run screen (xblossom, team, solo on go_chi 56 and click 2068, two seeds) was "running now" at 18:15 UTC; no results are in the folder [Verified] ORDER lines 26-31; directory listing of EXP/xblossom at 18:3x UTC.
- X-Blossom is Fan, Lee and Zhang, PVLDB 18(10), 2025, a parallel blossom algorithm; the notes map its static path table to the KV/prompt cache and to blob-hash-keyed facts, its vertex-disjoint augmenting paths to disjoint file sets, and its lock-free CAS claims to Symphony's first-push claim [Verified] XB lines 3-15 (the paper itself not read by me).
- Pre-registered question and analysis: does sdlc pass more often than coop on CooperBench's flash pairs, and how much of the gap to solo does it close; primary test sdlc vs coop on both_passed, two-sided exact McNemar at alpha 0.05; Wilson intervals plus a task-set bootstrap (2,000 resamples, seed 0); a sign-flip permutation over task sets is the planned follow-up [Verified] CB-PLAN lines 9-15, 103-118.
- Parity discipline: PARITY.md maps 149 measures (68 same, 24 equivalent, 49 different, 8 not measured); model-judged measures run only by hand and never on ANTHROPIC_API_KEY [Verified] CB-PARITY lines 64-80, 1820-1834.

### 5. What a convincing result would require

- Pre-registered size: all 50 flash pairs (20 tasks), five arms (250 jobs), each arm on every pair, one seed, 120 minutes per agent, Claude Code on the runners' route [Verified] CB-PLAN lines 17-58.
- Power, per the plan: at the paper's rates (solo ~47%, coop ~26%) about a third of pairs are discordant and an exact McNemar test over 50 pairs detects a gap of roughly 25 points; a 10-point sdlc-vs-coop gap "will not reach significance here"; a second seed on discordant pairs is the follow-up [Verified] CB-PLAN lines 128-134.
- My simulation of the exact McNemar test (alpha 0.05, one-third discordant, pairs independent): power for a 10/15/20/25-point gap is 0.17/0.38/0.64/0.87 at n=50, 0.14/0.31/0.56/0.81 at n=43, 0.34/0.70/0.94/0.99 at n=100; 80% power for a 10-point gap needs about 270 pairs (about 170 if only 20% are discordant); at n=8 power is about 0 (5:0 discordant gives p=0.0625) [Inferred] script /tmp/claude-research/power/power.py. Task clustering (50 pairs from 20 tasks) lowers effective n further [Inferred] from CB-PLAN lines 106-112.
- The step itself saw 1 discordant pair in 8 between solo and the two-agent arms and 0 among two-agent arms, so "even the 43 gradable pairs would detect less" [Verified] S8 lines 301-304.
- Strata: 50 flash pairs fall in 14 strata (python 35 pairs, python+c 6, rust 4, go 2, python+rust 3; gold conflict 37, clean 13; published difficulty none 19, few 26, many 5); the 43 gradable pairs fill 12; growing by the nested order keeps a cut-short run balanced at 16, 24 or 32 pairs [Verified] PILOT lines 147-167; S8 lines 22-25; S8-STRATA lines 1-16; ORDER line 33.
- Harness first: the adversarial review (2026-10-15 16:45-18:10 UTC) confirmed 30 of 32 findings, 10 blocking (session route drops plugins/options; scorer cannot tell integrated from duplicated work; gate runs no tests; bare remote enforces no ref rule so claims are not a CAS on the server; unmatched transcripts counted as zero; respawn accounting; lost subagents recorded as timeouts; lane re-spawns; permission refusals scored as arm failures; disk-full undetected) [Verified] REVIEW lines 3-65. The trial order requires six more blocking fixes before any larger run, and says grant numbers should come from standalone agents in GitHub Actions, as CooperBench runs them [Verified] ORDER lines 14-24.
- Repeats: at least two seeds per arm for the xblossom screen; at least 3 repeats for token comparisons because repeated runs can differ up to 30x in tokens (Bai et al., unverified); run paired seeds before claiming a gain ("How Much Coordination Gain Is Real?") [Verified] OTS lines 124, 140; RAG lines 225-228, 250-251.
- The noise-floor paper (Kaliyev and Maryanskyy, arXiv 2606.20695, 2026-06-15): on tau2-bench retail with Haiku 4.5, a single-seed +18 pp gap did not reproduce (-3 pp on seed 2); pooled +5 pp, CI [-2, +12]; seven of ten recent coordination architectures report effects below the local floor of about 15 pp [Reported] WebSearch: arxiv.org/abs/2606.20695 and its HTML.
- Equalities to hold: model, effort, per-arm budget, infrastructure and concurrency, task order; fresh repository per trial; interleave arms in time (the review found arms always run in the same order on every pair) [Verified] CB-RESEARCH lines 113-119; REVIEW line 151.
- Budget on one account: one five-hour window ran about 21 pair-runs at five lanes; 43 pairs x 5 arms is about eleven windows (about 2.5 days); the runners' route with several accounts runs the list in a day [Verified] PILOT lines 169-180.
- A curse can only appear on pairs where coordination fails; Claim Plane's biggest effect was on conflict-labelled pairs (6.7% -> 60.0%), which suggests stratifying the readout by gold conflict [Verified] Claim Plane README; [Inferred] for the suggestion.
