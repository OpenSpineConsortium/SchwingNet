# 03 Uniqueness: is Symphony the only system that combines (a) to (e)?

Adversarial check, 2026-10-15. The claim under test: Symphony is unique in combining
(a) a claim that is the first push of a per-issue branch `claude/N` on the shared forge, so the forge and not a server of the project's own makes the claim atomic across accounts and machines;
(b) automatic release of a claim idle 24 hours without a commit, by a CI job, with the work kept under a renamed branch;
(c) the board and the coordinator running as GitHub Actions jobs in the repository, with state only in GitHub objects;
(d) workers that include people's own interactive Claude Code sessions and agents in Actions on a Claude subscription token (CLAUDE_CODE_OAUTH_TOKEN), under one claim rule;
(e) validation of the protocol by exhaustive interleavings of the shipped library against an oracle written from the spec text, with mutants.

The target was a counterexample with (a)+(b)+(c), (a)+(c)+(d), or any four of the five.

Method: WebSearch (14 queries, budget not exhausted), shallow clones into /tmp/claude-research/rival/ (README and docs read, no code run; folder deleted afterwards), and raw.githubusercontent.com and PyPI/crates.io metadata. dev.to and forge.lthn.ai were unreachable from the session (DNS), so two leads were not read: a dev.to post on a git-built coordination layer and a Forgejo "issue dispatch" RFC. No GitHub MCP search was used.

Symphony's own (e) was confirmed: /home/user/symphony-protocol/validation/README.md describes the library's own code run against a stateful GitHub fake and real git, breadth-first search over every interleaving to a set depth, an oracle "written from the spec's own text", and a mutation lane (93 mutants, each caught on a shortest trace).

## Verdict: Survives with narrower wording

No candidate does (a)+(b)+(c) as stated, (a)+(c)+(d), or any four of the five. The claim as worded is too broad, though, and three findings narrow it.

1. **unsorry has a looser form of (a)+(b)+(c), four months earlier** (ADR-004, 2026-06-10). Its claims are first-push-wins pushes to GitHub with no server. An Actions cron reaper expires them every 15 minutes. Its board and dispatcher are Actions jobs over GitHub-only state. What differs from Symphony is the form of each part:
   - its claims are files on one shared branch, not a ref per item;
   - its expiry is a two-hour TTL from the claim, not idleness since the last commit;
   - nothing keeps or renames the work.

   unsorry lacks (d), since no agent runs in Actions and no subscription token is used there, and it lacks (e). It is the strongest counterexample and should go into the study.
2. **gh-aw does (c), and model-level (e).** Its work-queue claims are published by a forge CAS on one ledger branch. It has bounded TLA+ checking with 68 mutation configurations, but of abstract models, explicitly not of the shipped Go and JavaScript code. It has no idle release and no subscription token. So (e) must say "the shipped library", or gh-aw nearly matches it.
3. **agentic-setup's branch lock is stricter than Symphony's (a)**: it is create-only through `--force-with-lease=<ref>:`. Symphony's "GitHub refuses the second push" is really git's non-fast-forward rule (notes 07 l.177). So (a) should not say "create-once".

Exact narrower wording:

> Each mechanism has prior art, and a looser form of three of them already exists together: unsorry (2026-06) has first-push-wins claim files on a shared GitHub branch, a TTL reaper and a board and dispatcher that run in Actions. Symphony is the only system found that adds the other two to them: one claim rule for people's interactive Claude Code sessions and for agents in GitHub Actions on a Claude subscription token, and validation of the shipped library itself, by exhaustive interleavings against an oracle written from the spec's text, with mutants. It is also the only one found that claims through a branch per issue and releases a claim by idleness since that branch's last commit, keeping the work under a renamed branch.
