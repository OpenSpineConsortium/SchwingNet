## ENGINE

- Number formatting (SPEC 8 and 12) does not use the JavaScript forms the SPEC names. Instead of v.toFixed(6) and String(Number(h.toPrecision(6))), formatNumber, pyFixed, hoursWord (pyG) and pyRound format the double's exact decimal value with ties to even, as CPython does. Reason: the task requires an exact match with Python's format(v, ".6f") and f"{h:g}", and the named forms differ. toFixed(6) writes 0.0078125 as 0.007813 where Python writes 0.007812. toPrecision(6) writes 10.03125 as 10.0313 where :g writes 10.0312, which is inside the 0.1..48 range SPEC 12 says agrees. toFixed switches to an exponent from 1e21. Verified against python3.12 on about 1,300 values.
- Additions to the API, with nothing removed or renamed. jobs() returns {rows, totals, problems}: the SPEC 11 array "limit" problem is reported there and in compile().problems, not in propagate(). compile() adds a "problems" field holding propagation's and jobs' problems. Each request also carries command (FLOW_HEAD with --epochs, --seed, --hours, --recipe and --block words) and combination ([{node, param, value}]). SB also exports version, emptyType, formatNumber, hoursWord, pyFixed, pyRound, floatPlain, valueProblem and issueBody(named, epochs, seed, hours, recipe, data). Reason: the UI and the tests need them.
- Two problem codes not in SPEC 10. "node" (error) marks an id that is not n1..n9999, or a second node with the same id; that node, and every edge touching an id not in the graph, is left out. "text" (error) marks a name, node or edge string that canonical JSON cannot write (non-ASCII or a control character). On a node it has node = the id; on an edge, node = the edge's to; on the spec name, field "name". Reason: SPEC 2 and 8 make these invalid but give no code. A spec that canonical JSON cannot write gets the digest "".
- checkManifest keeps at most one problem per (code, field) and joins the texts of repeats with "; ". propagate keeps one problem per occurrence, as SPEC 10 counts them. Reason: one manifest rule can fail many times (for example R8 on every probe), and SPEC 13 gives one code per rule.
- A pattern's parts may be "any" as well as "split" or "unsplit" (SPEC 6 lists only the latter two). "any" behaves like an absent key; it is a tolerance, and DATA does not use it.
- Null values in ops. SPEC 7 defines null only for size (which removes the size) and for add_axis's size. Here a null value, whether written or read from an unconnected @in ref, also sets classes or family to null in a set op. Any other op given null, including axes and parts, leaves the type as it was with no problem. Reason: SPEC 7 makes an @in ref null when its port is unconnected, so an optional unconnected input must not raise an "op" problem; the R8 probe test hit this case. For the same reason a size op reads its value before checking the axis.
- Riders (SPEC 11, "first connected upstream compute node"). A rider follows the first of its own inputs, in manifest order, whose edge comes from a cpu or gpu node. It rides only when that node's class equals its own, and a rider of a rider rides with that rider's host. The rider's row has 0 submissions and keeps its own tasks and hours. Its hours per task are added to the host's row, and it counts in no total. Reason: the SPEC leaves "first" and chains of riders open.
- Choices SPEC 12 leaves open in compile: - ready is true on the experiment route only. - "only" is checked against the base value and every varied value. - float_plain checks refs to float params (their varied values, else the base) and any literal that is not whole. - When two nodes map the same value, the higher node number wins. - epochs, seed and hours fall back to 20, 1 and 4, experiments_panel.form_text's defaults, when no node maps them. - request.hours is the mapped number; jobs.gpu.hours is round(sum, 2). - The pipeline issue's body ends with a newline after its closing sentence.
- Prediction never offers the anchor's own block (SPEC 14 says any stage but source). Reason: the on-board penalty does not apply to evaluate, analyse and report, so report_claim would otherwise follow report_claim and evaluate_heldout would follow itself. After report_claim, predict now returns [].
- predict uses the section 15 signature, (spec, anchorId, data, stats, history), not section 14's line, which leaves out data. The task asked for section 15 exactly. The score formula is in the header: transition 2(c + 2h)/(total + 1); stage 1 for the next missing stage, decaying for later stages, 0.25 for the same stage, 0 for an earlier one; 0.5 bonus for a missing stage; -2 for a block already on the board outside evaluate, analyse and report; rounded to 3 decimals, ties broken by block id. The why sentences follow SPEC 14's examples ("after Train the classifier, the templates go to Evaluate on held-out test (3 of 4)", "the pipeline has no report step yet") but are not word for word.

## PY

- The compile step is the Python function compile_spec, not compile, so it does not shadow Python's built-in compile. The command-line word is still `compile`, as SPEC says.
- check_manifest(manifest, contract) checks the manifest itself and gives the same (code, field) pairs as engine.js's checkManifest. The checks that need the repository's files are in code_problems(manifest, root), which check and check-block add: implemented_by stays inside the repository and names files that exist; own code needs tools/sandbox/blocks/<id>.py with a docstring and a top-level `def run(inputs, params, context)`, plus tests/test_sandbox_block_<id>.py. They are separate because the browser cannot see files. As an extension beyond SPEC, the paths in card.from must exist too.
- A names pattern is compiled by Python's re as ^(?:pattern)\Z with re.ASCII. This agrees with JavaScript's RegExp on the plain classes, repeats and anchors that names patterns use. Rarer syntax, such as named groups, lookbehind or \p, could read differently in the two engines; none of it is in the data.
- A request's URL query is built with urllib.parse.urlencode. It escapes '*' and '~' differently from URLSearchParams, so the URLs can differ in those characters while the decoded parameters are the same. The tests therefore compare decoded queries, not raw URL strings.
- The four inputs go into the page verbatim, but write refuses any input that would break the page or make it load something: non-ASCII, CR, `</style` in page.css, `<script` or an unclosed `<!--` in shell.html, `</script`, `<script` or `<!--` in engine.js or ui.js, and `<script src`, `<link`, `@import`, `fetch(` or `XMLHttpRequest` anywhere. It also refuses data JSON that would hold `<script` or those words. write refuses only these assembly problems; check reports every problem.
- tools/experiments_panel.py is loaded by its file path (importlib), not by putting tools/ on sys.path. CLAUDE.md records that tools/profile.py would shadow the standard library's profile module for anything imported after it.
- Glyph names are matched in ui.js as `name:`, `"name":` or `'name':` anywhere in the file, not only inside the glyph table, because finding the table's bounds would need a JavaScript parser.
- DATA.experiment.hours_most is written as 48, as SPEC writes it, even when experiments_panel.HOURS_MOST is the float 48.0.
- Arithmetic on combinations, fan, tasks and hours (job totals, a rider's hours added to its host, the compile's GPU hours) follows JavaScript doubles: exact up to 2**53, rounded as a double above that. The numbers, and the texts that contain them, then match engine.js. SPEC says only 'the same results'.
- Two checks were added beyond SPEC: a template's id must be unique and equal its file name, as a block's must, and check-block refuses a manifest file whose name is not its id.
- The cross-check test reads every number past 2**53 as a double on both sides, because JSON.stringify writes the shortest digits (243405270090015000) for the same double that Python writes as 243405270090015008.

## UI

- Hold position: I read '120px right of a card's middle' as 120 px right of the card's right edge, at the card's vertical middle. UI.md's grow zone starts at the right edge +6. The card's centre +120 is the right edge +4, which is on the output handle, where a press starts a connection. The test checks that a node grows at the right edge +120 and that none grows at the centre +120.
- Escape always cancels a visible ghost, even with focus in a text field. The digits, Enter and the arrows reach the ghost only when focus is not in a text-entry field (a checkbox does not count as one). A press on the board takes focus off a focused field, so the board's keys and Ctrl+Z act on the board. Delete and Backspace still do nothing while any input field has focus, as UI.md says.
- Escape's suppression and the one-card-per-hold block apply only to a resting pointer. A deliberate press, click or tap in a zone still commits. On touch, a release after 250 ms but before the ring fills cancels without suppressing, because a finger has no hover with which to leave the zone.
- Additions beyond UI.md: (1) a ghost opened by a finger or by the keys scrolls the board to show the ghost and its strip; a mouse ghost never scrolls the board, since scrolling would move it under the pointer. (2) No ghost grows while a chip is being dragged over the board. (3) Edge labels take pointer events, so their <title> shows the full type summary. (4) The stored board is cleaned on load: only unique nN ids, edges between kept nodes, and two-number layout entries survive. (5) The panel starts at its top when another node is selected. (6) On the experiment route, a note under the plan table explains that the rows count jobs as the pipeline route would (a rider's hours added to its host's), while the tiles count requests. For example, train shows 5 h but the request is 4 h.
- The palette's stage tabs wrap from 700 px wide so all 11 stages show. Below that they scroll sideways inside their own row.
- window.sandbox adds timings(clear) beside the nine hooks SPEC 17 lists. It is used only by the browser test.

## INTEGRATOR

- SPEC.md section 5 and R10/R11 (code planned goes with today planned) is wrong in one corner: a block whose code exists only on an unmerged pull request can be neither existing (its paths are not on this branch) nor own, so the pending status it defines could not be reached. Both engines now accept code planned with today.status planned or pending (a pending note must still name #<number>). annealer_unet and train_annealer are pending on #483, as DATA.md, UI.md and the lead's README line 99 intend. contract.json's R10 text is reworded.
- SPEC.md R8 (every data block must accept every probe of its rank and time) made blocks say less than they need: every probe is level-targeted and split, so no block could ask for masks or unsplit data. Each probe now takes the first input's own targets (its first, where the probe's is not among them) and, for an input that asks for unsplit data, empty parts. Rank, time, channels, sizes and dtype are still probed as before. This is the same in engine.js (probeFor) and pipeline_sandbox.py (probe_for), and contract.json's R8 text is reworded.
- DATA manifests changed on that basis: split_person and split_anomaly_aware accept parts 'unsplit' (input text 'not split yet'); morphometry and annealer_unet accept targets ['mask'] (their own texts say masks). bordercall_naming stays open on targets, since it takes masks or a morphometry table, whose targets is 'level'.
- ui.js: the resources list now shows today.note for pending blocks too (it was hidden for pending), so the branch paths of #483 are visible beside 'built on #483, not merged'.
- I accepted the writers' other deviations as SPEC-compatible or as fixes of SPEC errors. Two are SPEC errors and the engine is right: the JavaScript number forms that SPEC names (toFixed, toPrecision) differ from Python at ties and at 1e21, and section 14's predict line omits data while section 15 includes it.
