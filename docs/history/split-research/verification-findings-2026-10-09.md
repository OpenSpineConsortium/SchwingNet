Each item names the area, the skeptic's verdict and its evidence verbatim. "fixed" items are left out.

The paths below are this repository's experiment/ as it stood on the branch claude/10 that day. That code now lives in OpenSpineConsortium/coordbench, where experiment/coordbench/ is the package coordbench/ at the root, the rest of experiment/ is under bench/cooperbench/, the tests named here are under its tests/, and the memory fact on MCP timeouts cited in the cli findings is its docs/mcp-timeout.md. ## skeptic:hub-runs

### PARTLY: 3. hub.py: the hub never forgot a run and re-executed arm.py per run (DELETE /api/runs/{run}, arm classes cached per directory, fresh instance per run)

Holds in the main case: DELETE on an open run -> 200 {released: true}, teardown once (three concurrent DELETEs of one run -> [200, 200, 404] and one teardown); with the team arm, wait_for_message blocking over /rpc and over /mcp (tools/call) both returned the no-message marker 1.0 s in when the DELETE arrived, threads ended, run_count 0, hub stderr empty; GET /api/runs and /rpc after DELETE -> 404; the events.jsonl stays on disk; 8 concurrent creates of 'coop' -> no errors, one cached class, one class seen across runs; the cache test fails on 7438ca2 (two loads gave two class objects). run.py close_run fetches metrics then events then release_run, which turns a HubError (the 405 test, or any OSError-derived HubError) into a warning and leaves hub_run True; the 405 test fails on old code (no HubClient.release to patch). FAILS on this path: Hub.release_run pops by id, not by identity (hub.py:268 self.runs.pop(run_id, None)). Reproduction (probe_arms_inflight.py): arm whose teardown sleeps 1.5 s; create run 'R'; send DELETE d1, 0.2 s later DELETE d2. d2 sees first_close False, pops 'R' and answers 200 while d1 is still in teardown; a create of run_id 'R' now succeeds (201, new run object); when d1's teardown ends it pops the NEW run. Result: GET /api/runs/R -> 404, run_count 0, teardowns run once (for the old run only): the new run is forgotten unclosed and never torn down, and its runner would get 404 on close/events. Also d2 answered 'released' before any teardown finished. Reachability: this runner's new_run_id appends secrets.token_hex(3), so it never re-creates an id; another harness with fixed ids, or a retried DELETE, can. One-line fix: pop only if self.runs.get(run_id) is the hosted that was closed. Minor: in run.py close_run, when hub.close_run succeeds but hub.events fails, the run is never released (stays hosted) and the metrics are dropped with a warning that says 'closing ... failed'.

### BROKEN OR LEFT: 

Nothing I could find was broken by these fixes. Checked specifically: the four arms' .mcp.json and cli.py/bridge.py all send the per-agent token, so the runner's always-on agent_tokens does not lock out any built-in arm; load_arm and find_arm behave as before (load_arm delegates to load_arm_class and instantiates); blocking tools of the team and coop arms end cleanly when their run is released; tests.test_coordbench_hub, tests.test_coordbench_arms_coop and tests.test_coordbench_run pass (152 tests).

### BROKEN OR LEFT: 

Narrow hole left by fix 3, not a regression: Hub.release_run (experiment/coordbench/hub.py:268) forgets whatever run holds the id at the time, so an overlapping second DELETE plus a re-create of the same run id drops the new run unclosed and untorn-down (reproduction in verdict 3).

### DOCSTRING: experiment/coordbench/hub.py:263-264, Hub.release_run: 'closing it first if it is still open, so the teardown runs once however the runner ends' is false under the double-DELETE/recreate race, where the re-created run is forgotten with no close and no teardown, and the second DELETE answers released before the first's teardown has finished.

### DOCSTRING: experiment/coordbench/hub.py:308-310, Hub.check_agent: 'in constant time so the comparison tells a guesser nothing' overstates secrets.compare_digest, which returns at once on unequal lengths; a guesser learns the token's length (43 characters). Harmless, but not nothing.

### DOCSTRING: experiment/coordbench/run.py:995-997 and 1004, close_run: 'a hub that has gone away leaves them empty and says so' and the warning 'closing the run on the hub failed' also fire when hub.close_run succeeded and only hub.events failed; in that case the metrics the hub returned are discarded and the run is never released, which the docstring and the release_run docstring at run.py:1011-1016 do not say.

## skeptic:mcp-transport

### PARTLY: 1. mcp.py/hub.py validation: -32602 vs -32603, per-member batch answers, null/boolean ids, non-string method, empty batch, 400 for parse errors and invalid messages, no session for an errored initialize, list params / list tool name crashes, /rpc list tool 500

Main cases hold: every listed input now gets the claimed code (probe /tmp/claude-0/.../scratchpad/probe-mcp/probe_shape.py), and the pinning tests (test_a_lone_message_that_is_no_request_is_400, test_a_request_with_a_bad_shape_is_refused_with_its_id, test_a_bad_batch_member_fails_alone, test_an_initialize_refused_for_its_shape_opens_no_session, RpcTest.test_a_tool_name_that_is_not_a_string_is_400) all FAIL against the 7438ca2 tree and pass now. Residual failures: (a) 'session only on a result' is refuted: opened_session (hub.py:470-476) tests `a.get("id") in asked` with Python equality, so the batch [{initialize, id:true, params:ok}, {ping, id:1}] gets the initialize refused -32600 id-less AND an Mcp-Session-Id header (1 == True); same for id:false with ping id:0, and for duplicate ids [{initialize id:1 params:[1]}, {ping id:1}]. Contrived input, but exactly the failure the finding named. (b) A deeply nested body (b'[' * 200000) raises RecursionError, not ValueError, from json.loads in handle_body; answer_mcp's fallback internal_errors() re-parses and raises again, so /mcp answers HTTP 500 {"error": FAILED} with three tracebacks on stderr, and /rpc answers 500 with one; same 500 when the body also carries a bad MCP-Protocol-Version (opens_session parses first). Not the claimed 400. (c) A lone {"jsonrpc":"2.0"}, {"jsonrpc":"2.0","id":1} or {"jsonrpc":"2.0","foo":1} (no method, no result) is taken for a response by mcp.py:161 and answered 202 with nothing, where JSON-RPC says -32600; hub.py:24-27 claims 400 for such a message. (d) tools/call with arguments [] / 0 / false / "" runs the tool with {} because of `params.get("arguments") or {}` (mcp.py:103); /rpc arguments [] likewise. Only a non-empty list is refused.

### PARTLY: 5. mcp.py/hub.py: notifications/cancelled ignored, a blocking tool took what it waited for and wrote it to nobody; a lost reply lost the item

Main path holds and is pinned: test_a_cancelled_wait_gives_the_marker_at_once_and_takes_nothing, both test_a_lost_reply_* tests, CallTest and the two kit WaitTest cancel/lost tests all FAIL on the old tree. Could not break: cancel on another session or on no session (separate in_flight dicts, 202, no effect); cancel for /rpc (never entered in in_flight, by design); string '41' for int 41 (ignored, per spec); cancelled call whose client dropped (reply_or_undo with no undos, no traceback, hub goes on); an undo raising Exception (others still run, traceback logged; a BaseException escapes lost() but the `with run.lock` releases the lock). Residual failures reproduced (probe_cancel.py): (A) cancel racing the pop: a cancel that lands after wait_for_message popped the message but before the reply is written (deterministic in-process via a run.emit hook on 'receive'; over HTTP a window of ms widened by the events.jsonl write in emit) finds the call in flight, sets cancelled, and the hub then writes the MESSAGE to a client the spec tells to discard it; no undo runs because the write succeeded; inbox is empty afterwards. The hub could run call.lost() when call.cancelled is set after the handler returns, and does not. Same shape in the team arm's send_request (arms/team/arm.py:362-367). (B) cancel for a batch member: batch [wait id 11 (1500 ms), wait id 12 (3000 ms)]; cancel 12 while 11 blocks -> 12 is not in flight yet (handle_body runs members sequentially), the cancel is dropped; 12 then runs its full wait and takes a message sent during it (inbox empty after, answer for 12 carries the message, the client discards it). (C) cancel racing the pop, id-collision flavour: two session-less clients (or one client reusing an id) both send tools/call id 1; in_flight[None][1] holds the second; the first's `finally: in_flight.pop(request_id, None)` (mcp.py:202-203) removes the second's entry; a cancel for id 1 then finds nothing and the second wait runs its full 5 s. A guard `if in_flight.get(id) is call` would avoid it. (D) a cancel arriving before started() (during tools_for/dispatch) is ignored as the spec allows, and the call then takes a message the client discards; noted only.
