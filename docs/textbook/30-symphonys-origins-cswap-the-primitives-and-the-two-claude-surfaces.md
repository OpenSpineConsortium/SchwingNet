# 30 Symphony's origins: cswap, the primitives, the build plan and the two Claude surfaces

Label: symphony-beethoven-separable. This chapter holds Symphony material alone, nothing of SchwingNet's method, data or numbers, and may be split out of the book with the rest of Part S without touching any other chapter.

This chapter records the line of thought of 3 to 9 October 2026 that became Symphony, so that a maintainer who inherits it knows why the repository, and not a claude.ai Project, is the one plane every Claude account shares. It settles five things for a planner: why no Claude product could be the shared plane; what the owner's own tool, cswap, and its browser extension Claude Swap Cloud could carry of a Project and what they could never do within Anthropic's terms; which of two routes was chosen, on what date, and what was left out of the first layer; what Claude Chat and Claude Code each do that the other cannot, and the procedure that combines them; and how the extension was taken to the Chrome Web Store, with the steps that stay the owner's. It also names the one superseded page in this line, the plan of 8 October, and says what that page alone still holds. What Symphony is today, its guarantees, its comparison with CooperBench and its cost, is [chapter 29](29-symphony-the-protocol-its-guarantees-its-comparison-and-its-cost.md); the Claude workers on the grid and the terms questions that belong to them are [chapter 31](31-claude-workers-on-the-grid-and-the-labs-machines.md); the Beethoven store release is [chapter 32](32-beethoven-the-repositories-the-roadmap-the-reforms-gates-and-the-store-release.md).

## The question that started it

The owner works through several Claude accounts and wanted them to work one project together. The first page in the line, the analysis of 3 October, was not about accounts at all but about which capabilities belong to Claude Chat or Claude Code alone. The question of accounts arrived five days later, in [Shared multi-account Claude project: plan](https://claude.ai/artifact/Rqzwh9ncY9aj6kZa5BQp7m) of 8 October, and its short answer set the direction for everything after it: build around the repository, not around a shared Project.

The plan's reason is a survey of every Claude surface that could host a coordinator. A redesigned Project at claude.ai/code belongs to one user and cannot be shared, which the plan quotes from the Claude Code documentation ("A project belongs to one user. You can't share a project or its threads with another user."), and it was then a beta on Pro and Max only. Project memory is per Project. Cloud sessions are snapshots, not live, and receive no event when the default branch moves. Routines belong to one account and act as it, with API fires capped at 30 an hour per routine and 100 an hour per account, events above that dropped rather than queued. Remote Control and cross-session messaging cover only one's own sessions. Agent teams are one local session on one machine. The one first-party product where several people drive one Claude, Claude Tag in Slack, was on Team and Enterprise only. The conclusion follows from the table: every surface that could coordinate is scoped to one account, so coordination across accounts has to pass through something outside Claude, and the plan chose the GitHub repository and Linear.

The point has been carried since without its source. The contradictions page for this cluster records that the build plan and later the student onboarding both state that a Project cannot be shared with no quoted clause or link, and that only the plan of 8 October quotes the documentation ([the origins contradictions](../../artifacts/_synthesis/contradictions/symphonys-origins-cswap-the-primitives-and-the-two-claude-su.md), row 12). A reader who needs the rule should cite it from there. The repository's own memory restates the consequence as the first fact of how this repository works: a claude.ai Project belongs to one account and its memory is private to that account, so everything more than one account or session needs is kept in the repository, which every account's Project links and every session clones ([docs/memory/how-this-repository-works.md](../../docs/memory/how-this-repository-works.md)).

## The plan of 8 October, and what it alone still holds

The plan of 8 October is superseded. The clusters record the chain: the primitives spec measures cswap against "the plan of 2026-10-08", the build plan builds on the spec, and the build plan records the owner's choice of 9 October that replaced the plan's two central pieces ([clusters](../../artifacts/_synthesis/clusters.md), cluster 11). Much of it nevertheless survived almost word for word.

What survived is the claim protocol and the memory layout. The plan already claims work by pushing a branch named after the issue, relying on git accepting only the first push of a new branch; its first commit adds a claim file naming the account, the plan and the files to be touched; the issue is announced with a label and a comment; a draft pull request opens at once; the pull request deletes the claim file before merging; and a blocker is an issue claimed like any other, which nobody fixes in parallel. Shared memory is one fact per file under docs/memory/ with a MEMORY.md index imported by CLAUDE.md, memory rides in the same pull request as the change it came from, and nothing can write into another account's Project memory. It also saw, before any code existed, that a Project with several repositories loads none of their hooks. Every one of these is in this repository today ([docs/agents/PROTOCOL.md](../../docs/agents/PROTOCOL.md), [docs/memory/a-project-with-several-repositories-runs-no-hooks.md](../../docs/memory/a-project-with-several-repositories-runs-no-hooks.md)).

What the later pages replaced is the machinery around the protocol, and the contradictions page dates each replacement. Linear was the queue, with states Todo, Claimed, In review and Done, and the claim branch was named after the Linear issue; on 9 October the owner chose GitHub Issues (row 0). The coordinator was a routine on the owner's main account, woken by pull request events, pushes to main and an hourly schedule, and acting as that account; by 14 October releasing idle claims and telling overlapping work are plain code in the board's own Actions run, with Claude kept for planning epics in coordinator.yml (row 1, and [Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho)). The hourly schedule did not survive either: on 9 October the board workflow's scheduled fallback was cut from hourly to six-hourly, and the later pages say every six hours (row 2). The plan's board was a file docs/agents/STATE.md on the default branch that the coordinator rewrote; today the board is STATE.md on a branch of its own, and docs/agents/STATE.md only describes its layout. The coordinator tidied memory hourly; the brief has it tidied weekly (row 40). The plan's stale-work rule released a claim after 24 hours without a commit and left a checkpoint comment; the build plan, quoting that rule, wrote it as an Action that only comments once on a pull request idle for a day, a misreading the contradictions page confirms (row 39). Symphony kept the plan's version: the release after 24 idle hours, with a comment saying whose the claim was and what the branch holds.

Four things are kept only in the plan of 8 October. Two are small: its nine setup steps, from exporting the Project with cswap to adding the other accounts one at a time, starting with two and adding a third only when the queue outgrows them; and its note that each Anthropic page it cites was checked against the live page by three independent reviewers on 8 October, the only such record in the line. The two that matter are these. The first is its failure-mode table, which sets each of ten ways parallel agents fail beside the design's answer, from two accounts taking one issue (answered by the branch push as the lock) and two pull requests editing the same files (answered by listing the files in the claim before any edit) to a thread dying mid-task (the 24-hour release), lost pull request events and account enforcement. The table carries figures from the literature that the plan reports and does not reproduce: in CooperBench two agents building separate features succeeded about 30 percent less often than one agent doing both, and a plan sent first nearly halved merge conflicts (29.4 against 51.5 percent); in one study of duplicate work, locks alone left 64 percent duplicates and locks with a shared record of finished work brought it to none, with synthetic agents rather than language models. CooperBench's own counts are in chapter 29, which carries them from the paper.

The second is the plan's warning on multiple accounts. It says that several accounts are not forbidden, that a member of the Claude Code team was quoted saying several Max accounts are not against the terms, and that in mid-February 2026 users reported bans of accounts held alongside other Max accounts, with a third-party article guessing, unconfirmed by Anthropic, that several accounts on one device or address set off the filter. Its rule from that is that every account signs in itself, only in Anthropic's own apps, and nothing scripts claude.ai. The later pages keep the rule and do not repeat the warning; how the record handles the accounts question afterwards is set out below.

## What cswap could carry of a Project

The [SDLC Primitives Spec](https://claude.ai/artifact/LDx4ZDE5CUexASCnEtHZVL) of 8 October is the canonical inventory of what the owner's existing tool could do. cswap is a command line that switches Claude Code between the owner's accounts on one computer; Claude Swap Cloud is its Chrome extension, which copies a claude.ai Project from one of the owner's accounts to another. The spec set out to list, for every field of a Project, where it lives on claude.ai, which primitive reads or writes it, in what format, and what nothing yet carries, so that the system the thread was designing could be built on the fewest new pieces. Every claim cites a file and line in the claude-swap repository as of 8 October, with main at pull request #45.

The spec's finding, which the build plan restates in one line, is that the read side of a Project is proven, the write side is proven only for a new project, and nothing in cswap can or should drive claude.ai unattended. The export script reads a Claude Code project's name, instructions, topic, memory, files, repositories, linked folders, model, effort and auto-continue settings, icon and colour, timeline, threads and session transcripts, and writes them as one folder or one .tar with a manifest, export.json, of format claude-project-export version 1. Memory is the crucial field: the spec records 19 entries read from the live site on 8 October (claude-swap pull request #41), while the import's write of memory rests on a precondition guessed in turn and never confirmed live, with anything refused landing as plain files under carried-memory/. The import always makes a new private project, never changes an existing one, and carries threads and sessions only as files, since claude.ai cannot create live threads. Connectors, routines, artifacts, decision cards, members, the environment and browser access are not carried at all; plugins, skills and MCP servers in the config are dropped without a report line; and whether a Project has config keys for proactivity or pull request attribution was not verified.

The spec also notes that the manifest's exported_at is wall-clock time and no checksum is recorded, so the same project exported twice gives different bytes, and a repository that wants an unchanged Project to give an empty diff has to drop the timestamp and write by content.

The spec measures where the code's weight lies. The two browser scripts are 6,864 lines and do all of the reading and writing of a Project. The extension and its bridge are given as 14,907 lines of plumbing around them, 2.2 lines for every line of script. That total is the spec's own arithmetic error: its listed parts, 9,758 lines of extension source, 4,661 of bridge.py and 287 of file_dialogs.py, sum to 14,706, and the build plan repeats the wrong total as its premise (rows 8 and 9). The book carries the parts and their sum, 14,706, until someone recounts at that commit; the conclusion, that the extension is roughly twice the size of the scripts it wraps and parses almost nothing of the export, does not change.

Against the system the thread wanted, the spec's gap table is the core of the page. Nothing wrote a Project's instructions into CLAUDE.md, although the checkpoint already owned a marker section of CLAUDE.md. Nothing wrote the exported memory under docs/memory/ or built its index, and the reverse direction, from repository to Project memory, rested on the unconfirmed write, so the spec advised that the plan should never need it. A Project has no goal field and no link to an issue; its topic is the nearest thing. The checkpoint, cswap checkpoint write, was deterministic (the same transcript gives the same bytes, Decision: and Constraint: lines first and never cut) but interactive only, local only, and inferred its other lines by word-list regular expressions, so a plausible wrong line could reach CLAUDE.md. No route could update a Project that already exists. And there was no export that nobody has to click: every route needs a signed-in tab, the folder and extension routes need the person at the Save As window, the sign-in and the Open window, and the one route that can run unattended is a prompt that the Project's own Claude runs to commit an export to a branch, which is lossy (no name, topic, settings or sessions) and gives different files run to run.

## What cswap could never do within the terms

The spec lists the constraints that bind any design and calls a design that breaks one a dead end, not a shortcut. The first is the terms. The spec reads the Consumer Terms (which, the plan of 8 October notes, cover Free, Pro and Max) as forbidding access to the services through automated or non-human means except through an API key or where Anthropic explicitly permits it, and treats routines and cloud sessions as Anthropic's own features rather than scripts against the site. From that it draws the rule the whole line keeps: nothing scripts claude.ai on a schedule, an export is a person's click in their own signed-in tab, and memory that must flow continuously flows through git, not through claude.ai's routes. The repository's later research quotes the same clause from the Consumer Terms effective 8 October 2025, with the clause against sharing a login or making an account available to anyone else, and reads routines, cloud sessions and desktop scheduled tasks as Anthropic's features used as offered ([docs/history/crowdsourcing/research.md](../../docs/history/crowdsourcing/research.md)).

The other constraints follow the same logic: shared state has to be a file or an issue, every account signs in itself and no challenged request is re-sent by code, the extension's trust boundaries and the store's fixed permissions stay, no new runtime dependency is added, and checkpoints stay deterministic so a committed handoff diffs cleanly.

Two things the thread had asked for are, in the spec's words, simply not in cswap's remit and should not be added: a webhook receiver or edge proxy, which belongs to GitHub's and Linear's machinery, and a scheduler of browser sessions, which runs against the terms and against the extension's own decision that nothing retries on its own and a person is present at three points.

## The two routes and the choice

The [SDLC Build Plan](https://claude.ai/artifact/BjZikNkPVNU2G4KGaCxawZ), written the same day on top of the spec, sets two routes side by side and recommends the second.

Route A would have taught the extension to feed the repository: a repository writer in the bridge that reads the whole export and commits CLAUDE.md, docs/memory/ and docs/history/; a scheduler inside the extension's service worker; and per-account logic inside the extension. The plan rejects it on three grounds. Every new path lands in plumbing already twice the size of the scripts and in the store's review cycle. Per-account logic and automatic switching inside the extension are out of scope by the extension's own recorded decision. And the scheduler, the piece the architecture most wanted, is the very thing the terms forbid a browser script to do. Its verdict is to keep Claude Swap Cloud as it is, a convenience for the one-time export, and build nothing of the new system inside it.

Route B is a focused utility on top of what existed. Its one job is to turn an export into files in a repository the same way every time: a materializer of one standard-library Python module that writes the Project's instructions into CLAUDE.md between markers, each memory entry under docs/memory/ with a MEMORY.md index, the conversations under docs/history/ by date but never the large event logs, and the name, topic, repositories, model and effort into docs/project.md, dropping exported_at so an unchanged Project gives an empty diff. The unattended export would be the sanctioned prompt route, run weekly by a routine on the main account's Project to a project-export branch, with a GitHub Action running the materializer on that branch and opening a pull request that a person reads before it lands. Each account would get a thin Project of about ten lines of instructions pointing at CLAUDE.md. The rest would be GitHub's and Anthropic's own features. The plan sizes the materializer twice: about 300 lines in its opening recommendation, and 300 to 480 lines plus 300 to 500 of tests in Route B, re-sized on 9 October because the export readers return counts, not rows; the second figure is the plan's own revision (row 38).

The plan's table of industry tools makes its preference explicit, since almost every need is met by something that already scales, and it draws two choices from that: GitHub Issues before Linear, because GitHub's events reach Actions and routines with no proxy, signature check or relay; and Anthropic-run agents before self-run ones, because they act as the signed-in account, so no API key is stored anywhere.

The choice was made the next day. The build plan's Phase 0 records that on 9 October the owner chose GitHub Issues and asked for the repository side first, as a GitHub template repository built from the bottom up with no export or import in its first layer; Linear and the materializer come later. That is the decision this chapter dates Symphony from. Its consequence is that Route B was chosen and then built from the other end: not from cswap's export toward the repository, but from the repository outward, with the export left for later.

What the first layer left out is therefore precise. The choice of 9 October deferred Linear and the materializer by name, and with the materializer went the weekly project-export routine and materialize.yml that feed it; no later page reports any of them built, nor an edge proxy, nor the build plan's Phase 5 changes to cswap (a headless checkpoint mode and capturing a cloud session's id in teleport). The contradictions page checked whether any later page reports the materializer or the export loop and found none, and also found that the later plan in the Symphony handoff replaces a plan of 12 October, not this one; it therefore carries the build plan's phases as a deferred design, not as an abandoned one, until a decision record says otherwise (row 31). One reason the deferral never had to be revisited can be read from this repository. The build plan's thin Project still held ten lines of pointer instructions; the template's setup page leaves the Project's instructions, description and memory blank, with the pointer text pasted only where people will chat in the Project outside a code session ([docs/setup/claude-project.md](../../docs/setup/claude-project.md)). With nothing kept in the Project, a materializer has nothing to carry from it after the first move. The checkpoint primitive did survive into the first layer: every repository made from the template keeps a block of CLAUDE.md between cswap markers that cswap checkpoint write rewrites, and its rules ask sessions to tag durable facts as Decision: or Constraint: so that the checkpoint keeps them word for word ([CLAUDE.md](../../CLAUDE.md), [.claude/rules/writing.md](../../.claude/rules/writing.md)).

The first layer moved quickly. [The Dollar-per-Feature Ladder](https://claude.ai/artifact/9Ymg61SPUZTqaNBCbzGHMx) of 9 October describes the product, then named sdlc-template, as a template repository that makes one repository the shared plane of a multi-account project, with the claude.ai Project on each account a bare link whose own fields stay blank, and reports three pull requests built and merged that day: the push guard and @claude on a subscription token rather than an API key (#3), the claim protocol enforced inside the required check with an opt-in scheduled worker (#5), and the plan ladder with the board's fallback cut from hourly to six-hourly (#7). The ladder's cost arithmetic and its prices are chapter 29's subject, and two of its figures are not to be quoted as current: its minute counts assume every scheduled run fires, which the handoff later measured to be far from true (row 3), and its GitHub prices were found four days later only in documentation of April 2020 (row 6). The product was renamed Symphony afterwards; the ladder's repository name and its worker switch are stale (row 36).

## The two Claude surfaces

The canonical page on the surfaces is [Claude Chat vs. Claude Code: Architectural Analysis of Interface-Exclusive Capabilities](https://claude.ai/artifact/SnuzFDHCC9kM3GgYziMApb) of 3 October. Its opening correction still matters to a reader of the rest of Part S: the two surfaces run the same models and differ in the harness around the model, the tools it is given and where the execution and trust boundary sits. Chat is a hosted conversation with a browser renderer and a disposable server-side sandbox. Claude Code is one agent loop shipped through the terminal, the IDE extensions, the desktop app's Code tab, cloud sessions at claude.ai/code, the GitHub Action and the Agent SDK, with read, write and execute access to a real environment, a permission system and configuration kept as code.

Fewer capabilities are exclusive than people assume. Vision, remote MCP servers, web search and fetch, memory across conversations and publishing a page to a link are on both. The analysis dates the last of these: Claude Code gained an Artifact tool in version 2.1.183, so published pages are shared, while Chat keeps the in-conversation preview runtime, the inline edit of a rendered artifact and the consumer gallery. What is exclusive to Chat is the preview panel that renders what the model writes while the conversation continues, Projects as server-side grounding (instructions, uploaded knowledge, and a retrieval mode once the knowledge passes the context window), and AI-powered artifacts that call the Anthropic API billed to whoever views them. What is exclusive to Claude Code is read, write and execute on the user's own machine, the write, run, read error and fix loop against the real toolchain, headless and programmatic use (claude -p, the SDK, the Action, routines) and orchestration of many sessions (subagents, worktrees, agent teams, cross-session messaging).

The analysis explains each boundary by where state lives and who can reach it. Chat's container has no working tree, no secrets, no internal network and a reset between tasks: in its words, a calculator, not a workstation. Claude Code has no preview pane, no server-side knowledge store and no hosted runtime for other people. Its worked scenarios each come out the same way: Chat wins when the work is bounded, visual, document-shaped or must reach people without a repository; Claude Code wins when the work is on disk, needs secrets or a network one controls, must run long, or must be enforced rather than requested. On security it notes that Claude Code also sends code to the cloud as context, and that on a consumer plan the training setting, not the surface, decides what may be done with the data.

The procedure that combines them is Phase 3.3 of the analysis. After one-time setup (CLAUDE.md, permissions, hooks and .mcp.json committed; a Chat Project with the specification material; the training setting checked), the work moves through five steps across the two surfaces. Design happens in Chat, where a mockup becomes a specification document and a prototype in the panel, and the specification is then committed to the repository. Planning happens in Claude Code in plan mode, read-only until the plan is approved. Building happens in Claude Code in an isolated worktree, tests first, with hooks enforcing formatting, linting and a refusal to finish while the checks fail. Verification and shipping happen on the pull request, with @claude reviewing from the Action and routines for recurring checks after the merge. Communication returns to Chat for release notes, a demonstration page and triage of screenshots, which re-enter at design. The handoffs go through things both sides can read: a committed specification, a pull request, a published page. The procedure ends with what each surface must never be asked to do: paste a whole repository into Chat, run with permissions skipped on a workstation, let Claude Code own the specification, or let Chat own the merge.

Two parts of the analysis need a date beside them. Its claim that a Code Project is a work organizer of task threads and not a knowledge base was overtaken five days later by the primitives spec, which read a Code Project's instructions, 19 memory entries, files and settings from the live site; the contradictions page carries the spec's inventory and keeps only the analysis' narrower point that a Code Project has no server-side retrieval index (row 14). And its version numbers (2.1.183 for artifacts, 2.1.224 for cross-session messaging, 2.1.51 for Remote Control) are quoted from Anthropic's pages as published on 3 October, with the analysis' own warning that Claude Code ships several times a week; the record also notes that the analysis and the grid playbook of the same day carry these gates as one claim, not two confirmations (row 43).

Symphony took the analysis' division of labour and changed one part of it. The analysis advises keeping the specification in a Chat Project, where non-engineers and the phone can reach it, and committing only the distilled constraints to CLAUDE.md. Symphony keeps everything a session needs in the repository and leaves every Project blank, because a Project's fields belong to one account and a merged pull request changes what every account reads at once. The analysis' own reasoning supports the change once there is more than one account: its table already gives the repository the advantages of version control and pull request review, and gives the Chat Project only reach to people without a repository. For the people who do not work in code, the later design reaches them through published pages rather than shared Project knowledge, which is what this book is.

## The accounts question, as the record gives it

The record states the accounts question several times and the owner has decided it; this chapter reports each statement and leaves the decision where the owner set it. The plan of 8 October says several accounts are not forbidden, notes the reported bans of February 2026, and makes each account sign in itself. The build plan names it as a terms question the owner raised and had not settled, and says the plan works the same with one account per person. The grid playbook of 3 October calls rotating accounts or pooling tokens to widen the usage window the behaviour the terms prohibit, and the Symphony handoff of 13 October records the owner's decision that the owner's own several accounts may be coordinated from one orchestrator of the owner's, each worker on one account's token, knowing the terms question; the contradictions page carries the pool as that recorded decision beside the playbook's reading (row 13). The handoff adds what the decision does not extend to: no contributor's credential, no pool of contributors' subscriptions, and workers in Actions only where the owner is the one writer ([Symphony Handoff](https://claude.ai/artifact/XQj71up9dbJhwSStCVUe9T)). The repository's crowdsourcing research turns the contributor side into rules (no contributor credential anywhere, no pool, no sign-in with Claude, no account driven by other people) and notes that a Usage Policy effective 12 November 2026 adds services that route requests through consumer subscriptions ([docs/history/crowdsourcing/research.md](../../docs/history/crowdsourcing/research.md), [docs/memory/crowd-mode.md](../../docs/memory/crowd-mode.md)). Chapter 31 holds the grid side of the same question.

## Claude Swap Cloud on the Chrome Web Store

The last canonical page of the cluster, [Store upload and repo move, step by step](https://claude.ai/artifact/Fpy3FhkGSwF4jkDUYRWXmu) of 8 October, is the runbook that took the extension to the store. It belongs here because it is the one piece of the cswap line that went on as its own product while the shared-plane work moved to the template.

The runbook opens with Step 1 already done: the two repositories, the extension's and its public privacy companion, were moved into the OpenSpineConsortium organization on 6 October and the main one renamed claude-swap-cloud on 7 October, with the steps kept as the record. It was refreshed on 8 October for the build numbered 773 of release line 0.2.0, a package of 124,457 bytes that carries its import and export scripts itself, so its answer to the store's remote-code question is No.

Every step after that is the owner's, by hand, because each needs the owner's own sign-in. Before submitting, cswap must be on PyPI, since the reviewer's test instructions install it from there: a pending trusted publisher on pypi.org for the publish workflow, then the tag v0.27.0b1 pushed from main. The item is born from the zip in the developer dashboard under the publisher that already publishes Beethoven, and its 32-letter id, fixed from the first saved draft, is needed twice later. The listing takes twelve fields, its description saying among other things that the extension stops and says why when the site pushes back, never retries on its own, and is an independent tool not made or endorsed by Anthropic; the privacy tab takes the single purpose, one justification per permission and four ticked data types. Distribution starts as Unlisted. Review of a first item with these permissions takes several days.

After the item exists, the runbook moves releases to CI. On each computer that installs the store copy, the native bridge must be registered once with the store's id, since Chrome lets a native host talk only to the extension ids its registration names. The release workflow needs five repository secrets, the publisher id, the item id and an OAuth client's id, secret and refresh token, made once through the Google Cloud console and Google's OAuth Playground; the consent screen must be published to production before the token is made, or the token stops working after seven days. A repository variable, CWS_ON_PUSH, then turns the store on: upload replaces the item's draft on every merge that changes the extension, publish also submits it for review, and off or unset leaves only the GitHub release, which is made on every such merge whatever the variable says. The version is the manifest's 0.2.0 with the commit count as a fourth number, so each build is above the last.

Three of the runbook's statements are not settled by the record. It says Windows runner minutes count double where the ladder says about 1.7 times, and neither cites a price table (row 4); the book quotes neither as current. It checks the privacy statement as version 15 on main, while the primitives spec, at a later pull request the same day, cites version 16, which the record carries (row 7). And it treats the organization as Free where the handoff later infers Enterprise Cloud from its internal repositories, an inference not checked against the billing page (row 5). Whether cswap reached PyPI as v0.27.0b1 and whether the extension was submitted, the record cannot tell: both pages of 8 October agree it was not yet published, and no later page in the cluster records the publish or the submission (row 30).

The route outlived the extension's own copy of it. [Beethoven on the Chrome Web Store](https://claude.ai/artifact/XxNp8Uy3FfWDSwMExpvLMT) of 13 October sets up the same five secrets and the same CWS_ON_PUSH switch for Beethoven through the organization's shared release kit, reusing the same Google client and refresh token where one was already made, and the handoff of the same day says claude-swap-cloud still runs its own copy of the kit and only plans its move to the shared one (row 29). The Beethoven note's one to three days of review is for an update to a listed item with no permission changed, not a first item, so it does not contradict the runbook's several days (row 28). Chapter 32 holds the Beethoven release itself.

## What a planner takes from this line

The line of 3 to 9 October makes four choices that a later design should not reopen without a reason the record lacks: the repository as the shared plane with blank Projects; nothing scripting claude.ai, so every continuous flow goes through git and GitHub; GitHub's native objects before any added service, which is why Issues won over Linear and the coordinator became code in the board's run; and Anthropic-run agents on a subscription before anything that needs a stored API key. The deferred pieces, the materializer, the weekly export routine and Linear, remain a design that can be picked up behind the same repository files, which was the build plan's stated reason for putting the files first.

## What we know

No Claude surface of October 2026 shares a Project, an agent or a memory across accounts, and the plan of 8 October quotes the documentation for it; that is why the repository is the plane. cswap's export reads a Claude Code project's fields, memory included (19 entries read live on 8 October), but its write of memory was never confirmed, an import always makes a new project, an export is not deterministic as written, and no export can run unattended within the terms except the lossy prompt route. Route B was recommended on 8 October, and on 9 October the owner chose GitHub Issues and a template repository built from the repository side first, with no export or import in its first layer; the materializer and Linear were deferred, and no later page reports them built. Chat and Claude Code share vision, MCP, web access, memory and publishing; Chat alone has the preview runtime and server-side Project grounding, Claude Code alone the real machine, the toolchain loop, headless use and multi-session orchestration, and the analysis' five-step procedure divides the work between them. The extension's store release was written as a runbook in which every dashboard, PyPI and Google step is the owner's and later releases go through CI behind five secrets and one switch.

## What we do not know

Whether cswap v0.27.0b1 reached PyPI and whether Claude Swap Cloud was submitted to or published on the store is not recorded by any page after 8 October. Whether the Project memory write was ever exercised live is not recorded either; the last word is the build plan's, that it never was. The current text of Anthropic's Consumer Terms on automated access and on account sharing was not read for this chapter, which was written without network access; the latest reads in the record are the crowdsourcing research of 10 October and the handoff's of 13 October, and the Usage Policy change dated 12 November 2026 is ahead of this writing. Which Claude Code features have shipped since the analysis' version numbers of 3 October was not checked. The Windows minute multiplier, the extension's exact line count at that commit, the organization's GitHub plan and whether the deferred build-plan phases are abandoned or only waiting are all open in the record.

## What would change our mind

A Claude product that shares a Project or its memory across accounts, under the plans the owner uses, would remove the reason the Projects stay blank and reopen the materializer's job. A change in Anthropic's terms that permits scripted access to claude.ai, or a documented API for Project export, would reopen the unattended export that Route A could not have. A live, confirmed write of Project memory would make the reverse flow, repository to Project, possible, which the build plan ruled out only because the write was unproven. A record that Linear or the materializer was built, or explicitly dropped, would settle the deferred phases. And a dated read of GitHub's billing page, or a recount of the claude-swap source at pull request #45, would settle the runbook's and spec's open figures.
