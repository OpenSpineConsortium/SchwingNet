# 31 Claude workers on the grid and the lab's machines

Label: symphony-beethoven-separable. This chapter belongs to Part S, which may one day be published apart from the rest of the book: it holds nothing of SchwingNet's method, data or numbers, names people by role, and names each machine only by its role (the login node, a compute node, the gate, the workstation).

This chapter settles, for whoever plans work that a Claude Code worker will do, how such a worker is run on the lab's Slurm grid and in GitHub Actions, and how the lab's own workstation is reached. It answers five questions in turn: how a grid worker is started, watched, stopped and updated, and by whom; how several workers share one grid account and one subscription, and what of that is not yet measured; how a session on the grid gets a GitHub login without the token reaching Claude; under what conditions a consumer subscription on a shared cluster stays within the terms, and how the owner's later decisions about the owner's own accounts sit beside those conditions; and how the workstation is reached and what would lock the owner out. The cluster's five canonical artifacts, all dated between 27 September and 21 October, carry the argument.

## Three ways a Claude worker runs, and one way an Actions job reaches the grid

The record describes three places a Claude Code worker runs and one further path that carries GitHub Actions jobs, with no Claude in them, onto the grid. Keeping the four apart prevents reading a fact about one as a fact about another.

The first is the grid worker. The [Grid and cloud Claude workers: review](https://claude.ai/artifact/L7nL3xkYzoitmWf4ab8ARN) describes it as a Slurm job on a compute node that runs Claude Code under Remote Control on one of the Claude accounts signed in on the grid, started through hpcworker, the lab's shared framework. A person drives it from claude.ai or the Claude mobile app, and a claude.ai project reaches it only through the project's own Work locally (below).

The second is the cloud worker. The same review describes workers.yml starting each registered worker in GitHub Actions on a token from the token pool, with the control panel's Runs tab cancelling a run through GitHub's API. Both kinds take work the same way: a worker claims issue N by pushing the branch `claude/N` first, and the board releases a claim whose branch has had no push for 24 hours, the rule [Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho) and [chapter 29](29-symphony-the-protocol-its-guarantees-its-comparison-and-its-cost.md) set out.

The third is the person's own session, local or in the cloud, which the [Claude Chat vs. Claude Code analysis](https://claude.ai/artifact/SnuzFDHCC9kM3GgYziMApb) separates from the others: claude.ai/code is one front-end of the same harness, its Projects are a work organizer distinct from Chat Projects, and a cloud session can drive a session on the person's own machine through Remote Control. A claude.ai Project thread, the [spine-program student onboarding](../../artifacts/spine-program-student-onboarding/) warns, has the clone and GitHub and nothing else: no grid, no ssh, no sbatch.

The fourth path is not a Claude worker at all. The repository's note [docs/research/wsu-grid-and-github-actions.md](../../docs/research/wsu-grid-and-github-actions.md) and its setup page [docs/setup/grid.md](../../docs/setup/grid.md) record that a GitHub Actions job can run on a compute node through GitHub's own self-hosted runner, served by hpcworker as a chain of Slurm jobs, registered for one GitHub job at a time with a credential minted on the grid and discarded after the job. The connection points from the grid out. The setup page is explicit that no Claude workflow runs there: claude.yml, workers.yml and coordinator.yml stay on GitHub's machines and the Claude token never reaches the grid. The memory fact [docs/memory/the-grid-runs-a-job-through-beethoven.md](../../docs/memory/the-grid-runs-a-job-through-beethoven.md) carries the same rule. A planner who wants Claude on the grid uses the first path; a planner who wants a repository's check run on the grid's hardware uses the fourth.

## Starting, watching, stopping and updating a grid worker

### The chain from a press to a claimed task

The review of 21 October is the canonical account. A press in the control panel's Grid tab runs the workflow grid-accounts.yml, which holds the gate's ssh key in a GitHub environment and speaks one fixed word, of the form `accounts start SLOT NAME`. On the grid the key can run only the gate script, which accepts a short list of words and nothing else. hpcworker turns the word into one sbatch: a job on a compute node that runs Claude Code under Remote Control on the account slot the word named, keeps the worker on that account even when the default account changes, and gives the worker a name of its own for its claims. Before its time runs out the job queues its own successor. The run then lists the workers again and writes the answer to the branch `grid`, which the panel reads. Stop is the word `accounts stop NAME`, which writes a stop file and then cancels the job.

The design choices behind this chain are older than the review and are recorded in the research note, for the first gate the lab built, the one that starts the runner chain of the fourth path. GitHub's runners cannot sign in to the grid, and the owner's rule is that no credential of the grid's sits at GitHub with any power beyond the narrowest. So that gate's key, the one GitHub holds, is restricted on the grid to a forced command: a client says one word, the line on the grid (not the client) names everything else, a second call for the same repository within a minute is refused, and the gate writes one line per call to its own log without the key. The note records that an adversarial review run against a real ssh server found one blocker and seven should-fix faults before the pull requests were marked ready, each fixed, and that the gate's own tests count 98 checks with 22 of them shown to bite by undoing them in a copy. Those are the note's figures for its own test suite, not outcomes on the grid. The note also records that the gate was built only after the owner's own test showed the sign-in it needs would work, and that on 18 October setting the gate up was made a single press in the Beethoven extension for the lab lead, since only a shell inside the grid account can write the key's line; the extension's change was to merge only on the owner's word.

The gate in the research note and the gate in the review are not the same object. The note's gate, planned on 16 October and built on 17 October, takes the three words start, status and stop for one repository's runner chain. The review's gate, at framework 22, takes the accounts words that start and stop Claude workers, over the grid-accounts key. The [Moving Beethoven for VS Code onto hpcworker](https://claude.ai/artifact/ApBd6TpHYnsWVKvP1NjvyX) plan of 7 October describes a third, the browser-key gate of framework 17. [The grid contradictions](../../artifacts/_synthesis/contradictions/grid-workstation-and-claude-worker-operations.md) (row 11) refute the reading that the browser-key gate, the accounts words and the SchwingNet gate words disagree: they are different versions and parts, each correct about its own. That the runner-chain gate is a fourth is this chapter's reading of the note.

### Who may press, and what waits for the owner

The review's state was read at 12:03 UTC on 21 October: the grid answered with framework 22, listed one worker online, and one account, the owner's university Max account, signed in. The Start and Stop buttons for named workers were live in the panel's Grid tab, which the review addresses to the owner. Nothing had started a second worker, because that spends allocation, and the review says it waits on the owner's word and a number. The [Several grid workers, one per project](https://claude.ai/artifact/UjuFBMxLEL8CnifRofU3Vv) plan proposes that once a project's pairing is shown in the Grid tab, a session could start or stop that project's worker through the gate without the owner; that is its design, not yet built. So the division the record gives is: the owner presses Start and Stop in the panel today, a session may do so once the plan's pairing is built, a lab lead runs the one-time setup and the pulls that update the grid side (below), a person types any Claude sign-in at a terminal (below), and the owner alone decides when allocation is spent on more workers.

### Updating

Changes to the grid side raise hpcworker's framework version and reach the grid through hpcworker's watcher or through one pull from the lab lead's own clone, the review says. The version has moved fast, and only the latest reading stands. The [Beethoven build roadmap](https://claude.ai/artifact/StTvVVwZBJRq7PELUmLSbG) read framework 11 on 3 October, and the plan of 7 October read framework 17 in the tree and said the live version was not established, each now a record, not a final value; the review read framework 22 live on 21 October, and the several-workers plan of the same day says 22 to 23. The contradictions page (row 18) carries framework 22 as of 21 October and the earlier readings as history. Whether a later version has been published since is a question the plan says phase 2 still owes, and nothing in the record answers it. The several-workers plan adds a workspace Update press, which would pull one worker's workspace to its repository's main by fast-forward only, the gate's own rule, and ask first if the worker is busy; it is planned, not built.

### Watching

Watching is the review's weakest area. The grid's state is known only when someone presses List. The review proposes a scheduled list every 15 minutes, and the contradictions page (row 15) confirms that this rests on an assumption the Symphony record measured as false: the [Symphony Handoff](https://claude.ai/artifact/XQj71up9dbJhwSStCVUe9T) of 13 October counted a ten-minute schedule running 8 times in about 300 slots, with gaps of 3.4 to 9 hours. A scheduled list is therefore at best a fallback whose stale threshold must allow for runs hours late, not a heartbeat.

### What the lab's own etiquette adds

Two older pages bind every grid worker whatever starts it. [The Lab Recipe](../../artifacts/the-lab-recipe-1t2gvp/) of 27 September restricts the login node to a handful of commands, after an incident of 21 September in which dozens of smoke tests ran on a node shared by about 95 users, and it sets the rule "submit, estimate, checkpoint, stop": an agent that submits returns the job ids, an estimate and the files to collect, and the turn ends, because on 24 September polling agents burned a session limit four times in one day while the grid did the work. The roadmap quotes hpcworker's related rule, nothing on the login node beyond one sbatch, squeue or scancel per action, which is why its outer orchestrator is planned as a chained Slurm job rather than a resident service. Whether git itself works on the login node is a disagreement the record has not settled: the recipe lists it among the permitted commands, the GitHub guide says it has not been tested there, and the contradictions page (row 5) calls it cannot-tell.

## The review's comparison and its ten fixes

The review sets each part of the system beside the tool the industry would usually use: GitHub's Actions Runner Controller, plain Slurm, Kubernetes operators, hosted coding agents and durable workflow engines such as Temporal. It is a comparison of documented designs, not of runs. Its verdicts are on par for cancel, idempotency (a start by a name already running submits nothing, from hpcworker's own check), coordination by claims, and continuation, mostly; good on credential scope but behind on credential lifetime, since the gate's key never expires; and behind on launching, request intake, tracking, observability and errors. Where it judges the design better than the usual tools is in what it does without: no server of its own, no open port on the grid, no Claude credential at GitHub, and a record of who did what that is ordinary git history.

The ten fixes, ranked by help against cost, are these.

| Rank | Weak point | Fix the review proposes |
| --- | --- | --- |
| 1 | A burst of presses loses one, since a concurrency group keeps one running and one waiting run | The panel writes each request as a file on the branch `grid`; each run carries out every waiting request, oldest first |
| 2 | Starting N workers takes about N minutes behind the gate's 60-second floor | One word that starts a count of workers in one call |
| 3 | A grid worker busy for a day without pushing loses its claim to the 24-hour release | Push the claim branch on a timer and on the signal the job receives before its time runs out |
| 4 | State is known only when someone asks | A scheduled list and a stale flag in the panel |
| 5 | A failed press shows a vague sentence | Show the shell's error with the press and split the long setup into short steps |
| 6 | A worker waits in one partition's queue while another is free | Submit to two partitions and cancel the loser (designed, never built) |
| 7 | Several workers on one account share its five-hour window | Show how many workers each account carries and warn before crowding one |
| 8 | The gate's key never expires | An ssh certificate with a lifetime, or rotation on a schedule |
| 9 | Grid and cloud workers live in two tabs | One Workers view for both |
| 10 | A cloud worker stopped at its time limit keeps only what it pushed | The same timed push as rank 3 |

Rank 1 rests on GitHub's documented rule for the default concurrency group, which the handoff's figure for a queued group does not contradict (row 14 of the contradictions page). Rank 10 rests on a 90-minute limit on a cloud worker that the contradictions page (row 35) finds in both the review and the handoff with no source in either; it stays unverified until workers.yml's own limit is read. The review's line that Actions admits at most 10 Claude runs a day per repository is also unsettled: the [Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/) of 15 October lists that cap as not built yet, and the contradictions page (row 13) calls its status cannot-tell. A planner should check each premise before building on the ranking.

## Continuation and its two disputed figures

A grid worker survives the end of its Slurm job by queuing a successor that resumes the same Remote Control session, with the workspace kept on shared disk. How long that resume may reach back is the chapter's clearest contradiction. The review says up to seven days and gives no source. The plan of 7 October read hpcworker's code at framework 17 and found the window set to 14,400 seconds, four hours, chosen on purpose after Anthropic's statement that a session can be resumed for about four hours, and it calls the seven days in hpcworker's own CLAUDE.md stale text. The contradictions page (row 0) confirms the disagreement and carries the four hours, marked as read at framework 17, with a re-read of framework 22's setting as what would confirm it. The repository's note [docs/research/beethoven-worker-opening.md](../../docs/research/beethoven-worker-opening.md) also works with the four-hour window. The review's seven days is quoted here as a record, not a final value, and not as a value to plan on.

The second disputed figure is not a number but a claim: that the successor actually continues the same session. The review states it as fact in its account of how the system works and then lists it as not measured; the several-workers plan assumes it and asks whether a project's pairing survives it; the plan of 7 October cites the code path and says it is not measured. The contradictions page (row 38) confirms the claim is unsourced. A planner should treat a worker's session as lasting one job, with resume a hope inside four hours, and should push work to git before the job ends, which is exactly ranks 3 and 10 above. In the cloud nothing survives a run except what it pushed.

## Several workers, one per project

### What exists and what the plan adds

The owner asked on 21 October to switch between projects using several Claude workers on the grid, because a laptop cannot keep several Claude desktops signed in at once. The several-workers plan answers that most of the grid side exists: since framework 22 the grid runs several named workers at once, each its own Slurm job, its own Remote Control link and its own status files. What is missing is in Beethoven, which at version 23 knew one worker name and one project address.

The constraint behind the design is the one [docs/memory/beethoven-worker-and-claude-projects.md](../../docs/memory/beethoven-worker-and-claude-projects.md) records from the documentation read on 16 October: a claude.ai project reaches a worker only when the project asks for it through Work locally and someone allows the folder on the card; a worker started on its own never appears inside a project. So each project must be paired with its own worker once, by hand. The plan's design follows: a projects list in Beethoven's settings, each row a short name, a project address, a worker name and an account slot; a switcher of project chips on the home screen, each project keeping its own tab; a start on press that issues the same one-sbatch start and never a second worker of the same name; the workspace Update press; and the same list in the control panel's Grid tab, stored once on the grid by a `project` field per worker in accounts.json, so that Beethoven and the panel read one record. The build order is four pull requests: the field and its listing in hpcworker, then Beethoven's list and switcher (a store release), then the panel's column, then the Update press on both sides.

### Sharing one account and one subscription

Whether two workers on one Claude account can each stay registered as a separate environment is the plan's first open question. Framework 22 keeps each worker to an account of its own, and the environment id is stable per machine id, so the plan's working answer is that the number of projects running at once equals the number of Claude accounts signed in on the grid: one on 21 October, two once a second account is signed in through the Grid tab. The plan of 7 October found a related hazard in the older VS Code edition, whose Remote Control host holds a lease precisely because two hosts on one login "would fight over it", while hpcworker takes no such lease; what happens when both run is not measured.

Whether workers on one account stall together is partly sourced. The taxonomy spec states, as verified in its research note 10, that Actions workers on one plan share its five-hour window and weekly limit, and it records that the project's own account reached its weekly limit on 15 October with several threads running. The playbook says the same of any subscription: limits apply to the account, not the node, so eight sessions on eight nodes draw one budget eight times faster. The contradictions page (row 39) accepts the shared window as sourced and marks the review's further claim, that grid workers on one account stall together, as the review's own inference. Fix 7 is the review's answer.

### What is not yet measured

The review and the plan list the same gaps, and nothing later in the record closes them: two or more grid workers running at once on real nodes; how long a start takes from press to online, and how long a job waits in each partition's queue; whether a successor's resume keeps a long session whole across several job ends; whether a project's Work locally pairing survives that resume; and the cause of a failed Beethoven Connect press, parked until the next failure's debug log. The contradictions page (row 26) records that nothing after 21 October shows the review's state changed. Whether the browser-key gate's cap of three worker names per seven days, read at framework 17, also binds the accounts start path at framework 22 is unsettled (row 12): the review mentions only the 60-second floor, and leaving a cap out is not saying it is gone.

## A GitHub login for a session on the grid

A student's Beethoven session on the grid reaches GitHub from the compute node, but without a login it can neither read a private repository nor push. [Connect the grid to GitHub](../../artifacts/connect-the-grid-to-github/) of 14 October is the canonical answer, and it supersedes the setup in the onboarding page of the day before, which the contradictions page (row 3) confirms. The onboarding asked for a read-only fine-grained token on one repository, kept in a file, as the probe for the task that would measure whether the grid can reach GitHub at all. The guide replaces it once that half was answered: the session had already cloned two public repositories from the compute node. Its setup is one classic token with the repository scope, from the student's own GitHub account, which covers the lab's private repository and the student's own repositories at once, with a suggested 90-day expiry; a fine-grained token is the fallback where the organization refuses classic ones, with contents, issues and pull requests at read and write, and one token per resource owner.

The guide's rules for where the token may go are the part a planner must keep. The student types the token into an editor, into a credentials file in a private folder that only the student can read, and git's credential helper reads it from there. It never goes on a command line, into a job script, into a chat with Claude, or into any file of a repository. Claude on the grid must not see it, and the guide says the session was right to refuse to handle it. The Claude GitHub App links a session may offer are for sessions on claude.ai and are skipped for git on the grid. Commits carry GitHub's no-reply address, so no personal e-mail enters a repository. And the commands run in the Beethoven session's terminal on a compute node, not on the login node.

The guarantee these rules give is narrower than it sounds, and the planner should know its edge. Claude in the session pushes with git, which uses the token through the helper, so the token's power is in Claude's hands while its value is kept out of Claude's context, out of logs and out of the repository. The file's mode protects it from other accounts, not from processes of the same account, so keeping the value away from Claude is a rule Claude and the student follow, not a wall. This is the chapter's reading, not a finding of the guide. hpcworker itself had no channel for such tokens at framework 17: the plan of 7 October found no deliberate way to hand a worker a token, noted that whatever the submitting shell exports still reaches Claude Code in the job (not measured on the grid), recommended that the student sign in to each tool on a compute node with no Beethoven code holding a token, and said that if tokens were kept as a product feature they must never go into a command line, a log, a job file or the scheduler's export list.

The one Claude credential leak the record names belongs to a different component. The plan of 7 October found, by reading code it did not run, a path in Beethoven for VS Code 5.0.0's own relay that could return a student's Claude credential file to the laptop, and its banner says the fix was being made separately when the owner deferred the move to hpcworker that evening. The contradictions page (row 16) scopes the review's claim that no Claude credential leaves the grid to hpcworker and the gate, and records the VS Code path as a separate defect whose fix the record does not show.

## A consumer subscription on a shared cluster

### The playbook's four conditions

[Claude Code on a Slurm + Apptainer Cluster with a Consumer Subscription](https://claude.ai/artifact/7dBJwcSiDjUFrAKSJfFhEF) of 3 October is a site-agnostic design, checked against Anthropic's documentation that day. It holds that running Claude Code on a shared cluster under a consumer subscription is permitted while four things stay true: one person's subscription authenticates only that person's sessions; the Claude Code binary runs unmodified; no one else's work is routed through the account; and nothing is done to multiply or evade the plan's usage limits. It adds a data policy: on Free, Pro and Max plans an account setting decides whether coding sessions are used for training, and regulated data, such as protected health information or export-controlled material, stays off a consumer plan, going instead through an API key, a Team or Enterprise seat or a cloud provider. It builds each condition into the deployment: an image with no credentials, each user minting and storing their own token in a file only they can read; the native binary pinned at build time with its updater off; no proxy or shared service between the user and Anthropic; and one account per user, no rotation and no pooled tokens, with batch jobs sized to the plan's windows.

Its credential model uses two credentials for two jobs. A one-year token from `claude setup-token`, minted on the laptop, authenticates batch and non-interactive runs, because it needs no refresh and a headless run after an expired login has been reported not to refresh (an issue it cites). A full sign-in done once on the cluster with the manual-code flow authenticates interactive and Remote Control sessions, since the token cannot open Remote Control. The token belongs in one file and nowhere else. On rate limits the playbook advises one job of about four hours per five-hour window, a cheaper model by default, capped turns, a limit treated as a requeue rather than a failure, and, in its words, keeping it one account: rotating accounts or pooling several users' tokens to widen the window is behaviour it reads the terms as prohibiting, and a workload that needs more than one subscription's window is a workload for an API key. The plan says phase 2 still owes a check of these conditions against Anthropic's current terms and the setup-token documentation; this chapter could not make that check and grades them as the playbook reports them.

### Beethoven's narrower rule

The roadmap of the same day sets a stricter rule for Beethoven as a product: Beethoven never reads, stores or relays a Claude credential, and the inner loop runs on the student's own `claude auth login` where it already sits. It names the playbook's choice, a setup token injected into jobs, and refuses it for Beethoven, and it makes its first phase a one-job measurement of whether a headless run on the student's own login works from a batch job. The contradictions page (row 1) confirms that the two pages prescribe opposite credentials for the same kind of run and resolves it by scope: the roadmap's rule for Beethoven and hpcworker, the playbook's setup token as a generic option outside Beethoven. The review's grid workers fit the roadmap: they run on accounts signed in on the grid, and no Claude credential leaves it. The plan of 7 October found that at framework 17 hpcworker refused to start any Claude sign-in for a call arriving through the gate, so a sign-in was typed by a person at a plain terminal; framework 22's accounts words include a login call and the panel offers Sign in another, and the record does not say how that rule reads now.

### What the owner later decided for the owner's own accounts

The owner's decisions about the owner's own several Claude accounts came after the playbook and differ from its credential model. They are given here with their dates, the later as current, and neither is judged.

The Symphony Handoff of 13 October records, as a decision the owner had already made, that the owner's own several Claude accounts may be coordinated from one orchestrator of the owner's, each worker on one account's token, knowing the terms question; the decision is also among the repository's durable decisions, which add that it does not change the rule for contributors, who each work under their own account while the project never holds anyone's credential. On 16 October the token wizard ([docs/memory/the-token-wizard.md](../../docs/memory/the-token-wizard.md)) began storing each account's subscription token from `claude setup-token` as a GitHub Actions secret, the main token for the Claude workflows and a pool of numbered slots, without the token being shown or written anywhere. On 17 October the token pool ([docs/memory/the-token-pool.md](../../docs/memory/the-token-pool.md), with its sources in [docs/research/claude-token-pool.md](../../docs/research/claude-token-pool.md)) added usage readings per slot and an auto mode that picks the slot with the least used five-hour window, then seven-day window, passing over a slot held at 90 percent until its reset. On 18 October the owner widened the pool to 32 slots, an organization's holding every member's tokens. The cloud workers of the review run on that pool. The grid is a different arrangement: framework 22 runs each worker on a Claude account signed in on the grid itself, not on a pooled token, and holds several such account slots, with a second account to be signed in through the Grid tab.

The record itself flags the open edge. The contradictions page (row 2) confirms that the playbook and the handoff disagree about one person rotating their own accounts, and that the handoff acknowledges the question without settling it. The handoff sets a step for it: re-read Anthropic's Usage Policy before 12 November 2026, when a version takes effect that names services routing requests through consumer subscriptions, and record the reading or switch the pool off. The owner's decision is the current rule for the owner's own accounts, and the playbook's reading stays on record beside it with its date; the dated re-reading, or the pool switched off, is the step the handoff itself sets.

## Reaching the workstation

The [Secure Hybrid RDP Access: Spec and Setup Runbook](../../artifacts/secure-hybrid-rdp-access-spec-and-setup-runbook-exbt1w/) of 27 September is the canonical and only page on the owner's workstation. This chapter keeps it to what it requires and leaves out every setting that would help someone reach the machine.

The design is five rules. No port is forwarded on the home router; the only way in is Tailscale. The workstation's firewall accepts Remote Desktop only from the tailnet. The tailnet's policy lets only the owner's own devices reach the workstation. Duo's second factor is skipped for one device alone, the owner's personal laptop, identified by its own tailnet address and nothing wider; every other device gets a Duo prompt. And the owner can never be locked out: Duo prompts only on Remote Desktop logons, so the workstation's own keyboard never needs it, and bypass codes are kept on paper for remote emergencies. The runbook records what changed from an earlier spec: Remote Desktop was once to be reachable from the public internet behind Duo, and the exemption once covered a whole address range; both were narrowed.

Two of the runbook's prerequisites, it says, can stop the plan outright: the workstation needs a Windows edition that can host Remote Desktop, and Duo's free plan cannot express the one-device exemption, so a paid Duo plan is needed. The others are lighter: the account needs a password logon, since Remote Desktop with Duo will not take a PIN; and the disk's recovery key must be saved offline before Duo is installed. Duo is set to wait rather than skip the second factor when its cloud is unreachable. The setup is done only when six tests give their expected results: the trusted laptop gets in with no prompt, another tailnet device gets a prompt, the exemption is shown to be the laptop's alone, nothing connects without Tailscale, nothing connects from the open internet, and the console needs no Duo.

What would lock the owner out is what the runbook guards against: Duo prompting at the console, which the Remote-Desktop-only option prevents; a lost phone or a Duo outage with no bypass codes; a Microsoft account sign-in that Duo breaks, where the runbook prefers a local account to any workaround that lets the account skip Duo; a workstation that sleeps or does not rejoin the tailnet unattended after a reboot, which the runbook prevents by never sleeping, running Tailscale unattended and disabling key expiry on the workstation alone (the laptop keeps its expiry, so a lost laptop eventually loses access); and a tailnet policy edit under which the two machines are not signed in as the same identity, for which the runbook keeps a backup of the old policy to paste back. At the machine itself, Safe Mode skips Duo and allows it to be removed, which is why the recovery key matters.

One date in the runbook has passed. It says the workstation's processor is not supported for Windows 11, that Windows 10 extended support ends on 13 October 2026, and that Duo ends Windows 10 support the same month, and it asks the owner to choose between an unsupported upgrade and an unpatched machine reached remotely. No later artifact records which was chosen, and the contradictions page (row 24) calls the workstation's present state cannot-tell. The plan says phase 2 owes a check of those support dates and of the Tailscale and Duo product claims against the vendors' pages; this chapter could not make it.

## What we know

The grid worker's control path is built and documented in one canonical review: a press runs grid-accounts.yml, one fixed word goes over a forced-command ssh key, the gate refuses everything else and a second start within a minute, and hpcworker submits one sbatch running Claude Code under Remote Control on a named account slot. Framework 22 was live on 21 October with one worker online and one account signed in; no port is open on the grid and no Claude credential leaves it through hpcworker and the gate. The design is on par with industry practice for cancel, idempotency and credential scope and behind on intake, tracking, observability, errors and key lifetime, with ten ranked fixes. Several named workers can run at once on the grid side; tying each to a claude.ai project, by hand once per project, is planned in four pull requests and not built. A grid session's GitHub login is the student's own token in a private file, kept out of Claude's context, command lines, jobs and repositories. The playbook's conditions, Beethoven's stricter credential rule and the owner's later decisions for the owner's own accounts are each recorded with their dates. The workstation is reached only over Tailscale, with Duo on every device but one and no way for the console to lock the owner out.

## What we do not know

Whether two or more grid workers run at once on real nodes, how long a start takes, and how long jobs wait in each queue. Whether the successor job's resume keeps a session whole, whether its window is four hours at framework 22 as it was at framework 17, and whether a project's pairing survives it. Whether two workers on one account can stay registered as separate environments, and whether grid workers on one account stall together. Whether the gate's cap on worker names binds the accounts path at framework 22. Whether the cap of 10 Claude runs a day in Actions was built, and what workers.yml's real time limit is. Whether git works on the login node. Which framework version is live today. Why the Beethoven Connect press failed. Whether the VS Code relay defect was fixed. How Anthropic's Usage Policy of 12 November 2026 reads on the owner's pooled accounts. Whether the workstation was moved off Windows 10 and whether Duo still runs on it.

## What would change our mind

A re-read of framework 22's resume setting showing seven days would restore the review's figure; a measured successor resuming the same session, or failing to, would settle continuation either way. A second grid worker started on one account and staying registered would remove the one-account-per-project limit. Reading the gate's code for the accounts start path would settle the names cap. workers.yml's own timeout and run cap, read on main, would settle the 90 minutes and the 10 runs. A recorded clone or pull on the login node would settle git there. The owner's dated reading of the Usage Policy that takes effect on 12 November 2026, or the pool switched off, would settle which credential model the owner's own accounts follow from then on. A record of the workstation's Windows version and Duo status after 13 October would settle its state. A documentation check that contradicted the playbook or the runbook would replace their statements here.
