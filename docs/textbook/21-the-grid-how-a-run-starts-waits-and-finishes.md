# 21 The grid: how a run starts, waits and finishes

Label: schwingnet-internal. This chapter is for the project's members until the provisional is filed: it says how SchwingNet's runs reach the Wayne State grid and what has run there, names each place by its role and each method by what it is for, and leaves how any stage works to Part III.

This chapter treats the grid as an instrument that a planner has to read before trusting anything it returns. It settles four things: how a run starts without the owner typing a command and what each job waits for; which grid rules hold, why, and which incident each one answers; where the data lives, how a fetch is refused before it can overflow the lab volume, and which fetches only the owner can set going; and which numbers on the gate's status page are limits and which are measurements. It ends with the schedule to the talk and what drops first if time runs short. What the jobs compute is told elsewhere: what version 1 trains is [chapter 12](12-detectors-the-architecture-and-the-version-1-training-plan.md), the split check and the leak checks are [chapter 9](09-splits-leakage-and-licences.md), the witness frames and intervals are [chapter 18](18-metrics-intervals-and-witness-frames.md), latency is [chapter 20](20-readiness-for-the-operating-room.md), and what a run costs is [chapter 22](22-quotas-cost-and-the-budget-of-a-run.md).

## How a run starts

The owner's rule of 21 October 2026, 19:37 UTC, is that nobody types a command on the grid. A run starts when a Claude session in the cloud dispatches the job action of the Grid accounts workflow in symphony-template, which only an admin of that repository may start and which the owner chose on 21 October to let a session run in his place. The workflow says one fixed word, `schwingnet` with the word and at most one id, over the gate's key to the Beethoven gate on the grid's login node. The gate brings its checkout of SchwingNet to main, cloning it when missing and otherwise only fast-forwarding a clean checkout, and runs grid/gate.sh with the word. The script queues Slurm jobs on compute nodes, and the answer comes back as one file on the branch grid of symphony-template, at most 200 kB, which the session reads and reports. The grid contradictions page keeps the 200-byte limit on what goes in apart from that cap on what comes back.

Because the gate brings the checkout to main before every word, the words that answer are those of SchwingNet's main at the moment of the call. While a version 1 run lasts, a hold file names the run's job and commit, the gate skips its fast-forward, and every word but a refused one clears a hold whose job Slurm no longer holds, so the run's later steps run the code it recorded. For the same reason nobody works in the grid's checkout: running the check in a working clone on 20 October left that clone with a blank git identity, a stray branch and six stray items at its root ([docs/memory/run-the-checks-in-a-throwaway-copy.md](../../docs/memory/run-the-checks-in-a-throwaway-copy.md)), and the gate fast-forwards only a clean checkout while the version 1 run refuses a dirty one.

The gate is one key with a vocabulary that grew. It was built from 16 to 18 October as the ssh gate of a runner chain, so that a GitHub Actions job could run on a compute node through runners that hpcworker serves as Slurm jobs, and it then took three words, start, status and stop, for one repository's chain, at most once a minute; no Claude token goes to the grid by it ([docs/research/wsu-grid-and-github-actions.md](../../docs/research/wsu-grid-and-github-actions.md), [docs/setup/grid.md](../../docs/setup/grid.md), [docs/memory/the-grid-runs-a-job-through-beethoven.md](../../docs/memory/the-grid-runs-a-job-through-beethoven.md)). A key alone signed in from outside the university's VPN on 17 October; the chain's first run that day stayed queued because its stop file was written minutes after it started. Since 18 October one command in the grid's own shell does the whole setup, and Beethoven 22.0.0 put it behind a button, Connect GitHub Actions. The same key later carried hpcworker's accounts words, through which the review read framework 22's answer at 12:03 UTC on 21 October, and its job words, SchwingNet's among them. The pipeline page of that day says one press by the owner remained before any SchwingNet word could run, Connect GitHub Actions once the extension's release reached him. No record read here states the press. The census ran through the word samples on 22 October and status answered on 23 and 24 October, so the route has worked since 22 October at the latest; that is inferred from the runs.

Students reach the grid another way, for which the onboarding page is canonical. A claude.ai Project thread holds the clone and GitHub and nothing else: no grid, no ssh, no sbatch. A data task runs in two places, the thread for the plan, the job script and the draft pull request, and the student's own Beethoven session, Claude Code in a Slurm job in the student's own grid account, for the jobs; the student's login must first be on the lab volume's access list. The connect guide adds what a student's session showed on 14 October: it cloned two public repositories from a compute node, so compute nodes reach GitHub; commands belong on a compute node, not the login node, where git had not been tested; and a clone belongs in the student's own folder on the lab volume, not under hpcworker's run folders, which the guide says the framework empties, a claim the grid contradictions page finds unsourced. Of issue 19, the onboarding's first task, the compute-node half is settled by those clones; the login-node half and a private read with a token remain open. The gate words run in the owner's account and are not the students' route.

On the login node the gate runs only bash, git, hpcworker, squeue, sacct, scancel, flock, awk, sed and coreutils. The login node kills Python by name, so every byte of work moves inside a Slurm job, and every Python step runs inside a container the setup job builds on the lab volume, because the nodes' system library is older than the locked environments need. Setup writes its ready marker only when all four environments import.

## What start submits and what each job waits for

The word start submits the whole graph once, with Slurm dependencies, and is refused with exit 75 while any job the gate submitted is still queued or running. The table gives each job, when it is submitted, what it waits for, and what its script header asks for. Where the environments are already made, no setup job is submitted and nothing waits on one. The times are wall-time limits, not measurements: a job may end long before its limit, and none of these jobs has a recorded duration on the grid.

| Job | Submitted | Starts after | Wall-time limit | CPUs, memory |
| --- | --- | --- | --- | --- |
| Setup: the container and the locked environments | only when pixi.lock changed since they were made | nothing | 6 h | 8, 32 GB |
| The one outside file version 1 needs | only when it is missing | nothing | 30 min | 1, 2 GB |
| C-ArmLSpine ingest into a train and a test shard | always | setup succeeded | 4 h | 8, 24 GB |
| First catalog version | always | setup succeeded and the ingest ended, whatever its result | 12 h | 8, 24 GB |
| X-ray fetch | when the room under the quota holds the chain's stated sizes | setup succeeded | 4 days | 8, 24 GB |
| X-ray bank and ingest | with the fetch, all three or none | the fetch ended | 2 days | 8, 24 GB |
| Next catalog version | with the fetch | its bank and the first catalog ended | 12 h | 8, 24 GB |
| CT platform fetches, 25 jobs | only when the X-ray chain went in | each the one before it ended; the first, the X-ray fetch | 4 days each | 8, 24 GB |
| Sweep probe | always | nothing | 10 min | 1, 2 GB |
| Version 1 run | always | the first catalog, the ingest, setup and the outside file each succeeded | 24 h on one GPU | 8, 64 GB |

The shape answers the plan's first question. Version 1 waits only on what it reads, so it can start hours after the C-ArmLSpine ingest rather than days after the X-ray fetch, and the X-ray sets reach the next catalog version as they arrive. The next catalog waits on the first so that two builds never run at once, and the CT fetches wait behind the X-ray fetch because the owner put X-ray before CT on 21 October. A stage of the X-ray chain refused after the first cancels what was submitted, so no fetch runs without its bank and catalog behind it.

The pipeline page drew six afterok edges in this graph, against the lab recipe's rule 3, afterany and never afterok, which an 8 h limit paid for on 9 September by leaving a whole chain pending on a dependency that could never be met. The grid contradictions page confirmed the disagreement and asked for gate.sh's flags to be read. Read, the merged code uses afterok exactly where a failed input must stop the job that needs it: version 1 on each of its four inputs, and the ingest, the first catalog and the X-ray fetch on setup. It uses afterany where the child must run whatever the parent did: the first catalog after the ingest, each stage of the X-ray chain and each CT fetch after the one before, the leak join after its array, and the latency CPU arms and sweeps after the GPU job. The incident was a stranded job, and the gate's comment states the guard: job submit adds the Slurm option that ends a job whose dependency can never be met, and status reports it as cancelled before it started. So the deviation is justified by design; whether Slurm here behaves so has not been seen in a recorded run, and a chain written by hand still follows rule 3.

The word v1 runs version 1 alone, after a failure or while start's other jobs are live, and is refused only while a version 1 run is queued or running. Each input is used where it exists, waited on where a live gate job is making it, or submitted now, and the run waits afterok on each one still to come, so an input that fails again cancels the run before it holds a GPU; it never waits on the X-ray chain's catalogs. It reads the newest catalog version that holds both parts of C-ArmLSpine and every C-ArmLSpine shard on the volume and whose split check passed against the frozen test persons as they stand ([chapter 9](09-splits-leakage-and-licences.md)). The job is never requeued, since a requeued job would start a second run beside the first. It refuses a dirty checkout, repeats the split check on the chosen file before any frame is read, names in its report the GPU it was given, and reads its commit again at the end, so a run whose checkout moved under it is not used. Naming the GPU answers an old record: the [OpenSpine Board](../../artifacts/openspine-board-t3gfds/) of 11 September, superseded by [Spine Program Decisions](../../artifacts/spine-program-decisions-qqhkqz/), alone still holds that day's grid job list, in which a training fold handed a 16 GB GPU in place of an H200 died in its first forward pass, a record, not a final value.

The merged gate holds twelve words: start, status, leaks, v1, latency, `fetch <id>`, `explore <id>`, `dropzip <id>`, `unpack <id>`, samples, stop and `cancel <job>`. The pipeline page's seven (start, status, leaks, v1, latency, fetch and stop) are a record, not a final value, and the README's table lists eleven, leaving cancel to the script's header. Leaks runs the leak checks over every shard once no ingest or catalog job is live, an array 32 tasks at a time and a join. Latency submits the latency jobs for the newest run that finished training, its GPU jobs narrowed to the H200 partition, where the retraining plan measures latency. Samples builds the sample index, of which status shows only aggregates. A fetch takes one set of the X-ray list or one gated CT source, after any live X-ray fetch. Explore looks inside a fetched set; dropzip and unpack came on the owner's word of 23 October, when one CT set came down as a single 534 GB zip. Stop cancels the gate's own live jobs and nothing else; cancel takes one of them with the live jobs its word queued.

The sender and the receiver do not hold the same list: the workflow's description in symphony-template offers words the gate.sh read here does not hold (prior, chain_eval and a census word) and omits unpack, and gate.sh refuses any word not its own with exit 64. Its exit codes are 0 done, 64 a word refused, 75 busy (another word still running after a 60-second wait, jobs still live, or squeue not answering), 2 the checkout or a file missing, and 1 a submission that failed. Inside the jobs, a fetch the size rule refuses ends with exit 4 having landed nothing, and a platform fetch that verified no file ends with exit 3.

## How a job reaches Slurm

Every job is queued through hpcworker's `job submit` with a class, the owner's order of 21 October ([docs/memory/grid-jobs-go-through-hpcworker-job-submit.md](../../docs/memory/grid-jobs-go-through-hpcworker-job-submit.md), issue #77). Batch puts a CPU job on the preemptible queue, requeued when preempted; gpu puts a job on the GPU partitions with their GPU QoS and one GPU; the site profile that hpcworker publishes gives the partitions, the QoS, the account and the GPU request. A job script's header keeps only its time, CPUs and memory, and a test fails any script that places a job itself. The order followed an incident: SchwingNet's own guess at the GPU QoS was refused (issue #74) while Beethoven had known the right one for weeks.

The wrapper asks Slurm whether it would take each job's shape before it queues it, so a job the scheduler would refuse never enters the queue and the reason comes back whole; arrays are not asked first, since whether the test takes an array is not measured on the grid. It refuses an hpcworker older than framework 27, turns the dependency text into job submit's own form and refuses anything else, so no job is queued without its wait, and passes each job's settings through its environment, since a comma once cut a value passed the other way. Which of the gate's jobs are live is read from squeue, not from job submit's own status, because that status reads every job as ended when neither squeue nor sacct answers, and a gate that took that for nothing live would queue a second graph beside the first. Every submission is one line of the gate's own job file, with its word, what it is and when, which status and stop read; neither touches a job that file does not name.

## The grid rules and the incidents behind them

The lab recipe's rules apply to every job, a ten-record test included. The table gives each rule as the recipe states it, the incident it names, and where the gate carries it now.

| Rule | Incident | Where it stands |
| --- | --- | --- |
| 1. The login node runs only a few commands; downloads are jobs; compute nodes have internet | dozens of smoke tests on a node shared by about 95 users, 2026-09-21 | the gate's fixed list of programs; every fetch a job |
| 2. Set the job's directory, since output paths resolve against it | logs where nobody looked | job submit's directory; stage reports that status prints |
| 3. afterany, never afterok; the child reads a file to decide | an 8 h limit stranded a whole chain, 2026-09-09 | afterany where the child must run; afterok only where job submit ends a stranded job |
| 4. Node /tmp is swept; scratch and IPC node-local, removed on exit | the sockets of two 18-hour runs deleted in the same minute | the records differ on where scratch goes (below) |
| 5. Large outputs on the lab volume, not home | home at 97 percent; 260 GB deleted; about 90 scripts then read an empty held-out set | the data root and the runs on the lab volume |
| 6. CPU on the preemptible queue; GPU partitions with the GPU QoS | GPU partitions accept only the GPU QoS | the site profile's classes since issue #77 |
| 7. Containers probed in step 0 | three jobs lost in a row: exit 127, starter not found, a bad bind | setup's ready marker |
| 8. Arrays with atomic claims, a heartbeat, a GPU self-test and a failure-streak stop | Blackwell nodes under a CUDA 12.4 build would have failed every claimed case | the version 1 report names its GPU |
| 9. A dependent job whose inputs are not ready resubmits itself and exits 0 | design | the gate resubmits missing inputs at the word instead |
| 10. No requeue unless the script is re-entrant | a restart must not mix two attempts' files | version 1 never requeued; fetches requeued and keep their admission |
| 11. One LaTeX compile at a time per directory | two compiles interleaved one aux file; a stale PDF stayed on disk | outside the gate |
| 12. Before cancelling, record every job with its script header | the owner's rule of 2026-09-27 | stop and cancel touch only jobs the gate recorded |
| 13. Take each job id on submit and write it to a file | ids that lived only in a terminal | the gate's job file |
| 14. A pre-registered decision gate between a timing run and a production array | cost control on a 21,622-CT census | the owner's word and count before every job |

Three habits sit beside the table. A job script runs with set -uo pipefail rather than set -e, because with -e a job dies without saying which check failed. An empty, missing, ambiguous or defaulted input stops the run, a habit the recipe says would have prevented 16 of the 29 incidents tallied on 27 September. And an agent that submits returns the job ids, an estimate and the files to collect, then stops: no squeue loop beyond about ten minutes, after polling agents burned a session limit four times in one day on 24 September. The playbook's one look a minute is a generic default, and [the programme contradictions](../../artifacts/_synthesis/contradictions/programme-direction-handoffs-and-onboarding.md) page carries both limits together: at most once a minute, for no more than about ten minutes. The gate keeps that discipline by design, since a word answers once with a bounded file.

Rule 5's incident is also on the [Ninety-Three Pixels](../../artifacts/ninety-three-pixels/) page of 21 September, superseded by [What Is Left After Physics](../../artifacts/what-is-left-after-physics/), which alone still holds the reading at that moment: 260 GB freed and home at 3,966 of its 4,295 GB soft limit, a record, not a final value. The verification cluster keeps a consequence: held-out numbers produced between that deletion and the fix to the held-out reader are flagged for re-checking ([the verification contradictions](../../artifacts/_synthesis/contradictions/verification-benches-overnight-audits-and-or-readiness.md)). Rule 9 needs a stop condition, and the board of 11 September shows why: a download chain resubmitted itself every five minutes, forever, after 17,073 of its 17,075 files had landed and the last two were dead, until it was cancelled; the same list records five folds in parallel slowing one another because only the first could stage to the node's fast disk. Both are records, not final values. Rule 4 the records have not reconciled: the lab recipe puts scratch and IPC in node-local shared memory, hpcworker puts container temp in a per-user folder under the node's /tmp, and the research note says the job's own temp variable is not node-local; the grid contradictions page carries both, flagged.

The playbook's other defaults give way the same way. Its login-node ceiling of one core, 60 seconds and 4 GB is generic, and the lab recipe's list is Wayne State's rule. Its expectation that most compute nodes cannot reach the internet does not hold here: egress was measured from a compute node on 28 September, and the student clones of 14 October came from compute nodes. The line in [docs/research/v1-demo/README.md](../../docs/research/v1-demo/README.md) that compute nodes have no internet is contradicted by both, and by the job that fetches version 1's outside file from a compute node.

The [FluoroCap Pipeline Map](../../artifacts/fluorocap-pipeline-map-h9rmbs/) of 14 September shows the practice the rules replaced: every stage was a Slurm job or a login-node orchestrator polling for a file or a job name, a pattern the grid contradictions page records as superseded by the lab recipe's rule. FluoroCap's network ran on the workstation's WSL, with closed journals through the university's proxy session; the plan to use the grid's outbound address was not used, and the map's claim that PubMed Central throttles that address is unsourced, so it is not stated here as fact until a probe is recorded.

## Where data lives and how a fetch refuses

The grid gives the lab two volumes. Home is a Panasas volume under a soft quota of 4,295 GB, for code and the checkout. The lab volume is CephFS under a quota of 20 TiB, which the size rule reads as 21,990 GB, for the data root, the catalog store, the containers and the runs. The [Imaging data holding](../../artifacts/imaging-data-holding-manifest-migration-and-index-fqmtjs/) page, canonical for the datasets cluster, read home on 7 October at 4,050 GB in 2.9 million files and the lab volume at about 6 TB by the university's quota tool, and its walk on 8 October counted 7.7 TB in 5.66 million files by apparent bytes. The ledger marks the home figure as updated later, so these are records of early October, not final values.

The layout is one folder per source id under the data root, each with the role folders raw, converted, derived, labels and meta and a README.yaml stating what the source is, where it came from, its licence and its annotation. The two restricted sets, VinDr-SpineXR under its PhysioNet agreement and BUU-LSPINE under its EULA, and every bank holding their pixels, are copied owner-only from the first byte. The move from home runs every step as a job on a compute node: a read-only pre-flight inventory, the copy, the verify, the cut-over (the home original renamed and a link left at its path, so scripts that name it keep working), the finalize after a second comparison, which frees home quota, and the publish. The pilot batch verified on 8 October, 76 files and 5.27 GB hashed equal on both sides at 59.6 MB/s over one stream. What the holding holds is [chapter 4](04-the-registry-and-the-holding.md)'s subject.

The census of 22 October, the word samples, is the first grid run with recorded durations ([docs/research/data-manifest/README.md](../../docs/research/data-manifest/README.md)): a plan job, a scan array of 64 tasks of 8 to 97 minutes each, the merge in 5 h 9 min, which wrote the index and failed in its report on a missing key (fixed in #114), and the manifest alone in 4 h 56 min. [The manifest](../../docs/research/data-manifest/MANIFEST.md) counts 140 groups and 7,008,826 files, 7.3 TB as its README totals it; the index stays on the grid and only aggregates leave it ([docs/memory/sample-index.md](../../docs/memory/sample-index.md)).

The size rule is the owner's of 23 October, issue #160, in his words: "just make sure any datasets that are selected for storage know exactly how much space they will require and block those which would cause overflow, all or nothing datasets" ([docs/memory/the-size-rule.md](../../docs/memory/the-size-rule.md)). Every fetch reads its exact size from its source before a byte lands, and is refused whole, with exit 4 and nothing landed, when it would pass the quota after what the admitted running fetches have yet to land. There is no floor and no margin, and a job Slurm requeues keeps its admission. The room is read from the quota's own attributes twice, a minute apart, keeping the smaller, and never from df, which on CephFS reports the whole Ceph pool: 5,881,937 GB free on 23 October under a quota of 21,991 GB. A source whose size cannot be read is refused, and three download routes with no size reader are refused until issue #163.

Three incidents of 23 and 24 October shaped how the rule reads the room. The volume's own use attribute printed as 48 digits, which bash's arithmetic wraps without a word, so every fetch would have been admitted; the rule now takes only counts of at most 18 digits. The grid's mount gives a folder's entry count as its size, so the use is summed from the volume's own entries, with checks (#172). And a quota above the volume, the group's 40 TiB, binds too, so every quota on the path counts (#190). The first status after #181, at 00:25 UTC on 24 October, read 17,102.81 GB used and 4,887.42 GB free of 21,990.23 GB, with no room while the quota above was not yet counted; once #190 counted it, the volume's own quota was the one that binds. That is a dated reading, not a final value. What the rule does not count can still fill the volume under a running set: the X-ray chain's bank and catalog writes, the jobs' temp files, the group's other users, the attribute's lag, a file limit, and an X-ray set whose size the list leaves blank; and a fetch sent before the rule keeps the old 5 TB floor. The pipeline page's refusal at the volume's free space minus 5 TB, which the programme contradictions page carried, is a record, not a final value: the size rule replaced it.

Which fetches are the owner's alone has a short answer and a long one. The short one is all of them: every fetch, grid job and training waits for the owner's word and the number of jobs (CLAUDE.md, and the owner's instructions as sessions received them on 23 October, which add fetches); a note that said grid jobs need no number was corrected as superseded ([docs/research/state-of-knowledge.md](../../docs/research/state-of-knowledge.md), item 3). The long one is the lines that run only by name ([docs/memory/the-xray-fetch-chain.md](../../docs/memory/the-xray-fetch-chain.md)). CT-RATE, 21.3 TB, is off by the owner's word of 21 October, printed for him and never submitted without his TB number. The full NLST is its own word on his yes of 22 October, 11.1 TB by its index's series sizes, not the 2.3 TB its card gave; the whole FluoroSeg set, about 2.65 TB, is one word on his yes of the same day. MIMIC-CXR-JPG (about 570 GB), VinDr-CXR (about 180 GB) and VinDr-PCXR (34.1 GB) are each one word once PhysioNet has approved the owner's access. A credentialed or gated source runs only with a token or link file of the owner's at mode 600, which the gate checks and never prints. The sign-ins, agreements and letters the README lists as the owner's hand only stay his, and Radiopaedia is never fetched by script. Nothing fetched is deleted, but for dropzip, which deletes a download zip only when every file in it sits unpacked beside it at the same size.

One deadline belongs here. The RSNA RATIC presigned link is good until 28 October 2026, 02:38 UTC. The pipeline page called it the owner's one exception, since no word could carry it; the merged code now fetches it by `fetch` with its id, reading the link from the owner's mode-600 file. Whether that fetch has run is in no record read here, and [the datasets contradictions](../../artifacts/_synthesis/contradictions/datasets-holdings-and-licences.md) page cannot tell.

## How a run finishes, and what has finished

Each stage writes a stage report into the checkout's log folder, and status prints them. Status opens with the lab volume's room and the space each set takes, largest first, by label and never by path; then the gate's newest jobs as sacct sees them; for each failed newest job the end of its log, masked, and for a job that reads image headers, person keys or a sign-in only its tracebacks and status lines; then the sweep probe, the latency lines, the stage reports with their paths cut, and the newest run's checkpoint state, W&B links and the head of its test table. However much the logs hold, at most 400 lines and 64 KiB reach the gate.

Weights and Biases is online where the grid's key is found, by the owner's words of 21 October, and offline otherwise, each step's offline run pushed as the step ends; the flow's last line, the run's sync record and its ledger row say whether it reached W&B and why not ([docs/memory/evaluation-and-wandb.md](../../docs/memory/evaluation-and-wandb.md)). Those words replace the retraining plan's earlier default, offline and synced from the owner's computer. On the gate's path the flow runs in local mode inside the one GPU job, since its Slurm mode would need sbatch inside the container, so each push comes from the compute node; the memory's and the demo note's line that the flow pushes from the login node describes a mode the gate does not use, and the login node would kill it. The run's record is written first and its ledger row last ([docs/memory/the-v1-flow.md](../../docs/memory/the-v1-flow.md)), and the record lands here by pull request.

Version 1 has not run on the grid. The run ledger, [docs/research/v1-demo/LEDGER.md](../../docs/research/v1-demo/LEDGER.md), holds two local dry runs of 21 October on synthetic frames at 0.00 GPU hours and no grid run, and as of 23 October no ingest of a real frame is recorded (state-of-knowledge, item 8). What has run on the grid is the census, the status words and fetches. Three platform fetches ended COMPLETED with nothing fetched on 23 October, because one helper reads its include pattern as a glob, and such a run now ends with exit 3 (issue #158); one Drive set came down whole, 6.2 GB still zipped, was found to hold another anatomy and was taken out of the registry the same day (state-of-knowledge, item 4).

Two things wait outside the run. The leak verdict holds training back only by instruction: version 1 waits on the split check, not on the leak checks, as the pipeline page said on 21 October and the merged code still does ([chapter 9](09-splits-leakage-and-licences.md)). And a Claude worker that works on the grid for a day without pushing loses its claim, because the board releases a claim after 24 hours with no push ([Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho)); the review ranks this third and proposes a push every 30 minutes and on the signal a job receives 120 seconds before its time runs out. On 21 October the grid ran framework 22 with one worker and one Claude account signed in, and no record shows a second worker since; the resume window is carried as 4 hours, read from the code at framework 17, not the review's unsourced seven days. [Chapter 31](31-claude-workers-on-the-grid-and-the-labs-machines.md) holds the rest.

## Limits and measurements on the status page

The fourth question has a plain answer: almost every grid number in the record is a limit or a stated size. The wall times in the table are what each script asks Slurm for. Version 1's 24 hours on one GPU bounds that job at 24 GPU-hours; it is not a cost. The demo note's other path, the flow's own Slurm mode with two jobs of 4 and 1 hours, at most 5 GPU-hours, is not the gate's. The 6 GPU-hours several notes give for version 1 has no written source, the retraining plan gives hours per stage instead, and the bound is the owner's to set with his word and number; the record has not settled it ([chapter 22](22-quotas-cost-and-the-budget-of-a-run.md)). Fetch sizes are what a page or a card states, and the README's one hour per 20 GB is a guess until a log says otherwise.

What the record measured on the grid is short: the census's task and merge durations, the volume readings of 23 and 24 October, the pilot batch's copy rate, and the single CT zip's size. No record gives a queue wait, how long any job sat before a node took it, so the schedule's dates cannot yet be turned into hours on the grid; nor the grid duration of an ingest, a catalog build or a version 1 run, the GPU-hours any run spent, or the latency on the grid's GPU. The README's measurements of the X-ray chain on 21 October were made in a cloud container, off the grid.

## What we know

A run reaches the grid by one word from a cloud session through the Grid accounts workflow to the Beethoven gate on the login node, which brings the checkout to main and runs grid/gate.sh; the answer returns as a file of at most 200 kB. The merged gate holds twelve words, refuses a busy or a bad word with its own exit code, and runs nothing on the login node but a short list of shell tools. The start graph lets version 1 begin hours after the C-ArmLSpine ingest rather than days after the X-ray fetch, and uses afterok only where a failed input must stop the job and job submit ends a stranded one. Every job reaches Slurm through hpcworker's job submit by class, after the GPU QoS incident. The lab recipe's fourteen rules each carry an incident, and the gate carries most of them in code. Data lives on the CephFS lab volume, one folder per source with role folders; every fetch is admitted or refused whole by its exact size under the quota, with no margin, and every fetch, job and training waits for the owner's word and count. The census of 22 October is the one grid run with recorded durations, and version 1 has not run on the grid.

## What we do not know

Whether the owner's Connect press happened as such, or the route came up another way, is not recorded; that the route works is inferred from the runs since 22 October. No queue wait and no grid duration of an ingest, a catalog build or a version 1 run is recorded, so the schedule's later dates cannot be checked against the grid. Whether Slurm here ends a job whose afterok parent failed, as the gate's design relies on, has not been seen in a recorded run. Where a job's scratch belongs is unreconciled between three records. Whether git works on the login node, the other half of issue 19, is open. The GPU-hour bound of version 1 is the owner's to set and unwritten. Whether the RATIC fetch ran before its link lapses on 28 October is not in the records read. Whether the grid's checkout of main holds the words the sender offers is a question of SchwingNet's main on the day, which this chapter did not read.

## What would change our mind

A recorded version 1 run on the grid, with its queue wait, wall time and GPU-hours in the ledger, would replace the limits in this chapter with measurements and either confirm or move the dates to the talk. A status answer showing a job cancelled before it started after its afterok parent failed would settle the afterok question; a job left pending would send the gate back to the lab's rule 3. A git clone or pull on the login node, recorded as completed or killed, would settle issue 19's other half. A grid run that admitted a fetch the volume could not hold, or refused one it could, would reopen the size rule. A recorded press, or the owner's word on how the route was connected, would replace the inference about the route. And a second worker started on the grid would move the workers' state that chapter 31 carries.
