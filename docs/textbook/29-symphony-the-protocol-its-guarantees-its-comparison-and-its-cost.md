# 29 Symphony: the protocol, its guarantees, its comparison and its cost

Label: symphony-beethoven-separable. This chapter belongs to Part S, written so that it can be published apart from the rest of the book: it holds nothing of SchwingNet's method, data or numbers, links no SchwingNet chapter for them, and names every person by role.

This chapter says what Symphony is and what may honestly be claimed for it, for a planner who means to run work through it, explain it to a reviewer or set it beside a rival. It settles how the claim protocol works and what it leaves unpromised; which of its seventeen guarantees were checked, by what kind of search, and which were broken or unchecked; where Symphony and Beethoven sit in a twelve-axis taxonomy and which narrow uniqueness claims survived an adversarial search; how Symphony compares with gh-aw, unsorry, openai/symphony and the rest, every "better" graded better by design with no outcome measured; what the handoff of 13 October set up; and what each rung of the price ladder buys, where the repository's later table supersedes it. Every outcome figure from the project's own coordination benchmarks is held back by the owner's rule of 15 October and appears nowhere here.

## What Symphony is

Symphony lets many Claude Code workers share one GitHub repository using only GitHub's own objects. Issues are the queue; the first push of a branch named `claude/N` is the lock on issue N; a pull request is the only way work lands, and only with the required check green ([Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho)). Every rule lives once, in a dependency-free Python library, symphony-protocol, which each repository carries as a vendored copy pinned file by file. A worker is anything that claims: a person's local or cloud sessions, a routine on a Claude account, or a worker in GitHub Actions, each under a name and a label `worker:<name>` ([docs/agents/PROTOCOL.md](../../docs/agents/PROTOCOL.md)).

A worker reads the board and picks an issue given to it by label, else an unclaimed blocker, else the next unclaimed todo issue, never an epic. It claims by pushing a new branch whose single first commit adds a claim file naming the worker, the plan and the files to touch; GitHub refuses a second push that would create the same name, so a second claimant picks something else. It opens a draft pull request at once and pushes often, and finishes by deleting the claim file, passing the required check and marking the pull request ready; the owner merges, or GitHub does for a worker set to auto-merge. A claim with no commit for 24 hours that is not finished is released: its labels come off, a comment says whose it was and what the branch holds, and the branch is renamed `released/N-<sha>`, so the work is kept and the issue is listed again.

Around those steps run three pieces of plain code on the repository's own token, with no model call. The board is a file on its own branch, rewritten on every event and every six hours. The coordinator, a step of the same run, releases idle claims and tells overlapping work, once, its landing order: a blocker, then ready work, then the oldest. The fences are the push guard, a Claude Code hook that refuses forbidden pushes before they run; GitHub's rulesets behind it; and a protocol check in CI. Claude runs only where judgment is needed (a mention, a queued task, planning an epic and checking the whole after its last task), on one account's subscription token and no API key ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), section 2).

The repository's protocol text has moved past the artifacts in one respect. The brief of 14 October says overlaps are found by file name only. PROTOCOL.md now holds a Locks section, off unless switched on, under which a claim can lock a file, one Python symbol, one Markdown section or an outside resource, and an overlap reading that asks a pull request to bring the default branch in only where the two changes meet. Here it has stood at advise since 20 October, when the owner had the rule requiring an up-to-date branch turned off. The contradictions page could not settle either point from the artifacts; the repository does ([the Symphony contradictions](../../artifacts/_synthesis/contradictions/symphony-the-protocol-its-evidence-and-its-place.md), rows 51 and 56).

## What the protocol does not promise

Symphony guarantees how work is shared, not that it is good, finished or faster. Quality is only as strong as the repository's required check, and tasks can each pass while the merged whole fails. Nothing promises an issue gets done: a stalled claim sits up to a day, and finished work waits for review however long it takes. Two changes that touch different files can still break each other. The push guard lives in a worker's own Claude Code, so a push made from anywhere else meets only GitHub's rules, and nothing holds against someone who may write to the repository ([Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho)). And nothing measured says parallel work under Symphony beats one agent.

One hole every engineer asks about: GitHub enforces a claim only at its creation. A fast-forward or forced push onto an existing claim is accepted, because rulesets must leave `claude/**` alone so the board can rename a released branch. Only the local guard refuses a lease onto another worker's claim, and on 15 October it was found to judge such a lease by the session's own directory rather than the clone a `git -C` command names (spec, risk 12). That became finding F21, fixed in the library, and the template's hook took the fixed reading on 18 October ([docs/research/protocol-fixes-after-0-5-0/README.md](../../docs/research/protocol-fixes-after-0-5-0/README.md)). The hole at the server remains.

## The seventeen guarantees and how they are checked

### What they are and what "checked" means

The seventeen guarantees are safety properties of the bookkeeping, each restating one sentence of the spec: one holder per issue (G1); a release only when due, in order, never half done (G2, G3, G3L); no commit made unreachable (G4); nothing freed too early or by an untrusted author (G5); finished work never released (G6); overlaps told once, in order (G7); labels that name the holder (G8); a true board (G9); each notice posted once (G10); every forbidden push the guard can read refused (G11a), and the rest stopped by GitHub (G11b); a protocol check that passes exactly what the protocol prescribes (G12); a merge gate that lands only a clean merge with a green check (G13); no issue dealt to two workers of one run (G14); and no crash of the board's run (G15) ([Symphony in brief](https://claude.ai/artifact/9CDCiZqYfbrobDk6rRrMho)).

They are checked by a validation harness that runs the library's own code against a stateful fake of GitHub, driven by scripted workers, while an oracle written from the spec's words, importing nothing from the library, judges each step. A breadth-first search tries every order in which the workers' steps could run in small worlds, and deliberately broken copies of the rules, mutants, must each be caught. It is bounded checking, not proof, and every record says so. Its sizes grew over a week, and the contradictions page rules each later figure supersedes the earlier (rows 8, 11 and 12): 59 mutants and a depth-5 search of two workers on one issue, about 29,500 states, on 14 October; 16.7 million states at depth 8 and 18.8 million with two issues at depth 7, no violation, and 93 mutants by the spec of 15 October; 109 mutants a day later; and in the repository's notes 194 within a bound of 200 on 18 October, then 225 ([docs/research/protocol-fixes-after-0-5-0/README.md](../../docs/research/protocol-fixes-after-0-5-0/README.md)). The depth-5 search runs inside the required check and the deep searches weekly. These figures measure how hard the checks bite, not whether Symphony is useful.

### The tally of 14 October, and what moved

On the library's main at commit b5f098d, twelve guarantees held; G2 and G3 held only if commit dates are honest; G7 was broken, a claim being told of an overlap again when it opened its pull request; G13 was checked only in memory; and G11b was not checked, since only a live canary run by hand measures what GitHub does with a push the guard cannot read. Behind G11a, of 20,970 generated push commands the guard matched git on 16,542, also refused 1,584 that git shows harmless but whose shape the rules forbid, and could not read 2,844 hidden inside `bash -c`. Four rules had no check at all: a second pull request closing a claimed issue, a claim commit holding only the claim file, an epic's tasks going only to a worker whose area fits, and work waiting behind a blocker. The contradictions page confirms the tally for that commit (row 13).

Three of those gaps then closed in code. G2 and G3 rested on finding F8, idleness read from the committer date that the pusher writes, so a future date held a claim indefinitely and a past one released it at once; the fix reading GitHub's own record of the push merged on 15 October, and the manual's "not merged" of that day is superseded (rows 7 and 50). G7 is F2, fixed by naming each piece of overlapping work by its identity. And the `bash -c` blind spot is F32, fixed on 18 October so that text handed to another shell is read as a command, with the stated remainder that text the command does not spell out, sudo and xargs still pass. The count of findings grew the same way: twelve in the handoff of 13 October, six of them fixed in release 0.4.1; nineteen in the spec; F32 by 18 October, each fix through two adversarial reviews (rows 9 and 10). Findings at that rate from a library first committed on 10 October show at once that the checks bite and that the library is young.

## The evidence on coordination

### CooperBench, quoted by its counts

The need is documented by CooperBench, a 2026 preprint that gave 652 feature pairs from 12 repositories either to one agent or to two agents in isolated workspaces that talked only by message and merged once at the end. One agent passed far more often: GPT-5 315 of 652 against 183 as a pair, Claude Sonnet 4.5 307 against 168 (47.1 against 25.8 percent). The paper states the gap three different ways, so the spec says to quote the counts ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), section 7.1); the contradictions page counts the spec's and the brief's figures as one sourced claim repeated (row 31). The plan of 8 October gives the gap as "about 30% less often", the abstract's framing.

What failed was duplicated or incompatible work, not skill: 33.2 percent of failed pair runs were work overlap, the hand-read root causes were expectation 42 percent, commitment 32 and communication 26, messaging took up to a fifth of the steps without raising success, and a plan in the first turn nearly halved conflicts, 29.4 against 51.5 percent. The authors' later ablation, one model, 50 pairs, one seed and not peer reviewed, found messages only 26 percent, one agent 48, a shared git remote 56 and a lead with a shared task list 62; every record calls it weak (row 32). Symphony is the opposite of the coop design, shared and visible work merged continuously, and each primitive maps onto one failure: one claim per issue against duplicated work, a board with an Overlaps section against ignoring a partner's work, the claim file as the plan before the code, the idle release against locks never freed. Each row of that mapping says what a piece is for, not that it works, and is graded Inferred.

### What the project's own runs may say

The project built coordbench to run Symphony's arm on CooperBench's pairs beside solo, coop and two other arms under a pre-registered plan, and flowbench to do the same on SWE-bench instances. A full coordbench run and a flowbench pilot have since run and are recorded in the repository ([docs/research/curse-of-coordination-full-run.md](../../docs/research/curse-of-coordination-full-run.md), [docs/research/flowbench/README.md](../../docs/research/flowbench/README.md)); their figures are held back by the owner's rule of 15 October, which the site's comparison pages keep for both ([docs/research/symphony-compared-by-domain.md](../../docs/research/symphony-compared-by-domain.md)). An earlier coordbench step reported in the spec was withdrawn the next day after a harness audit found spoiled runs (rows 16 and 17). A planner may say the runs exist and that no outcome is claimed from them.

One field measurement is kept. On a private copy of the owner's, over its first four days, the median wait from a claim commit to its draft was 84 seconds over 38 pull requests, and from opening to merge 9.6 minutes over 37, with no interval given, no review on any pull request, nearly all opened by one login, and no check of the work itself ([docs/research/claim-waits-in-a-real-copy.md](../../docs/research/claim-waits-in-a-real-copy.md)). It is a lower bound on a claim's cost in a session's time, from one young copy, and says nothing about parallel work.

## The taxonomy, and where Symphony and Beethoven sit

### Twelve axes, three that carry the argument

No published taxonomy of agents asks where a coordinator's compute runs and who pays, so the spec of 15 October kept the axes that recur in the literature and added that one: stack layer, autonomy, control topology, communication medium, concurrency control, dependencies managed (after Malone and Crowston), execution environment, trigger and lifetime, state and memory, cost model and payer, verification and governance, and domain and maturity ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), section 3). Three carry the study. Axis 10, cost and payer, holds the Actions story. Axis 5 holds Symphony's claim, a hybrid of a claim made by creating a branch, a lease-like release, a local fence and optimistic merging through the required check. Axis 11 holds Beethoven's, that a tool and never a model decides. The manual tells a writer to use those three in a short explanation ([Symphony and Beethoven Taxonomy Manual](https://claude.ai/artifact/RE4jtXqsFFgiZxhQLamUDR), section 6).

Two axes separate Symphony from its neighbours at a glance: where the coordination state lives and what one more agent run costs. In the corner with state on the forge and a flat price the spec finds four other systems, and Symphony is the only one there that puts agents in Actions and people's own sessions under one claim rule; gh-aw's work queue, the closest neighbour, sits outside the corner only because its Claude engine refuses the subscription token. Every placement is graded Inferred.

### Beethoven beside it, and the stack that is a design

Beethoven is the research layer: a launcher that runs a student's own Claude Code Remote Control session as a batch job on a university cluster, started through Open OnDemand; a shared library with data-only site modules; beethoven-qa, which holds agent-written code to contracts searched symbolically as a required check; an agents image with a tool guard; and beethoven-research, meant to turn the REFORMS and CLAIM checklists into gates over each run's record, one module of which was built by 15 October. [Chapter 32](32-beethoven-the-repositories-the-roadmap-the-reforms-gates-and-the-store-release.md) holds Beethoven and [chapter 31](31-claude-workers-on-the-grid-and-the-labs-machines.md) the Claude workers on the cluster.

The stack the owner designed, Claude iterating the scientific method inside Beethoven's frameworks while Symphony coordinates the agents, is a design, not code: no Beethoven repository runs Symphony's code or holds a Claude token, and the one step the plan allows is a Markdown-only pilot of the claim protocol in beethoven-qa after Symphony's rails for unattended workers exist ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), section 6.5). They meet in practice in one way: the review of 21 October finds cluster workers claiming by pushing `claude/N` like any other, and the 24-hour release freeing a busy worker's claim because only a push renews it, so it proposes pushing work in progress on a timer ([Grid and cloud Claude workers: review](https://claude.ai/artifact/L7nL3xkYzoitmWf4ab8ARN)).

### The narrow uniqueness claims

Every single mechanism Symphony uses has prior art, and the spec says so first. It names five: (a) a claim made atomic by a git ref on the forge; (b) automatic release of an idle claim by a CI job, keeping the work; (c) a board and coordinator run as CI jobs with state only in forge objects; (d) people's sessions and CI agents under one claim rule on a flat-rate subscription; (e) the shipped protocol code checked over exhaustive interleavings against an oracle from the spec, with mutants. An adversarial search of 25 candidates on 15 October found none with four of the five, and none with (a), (c) and (d) together; unsorry has (c) and looser forms of (a), (b) and (d), so the claims are narrow ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), section 8).

U1 says Symphony is the only system found that puts people's sessions and Actions agents on a subscription token under one claim rule, with claim, board, release and coordinator kept in GitHub objects; U2, the only one found that releases a claim by idleness and keeps the work under a renamed branch; U3, the only coordination protocol found whose shipped code, not a model of it, is checked over every interleaving against an oracle with mutants. Beethoven's U4 to U6, on narrower searches that ran out of budget, say it alone combines cluster jobs on the student's subscription with checklist gates and symbolic contracts, that its launcher alone starts Remote Control from a batch job through Open OnDemand, and that beethoven-qa alone, in a narrow search, makes contracts plus symbolic execution the required gate for agent-written code. All six are Inferred, each with the observation that would refute it, and U4 describes a mostly unbuilt system. The manual records how the claims narrowed: an early draft said only Symphony had an atomic claim, the search found three systems with one, and the atomic claim moved to the list of what is not unique.

## The comparison with the neighbours

### The two questions, and the answers

The comparison of 16 October asks of each system's code, not its README: when two agents want the same work, what stops the second, and what frees a claim nobody finishes ([Symphony versus competitors](https://claude.ai/artifact/LynwZkPadyo2SQ7G4mJfHc)). gh-aw's work queue grants one claim per item by compare-and-swap on a ledger branch from a trusted scheduler, never expires a claim by time, admits only Actions runs, and its Claude engine says the subscription token "is not supported". unsorry, a Lean proof swarm, claims by first push to a shared branch and reaps a claim two hours after it was made, keeping nothing, with agents on volunteers' machines. openai/symphony holds claims in one daemon's memory and kills a stalled worker on a timeout. Copilot's cloud agent has no lock between sessions and stops at 59 minutes. Agent teams lock a file on one machine and do not run in CI. CCPM's claim is a label two agents can both set; Beads claims atomically inside one database; paperclip locks on its server; agentic-setup's create-only push is stricter than Symphony's; and the C compiler harness used a lock file with no release. The hosted agents compete for the same user, not the same job, and the frameworks (LangGraph, Temporal and the rest) coordinate steps inside one program; a worker could be built with one, and none replaces the claim.

### Better by design, and where it is not

The comparison makes three claims, and its own words fix their grade: better designed, since no outcome is measured. One claim rule covers every kind of worker, where each rival stops at Actions runs, volunteers' machines, one machine, one daemon or one account. An idle claim is released and its work kept, where gh-aw never expires a claim by time and unsorry keeps nothing. The shipped code is checked over every interleaving, where gh-aw checks TLA+ models of its queue's design, with 68 broken configurations, and says the models do not verify its runtime. Each is Inferred. Its further points are weaker: free coordination steps are shared with the nearest neighbours on a public repository, file-level overlap ordering is unmeasured, and gh-aw's 2,065-line lock file comes from one workshop repository and is Reported.

The neighbours are ahead in what a reviewer would name first. gh-aw has a sandboxed read-only agent job with a network allowlist, pinned actions, separate write jobs, threat detection, per-run cost records, a task graph and an attempt budget. The hosted agents need nothing installed and give a screen, a fresh VM per task and a choice of models. Beads has a dependency graph and a bisecting merge queue; agent teams have live messages. Symphony has none of these, and shares its name with the far larger openai/symphony.

### What not to claim

The spec, the comparison and the repository's memory list the same forbidden headlines ([docs/memory/symphony-versus-competitors.md](../../docs/memory/symphony-versus-competitors.md)). Not an atomic claim on the forge, which gh-aw, unsorry, agentic-setup and older lock actions have; not coordination in Actions with no server, which unsorry and gh-aw also do (row 1); not free coordination on a public repository, which any of them gets; not the subscription token in Actions, which anyone using claude-code-action has; not one issue, one branch, one pull request, which is Copilot's way too. Not "agents run for free", since inference is paid by a Claude plan; not "unlimited agents", since GitHub Free runs 20 jobs at once, the workflow token gets 1,000 API requests an hour per repository and every Actions worker shares one plan's window; not "nothing else does this", since only the combination is claimed; not Anthropic's approval of agents on a subscription in CI, since it advises an API key for a shared secret and says plan limits assume ordinary, individual usage. No benchmark win, and the Symphony and Beethoven stack only as a design.

## The handoff of 13 October

The handoff of 13 October records the night that made Symphony something others could rely on, and its plan is the map later sessions followed ([Symphony Handoff](https://claude.ai/artifact/XQj71up9dbJhwSStCVUe9T)). Three of its decisions bound what may be claimed. First, the release gate: each release of the library waits in a GitHub environment whose required reviewer is the owner, fails closed without that approval, and the sync to consumers carries only a published release; 0.4.1 was the first through it. No session can approve or publish a release, and although the owner allowed releases without approval for the development phase, each still waits for the owner's click until the owner says otherwise in the owner's own words. That is why later records speak of fixes "on main and unreleased".

Second, the design for one public runtime. A simulated adoption then landed 145 files and 28,436 lines in a whole-template copy and 28 files in a protocol-only one, and copies of three generations were already live, one with a metrics script failing at import. The design moves all of Symphony's logic into the library's public repository, which copies call through three thin workflow files and a small bootstrap, cutting a whole-template copy to 38 files and about 1,070 lines; background jobs follow a moving tag, while the required check, the hooks and every job holding a Claude token run a reviewed pin. The comparison of 16 October still lists the runtime as not built.

Third, the owner's questions. Five were answered that day as recommended: only writers queue work for a worker; a qa check from the default branch and code-owner review stop a worker changing what steers workers; the token in the organization secret is best an account nobody uses by hand; at most 10 Claude runs a day per repository; and each release waits for approval. Nine wait for their phases, among them the runtime's licence, how copies follow releases and which repositories the account pool may reach. The handoff also flags that from 12 November 2026 Anthropic's Usage Policy names services that route requests through consumer subscriptions. It says its own claims were not rechecked against GitHub (row 59), and its rails for unattended workers were still unbuilt on 16 October, so Symphony's own tests had not yet run on the public repositories the economics assume (spec, risk 4).

## The price ladder

The Dollar-per-Feature Ladder of 9 October makes the economic argument in three numbers ([The Dollar-per-Feature Ladder](https://claude.ai/artifact/9Ymg61SPUZTqaNBCbzGHMx)). $17 a month runs the whole template: one Claude Pro seat billed annually beside a public repository on GitHub Free, where standard-runner minutes are free without limit and the gate is enforced. $0 is the GitHub bill there by construction, since with no payment method GitHub stops at the quota rather than billing. And 3,000 included private minutes on both Pro and Team means that above the bottom rung money buys governance and usage, not compute, until Enterprise's 50,000. Its rungs run from $21 for one person on a private repository to $120 for five people on Team, with Max or premium seats only where a seat hits its limits, and Enterprise unpriced because its figure could not be verified. Its rule is the protocol's own: a native setting beats a workflow, a workflow beats inference, and inference runs only when asked for.

The ladder is a member of its cluster, not the canonical record, and the repository's table of 13 October overrides it ([docs/setup/free-or-paid.md](../../docs/setup/free-or-paid.md); [docs/memory/the-plan-ladder.md](../../docs/memory/the-plan-ladder.md)). GitHub's documentation gives the $4 Pro and Team prices only from 2020, so they are not confirmed current, which the contradictions page confirms against the ladder (row 25). A private repository on GitHub Free enforces nothing of the gate, since a ruleset there is saved but not enforced. And in a private repository code scanning, dependency review, secret scanning and push protection are paid add-ons that only Team and Enterprise can buy, while on a public one almost everything is free on every plan. The ladder's word that the subscription token is "sanctioned for CI" is too strong (row 2), its fallback minutes assumed every scheduled slot runs (row 6), and its Windows and macOS multipliers have no source line (row 48). What survives is the shape and the bottom rung: Pro at $17 a month billed annually or $20 monthly, Max at $100 or $200 for usage alone, Team at $20 a seat annually, the setup token from Pro up.

The spec states what still costs money. Every Actions worker draws on one person's five-hour and weekly limits, which this project's own account reached on 15 October, a fact given without a record (row 46). A private repository bills minutes past its quota: ten one-hour Claude runs a day on a private Team repository come to about $90 a month, an illustration on an assumed workload (row 35). And what binds first at scale is probably GitHub's API and queue limits, not minutes, unmeasured (row 33).

## What to say, and to whom

The manual fixes one order for every audience: the need, the mechanism, the economics, the evidence, then the limits before anyone asks ([Symphony and Beethoven Taxonomy Manual](https://claude.ai/artifact/RE4jtXqsFFgiZxhQLamUDR), section 6). A grant reviewer hears the science first, that AI-run research fails in ways its paper cannot show, then the laboratory's rule of one issue, one branch, one pull request; CooperBench's counts may go in at the owner's call, nothing from the project's own runs may, and what is built is told apart from what is planned. An engineer hears the mechanism and its holes unprompted: no lock server, deterministic Actions jobs, bounded exhaustive checking, the claim enforced by GitHub only at creation, the idle clock that was the pusher's until the fix now vendored here, and API limits nobody has measured. A lab lead hears what people do and pay: a GitHub login and each person's own Claude plan, no server, free bookkeeping on a public repository, Actions agents sharing one plan's limits, no GPUs on GitHub's free machines, and a pre-release product.

## What we know

Symphony's mechanism is settled: issues as the queue, the first push of `claude/N` as the lock, a draft at once, a required check before any merge, and a board and coordinator run as Actions jobs with no model call and no server. Its guarantees are safety properties of bookkeeping, checked by bounded exhaustive search of the shipped library with mutants that bite; on 14 October twelve of seventeen held, and the fixes for the conditional and broken ones are in the release vendored here. The need is documented by CooperBench's counts, and Symphony's answer to it is a design. Its distinctive claims are three, narrow and Inferred. On a public repository the coordination costs nothing, and the inference costs a Claude plan from $17 a month billed annually.

## What we do not know

Whether Symphony makes agents finish more, or cheaper, work than one agent or any rival: the benchmark figures exist and are held back. Whether all seventeen guarantees hold on the released library, and whether 0.5.1 went through the owner's approval. What GitHub does with a push the guard cannot read, which only the unadopted live canary measures. Which GitHub limit binds first. Whether several Actions workers on one person's subscription count as ordinary, individual usage, whether the subscription path survives bare mode, and whether a benchmark or a paid App sits inside GitHub's Actions terms; nothing here is a legal opinion. Whether the $4 plan prices are current. Whether U1 survives a search of the research literature, which the search of 15 October did not cover.

## What would change our mind

A system with four of the five mechanisms, or with (a), (c) and (d) together, would refute U1; one releasing by last activity and keeping the work would refute U2; a coordination layer with model-checked shipped code would refute U3. A matched-budget benchmark, reported with exact tests and intervals once the owner lifts the hold, would replace "better by design" with a measured answer either way. A canary seeing GitHub accept a forbidden push the guard could not read, or a second creation of a claim branch, would break G11b or G1 on the live service. A change to GitHub's free public minutes or to Anthropic's position on the subscription token in CI would move the economics.
