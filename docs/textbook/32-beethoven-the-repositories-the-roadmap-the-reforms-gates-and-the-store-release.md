# 32 Beethoven: the repositories, the roadmap, the REFORMS gates and the store release

Label: symphony-beethoven-separable. This chapter belongs to Part S and may be published apart from the rest of the book: it holds nothing of SchwingNet's method, data or numbers, links no SchwingNet chapter, and names every person by role.

Beethoven is the owner's research layer for a university cluster: a launcher that puts a student's own Claude Code onto a compute node and in front of them in the browser, and an engine, mostly still on paper, meant to plan, run and gate research so that a result which skips a reporting item cannot leave the run. This chapter settles, for whoever plans the next piece of Beethoven work, what is built and what is planned, which REFORMS items a gate can enforce and where, how the repositories are sealed, what the deferred VS Code move would cost, and how a release reaches the Chrome Web Store and what a session cannot do there. It keeps the built apart from the planned throughout, because the artifacts themselves warn that Beethoven's evidence is mostly plans ([Symphony and Beethoven Taxonomy Spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/), risk 8). Chapter 29 ([Symphony: the protocol, its guarantees, its comparison and its cost](29-symphony-the-protocol-its-guarantees-its-comparison-and-its-cost.md)) covers the coordination layer, chapter 30 ([Symphony's origins](30-symphonys-origins-cswap-the-primitives-and-the-two-claude-surfaces.md)) the store kit's first use, and chapter 31 ([Claude workers on the grid and the lab's machines](31-claude-workers-on-the-grid-and-the-labs-machines.md)) the grid workers themselves.

## What Beethoven is, built and planned

The [Beethoven build roadmap](https://claude.ai/artifact/StTvVVwZBJRq7PELUmLSbG) of 3 October opens with the sentence a planner should keep: the two repositories that existed then, hpcworker and beethoven-extension, are "the transport layer of the engine, not the engine". hpcworker held site profiles, a scheduler adapter for Slurm, PBS and LSF, an always-on `claude remote-control` worker in a shared Apptainer image with `afterany` successors, status files and grid CI on real compute nodes. The extension held a Chrome side panel, an Open OnDemand shell driver, a native ssh bridge, an approval check, a kill-list for withdrawn versions, a terms flow and a mock portal. Nothing in either planned research, ran it headless or enforced REFORMS; no Hydra, run hashing, clean-tree gate, group-level splitter, Weights and Biases, CodeCarbon, LaTeX macros, Zenodo, Hugging Face, LangGraph or Metaflow code existed. That was the starting point, and it is reported, not measured: the roadmap read both repositories at named commits, but this book has not read them.

By 15 October the [taxonomy spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/) gave the wider family as the owner describes it: beethoven-base and beethoven-sites for grid-job protocols and site data, beethoven-research for the CLAIM and REFORMS workflows, beethoven-qa for the checks on code that agents write, and beethoven-agents for the agent image and its guard. Its status column is the most compact statement of what is built. The launcher works at one site. beethoven-base and beethoven-sites are built. beethoven-qa is built: contracts on every public function, CrossHair with Z3 as a required check, six code-standards groups reported as SARIF, and auto-merge with no human gate. beethoven-agents has its hermetic image, Claude Code managed settings, a tool guard and bee, an account switcher that never touches a credential; Metaflow on Slurm, the fenced lease, the registry and the bus are not built. beethoven-research holds one module, the split-level disjointness check; the rest of REFORMS and all of CLAIM are not built. The [beethoven-qa memory](../../docs/memory/beethoven-qa-in-a-symphony-repository.md) of 20 October says the same of the research pipeline: one module, the split check, with the study record and result rows not built.

The engine's evidence, then, is one gate and a quality toolchain. A planner who reads "REFORMS gates enforced by code" anywhere in the record should read it as a design that the record grades Inferred until a gate refuses a real run.

## The roadmap: six phases, six gates, six decisions

The roadmap builds the engine in six phases on top of the launcher, each ending at a gate measured on the grid rather than asserted, and each changing both repositories, with every new file a job writes entering the shared contract in the same change. None of the six phases is recorded as finished in any artifact read here.

Phase 0, ground truth, is one probe job: `claude -p` with streaming JSON output, in the shared image, on the student's own login, under `sbatch` with no terminal, recording which credential the run reports and how the five-hour limit behaves. Its gate is that a headless run completes from a batch job on the subscription login, or the fallback is chosen. The roadmap highlights it because the answer reshapes phases 1 and 2: if headless runs are not allowed or do not work, the inner loop becomes a Remote Control session steered by the outer loop. No artifact reports the probe's result. The record does hold an indirect datum: the VS Code edition already runs `claude -p` per request from a daemon on the grid, on the student's own sign-in ([Moving Beethoven for VS Code onto hpcworker](https://claude.ai/artifact/ApBd6TpHYnsWVKvP1NjvyX)), which the contradictions page reads as no contradiction of the roadmap's "nothing yet", since that is a separate edition outside hpcworker (row 23). It shows the path is possible, not phase 0's answer under hpcworker's rules.

Phase 1 turns a prompt typed in the side panel into one research job whose stage events the panel reads at the sixty-second polling floor. Phase 2 is the outer loop as a chained Slurm job through the stages plan, code, experiment, analyse and write, with a run ledger and hooks that re-inject decisions across compaction; its gate is a run that crosses two wall-time boundaries and one compaction with the same decisions on record. Phase 3 adds the REFORMS gates, a research template and a standard-library checker that refuses to dispatch on a failed check; its gate is that a deliberately leaky split and a dirty tree are both refused before any GPU time is spent. Phase 4 carries numbers into the manuscript and the archive without hand copying, with a DOI minted only after the student presses Publish. Phase 5 scales to two concurrent projects and a second site, with a store release.

The orchestrator is a chained job, not a service, because of the site's rule that nothing runs on the login node beyond one `sbatch`, `squeue` or `scancel` per action. That rule, the sixty-second polling floor, the `afterany`-only chaining and the framework's confinement to bash 4.2 and the Python 3.6 standard library on the CentOS 7 login node all come from the two repositories' own instruction files, which the roadmap cites (contradictions row 36), and they shape every later design here. The roadmap also lists what it leaves out of the owner's research notebook, and why: no interception of claude.ai, no setup token injected into jobs, no resident server on the login node, no copying of transcripts across accounts, and no rotation of several accounts' keys behind a proxy.

### The owner's six decisions and where they stand

The roadmap asks the owner six questions, each with a recommended answer. The record answers some of them by what happened later rather than by a dated reply, and a planner should treat those as settled in practice, not on paper.

1. Who pays for the inner loop's tokens. Recommended: the student's own subscription login. Every later Beethoven artifact keeps that rule; no dated answer is recorded.
2. The workflow engine. Recommended: plain `sbatch` for phase 2, Metaflow later. By 15 October the spec and the [taxonomy manual](https://claude.ai/artifact/RE4jtXqsFFgiZxhQLamUDR) record Metaflow as chosen and not built, and the manual adds the catch: metaflow-slurm drives `sbatch` over SSH with a key file, which Beethoven's credential rule forbids unless a plain `sbatch` adapter replaces it (row 5).
3. Where the research template lives. Recommended: a new repository. beethoven-research exists by 7 October (row 9), so this is answered as recommended.
4. Environment pinning. Recommended: pixi lockfiles in the image. beethoven-qa runs under a locked pixi environment, but no artifact says the research image does.
5. Verification extras in the first REFORMS release. Recommended: defer contracts and CrossHair to after phase 4. In fact beethoven-qa, that toolchain, was built first; the order of work overtook the recommendation without a recorded decision.
6. Human approval points. Recommended: only the Publish press, which the checklist also requires. No gate exists yet to hold it.

One tension runs under decision 1. The roadmap and the checklist keep "one person, one account" and say concurrency is bounded by the account's own limits, with no extra accounts. The grid plan of 21 October runs projects on several Claude account slots of one person, and the template's recorded decisions allow the owner's own several accounts to be coordinated from one orchestrator. The contradictions page confirms the difference (row 21). For students the rule stands as written; the multi-account slots are the owner's own arrangement, and chapter 31 treats them.

## The REFORMS checklist: what a gate can enforce

The [REFORMS compliance checklist](../../artifacts/reforms-compliance-checklist-bpzdoi/) is the canonical reading of how the reporting standard maps onto gates. It takes its item list from the REFORMS paper (Kapoor et al., 2024; the checklist cites the arXiv preprint and the project's site for the module names): 32 items in eight modules, lettered 1a to 8b. Every item can be tied to a gate, but only 20 can be verified by code. The other 12 (1a, 1b, 1c, 3b, 3c, 3g, 5b, 5f, 6c, 7c, 8a and 8b) can only be required as a written field in the study's record that the gate refuses to see empty; the code checks presence, not truth. The contradictions page confirms that the 20 and 12 are derived from the checklist's own table, not asserted without a source (row 40). Energy reporting is not a REFORMS item; the checklist lets it ride on 2c, the computing-infrastructure record, as an addition.

### Where each gate fires

Each gate fires at one of four points. Before dispatch, the run is refused before `sbatch`: eleven items fire here, three of them by code (2b, the clean tree and a head the remote holds; 5c, the split file hashed into the run's identity; 6b, zero group overlap and zero identical pixel hashes across splits) and eight as declared fields (population, its rationale, why machine learning, sampling frame, fitness of the data, representativeness, model rationale, feature legitimacy). After the run, the run finishes but is stamped non-compliant in its manifest: twelve items fire here, all by code, from the computing record and the sources per split through data summaries, exclusions, transforms, every model trained, model selection, every tuning trial, and preprocessing fitted on training data only (2c, 3a, 3d to 4c, 5a, 5d, 5e and 6a). Before publish, the manuscript build, the deposit or the model card is refused: nine items fire here, five by code (the dataset DOI, the generated README, the regenerated reproduction script, all metrics logged, and an interval on every reported metric, with the macro writer refusing a metric that has none) and four declared (baselines, statistical tests, external validity, where the findings will not hold). The checklist marks 5f, baselines, as declared even though its gate also asks that a baseline's run exist, so the count follows the checklist's own label.

### Which repository owns each gate

The gates split three ways, plus the panel, because of the login node's limits. hpcworker's framework, standard library only, takes the run manifest and run identity, the clean-tree refusal, the environment and compute record, the gate runner that reads the manifest, and the publish lock. hpcworker's image build takes the pinned heavy libraries, since a job must not install packages at run time. beethoven-research takes the domain code: the configuration schema, the group-level splitter and leakage checks, bootstrapped intervals, calibration and transform checks, the macro writer and the card builders. The extension takes a read-only checklist view per run and the student's Publish press, and never holds a deposit token. The seam is one contract file per run, the compliance record (item, state, evidence path), written by the gate runner and read by the panel, added to the contract text and the extension's contract module in the same change. The build order starts with hpcworker's standard-library gates (2b, 2c, 3a, 5a, 5c), since every later gate writes into the manifest they create, and ends with the extension's view and the Publish press.

Of this, one gate is built: the split-level disjointness check in beethoven-research, which the spec reports as REFORMS 6b "in a draft's lettering" and which the contradictions page confirms makes the checklist's "none of these gates exists yet" stale (row 8). No other gate, no compliance record and no Publish press exists in any artifact read here.

### Where the roadmap and the checklist disagree, and which holds

The two pages are dated the same day and disagree in two places. The roadmap's run identity hashes "the Slurm environment"; the checklist warns that hashing volatile Slurm variables makes every rerun a new identity and defeats the reproduction script, and records them beside the identity instead. The roadmap files energy telemetry under REFORMS module 7; the checklist says energy is not a REFORMS item. The checklist holds in both, because it names the failure in the first and took its items from the paper in the second, while the roadmap says its own module column follows the notebook's mapping and is unchecked (row 7 explains these caveats concern different tables). A planner should cite REFORMS by the checklist's lettering.

The lab's own practice already does by hand much of what phases 3 and 4 would mechanise. [The Lab Recipe](../../artifacts/the-lab-recipe-1t2gvp/) of 27 September has a number enter a manuscript only through a recorded chain, a pre-registration frozen with its hash, results files carrying a run block, a numbers manifest, result macros in the source and a reproduce target that fails on a missing or moved number, and it keeps chains on `afterany`, the rule the roadmap restates (row 41). That page is the forerunner of the macro and publish gates; it enforces by procedure and review what Beethoven proposes to enforce by code.

## How the repositories are sealed

The [encapsulation report](../../artifacts/how-the-beethoven-repositories-are-encapsulated-6h4zq9/) of 7 October is the canonical account of the boundaries. Seven code repositories that the work could change are sealed: hpcworker, beethoven-sites, beethoven-extension, beethoven-desktop, beethoven-qa, beethoven-agents and beethoven-research. beethoven-base, which the spec lists, is not among them; the contradictions page explains that the report's seven are those the work could change, not an inventory (row 10). The standard is written in the hub repository as INTERFACES.md and merged there.

### The five rules

Each repository checks the five rules on itself in its own test run, with no secret and no network. Own tree: a repository builds, tests and runs from its own tree, and no tracked file reads, runs or copies another checkout, which rules out sibling paths, a variable naming another checkout, submodules, dependencies by path or git address, and a clone of another repository in CI. One declaration: an interface file lists every export, with its kind, integer version, paths and consumers, and every import; everything unlisted is private. Pinned, checked copies: an import is one folder with an ORIGIN record, filled only by its pull script through the person's own `gh` sign-in from a commit the provider's main contains, never edited by hand, with the consumer's tests failing on one differing byte. Published surface only: a parser is tested against the provider's schemas and the vectors its real code wrote, and a hand-typed constant is tested equal to the pinned export. Direction: beethoven-qa, then beethoven-agents, then beethoven-research, never back; the launcher (hpcworker, sites, extension, desktop) and the engine (qa, agents, research) share data only, never code. An export has one of eight kinds, and its version rises only when a consumer must change its code.

The rules are enforced, not only written, and they found real faults. Running hpcworker's own vectors through each client's real readers found fourteen readers that disagreed with what the cluster side writes, seven in the extension and seven in desktop, each fixed in that client's pull request, and beethoven-qa's CI found two faults in CrossHair 0.0.111 that a local run had missed. This book has not read those runs, so the counts are Reported.

### What still crosses a boundary

The report lists three entries that still reached another checkout, each on a known list in that repository's boundary test, so that a new reach fails the test and so does an entry whose line has gone. Two are in beethoven-extension: a maintainer's live check of the signed kill-list that reads the website's checkout, and a store-assets build flag that copies the home page's diagram from the website's checkout. Both stay because the website offers no export yet, and both are removed when it does. The third, a comment in beethoven-desktop's CI file naming an out-of-date variable, was reworded and its exception list emptied in a merged pull request, so on the report's own evidence two crossings remain, both maintainer tools switched on only by a variable or flag, neither running in CI or anywhere a student goes. The report's opening paragraph lags its own body on another point too: it says beethoven-agents and beethoven-research have open pull requests, while its step list and table record both merged that day (row 28). The body holds.

The report audited, without changing, the read-only neighbours. The VS Code edition shares the student's sign-in folder with hpcworker and beethoven-agents, sets the lab volume's access entries over the folder hpcworker's access script keeps, and mirrors by hand bee's account registry, hpcworker's credential strip list and the site's scheduler facts, with nothing checking the copies. The website reads both editions' agreement texts from sibling working trees and was rendering an older version of the VS Code terms. One study repository's worker container binds a whole lab folder beside data that holds patient records, which the report says beethoven-sites and hpcworker should decide instead. Each row is a change that repository's owner would make.

The report also found faults it did not fix, which a planner should treat as open unless a later page closes them: hpcworker counts a sign-in as a subscription when the provider field is an empty string, against its own published rule; its line grammar lacks the stop line desktop reads; its command list omits several commands clients type; beethoven-agents imports the contracts library directly in five modules; and qa's vendor command copies from a local checkout at a release tag, the one exception to rule 3, which the owner was asked to decide.

## The VS Code edition: what the move would cost, and why it waits

The encapsulation report put the largest remaining question to the owner: Beethoven for VS Code copies its own grid scripts into each student's grid home and runs its own workers, a second cluster side beside hpcworker from before the split. Everything that runs on the grid should be hpcworker's, the report argued, with the VS Code edition becoming a client as the browser and desktop editions are. [Moving Beethoven for VS Code onto hpcworker](https://claude.ai/artifact/ApBd6TpHYnsWVKvP1NjvyX), written the same day and checked against the code of both repositories at named commits by a second reader, sets out the cost. Its banner records the owner deferring the move on 7 October, because the owner is the only person using the VS Code edition and nothing else in the ecosystem depends on it; VS Code keeps its own grid scripts, including the builder of the lab's shared image. The contradictions page marks the report's open question superseded by that dated decision (row 11).

### What it would take

The plan finds that starting, stopping, status, logs, the shared sign-in folder and the subscription-only sign-in rule carry over as they are. hpcworker would first have to gain four things. Ask, VS Code's main feature, hands a task from the laptop's Claude to the grid worker and returns the answer; today it rests on a login-node relay that wakes every 250 ms, which hpcworker's etiquette forbids, and no gate verb can carry a prompt, since a gate line is at most 200 bytes with only eight verbs. Worker sizes, without which a moved student gets a smaller default worker and no GPU worker. The Remote-SSH lines VS Code's server needs on the CentOS 7 nodes. And a way for the worker to use the student's GitHub and Hugging Face access. The grid licence check, VS Code's own lab-access requests, the per-student image build, bypass mode and the polling loops would go away rather than move.

The order is six steps: hpcworker's small additions (framework 18), the new site fields, an hpcworker client in VS Code behind a setting, Ask built in hpcworker (framework 19), VS Code 6.0.0 switching over with new terms (version 8), and VS Code 7.0.0 removing its grid scripts after one term. The plan sets fourteen decisions before the owner, each with a recommended answer; the four needed before any code are where Ask goes (hpcworker), which licence holders are off the grid's approved list (require the extension grant before any key is issued by hand), whether VS Code may choose worker sizes (hours, CPUs and memory now within new site limits, GPUs after one measured GPU job) and how GitHub and Hugging Face tokens reach the worker (the student signs in to each tool on a compute node, so no Beethoven code holds a token). Bypass mode is never to be offered, and old grid files are left for one term and then tidied without touching results, accounts, the sign-in or the work folder. None is recorded as answered, since the move was deferred.

The plan lists what it did not measure, among them the latency of a request channel through the gate, two Remote Control hosts on one sign-in and the framework version actually deployed; its baseline for the old relay, about 20 ms a round trip against about 2.0 s for one ssh per prompt, comes from the VS Code edition's own architecture document and is Reported.

### Four findings that do not wait for the move

The plan names four things that matter whether or not the move happens, and they are the most important part of it for anyone working on Beethoven now. First, a credential path in VS Code 5.0.0, found by reading the code and deliberately not run, since running it would print a credential: the grid command's result and its relay check neither the worker name nor the request identifier, and the MCP tool passes any identifier through, so an identifier that climbs out of the outbox folder returns the student's Claude credential file to the laptop's Claude. That breaks the rule that Beethoven never relays a credential. The fix is small, belongs in beethoven-vscode and was "being fixed separately"; no artifact read here records it merged, so a planner should treat it as open until the repository shows the fix. Second, bypass mode: VS Code 5.0.0 lets the laptop's Claude ask the grid to skip permissions, which hpcworker's contract refuses, and hpcworker's own terminal verb for starting a worker does not check its permission mode, so a client must use only the contract's lines. Third, VS Code's bootstrap job is the only tool that has ever built the image hpcworker runs at the site, so someone must own rebuilding it before the VS Code scripts go (row 12). Fourth, a VS Code student approved only through VS Code's own lab-access approval, and not on the access service's roster, loses the lab folder at every sync of hpcworker's access script.

The plan also corrects a number other pages repeat. hpcworker's code sets the window in which a successor job resumes a Remote Control session at four hours, while hpcworker's instruction file, its diagnostics guide and the extension's instruction file say seven days; the grid review of 21 October repeats seven days with no source. The contradictions page confirms the code's four hours (row 4), and the [worker-opening research](../../docs/research/beethoven-worker-opening.md) of 16 October reads the same four hours from the profile code. Whether a resumed session keeps a long conversation whole across several job ends is still not measured (row 29).

## The store release

### By hand, the first time

[Beethoven on the Chrome Web Store](https://claude.ai/artifact/XxNp8Uy3FfWDSwMExpvLMT) of 13 October is the canonical runbook. The first upload of 20.0.0 stays with the owner, because it is the owner's Google sign-in on the developer dashboard and the automatic route needs the item identifier the listing already has. A kit folder holds every file in the dashboard's field order: the package (441,350 bytes, its SHA-256 pinned beside it), the texts, the images and the reviewer's test instructions. Before the dashboard the owner runs the hand test on the real grid and checks the package and the images. The privacy answers are 19.0.0's, since 20.0.0 changes no permission and no data type, and the distribution changes: Visibility Public, trusted testers empty, the United States only. On 8 October Beethoven was published Private behind a testers' group ([Store upload and repo move, step by step](https://claude.ai/artifact/Fpy3FhkGSwF4jkDUYRWXmu)); the 13 October page retires the group, and the access service's approval check, not the store, then decides who may use the installed extension (rows 19 and 20).

Whether 20.0.0 was in fact uploaded by hand is not recorded; the contradictions page leaves it cannot-tell (row 27). The later record implies the item exists and takes uploads from CI, which is what the next section describes.

### From CI, through the organization's release kit

The automatic route is the organization's private Chrome Web Store release kit, the reusable workflow every extension repository of the owner's calls, first used for the cswap extension ([Store upload and repo move, step by step](https://claude.ai/artifact/Fpy3FhkGSwF4jkDUYRWXmu); chapter 30) and the same for Symphony for Chrome ([docs/research/symphony-extension-store-release.md](../../docs/research/symphony-extension-store-release.md)). The contradictions page confirms that the two store pages describe one kit (row 35). On every push to main it installs, runs the same type check and test suite as CI, and stops on a failing test; builds the package; writes a fourth version number, the count of commits on main, into the package's manifest, so every build is higher than the last without a commit that only raises the version; keeps the build as a GitHub release marked latest; and then, depending on one repository or organization variable, `CWS_ON_PUSH`, does nothing more, uploads the build as the item's draft (upload), or uploads and submits it for review (publish). A tag with the exact three-part version always uploads. The store refuses a version lower than one it has, so once a four-part build is on the item the next hand upload must be a higher three-part version.

The kit needs one Google OAuth client, one refresh token and five secrets: the publisher identifier, the item identifier, the client identifier, the client secret and the refresh token. None is a Claude credential or an API key; they are the store's own sign-in for the one Google account that owns the item, sent only to the store's API. The other four secrets serve every item one account publishes, so only the item identifier differs between repositories. That is the source of the one hazard the Symphony store note records: with the organization's variable set to publish since 18 October, a push to an extension repository whose item identifier is inherited from an organization-level secret naming Beethoven's item would upload the wrong extension onto Beethoven's listing; the store would most likely refuse it on the version number, "but that is luck, not a rule", so each extension repository sets its own item identifier as a repository secret, which overrides the organization's.

Both store pages say a consent screen left in Testing gives refresh tokens that expire after seven days, and that a refresh token stops after about six months unused; the 8 October page adds that Google deletes an OAuth client unused for six months. The contradictions page marks these lifetimes as a shared claim neither page sources beyond a link to Google's guide (row 33), and this chapter could not check them against Google's documentation from here, so they stand unverified. How long a review takes is given differently by the two pages because they speak of different items, a first item with native messaging and a new version of an existing one (row 34); neither figure is measured.

### What happened next

The repository's own notes carry the story past the artifacts. The five secrets were set on 16 October, and a run started by hand then left 21.0.0's build as a draft, because a hand run uses its own upload and publish boxes ([docs/memory/beethoven-worker-and-claude-projects.md](../../docs/memory/beethoven-worker-and-claude-projects.md); [docs/research/beethoven-store-updates.md](../../docs/research/beethoven-store-updates.md)). With the organization's variable at publish, 22.0.0 went to review from a push on 18 October, the run reporting that the item was submitted for review. 23.0.0 addresses a further gap: an open side panel keeps Chrome from installing a downloaded update, so 23.0.0 reloads itself once nothing a restart would lose is under way. That restart is held by tests against a fake Chrome and has not been watched in a real browser; how long each review takes and how soon an approved version reaches a student's Chrome are not yet measured. Whether 23.0.0 was approved and published is not recorded in what this chapter read.

21.0.0 shows the discipline this forces. Because a merge to main may reach students, its pull request went through two adversarial review rounds, thirteen findings and then twelve, among them store texts that would have shipped ahead of the public privacy page ([docs/research/beethoven-21-reviews.md](../../docs/research/beethoven-21-reviews.md)). Its feature is narrow: a Claude project cannot adopt the plain session Beethoven's worker starts, so 21.0.0 opens the project's page named in Settings and tells the student the three steps of Work locally ([docs/memory/beethoven-worker-and-claude-projects.md](../../docs/memory/beethoven-worker-and-claude-projects.md)). The grid plan of 21 October puts the next step on paper, a list of projects each paired with its own named worker, which needs an hpcworker contract change and another store release and is not built.

### What a session cannot do

The store runbook is explicit, and the later notes agree. A Claude session cannot sign in to the dashboard or to Google Cloud, cannot upload or submit anything, and cannot read or set repository secrets; every value lives in the owner's browser under the owner's sign-in, pasted only into the secret's box. A session also cannot create a release tag, so beethoven-qa's tags and any exact-version store release wait on the owner. A cloud session cannot read the `CWS_ON_PUSH` variable, so it treats any merge to beethoven-extension's main as one that may reach students, and asks the owner before merging there; a submission is withdrawn only with Cancel review in the developer console. What a session can do is prepare the kit, the texts and the pull request that changes the workflow, and merge that pull request once its checks pass where the owner's standing word allows it.

## Older and secondary versions

No artifact in this cluster is superseded as a whole, but several are overtaken in part. The [REFORMS compliance checklist](../../artifacts/reforms-compliance-checklist-bpzdoi/) alone holds the item-by-item gate table and the build order; its statements that no gate exists and that beethoven-research is a proposal are stale (rows 8 and 9). The [Store upload and repo move](https://claude.ai/artifact/Fpy3FhkGSwF4jkDUYRWXmu) page, canonical for the cswap extension, alone holds the kit's table of refusal messages and the record that Beethoven was Private on 8 October. The [taxonomy spec](../../artifacts/symphony-and-beethoven-taxonomy-spec-lcbqro/) and [manual](https://claude.ai/artifact/RE4jtXqsFFgiZxhQLamUDR) alone place Beethoven among research-automation systems. The [Symphony Handoff](https://claude.ai/artifact/XQj71up9dbJhwSStCVUe9T) holds the rule that no Beethoven repository runs Symphony's code or holds a Claude token. [Connect the grid to GitHub](../../artifacts/connect-the-grid-to-github/) settles only that a compute node reaches GitHub and that a private repository needs the student's own token, which Claude never handles (row 16).

## What we know

The launcher works at one site: hpcworker runs a student's own Claude Code under Remote Control as a Slurm job, the live grid answered framework 22 on 21 October, and the extension reached 22.0.0 submitted and 23.0.0 written by 18 October. The engine is mostly planned: beethoven-qa and beethoven-research's split check are built, and no other REFORMS gate, compliance record, headless run template, outer loop or Publish press exists in the record. REFORMS has 32 items in the checklist's lettering, 20 checkable by code and 12 only as declared fields, firing 11 before dispatch, 12 after the run and 9 before publish. Seven repositories are sealed under five self-checked rules, and two maintainer-only crossings remain. The VS Code move is deferred by the owner's dated decision, but its credential, bypass, image and lab-access findings stand on their own. The store route is the organization's release kit, live for Beethoven since 16 October, with the first upload, the secrets, the tags and the listing always the owner's.

## What we do not know

Whether phase 0's headless probe has run, and so whether the inner loop can be `claude -p` on a student's login under hpcworker's rules. Whether the credential path in VS Code 5.0.0 has been fixed. Whether 20.0.0 was uploaded by hand, and whether 22.0.0 and 23.0.0 passed review and reached students' browsers, and how long that takes. Which beethoven-qa version is tagged now, beyond a consuming copy that records 6.0.0 untagged. Whether two grid workers run at once on real nodes, whether two workers on one account each stay registered, and whether a successor's resume keeps a session or a project pairing whole. Whether the roadmap's REFORMS module column matches the paper; this chapter could not check the item list against Kapoor et al. from here, and relies on the checklist's statement that it took the items from the paper. Whether the Chrome Web Store's refresh-token lifetimes are as both store pages state.

## What would change our mind

A run that the phase 0 probe completes headless from a batch job on a student's login would fix phases 1 and 2 in the shape the roadmap recommends; a refusal would turn the inner loop into a steered Remote Control session. A phase 3 test that refuses a deliberately leaky split and a dirty tree before GPU time would move "REFORMS gates enforced by code" from Inferred to a measured claim; until then it is a design. A reading of the REFORMS paper that differs from the checklist's lettering would require renumbering every gate and the one built check. A merged fix in beethoven-vscode would close the credential finding; a second student on the VS Code edition, or anything else coming to depend on it, would reopen the deferred move. A store answer refusing a four-part version, or a refresh token failing sooner than the pages say, would change the release runbook.
