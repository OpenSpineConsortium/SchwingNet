# How work is claimed

The queue is GitHub Issues on {{REPO}}. The board is the file STATE.md on the branch `board`, rendered from the issues, the branches, the claim files and the pull requests by .github/workflows/board.yml, which rewrites that branch's one commit on every issue and pull request event, every branch made or deleted, every push to {{DEFAULT_BRANCH}}, and every six hours as a fallback; nobody edits it by hand. Read it with `git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`, the form /board uses, since `git fetch origin board` updates no remote-tracking branch in a clone made for one branch, as a cloud session's is; the session hook prints it at the start of every session, and docs/agents/STATE.md on the default branch only describes its layout. A claim is the first push of a branch: GitHub refuses the second push of the same name, so two workers can never hold the same issue. Everything below is done by the worker doing the work, in the open, and the claim skill (.claude/skills/claim) is the same steps as commands.

## Workers

A worker is anything that claims issues: a person's sessions, local or in the cloud, with whatever helpers they start; a routine on someone's Claude account, which runs on its own; or a worker in GitHub Actions, which .github/workflows/workers.yml runs on the repository's own Claude token. There is one way of working for all of them, whether one person works alone, one person runs several sessions and routines at once, or many people and their routines share the repository: each worker claims, works and finishes by the steps below, and the board and the coordinator treat them alike. docs/agents/WORKERS.md says how they share the repository.

Each worker has a name, unique in the repository: its label is `worker:<name>` and its claim files say `- Worker: <name>`, so two workers on one Claude account still tell their claims apart. A person's sessions take the person's GitHub login as their name, unless the session's environment sets `SYMPHONY_WORKER` to another; a person needs no file to work here. A routine or a worker in Actions is registered by a small file, `.github/symphony/workers/<name>.json`, which says where it runs (`actions`, `routine` or `session`), what it is for, the area of the repository it prefers (paths or globs), how its pull requests land (`owner`, the repository's owner merges, or `auto-merge`, GitHub merges once the required check is green), and, for a worker in Actions, the model, the turns one run may take and how many runs it may take in a row; it never holds a credential. .github/symphony/workers/README.md lists the settings, and `bash scripts/check.sh` fails on any file that does not hold together (`python3 tools/workers.py check`). A worker is added with the "Add a worker" issue form, whose workflow .github/workflows/add-worker.yml opens the pull request that adds its file, or by adding the file by hand in a pull request of its own. A person may register too, with `"runs": "session"`, to give their sessions an area. Name a routine or a worker in Actions after its job, not after anyone's login, so it never shares a name with a person's sessions.

## Labels

- todo: the queue. An issue labelled todo and shown unclaimed on the board is free to take as Pick says.
- claimed: a worker has pushed its branch. The worker's own label goes on with it.
- in-review: the pull request is ready; the owner merges it and the merge closes the issue.
- blocker: the issue stops everyone: work it stands in the way of waits until it is done (Blockers).
- worker:<name>: the worker that holds the issue, or that the coordinator gave it before any claim. An issue a worker's label names is that worker's alone: it is left out of the board's Queue and shown under Given to workers until the worker claims it. Where the labels of several workers name one issue, it is theirs alone in the same way: given to each of them, and held by the first of them to claim it, whose Announce takes the others' labels off. The older spellings account:<name> and agent:<name> are read as the same label.
- epic: a request the coordinator plans into tasks (Planning, below). The board's Queue leaves an epic out, since nobody takes one whole.
- blocked: a worker waits on a peer or the coordinator.

template-init makes every label above but worker:<name>, six in all, when the repository is made, and scripts/setup-repo.sh makes them again from a clone. A worker's label is made when the worker first needs it: the claim skill makes it before putting it on an issue, and the coordinator when it gives a worker a task.

## Pick

Fetch, then read the board (`git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`). Take an issue the Given to workers section gives you first. Else take a blocker, with or without todo, that the Blockers section lists, that nobody has claimed and that no worker's label gives to another, since a blocker comes before the Queue. Else take an open issue labelled todo that the Queue section shows as unclaimed and that no open blocker stands in the way of. Of the blockers and the Queue, take only one in your area when your file under .github/symphony/workers/ gives you one; an issue that lists no files fits every area (Planning). Wherever an issue is listed, never take an epic, which the coordinator plans (Planning), nor an issue labelled blocked, which waits on a peer or the coordinator. An issue with a branch `claude/<issue>` on origin, or a file `docs/agents/claims/<issue>.md` on the default branch, is another worker's, whatever its labels say. Before you start, read the board's Overlaps section: open work that changes the same files as the issue you take lands in the order it gives.

## Claim

Push a new branch `claude/<issue number>` from the default branch whose first commit adds `docs/agents/claims/<issue number>.md`: the worker, the plan, the files to touch, the issue's link, on the template in docs/agents/claims/README.md. Nothing else is in that first commit. The claim branch of issue N is exactly `claude/N`, with N in one to nine ASCII digits and no leading zero, since GitHub refuses only a second push of the same name: `claude/03` is no claim on #3. The board shows such a branch as not a claim, and the push guard refuses a push to one and the protocol check fails a pull request from one, both naming the issue's own claim branch. If the push is refused because the branch exists, another worker has it: delete the local branch and pick another issue. The board reads two parts of the claim file: the `- Worker:` line (or the older `- Account:`), whose name is the worker's label without the `worker:` prefix (a line with nothing after it but markup or a note in parentheses names nobody: the board shows such a claim as unnamed, since the file is there to be corrected, while the clerk and a release, which must name a worker, take the one the issue's label names, as they do once the pull request has deleted the file), and the list under `## Files to touch`, which fills the board's Files column and its Overlaps until the pull request has files of its own; a release quotes its `## Plan`. A claim file over 1 MB, more than GitHub's contents API gives the text of, is read for none of these: the board names the worker by the issue's worker label, or says the file was not read, and takes no files from it, and a release says where the file is in place of quoting its plan.

## Announce

Add the label claimed and the worker's label to the issue, taking off every other worker's label, one an earlier claim left there or one that gave the issue to several workers, so that from the claim on the labels name the holder alone, as the claim file does; and post the plan as a comment, so the board and the people reading the issue see the same thing the branch says.

## Work in the open

Open a draft pull request at once, from the branch to the default branch, with "Closes #N" in its body. GitHub opens one pull request at a time between the same two branches, so where one that someone who may not write opened from the branch stands in the way, which is no claim's (Rules that hold everywhere), close it, as anyone who may write can, and open your own. Push often: a branch with no commit for 24 hours is released (below). When the board comments "main moved" on the pull request, which it does in whichever run finds the branch behind or conflicting, once per commit of the default branch, the default branch has moved past the branch: bring it in, by rebasing on it and pushing again with `--force-with-lease`, or by merging it in, which needs no forced push and is what a worker in Actions does. The board reads a branch as behind where GitHub calls its pull request behind, as it does under a rule that requires an up-to-date branch, or, where GitHub's word is blocked or draft, which says only that something else stops the merge, a rule still holding the pull request or the draft itself, where the comparison of the branch with the default branch says so. A pull request GitHub calls clean, unstable or has_hooks, a draft among them, since GitHub gives a draft the word its branch has, is not held for being behind under the repository's rules, so it hears nothing however far the default branch has moved; one GitHub calls dirty, in conflict with the default branch, hears it. That `--force-with-lease` is the one forced push the protocol allows, and only on your own claim branch. Since a worker that has fetched holds a remote-tracking ref that matches origin, git itself would take its lease onto any claim, so before a lease onto `claude/N` the push guard reads the claim file `docs/agents/claims/N.md` on the branch the lease holds against (the commit the lease names, else origin's `claude/N` as the fetch left it) and on the branch pushed, each at its tip or, once the branch has deleted the file, where its history last added it, and refuses a lease that would take another worker's claim: one whose two files name different workers, or whose branch pushed carries none; a claim file git cannot show leaves the lease to GitHub's rules, as the guard leaves everything it cannot read (the template carries it since symphony-template#78 on 2026-10-14, ahead of symphony-protocol 0.5.0, the release that carries it; an older copy takes it once that release is published, by hand as docs/start/protocol.md's step 7 says, with the template's tests/fixtures/board-STATE.md, whose Given to workers heading 0.5.0 changes, since the copy's protocol.yml brings only tools/, and with the template's tools/guard_push.py where its own predates symphony-template#69, since an older one hands the guard no claim files).

## Finish

The pull request deletes its claim file, says "Closes #N", passes `bash scripts/check.sh` and is marked ready; the issue gets the label in-review. The owner merges, or, for a worker whose file says `"lands": "auto-merge"`, GitHub merges once the required check is green; the merge closes the issue, and the next board no longer lists the claim. A worker that may not mark its own pull request ready, such as a cloud session whose `gh pr` calls are refused, keeps the claim file instead, pushes the finished work with `bash scripts/check.sh` passing, comments "finished; ready to mark" on its draft and stops, leaving the steps above to a person who can take them; until then its claim is not released (Release). Delete the branch after the merge if the repository does not do it by itself (docs/setup/github.md). An issue closed without a merge loses its branch too: .github/workflows/tidy.yml deletes `claude/<issue>` once no open pull request uses it, and with it any `released/<issue>-<sha>` a released claim left (Release).

## Blockers

An issue labelled blocker stops everyone: work it stands in the way of waits until it is done. The board lists every open issue labelled blocker under Blockers, claimed or not, and a worker takes one there before the Queue, as Pick says. It is claimed like any other issue, by one worker, and nobody else fixes it in parallel; a second worker that sees it held waits for it, helps on the one pull request by review, or takes other work it does not stand in the way of (Pick).

## Release

A claim whose branch has had no commit for more than 24 hours is released by the coordinator, unless it is finished: an issue labelled in-review, a pull request marked ready, or a draft whose author's latest comment on it starts with "finished; ready to mark" waits for review however long it takes. That comment is how a worker that may not mark its own pull request ready says it is done (Finish). When a branch's last commit came, here and below, is when GitHub received the push that set its head, as the repository's activity records that push, so no worker's clock decides it; an entry that set the branch to another head, or deleted it, dates it too when it came after the run began, a push after the run read the branch, while an older one is stale and lists no push that set the head; the head's committer date stands in where the activity, read once more after a pause when the first read lists no push that set the head or GitHub gives it no answer that holds, still lists none, or where GitHub refuses to read it, since the push a run was started by is the one the activity is likeliest not to list yet, but never earlier than the newest entry either read listed for the branch, which the push that set the head came no sooner than. In the run that a push to the branch started, which the workflow's event names, a head no read dates is dated at the run's start instead, and so is one a read dates by an entry that set it more than a few minutes before the run began, an older push of the same head that the activity lists while it does not list that push yet, or that push itself where the run, queued behind others, began that much after it, for that run alone, since that push came just before the run, whatever the two reads list, so no claim is released in the run its own push started; the next run reads the activity again. The coordinator here is a step of the board's own run, in .github/workflows/board.yml, on the repository's own token, so releasing needs no Claude account and no routine (docs/agents/WORKERS.md). Before it releases, it frees each reopened issue whose labels still speak of a claim that ended with its close (Finish), so the in-review that claim left finishes no claim, and a claim branch still standing for the issue is released in that same run once it has gone a day without a commit. The coordinator first takes the label claimed and every worker's label off the issue, a label already gone counting as taken off, and puts the label todo on it when it carries none of todo, epic and blocker, so the Queue lists it again even when a worker's label alone gave it to the worker, while a blocker is listed under Blockers without it; then it posts a comment on the issue whose first line is `<!-- sdlc-coordinator: claim-released -->` and which says why and whose the claim was, what the branch holds beside the default branch and what the claim's plan was, so the next worker can carry the work on or start over. A release counts only once both are done (below). A run that fails at the labels, taking one off or putting todo on, puts back the labels it took off, even one whose taking off GitHub answered with an error, unless GitHub refused it with an answer from 400 to 499 other than a rate limit's, on a try that followed none GitHub refused for a rate limit, which GitHub gives in place of taking it off, since GitHub may have taken it off and a label put back that is still on changes nothing, and takes off the todo it put on, even one whose putting on GitHub answered with an error, since GitHub may have written it, so the issue is as it was and the next run starts the release over. A run whose comment fails reads the issue's comments, and the comment there after all, one GitHub wrote and lost its answer to, makes the release whole. Where they list none and GitHub refused the comment, with an answer from 400 to 499 other than a rate limit's, on a try that followed none GitHub refused for a rate limit, which GitHub gives in place of writing anything, the run puts back the labels it took off and takes off the todo it put on, so the issue is as it was and the next run starts the release over. Where they list none after any other answer to the comment, a rate limit's refusal, a 429 or a 403 that names a rate limit or a wait in retry-after, on the last try or on one the run made the comment again after, which GitHub's documentation never says it gives in place of acting on the call, a server error, a redirect, an answer the run could not read or no answer at all, none of which says GitHub wrote nothing, and GitHub may list a comment it wrote only later, or where the run cannot read them, whatever GitHub answered the comment with, the run cannot tell whether a release comment stands, its own, an earlier run's or one someone else wrote: it leaves the labels as the release left them and counts no release of its own, so its page lists the claim as held and the branch keeps its name, since labels put back beside a comment that stands would hold the claim for good, the comment telling every later coordinator the claim is released and the label claimed telling the board it is held, and the next run, reading the comments, finds the release whole where a release comment that counts stands, or releases the claim again where none does, unless its holder pushed since, which keeps the claim, its labels as the release left them, naming no holder, until it finishes, a person puts them back or it goes a day without a commit and is released again, or a person put the label claimed back beside a comment that stands, which undoes that release (below), though a branch at a head a release already kept is released in that same run by its latest release comment, where one that counts stands, which counts for such a branch whenever it came, with no word on the issue of this run's release where GitHub wrote none. Where GitHub refuses the putting back too the labels are left off with no comment, until a run releases the claim or a person puts them back. It never pushes to the branch, deletes it or renames it. It takes its candidates from the open issues that have a branch `claude/<issue>`, whatever their labels, and skips a claim whose latest release comment came more than 24 hours after the branch's last commit, which is a claim already released; so, running on every board run, it releases each claim once, and releases again one it released too soon or one claimed anew that went idle again. A person or a coordinator routine may release a claim too, in the other order: the comment first, then the labels, todo put on as the coordinator puts it, since taking a label off starts a board run, whose coordinator, finding no release comment yet, would release the claim with a comment of its own; or, for any claim but a draft its author said is finished, a person takes the labels off and leaves the comment to that run.

The board does the rest. A claim counts as released when its issue is open, labelled neither claimed nor in-review, its pull request, if any, is still a draft, and its latest release comment came more than 24 hours after the branch's last commit, with no commit since. That holds for a draft whose author said it is finished as for any other, though the coordinator never releases one: a person releases one by hand with the release comment first, then the labels, which frees it, the board reading its issue's comments once the label claimed is off. Taking its labels off alone leaves it held, with no labels, until a person posts the release comment or puts the labels back, since no coordinator's comment follows. A release comment counts when it is by the repository's owner, a member of its organization or a collaborator, by the repository's own workflows (the bot `github-actions[bot]`, which only a workflow someone who may write put there can write as), or by anyone else who may write to the repository. The board then leaves the claim and its pull request off the page and lists the issue as it lists any unclaimed one, in the Queue or, for a blocker, under Blockers, though until the same run has renamed the branch Pick reads the branch as another worker's and the clerk deals the issue to nobody (Planning), and .github/workflows/board.yml renames the branch to `released/<issue>-<short sha of its head>`: the name `claude/<issue>` is free, the work stays under the new name, GitHub closes the branch's pull request with the rename, and the board says on the issue where the branch went. The next worker claims the issue by the steps above, a new branch `claude/<issue>` from the default branch, and may carry the released work on in it after the claim commit, keeping its own claim file (.claude/skills/claim says how). Since the coordinator releases in the board's own run, before the board is rendered, the same run renames the branch. A release comment made sooner, or by anyone else, frees nothing; a commit pushed to the branch before the rename, its holder coming back, keeps the claim; and putting the label claimed back undoes a release, before the rename or after it, when the branch is renamed back and its pull request reopened. A branch pushed again at the head a release already kept, one a branch `released/<issue>-<short sha>` stands at, brings nothing new: its latest release comment counts for it whenever it came, before that push or after, so the board deletes it instead of renaming it, since its work is already kept, and the coordinator releases it only where the board counts no release of it, no release comment counting or the label claimed put back, once it has gone a day without a commit. Until the board has renamed the branch, a push of the name is still refused; the board renames it in the run that releases the claim, or, for a release made by hand, in the run that the label's removal starts. When GitHub refuses the rename for good, for a ruleset whose target takes in the claim branches or a token without the right, the board says so once on the issue, naming each ruleset that applies to the two names with its rules, and every run tries the rename again; a ruleset meant for the default branch leaves `claude/**` and `released/**` out of its target (docs/setup/github.md).

## Overlaps

Two pieces of open work that change the same file meet when the second lands. The board's Overlaps section lists each file that more than one piece of open work changes, an open pull request by its files or, while it changes nothing but its claim file, by the files its claim lists, and a claim with no pull request yet by the files its claim lists, with that work in the order it should land: a blocker first, since it stops everyone; then work marked ready, which waits only for its merge; then the oldest, the work that began first, when GitHub says the push that made its branch came, or, for a pull request from a fork or from a branch it says nothing of, when the pull request was opened; work whose beginning nothing says, which can only be a claim with no pull request yet, counts as the newest, since a claim opens its draft at once (Work in the open), and the number breaks a tie. In the same run the coordinator tells each piece of open work about the work it meets, once, in a comment whose first line is `<!-- sdlc-coordinator: overlap <numbers> -->` naming every piece it told of, with the shared files and the order, and tells it again only when work it has not been told of starts to meet it; a marker counts only from an author whose release comment would count (Release), so no one else can keep work from being told. The marker names each piece by its identity: a claim and its own pull requests are one piece, the issue's number, told on that issue, so opening a pull request tells nothing again, and a marker on one of the claim's own open pull requests counts as one on the issue; a pull request that is no claim's is a piece of its own, its number, told on itself. An issue's number names each claim on it in turn, so a marker tells a claim's work, or tells of it, only when it came no earlier than the push that made that claim's branch, as GitHub dates that push for the order above, and every marker counts for a claim whose push GitHub does not date. Each piece after the first brings the default branch in once the one before it has landed.

## Planning

An issue labelled epic is a request for more than one piece of work. The coordinator, here Claude in .github/workflows/coordinator.yml on the repository's Claude token (docs/agents/WORKERS.md), plans it into tasks, each with the files it owns and the interfaces it shares with the others, and gives each task to a registered worker whose area fits, labelling it todo and `worker:<name>`; where no worker is registered the tasks go to the open queue, labelled todo alone. When a worker labels its task blocked, the coordinator settles what it needs; when the last task closes, the coordinator integrates: it checks the default branch as a whole and fixes what the pieces broke together, under this protocol. The clerical part, writing the plan into the epic, opening the tasks and telling each worker what to do next, is code, not Claude: tools/team.py. Workers that ask at the same moment, as the workers in Actions of one run of .github/workflows/workers.yml do, are dealt the open work so no two race for one claim: each takes its own claim that needs work, one whose claim file names it, whatever the issue's labels say, or, where no claim file names a worker, one whose issue's label names it, a worker:<name> label before the older spellings and the first by name among labels of one spelling, as a release names whose the claim was, but never a claim that counts as released, which no worker carries and none takes until the board has renamed its branch (Pick, Release), nor a claim labelled blocked, whose holder waits on a peer or the coordinator (Labels) and so has nothing else to do; else the task it was given, one given to it alone first, and a task the labels of several workers give going to the first of them, in the order the registry lists the workers in Actions, with nothing else to do; else the next unclaimed blocker or queued issue, blockers first, whose listed files fit its area (the Task form's "Files likely touched", or a planned task's "Files to touch"; an issue that lists none fits every area). The order is the team's: every worker the deal is for, in .github/workflows/workers.yml every registered worker in Actions, whether or not the run starts it, so a worker outside the run keeps its share, and two runs that look at one state deal no issue to two workers. The workers of one run are dealt from one look at the repository, taken once for the run and handed to each worker (`python3 tools/team.py deal`), since two workers looking for themselves at different moments, one while a peer's ready pull request is still clean and one after the default branch has moved past it, could be dealt one issue; a worker that asks alone (`python3 tools/team.py next`) is dealt by the same rule from its own look.

## Rules that hold everywhere

- One issue, one branch `claude/<issue>`, one pull request.
- Never push to another worker's branch. Never force-push the default branch or any branch that is not your own claim. The push guard, tools/guard_push.py, wired as a hook in .claude/settings.json, refuses those pushes before they run, and branch protection on GitHub stands behind it (docs/setup/github.md).
- Memory rides in the same pull request as the change it came from (.claude/rules/memory.md).
- `bash scripts/check.sh` passes before a pull request is marked ready.
- CI holds a `claude/<issue>` pull request to this protocol (tools/check_protocol.py, part of the required check): the claim file is there while the pull request is a draft, gone once it is ready, the body closes its issue, and the branch lives in this repository, never in a fork; and a pull request from a branch that reads as a claim and claims nothing, as `claude/03`, fails it.
- A claim and its pull request live in this repository, so a pull request from a fork is no claim's, whatever its branch is called: the board lists it as a pull request of its own and tells it what it tells any other, it finishes no claim, marked ready or said finished, and a release's rename, which closes the claim's own pull request, leaves it open.
- A claim's pull request is opened by the repository's owner, a member of its organization, a collaborator or anyone else who may write to the repository, or by a GitHub App, which opens one only where it is installed, as the workers in Actions open theirs; a pull request anyone else opens from a claim's branch, as GitHub's documentation says anyone who may read the repository can, is no claim's either: the board lists it as a pull request of its own and tells it what it tells any other, it finishes no claim, marked ready or said finished, and a release's rename closes it with the claim's own, since GitHub closes each open pull request whose branch it renames. Where GitHub will not answer whether someone may write, a pull request they opened stays the claim's, and a release comment or an overlap marker they wrote counts for nothing, so a lost answer never frees a finished claim and never keeps work from being told.
