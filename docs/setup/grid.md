# A job on the WSU grid

A workflow job of this repository can run on Wayne State's grid instead of GitHub's machines, through Beethoven: `tools/grid_runner.sh` in OpenSpineConsortium/hpcworker serves GitHub's own self-hosted runner as a chain of Slurm jobs, and .github/workflows/grid.yml here names the runner's labels, so the command it is given runs on a compute node, in a checkout of the ref, and the output comes back as the job's log and as an artifact. docs/research/wsu-grid-and-github-actions.md says what was measured and weighed before this was built; the owner's thread "Symphony on the WSU grid" decided it on 2026-10-16.

## How it works

A workflow's job cannot be pushed into the grid: the portal sits behind the university's VPN, ssh asks a password and a one-time code unless a key is on file, and neither the password nor a key that could run anything may sit at GitHub, nor anything of GitHub's reach a workflow's job beyond that job's own credential (hpcworker's CLAUDE.md). So the connection points the other way, as the grid's CI lane does; the one key GitHub holds, the ssh gate's (below), can only start, read and stop the chain. On the grid, under the account's own gh sign-in, `tools/grid_runner.sh --start --repo OWNER/NAME` queues a Slurm job on the worker queue the site profile names (reqp/requeue at Wayne State, preemptible; --partition and --qos choose another), 8 hours of wall time unless --hours says otherwise, which, before anything else, queues its own successor (afterany, singleton), so the runner is back after a wall time or a preemption with nobody at the keyboard. In the job the runner runs inside GitHub's own image (ghcr.io/actions/actions-runner as a SIF: the runner is a .NET 8 application built for RHEL 8 and later, which the grid's EL7 nodes are not) with `--containall --cleanenv --no-mount bind-paths`, and none of Apptainer's own settings from the shell or the module: it sees no home, no lab volume, no scheduler and none of the environment, only its own files on the node's disk and a /tmp there. It is registered for one GitHub job at a time with a just-in-time credential: gh mints it into a mode-0600 file on the node's disk, the runner reads it, listens, runs one job and ends; GitHub removes the registration itself, and the chain deletes one that ran nothing. The account's gh sign-in, which mints it, stays in the home, which the container never sees. Registrations stop a margin before the wall time (--margin, 60 minutes unless set), so a job must end within that margin, or the wall time cuts it off and GitHub reports the runner lost. The chain stops itself, writing STOP with the reason, when three of its jobs in a row could not serve (no image, no node-local temp, gh unable to say whether the repository is private), when the repository is public, and when the runner asks for a newer version than the image holds, which an actions/runner release brings: the image cannot update the runner inside it, so `--install` takes the new image and `--start` starts the chain again.

A workflow job reaches the runner with `runs-on: [self-hosted, grid]` (GitHub adds linux and x64; the chain adds the site's name and what --labels gave it). grid.yml is such a job: one command, typed on the workflow's page or passed by another workflow, run with bash in a checkout of the ref, its output in the job's log and in the artifact grid-<run>-<attempt>, kept 14 days (a caller gives the artifact another prefix with the input artifact, as one that runs grid.yml twice in one run must). The runner's image is Ubuntu 24.04 with git, curl, jq, Ubuntu's own python3 and the runner's own node (read from actions/runner's images/Dockerfile, not measured here); grid.yml sets Python 3.12 up with actions/setup-python, as the checks on GitHub's machines do, unless its python box is unticked, and the default command, `bash scripts/check.sh`, then runs the repository's own check there. A step never reaches Slurm, the home or the lab volume: a job it queued as the account, or a bind of the home or the volume, would give every workflow's code all the account holds, its gh sign-in and its Claude login among them. A workflow that needs more than a small share of one node runs on a chain sized for it at --start (--cpus, --mem, --gres; with --gres naming a GPU the container is given the node's GPU).

## What it takes

- A private or internal repository. The chain refuses a public one, as GitHub advises: a public repository's forks could run their pull requests on the grid. grid.yml also runs only for an event that names a private repository that is not a fork, and never for a pull request from a fork. A caller started by a schedule is skipped, since a schedule's event names no repository; start such a caller from workflow_dispatch or a push instead.
- The setting "Run workflows from fork pull requests" left off, as it is unless someone turns it on: https://github.com/OpenSpineConsortium/symphony-template/settings/actions, under "Fork pull request workflows in private repositories", shown only where the organization lets its private repositories be forked. A pull request runs the workflow files of its own branch, so a fork's could drop grid.yml's test; with the setting off, GitHub runs none of a fork's.
- On the grid: a clone of OpenSpineConsortium/hpcworker under the account, gh signed in there as an administrator of the repository (a just-in-time registration needs one; `gh auth status` says who is signed in), and the site profile wayne, which names the module apptainer/1.2.2, the worker queue and the lab volume. Every command names it with --site wayne; hpcworker reads it with its own awk reader, since the login node's banner bans python3.
- No secret and no token in the repository, a job file or a command line. The runner's one-job credential is minted on the grid by the account's gh sign-in, which stays in the home, and leaves with the job; a workflow's job on the grid holds that credential and GitHub's own token for its run, and nothing else. The Claude token the repository's own workflows use never reaches the grid, and no Claude workflow runs there: claude.yml, workers.yml and coordinator.yml stay on GitHub's machines.
- No Actions minutes: a self-hosted runner's time is not billed.

## The owner's steps

Everything on the grid is the owner's. Each step, with where to click:

1. Open the grid's shell: https://ondemand.grid.wayne.edu on the VPN, the Clusters menu, then the shell entry.
2. Take hpcworker's current main there: `gh repo clone OpenSpineConsortium/hpcworker` the first time, `git -C hpcworker pull` after.
3. Install the runner's image once: `cd hpcworker && bash tools/grid_runner.sh --install --site wayne`. It prints the install job's number; the job's log is /rs/rs_grp_oschome/$USER/hpcworker-runner/image/install-<job>.log and ends with "installed: runner <version>". A line starting "STOP:" names what the grid refused; hpcworker's docs/OPEN_QUESTIONS.md lists what is not yet measured, and the install job is the first test of most of it.
4. Start the chain: `bash tools/grid_runner.sh --start --repo OpenSpineConsortium/symphony-template --site wayne`, with `--hours`, `--margin`, `--cpus`, `--mem` or `--gres` to size it. It prints the job's number and the labels a workflow names.
5. See the runner: https://github.com/OpenSpineConsortium/symphony-template/settings/actions/runners lists it as grid-wayne-<job>-<n>, Idle, while the chain's job runs and is registered. Between two registrations, or while the chain's job waits in Slurm's queue, the list is empty and a job waits for the next registration, up to 24 hours.
6. Run a job: https://github.com/OpenSpineConsortium/symphony-template/actions/workflows/grid.yml, press "Run workflow", keep or change the command, press the green "Run workflow" button. The run's page shows the log as it comes; the artifact grid-<run>-<attempt> is under Artifacts at the bottom of the run's summary page.
7. Watch the chain: `bash tools/grid_runner.sh --status --site wayne --repo OpenSpineConsortium/symphony-template`, which names the runner's folder first; its logs are /rs/rs_grp_oschome/$USER/hpcworker-runner/OpenSpineConsortium-symphony-template/runner-<job>.log.
8. End it: `bash tools/grid_runner.sh --stop --site wayne --repo OpenSpineConsortium/symphony-template`; a GitHub job in flight finishes first, and `--now` cancels it too.
9. After the chain stops itself: step 7 names the reason. For "the runner asks for a newer version", repeat steps 2 to 4; for anything else, fix what it names, then step 4.

## The ssh gate

A chain kept running waits in Slurm's queue between jobs. The ssh gate lets a workflow on GitHub's own machine start the chain only when a job needs it, read its state, and end it: .github/workflows/grid-gate.yml sends one word, start, status or stop, over ssh to the grid, where one restricted line in the owner's ~/.ssh/authorized_keys lets the key run hpcworker's tools/grid_gate.sh and nothing else. The gate runs `grid_runner.sh --start`, `--status` or `--stop` for this repository alone, with the chain's size fixed in the line, at most once a minute; it never opens a shell, never queues a job of the workflow's own, and every command of a workflow's still runs on the runner. A key alone signs in to grid.wayne.edu from outside the VPN (the owner's test of 2026-10-17); the password is nowhere. The key's private half is the secret GRID_GATE_KEY of the environment grid, which only main may deploy to. grid.yml's start box runs grid-gate.yml with start before its job, and a chain already queued or running counts as started; a workflow that calls grid.yml with start passes the secret on by name (`secrets: GRID_GATE_KEY: ${{ secrets.GRID_GATE_KEY }}`). An environment with a secret on a private repository needs GitHub Pro, Team or Enterprise; this repository, internal to its enterprise, has it.

The wizard does all of it in one command typed in the grid's shell, with nothing run on your own computer: no Git Bash, no WSL, only a browser. Open https://ondemand.grid.wayne.edu on the VPN, choose the Clusters menu, then the shell entry, and type:

```
cd ~/hpcworker && git checkout main && git pull && bash tools/grid_runner.sh --gate-setup --repo OpenSpineConsortium/symphony-template --site wayne
```

It needs the grid's `gh` signed in as an admin of this repository, as the runner already has it (`gh auth status` says which account). It closes the clone to others; makes the environment grid, deployable from main alone, where it is missing (one that exists is kept as it is, and refused while it may deploy from any branch or a pattern); makes a new key in a folder of its own in memory (/dev/shm); writes the gate's line as `--gate-key` does, replacing an earlier one; sets the variables GRID_ACCESS_ID (your account) and GRID_HOST_KEY (the login node's own host key whose fingerprint the site's profile recorded from the internet, SHA256:kLTz1xK6anQ1denM+31kDEryQtgan2P76r9aLno+K3s) and the secret GRID_GATE_KEY, handing the private key to gh on its standard input; deletes the key; and starts grid-gate.yml with status, whose run at https://github.com/OpenSpineConsortium/symphony-template/actions/workflows/grid-gate.yml is the gate's first call from outside. The key is never printed or put on a command line, and its folder goes however the command ends. `--hours`, `--margin`, `--cpus`, `--mem` and `--gres` size the chain as `--start` takes them; run it again for a new key.

The same by hand, step by step:

1. On your own computer, in Git Bash or WSL: `ssh-keygen -t ed25519 -f ~/.ssh/grid_gate -N '' -C grid-gate`, then `cat ~/.ssh/grid_gate.pub`, and copy the one line it prints.
2. In the grid's shell (https://ondemand.grid.wayne.edu on the VPN, the Clusters menu, then the shell entry): `cd ~/hpcworker && git checkout main && git pull && chmod -R go-w tools framework` (the login node's umask may leave what git writes group-writable, which the gate refuses; do the same after every later pull), then `bash tools/grid_runner.sh --gate-key 'PASTE' --repo OpenSpineConsortium/symphony-template --site wayne`, with the line from step 1 in place of PASTE, inside the single quotes, and with `--hours`, `--margin`, `--cpus`, `--mem` or `--gres` if the chain should be sized other than 8 hours with 60 minutes of margin. It says "the gate's key is in ~/.ssh/authorized_keys". A line saying "others may change the clone" names the folder; `chmod go-w` on it, then run the command again.
3. The grid's host key, as GitHub's machine will see it. With the VPN off, on your own computer: `ssh-keyscan grid.wayne.edu 2>/dev/null | grep -v '^#'`, and copy the line it prints. From outside the grid offers only its RSA key (the owner's scan of 2026-10-17), so the line starts "grid.wayne.edu ssh-rsa", though /etc/ssh on the login node holds an ed25519 key too. To be sure it is the grid's, run `ssh-keyscan grid.wayne.edu 2>/dev/null | grep -v '^#' | ssh-keygen -lf -` there and `ssh-keygen -lf /etc/ssh/ssh_host_rsa_key.pub` in the grid's shell: the two SHA256 fingerprints must be the same (on 2026-10-17 both were SHA256:kLTz1xK6anQ1denM+31kDEryQtgan2P76r9aLno+K3s). If they differ, stop and send me both.
4. With the VPN off, on your own computer: `ssh -i ~/.ssh/grid_gate -o IdentitiesOnly=yes <AccessID>@grid.wayne.edu status`, with your AccessID. It prints the runner's folder and the chain's state, then "HPCW-GRID-GATE status ok".
5. Open https://github.com/OpenSpineConsortium/symphony-template/settings/environments, press "New environment", type `grid` and press "Configure environment". Under "Deployment branches and tags" choose "Selected branches and tags", press "Add deployment branch or tag rule", type `main` and press "Add rule". Leave "Required reviewers" unticked so a run need not wait for you, or tick it and add yourself if every start should wait for your approval.
6. On the same page, under "Environment secrets", press "Add environment secret": Name `GRID_GATE_KEY`, Value the whole output of `cat ~/.ssh/grid_gate` on your computer (the private key, from its BEGIN line to its END line), then "Add secret". Under "Environment variables", press "Add environment variable": `GRID_ACCESS_ID` with your AccessID, then again `GRID_HOST_KEY` with the line from step 3.
7. Delete the private key from your computer: `rm ~/.ssh/grid_gate`. The secret is its one copy; a new key from step 1 and step 2 replaces it at any time.
8. Run it: https://github.com/OpenSpineConsortium/symphony-template/actions/workflows/grid-gate.yml, press "Run workflow", keep the word status, press the green "Run workflow". The run's summary shows what the gate printed. Then grid.yml's "Run workflow" with "Start the runner chain first" ticked starts the chain and runs the job.

To take the key away: `bash tools/grid_runner.sh --gate-off --repo OpenSpineConsortium/symphony-template --site wayne` in the grid's shell. Each call is one line in the chain's gate.log, /rs/rs_grp_oschome/$USER/hpcworker-runner/OpenSpineConsortium-symphony-template/gate.log: the time, the word, the address it came from and how it ended. Not yet measured: whether GitHub's machines reach the grid's ssh port as the owner's home connection did, whether the forced command's shell finds sbatch and gh on the login node, and whether every login node behind grid.wayne.edu has the same host key (hpcworker's docs/OPEN_QUESTIONS.md).

## What to expect, and what is not yet measured

A job waits while the chain's Slurm job waits in the queue, and a job that arrives in the seconds between one registration's end and the next waits for the next; GitHub holds a job for a self-hosted runner for 24 hours and then fails it. A job the wall time cuts off fails as "the runner has lost communication": keep each job under the margin. reqp/requeue is preemptible: a preempted chain job is requeued, deletes the registration it left and registers afresh, and a GitHub job that was on it fails. Nothing of this has run on the grid yet: compute nodes reaching ghcr.io and github.com, the container flags on the grid's Apptainer 1.2.2, the runner on an EL7 kernel, Slurm's end time, the chain of jobs, actions/setup-python inside the container, the node's GPU with --nv and how often GitHub asks a runner to update are open questions in hpcworker's docs/OPEN_QUESTIONS.md, each with the first test that answers it.
