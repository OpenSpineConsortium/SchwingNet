# The board comes first

Before any change in this repository:

1. Fetch: `git fetch origin`. The session-start hook does this once; do it again before you push.
2. Read the board and docs/agents/PROTOCOL.md (how work is claimed). The board is the file STATE.md on the branch `board`, rewritten by the board workflow; read it with `git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`, the form /board uses, since `git fetch origin board` updates no remote-tracking branch in a clone made for one branch, as a cloud session's is. The session-start hook prints it at the start of every session; docs/agents/STATE.md on the default branch only describes its layout.
3. Check the claim on the issue you mean to take: a branch `claude/<issue>` on origin, or a file `docs/agents/claims/<issue>.md` on the default branch, means another worker has it, and a `worker:<name>` label that is not yours, with none that is, means the issue is that worker's: pick another. An issue the labels give to several workers, you among them, is each of theirs, and the first to claim it holds it. An issue the board's Given to workers section gives you comes first, then an unclaimed blocker, then the Queue; never take an epic, which the coordinator plans, nor an issue labelled blocked, which waits on a peer or the coordinator.

You work here as a worker under a name of your own (docs/agents/WORKERS.md): in a person's session, the person's GitHub login unless the environment sets SYMPHONY_WORKER; in a routine or a worker in Actions, the name its prompt gives. One issue, one branch `claude/<issue>`, one pull request. Claim with the claim skill (.claude/skills/claim) before the first change to any other file, and open the draft pull request at once.

Never push to a branch another worker claimed. Never force-push the default branch or any branch that is not your own claim; after a rebase, your own claim branch takes `git push --force-with-lease=claude/<issue>:<the tip you last pushed> origin claude/<issue>` (the claim skill's step 7), the branch named so that the push forces nothing else and the tip so that it never forces over a push made since, and nothing else ever does. When the board comments "main moved" on your pull request, bring the default branch in: rebase on it and push again, or merge it in. An issue labelled blocker is claimed like any other, and nobody fixes it in parallel.

A hook enforces the push rules before they can be broken: tools/guard_push.py, wired in .claude/settings.json, refuses a push to the default or board branch, a plain --force anywhere, a + before a refspec, which forces that ref as --force does, the refspec : and patterns with *, which move branches wholesale as --all, --branches and --mirror do, a push to a name that reads as a claim and claims nothing, such as claude/03 (a claim branch is claude/ and the issue's number in one to nine ASCII digits with no leading zero, docs/agents/PROTOCOL.md, Claim), --force-with-lease outside your own claude/ branch, and, where the copy carries the fence (the template since symphony-template#78 on 2026-10-14, ahead of symphony-protocol 0.5.0, the release that carries it; an older copy once that release is published, by hand as docs/start/protocol.md's step 7 says, with the template's tests/fixtures/board-STATE.md, and with its tools/guard_push.py where the copy's own predates symphony-template#69), --force-with-lease onto a claude/ branch whose claim file on origin names another worker, or with a branch that carries no claim file for the issue, since a lease after a fetch is the one push git itself would take onto another worker's claim. A refusal is the rule working, not an obstacle; the answer is a pull request, a rebase or another branch, never a way around the hook. Branch protection on GitHub (docs/setup/github.md) stands behind it.
